# Agent Note: Host 之外的自动化

Status: proposed

[English](2026-10-12-automations-next-phases.md) | 中文

## 问题

Aeven 已经交付了持久的本地自动化：用户描述重复性工作，服务为每次触发持久登记，再由一个全新的根会话以用户自己的预设、模型、工作区和连接器执行。该服务运行在提供服务的 Host 进程内，因此包自身的限制清单是诚实且必须遵守的——Host 必须在运行，计算机必须保持唤醒，没有任何执行能脱离该进程。

六项差距使已交付的能力离它应当成为的产品还有距离。关闭桌面应用会终止持有调度表的 Host，所以自动化只在 Aeven 打开时运行；机器进入睡眠则计时器随之停止。涉及外部写入的运行会失败关闭，因为无人值守运行携带审批策略 `never`，且不存在为它应答的应答者，这恰好排除了用户最想排期的重复性工作：发送报告、归档回复、更新记录。运行结果只有打开 Aeven 的人能看到，因此凌晨三点完成的一次自动化不会让用户注意到任何东西。时间是目前唯一的触发条件。托管运行完全不存在，它带来的账号、凭据与权限问题因此未被回答。而用于呈现排期工作的界面只是一个占位符，普通用户看到的东西里没有任何一处暗示他们可以拥有一个重复性任务。

## 提案

本记录规划剩余的阶段。它确定每个阶段的产出、所使用的接缝、证明阶段成立的证据，以及每个阶段的风险。它有意不规定内部结构：已有的包、服务、存储域、会话生命周期与组合行决定每个阶段如何实现，每个阶段都应当作为这些抽象的扩展落地，而不是作为一套并行机制。

本提案扩展[内置自动化记录](../../implemented/architecture/2026-10-11-built-in-automations.zh.md)与[托管 Web 表面与同步](../../proposed/architecture/2026-09-30-hosted-web-surface-and-sync.zh.md)两份约定；它不取代其中任何一份，已交付的本地服务仍是今天现状的权威。本提案落地时不会归档任何有效的 Agent Note。

以下约束在实现过程中不可交换。

- 自动化执行真实的智能体工作，在全新的会话中进行，绝不是定时提示词，也绝不恢复源会话。
- 本地执行与托管执行是同一套模型的两个执行目标。执行目标在创建定义时确定，或者被显式留作「我当前所在的机器」，管理界面不会为第二个目标生长出第二套概念。
- 可靠性要求为：结果验证、持久登记、不重复产生外部副作用、显式的错失运行策略，以及绝不静默重放可能已经写入过的工作的崩溃恢复。
- 权限与审批决定在重启后依然有效，无人值守运行绝不自行扩大权限。
- 创建与管理保持以 composer 为先、以自然语言为主，现有的 Automations 屏幕作为检查与调整界面。
- 模型保持可替换；一次运行沿用用户批准的提供方与模型。
- 复用现有连接器、记忆、技能与习得流程；不新增第二个连接器注册表、第二个云端后端、第二个智能体框架。

第一个仓库是已交付实现的直接祖先：`recurrence.ts:1` 记录了提交号，`LICENSE:1-3` 保留了上游版权行。它现在的价值在于 Aeven 没有移植的部分。它的结果处置模型把失败的运行视为待用户裁决的开放问题：用户通过确认结果，或者通过在新会话中创建一次关联重试来解决；记录中写入 `retryOfRunId`、`retryScheduledFor` 与一份处置审计，并在同一自动化还有排队或运行中的工作时禁止确认与重试。它的会话兼容工作更像一则警告而非一种技术：宿主 API 的一次变化使已完成的运行被记录成执行器错误，修法则是一条唯一的读取边界——优先使用当前的快照 API，保留旧数组作为回退，并在读取失败时明确报错，而不是伪造一个空事件列表。已交付的执行器已经在 `index.ts:309` 读取 `handle.agent.session.snapshotEvents()`，并从事件流推导完成状态，因此剩下的只是读取失败时拒绝虚构成功。它那份 1961 行的客户端控制中心及其客户端协议依赖 DeepSeek Harness 的模块加载约定，不可移植。

第二个仓库是三者中覆盖最广、也最诱人照搬的一个。它按任务选择通道、在发送时按引用解析凭据、按通道隔离故障使一个不可达端点无法吞掉其余结果、把投递超时包住整个处理器、提供 `onlyOnFailure`，并且拒绝在浏览器回显掩码值时覆盖已存的密钥——这些都是通知投递应有的语义，也与 Aeven 现有的凭据服务契合。它的非 LLM 运行方式——shell、Node、Python、HTTP、SSH、Docker——描述了一种不消耗 token、适合无需判断类任务的第二类执行器。它新增的其余一切都是第二套产品表面：自己的 REST API、自己的设置文件、看板集成、Prometheus 指标、TTS 通道、心跳端点，以及带退避的自动重试。采纳这些会重复 Host 的连接、设置与连接器服务，而它的重试默认值与本记录的规则相冲突——可能已经写入过的工作绝不自动重试。

第三个仓库在精神上与 Aeven 的调度器最接近，在策略上也最清晰。它按作业显式规定重叠与错失行为（`skip`、`queue`、`allow`；`skip`、`run-once`），在同一次原子状态变更中登记一次触发并推进持久的 `nextRunAt` 水位，在任何智能体工作之前把运行记为 `running`，崩溃后记为 `interrupted` 且不重试，用 `realpath` 对照可选的允许根列表规范化作业根路径，并把执行置于注册表之后，使后续的工作流或任务图执行器无需改动调度器。它在 Harness home 下的状态文件与纯 JavaScript 的客户端实现不可复用：这里的持久性由存储域拥有，客户端是带自身设计系统的构建产物。

许可与署名。凡是取用的部分都必须保留上游版权行，并在承载改编代码的模块中记录所检查的提交号，形式与已交付的移植版一致。改编的通知语义应在其投递模块头部声明来源；策略词汇与带水位的占位也应如此。三者都不附带 copyleft 义务。

## 架构

剩余阶段扩展四条接缝并新增三条。

| 关注点 | 接缝 | 提供方 | 使用方 |
|---|---|---|---|
| 运行在哪里执行 | 定义上的一个字段，在创建定义时解析，初期只提供本地 Host | 本地 Host，阶段 8 加入托管 Host | 运行执行器，形态不变 |
| 什么启动一次运行 | 定义上的触发种类，解析到触发提供方 | 时间触发沿用现有计时器；事件触发由各连接器声明的事件提供，webhook 运行时只是其中一个提供方 | 登记路径 |
| 目标支持哪些触发 | 执行目标上的声明式能力 | 当前提供服务的 Host，日后加入托管 Host | 管理界面与入门模板目录 |
| 登记一次触发 | 自动化服务现有的持久占位，不变 | 存储域 | 调度器与手动运行 |
| 执行一次触发 | 一个全新的根会话，带已保存的预设、模型、权限与工作区 | 智能体预设、模型选择、工作区注册表 | 用户可以打开的那个会话 |
| 告知用户 | 账号连接器之上的一个投递使用方 | 用户选择的连接器，凭据在发送时解析 | 运行记录上的投递状态 |
| 延续一次审批 | 由运行拥有的持久审批记录，由一个可跨重启存活的应答者应答 | 运行域与审批服务 | 运行会话的审批闸门 |

执行目标是定义的属性，而不是运行时的属性，因此本地 Host 与托管 Host 是同一模型背后的两个提供方，用户的心智模型始终是「在这台机器上运行，或者在我的常开机器上运行」。单机上的所有权问题已经解决：同一时刻只有一个进程拥有一个 Aeven home，因为 home 租约把启动者串行化，并让其余进程得到附加结果，所以守护进程 Host 与应用启动的 Host 不会同时派发同一次触发。托管部署需要把同一保证表达在共享存储之上，这是云端引入的唯一新协调事实。除此之外，云端提供方必须复用托管表面而不是另造后端：按账号划分的 home、凭据与执行世界正是托管记录的第 3 至第 5 阶段，云端的一次自动化就是那个 Host 以同一份 schema 运行同一个服务。另一个值得现在就定下的事实是安装标识，使一次运行能指明登记它的 Host。

存储沿用现有的存储域提供方；definitions 与 runs 两张表仍是持久权威，后续阶段只增加字段与至多一张新表，而不是新的存储。现有域是版本 1，因此每次 schema 变更都要说明版本提升以及它对旧有磁盘数据的拒绝。会话不变：一次运行就是带已保存预设的根会话，托管运行也不例外。审批从无条件拒绝转向持久记录：运行默认保持 `never` 策略，只有当定义携带针对某个具名连接器操作的预授权范围时，运行的审批闸门才查询该范围。通知是账号集成之上的使用方，而不是新的通道注册表；一次运行的投递结果记录在运行自身之上，使重启不会重复发送。

## 阶段

每个阶段说明其产出、所触及的接缝与包、证明它的证据，以及风险。仓库的[测试政策](../../../../docs/testing.zh.md)对每个模型可见或产品可见的阶段提出两项要求：一项非单元的真实组合测试，通过 Loader 启动仅供测试的 `cordis.yml`（`docs/testing.md:38`），以及针对任何模型可见或用户可见变化的无密钥录制会话场景（`docs/testing.md:52-54`）。`pnpm run test:coverage` 还要求 `packages/*/*/src` 逐文件 100% 行覆盖（`docs/testing.md:10`），因此每个阶段都把测试文件算作自身范围的一部分。

### 阶段 1 —— 验证基线

产出：已交付的本地服务被真实测试覆盖，使后续阶段拥有回归信号，当前的结论也不再只依赖构建通过。

接缝与包：不新增接缝。触及 `packages/core/automations/tests`、包内或共享测试支持族的仅供测试 `cordis.yml`，以及一个录制场景。

证据：一次真实组合启动，通过工具界面创建定义，以注入的时钟样本驱动一次已登记的触发，并断言持久运行记录与模型可见的请求；针对创建、列表与立即运行的无密钥录制会话用例；包内 `src` 的逐文件 100% 覆盖。

风险：重复规则是确定性的，但调度不是，计时器驱动的服务也不易构造夹具。缓解办法是仓库已有的时间处理方式：生产路径继续使用平台墙钟，测试提供显式样本，因而不引入生产时钟服务。

### 阶段 2 —— Automations 屏幕与起始模板

产出：用户能看到存在哪些自动化、每一个下次何时运行、上一次发生了什么，并且可以从模板开始，而不必自己写出整条指令。

接缝与包：这是一个管理界面，创建仍留在 composer 中。`automation_create` 已经要求人工确认（`index.ts:88-97`），因此本阶段不新增第二条创建路径；两条创建路径意味着两处授予权限的地方。触及 `packages/client/ui-automations` 以呈现列表、下次运行、上一次结果与 Host 状态，并新增模板目录。卡片携带一条指令，并通过现有的 `InputActions` 路径（`packages/client/ui-conversation/src/client/contract/input.ts`，`setDraft`）把它写入 composer，由普通的确认创建定义。要遵循的模式是 Imagine 界面——`packages/client/ui-imagine/src/client/prompts.ts` 中的目录、`ImaginePrompts.tsx` 中的网格，在 `UiConversation.startPage` 为真时渲染于 `conversation.start` 槽位，并通过 `setDraft` 写入 composer——而本阶段不修改那个包。

卡片内容取自 Grok 而不是 Codex：Grok 的卡片显示下次运行，Codex 的只显示上一次运行，而在排定的卡片上，下次运行是最有用的事实。页面的克制来自 Codex 的 Scheduled 页面——它只承载约 270 个字符：一个标题、一句说明该能力的话、一个 Active 列表和一个 Recommended 条带——创建则在其下方的 composer 中。

模板不能只是文本。它携带触发、连接器与 skill（技能）绑定、模型选择以及通知通道，这些都不是 composer 文本能表达的，因此卡片携带指令，确认过程决定其余部分。模板受能力门控：每个模板声明它所需的触发，界面只提供当前运行目标声明了相应触发的模板。这正是该门控落在这里而不是托管阶段的原因，托管阶段现在引用它，而不是引入它。目录是一份有类型、已本地化的资产，形如 Imagine 的提示词，因为客户端文案由 locale 拥有，`verify-client-ui-i18n` 会拒绝硬编码字符串。界面明确说明是否有 Host 在提供服务，以及这对计划意味着什么；参考产品省略这一点，因为它们任务在服务端执行，而本地优先的运行方式做不到。之后，Recommended 条带应当来自用户自己的历史（经 Personal Knowledge Model），而不是来自固定的目录。

证据：针对界面管理操作的真实组合测试；模板目录在模型可见处的快照；覆盖卡片到 composer 路径的 GUI 测试，与 Imagine 卡片的覆盖方式一致。

风险：起始模板是一份承诺。Grok 的每个模板都是每日计划，Grok 能这样承诺是因为它的任务在服务端运行，而 Aeven 的自动化只在有 Host 在服务并且机器醒着时运行。在受托管 Host 之前上线模板条带，等于卖出一场无法发生的运行，而一次静默错过的运行比从未存在过的模板更伤信任。缓解办法是界面上的能力声明加上声明的触发门控，而模板内容不得暗示常开执行。

### 阶段 3 —— 结果处置与历史保留

产出：失败、被中断或被跳过的运行成为用户可检查、可确认、可有意重试的对象；重复性定义可以被赋予结束条件，而不是永远运行下去；运行历史在存储中受限，而不只是限制响应。

接缝与包：自动化服务的公开操作、它的 RPC 派发、它的智能体工具，以及 Automations 屏幕。definitions 表增加可选的重复结束条件，runs 表增加可选的处置字段，因此域版本为两者一次变更。触发模型是否也采用 Codex 提供的按月与自定义规则形式，以及 Grok 提供的按年与按小时上界的每小时形式，在此定夺；拒绝其中任何一种都是有效结果，并记录为一项决策，而不是留作遗漏。

证据：覆盖裁剪规则的单元测试，该规则绝不删除排队或运行中的记录，也覆盖结束条件的边界落在两次触发之间的情况；针对关联重试的真实组合用例；针对新增工具结果与模型可设置的触发字段的快照。

风险：重试是唯一可能重复外部副作用的路径，因此它始终由用户发起，在同一自动化有活动工作时被拒绝，并被记录为一次关联运行，而不是重新派发原记录。给版本 1 的域增加字段会拒绝更早的磁盘数据，预发布立场允许这一点，但该改动必须说明它。

### 阶段 4 —— 通知投递

产出：完成的运行经用户选择的连接器送达用户；投递失败的运行如实说明投递失败，而不是假装已经报告。

接缝与包：`packages/host/account-integrations` 之上的投递使用方、凭据服务、自动化定义中的投递选择，以及运行记录上的投递状态。

证据：针对桩连接器的单元测试，覆盖按通道隔离、投递超时与掩码密钥规则；一个通道不可达而另一个仍能送达的真实组合测试。

风险：重启后的重复投递，必须由运行自身的投递状态阻止；某个已选通道的凭据被撤销，必须以运行上的投递失败呈现，而不是无声缺席。

### 阶段 5 —— 事件触发

产出：自动化除了按时间触发，还能按已认证的外部事件触发。

接缝与包：每个事件来源一个触发提供方、定义上的一种触发种类，以及沿用现有登记路径、但由事件而非时钟推导出的触发标识。每个连接器声明自己的事件目录及其过滤语义，webhook 运行时则成为它们之中的一个触发提供方，而不是唯一的触发提供方：一个集中式 webhook 无法表达「符合你的过滤条件的新邮件」或十来个带作者过滤的 GitHub 事件，这就是该接缝必须由连接器拥有的原因。Grok 正是这种形态，本记录的既有实现一节记录了它暴露的目录。

每个触发提供方都提供一个稳定的事件标识，因此重投的投递是同一次触发，而不是第二次运行。这一要求回答了本记录此前留下的触发标识问题。

证据：一次真实组合测试，把已签名的投递经 webhook 提供方派发，并把一个连接器事件经其自己的提供方派发，各自成为一次已登记的触发；针对模型可设置的触发字段的快照。

风险：webhook 运行时是即发即忘的，因此重复投递是它的正常行为而非错误，而连接器的事件流也可能合法重放。正是提供方的事件标识使这些重放成为同一次触发，因此无法提供该标识的提供方还不适合作为触发来源。

### 阶段 6 —— 可延续的审批

产出：需要为某个具名外部写入取得审批的运行，可以在无人当时在场的情况下跨重启等待该审批。

接缝与包：审批服务及其应答者、由运行拥有的持久审批记录，以及定义上的预授权范围。

证据：一次真实组合用例，在询问与回答之间停止进程，并在授权完好无损的情况下恢复；一个展示运行在回答之后完成的录制场景。

风险：这个阶段把只读的调度器变成会无人值守写入的东西。安全的形式是窄授权——一个连接器操作、一个账号、一个有效期——且对任何未预授权的操作默认仍然拒绝。

### 阶段 7 —— 由操作系统托管的 Host

产出：桌面应用关闭时，排定的触发仍然运行，并且机器的主人能看到它确实运行过。

已经存在的部分，以及真正缺失的部分。Host 本身已经是独立的操作系统进程：桌面应用把 `@aeven/desktop-host` 作为子进程启动，并在专用描述符上以分帧管道承载其 API（`apps/desktop/src/host-process.ts:119`，`:132`）。关闭应用会终止该子进程——退出路径发送 `SIGTERM`，并在两次有界等待后升级为 `SIGKILL`（`apps/desktop/src/host-process.ts:239-243`）——关闭 Aeven 会停止自动化，原因在此，而不在自动化设计。每个 Aeven home 的单所有者已被强制：`claimOrAttachHost(home)` 在 `runtime/host.lock` 上取得内核文件锁，以 0600 模式发布 `runtime/host.json`（因为公布的 URL 携带一个有效的启动凭据），并返回所有权或指明在任 Host 的附加结果（`packages/util/home-paths/src/host-lease.ts:108`，`:192`，`:211-214`）。Host 子进程已经处理附加情形：收到附加结果时，它上报 `ownsHost: false`，销毁两条管道，断开连接并返回，让在任 Host 继续服务（`apps/desktop-host/src/index.ts:517-524`）。Host 如今也能在没有 Electron 的情况下启动，因为启动器按名称启动 profile，并使用同一个 home 与同一个租约（`apps/cli/src/args.ts:13`）。

接缝与包：不新增子系统，也不新增第二个守护进程。本阶段增加一个操作系统托管提供方——macOS 的 LaunchAgent、Linux 的 systemd 用户单元、Windows 的服务或计划任务——加上一个用户可见的设置，用于在后台运行 Aeven 并在登录时启动它，以及桌面进程的一条规则：附加到在任 Host，只有在自己是首个启动者时才创建 Host。被托管的进程应从应用包之外的稳定安装位置运行，因为一次应用更新会在运行中的服务之下替换应用包；home 侧的安装区域 `<home>/profiles` 是候选锚点，在被依赖之前必须先核实。

证据：一个进程级用例，由被托管的 Host 提供服务，在一次运行进行到一半时中断它，并验证运行记录显示失败且没有重放；一个附加用例，第二个启动者加入在任 Host 并且不拥有任何东西；macOS 与 Linux 上的系统级冒烟测试，证明该单元在登录后启动，且第二个启动者绝不会派发在任 Host 已经登记的触发。

风险：租约已经解决了重复派发，这正是本阶段体积小的原因；剩下的是一个必须以同一用户身份运行的单元，以保持仅所有者可读的租约及其凭据处理不变，以及一条绝不能替换运行中服务文件路径的更新路径。各平台托管机制不同，因此本记录预期每个操作系统各有一个提供方，而不是用一种机制假装覆盖三者。

本阶段诚实的边界：操作系统托管解决的是「用户关掉了窗口」，并不解决「机器睡眠或关机」。睡眠会停止计时器，`misfireGraceMinutes` 与只取最近一次触发的追赶（`index.ts:250-258`）仍是现有的缓解手段。被托管的本地 Host 不是常开的，常开覆盖是托管运行器的职责。

### 阶段 8 —— 托管执行

产出：同一份自动化在用户自己的机器上或托管 Host 上运行，管理界面相同，凭据与权限的表达在两处是一致的。

接缝与包：托管表面记录的第 3 至第 5 阶段，用于按账号划分的 home、凭据与执行世界；api 组的连接与 remotes 用于管理；本记录架构中的执行目标字段；以及每个目标声明的触发能力——阶段 2 引入它们，本阶段遵循它们而不是重新发明。

证据：跨独立 home 的双 Host 测试，展示不存在跨账号可见性，也不存在重复派发；一个在本地创建的定义于托管目标上执行的录制场景。

风险：托管表面本身尚未建成，因此本阶段受制于自动化之外的工作，不应在阶段 7 证明单所有者之前开始。混合交接——托管运行需要只有本地机器才具备的东西——是本设计中辩护力最弱的部分，本记录有意不作规划。

## 待决问题

- 托管 Host 是运行调度器，还是只执行用户自己的机器所登记的触发？前者需要一个能在 Host 更替后存活的租约；后者把用户自己的机器保持为权威，并使「常开」意味着「守护进程在运行」。
- 通知投递属于自动化服务，还是属于一个其他生产者也能使用的通用运行完成能力？后者可复用性更强，工作量也更大。
- 当裁剪变为持久操作之后，`historyLimit` 是否仍是正确的保留控制，还是说保留既需要数量上界也需要时间上界？
- 在三条非 LLM 运行方式中，哪一条值得拥有——毕竟一条 shell 命令既不需要模型，也不需要智能体会话？

## 未能核实

- 仓库中目前没有任何测试、快照或进程预期覆盖自动化服务；以上关于当前状态的每一条结论都来自阅读代码，而不是观察到的行为。
- 插件克隆与 DeepSeek Harness 检出仅被阅读。它们在真实 Host 下的行为未被运行，因此关于其运行时语义的说法来自它们的 README 与设计文档。
- 托管表面记录是一项提案，因此阶段 8 中没有任何内容被验证为今天可构建，它依赖的按账号凭据工作也不存在。
- 当前 `automations` 域能否在不提供迁移路径的情况下增加字段，未对照存储提供方的版本处理进行核实；本记录假定可以提升版本，并假定旧数据可能被拒绝，这与仓库的预发布立场一致。
- 仓库中不存在任何操作系统服务相关的管道，也没有找到 Host 的 launchd、systemd 或 Windows 服务文件；阶段 7 的操作系统托管是在此设计的，而非观察到的。`<home>/profiles` 是否是受托管进程的正确安装锚点也未经验证。
- 既有实现一节中关于 Grok 的发现来自登录状态下它的界面，而不是来自它的源码或 API，因此它们描述的是那个界面暴露了什么，而不是它的服务存了什么。关于 Codex 的发现来自一个提取出的应用包及其附带发布的分析文档。

## 考虑过的替代方案

**复用 `packages/jobs` 作为执行载体。** 作业注册表是长时工作显而易见的归属，并且已经拥有 id、所有权、取消与完成通知。它落选的原因是它的约定把回调与活动 `Agent` 对象交给生产者，因此重启后无法重建作业的任何信息，而一个持久后端必须先重塑标识、所有权与观察方式才能实现该接缝。自动化服务已经拥有持久登记与按次执行，采纳该注册表意味着重建这片地基，而不是在其上建造。

**复用 `packages/schedule` 实现离线投递。** Schedule 是持久的，从会话日志折叠，并且已经正确处理错失的间隔。它因其既定范围而落选：投递是会话本地的，冷会话什么都收不到，而这正是自动化存在的理由。它的提醒框架同样假定存在活动所有者，其重复规则止于固定间隔，而非日历规则。

**整体采纳 `dsh-cron`。** 它是三者中最完整的，且差距明显。它落选是因为这种完整本身就是第二套产品：它自己的 REST API、设置文件、通道注册表、指标、看板与语音通道会重复 Host 的连接、设置与连接器服务，而它的自动重试与本记录的规则相冲突——可能已经写入过的工作绝不重放。它的通知语义值得取用，其架构不值得。

**把专用自动化守护进程作为独立产品构建。** 一个拥有自己调度表、存储与 API 的进程可以一步移除 Host 依赖。它落选是因为 Host 已经是独立进程，并已具备 home 租约、附加路径与按 profile 启动的启动器，所以缺失的是托管而非架构；第二个守护进程会为同一个 home 增加第二个所有者，并重复仓库已经付出的 Host 与存储生命周期成本。

**先交付托管执行，本地托管随后。** 云端最容易承诺「常开」，因为机器不必唤醒。它因依赖与风险而落选：托管表面是含六个阶段的提案，其按账号凭据工作尚不存在，而且在无人值守工作的凭据与权限表述在本地确定之前，它就扩大了用户的信任请求。

**保留失败关闭的审批，永不支持无人值守的外部写入。** 这是已交付的行为，也是安全的。它作为永久答案落选，因为它排除了用户真正想排期的重复性工作；它作为默认值继续存在，窄范围的预授权是无人值守写入的唯一途径。

## 验收标准

- Automations 屏幕列出每个定义及其下次运行与上次结果，说明是否有 Host 在提供服务，只提供当前服务目标声明了相应触发的模板，且不为创建定义增加第二条路径。
- 以自然语言创建的定义在桌面应用关闭时按计划执行，且运行记录显示是哪个 Host 登记的它。
- 外部写入需要审批的运行，要么在定义上记录的预授权范围之下完成，要么停止并报告它无法完成；中间发生重启也不例外。
- 完成的运行经用户选择的连接器送达，按运行记录恰好一次，且投递失败在运行上可见。
- 用户可以从界面确认或重试失败的运行，且在同一自动化有活动工作时绝不重试。
- 同一份定义只创建一次，即可指向本地 Host 或托管 Host，而无需第二套概念；托管运行绝不读取其他账号的数据或凭据。
- 同一个 Aeven home 上的两个进程绝不重复派发同一次触发：第二个启动者附加到在任 Host，而不是成为调度器。
- 保留策略限制已存储的运行历史，而排队与运行中的记录始终保留。
- 任何阶段都不改变这条规则：无人值守运行不继承源会话、不继承既有审批授权，也不拥有超出其已保存权限选择的任何权限。

## 风险

最大的技术风险是重复的外部副作用。跨越崩溃与网络边界无法实现精确一次，因此本记录的答案是：以确定性触发标识实现的至多一次派发、由用户发起的重试，以及在目标系统允许时要求排期任务自带幂等。写入之后崩溃的运行可能已经写入；记录必须如实说明，而不是声称成功或失败。

最大的产品风险是审批延续把一个安全特性变成会按用户设定、随后被遗忘的范围进行无人值守写入的能力。缓解办法是具名一个连接器操作、为其设定时间上界，并在使用之前把它显示在 Automations 屏幕上；默认值仍是拒绝。

托管执行显著扩大了信任表述：今天在用户自己的进程内读取其文件的同一个服务，将带着账号的连接器与凭据运行在别人的机器里。之所以接受这一风险，仅因为托管表面记录已经规划了按账号划分的 home、凭据与执行世界，而本记录拒绝为此另造后端。

受托管执行以一种失败换取另一种。「用户以为已经停止，服务却仍在运行」是一种需要管理的新预期：登录启动的 Host 会比用户关闭的那个窗口活得更久，因此启动它的设置、它持有的凭据，以及停止它的方式都属于产品，而不只是操作系统里的一个文件。

每个阶段都比表面上更大，因为每一阶段都欠一项真实组合测试、一个在其模型可见或用户可见时的录制场景，以及逐文件覆盖。规划时应假定证据义务占工作量的三分之一。

最后，本记录放弃了某些值得点明的东西。它把自动化保留在现有服务与现有抽象之后，这意味着各阶段会比全新的调度器落地得更慢，服务也保持着它在仅本地时期所选择的形态。这笔代价换来的是产品中永远不会出现两个调度器、两个存储或两套账号模型。
