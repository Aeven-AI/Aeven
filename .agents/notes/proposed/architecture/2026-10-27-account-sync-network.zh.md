# Agent Note: 一个账户，一个同步的数据网络

Status: proposed

[English](2026-10-27-account-sync-network.md) | 中文

## 问题

一个 Aeven 账户目前绑定在一台机器上。在第二台电脑上登录会得到相同的身份、连接器和额度，但记忆是空的，没有对话历史，没有学到的流程，也没有个性化设置。长期记忆是产品的差异化所在，而它今天止步于一个 `$AVN_HOME` 的边界。

目标是让一个账户成为一个网络：登录该账户的每台设备持有相同的数据，一台设备上的编辑在一两秒内出现在其他设备上，离线的设备在重新连接时追上进度。设备能直接互通时直接交换数据，无法互通时由 Aeven 服务器中转并存储。服务器永远不知道数据的内容：它中转或存储的每个字节都经过端到端加密，账户的恢复途径是回到数据的唯一方式。本地数据在磁盘上保持不加密。

需要移动的状态体量大、种类杂，并由不同的所有者存储：

| 状态 | 所有者与位置 | 开发者本人 home 中的大小 |
|---|---|---|
| 会话日志 | `@aeven/session-persistence-jsonl`，`sessions/<projectKey(cwd)>/<session id>/session.jsonl.zstd`（[`format.ts`](../../../../packages/session/session-persistence-jsonl/src/format.ts)） | 压缩后 686 MB |
| 记忆 | `@aeven/memory-memos`，每个账户一个 MemOS 数据库，位于 `accounts/<sha256(account)>/memory/data/memos.db`（[每个账户一个记忆数据库](../../implemented/architecture/2026-10-07-per-account-memory-databases.zh.md)） | 576 MB：21,887 条 trace（58 MB 文本、67 MB 向量）、888 条 policy、328 个 skill、24 行 world model、80,165 行 `api_logs` |
| 工作区注册表 | `@aeven/storage-domain` 的 `workspace` 单元：`storages/workspace/global.json`，以及每个工作区一条带 UUID、绝对 `path`、`title` 和 `sessionIds` 的记录 | 小 |
| 个性化 | `personalization/<userId>.json` | 小 |
| 设置 | `settings.yaml`，混合了设备事实（端口、路径、运行时）与账户偏好 | 小 |
| 自动化、消息反馈 | `storages/automations.json`、`storages/message_feedback/sessions/` | 小 |
| 学到的能力 | `capabilities/<owner>/` 与记忆中的流程 | 小 |
| 附件 | 内容寻址的附件存储 | 不定 |

这些状态的四个特性决定了设计：

- **会话日志已经具备同步所需的复制特性。** 持久化 seam 固定了四条不变量：只追加、`seq` 连续、JSON 无损，以及 `append` 仅在持久化后才 resolve（[README](../../../../packages/session/session-persistence/README.zh.md)）。回退与压缩（compaction）都是追加的事件（[会话子系统](../../../../docs/subsystems/session.zh.md)中的 `session/rewind`、`compaction/*`），而不是改写，因此复制一份日志就是按 `seq` 顺序复制事件。
- **每个会话一个写入者只在一个 home 内强制。** `acquireWriter` 在存储根目录下为每个会话持有一个内核文件锁（[`writer-lock.ts`](../../../../packages/session/session-persistence-jsonl/src/writer-lock.ts)），因此同一 home 上的两个 Host 进程不能同时写一个会话，但没有任何机制协调两台设备。两台设备追加到同一个会话会交错写入。
- **会话按机器路径归档。** `projectKey(cwd)` 把绝对工作目录编码进文件夹名，工作区记录也保存绝对 `path`。第二台机器，尤其是 Windows，两者都没有。
- **MemOS 从许多地方写入。** 轮次捕获、修订循环、后台 L2 policy 与 L3 world model 归纳、skill 结晶、整合以及 Aeven 学习器都会写 `memos.db`。挂钩单个写入路径的同步桥会漏掉下一条新增的路径。

服务器一侧约束了密钥设计。登录方式是 Apple、Google 或 X 的 OAuth，或在服务器上用 bcrypt 验证的邮箱与密码（`servers/node/services/AuthService.js`）。在每一种流程中，服务器都能以用户身份完成认证，因此任何仅凭账户登录就能恢复的密钥，服务器也能恢复。

## 提案

### 术语

- **保管库（vault）**：一个账户的同步数据。每个账户一个保管库。
- **设备**：一个登录该账户并加入保管库的 Aeven Host home。一次桌面安装、一个 CLI home、一个无界面 home 各算一台设备。
- **文档**：一个通过 CRDT 复制的状态单元（Yjs `Y.Doc`）。
- **流**：一个有序、单写入者、只追加的复制序列（每个会话一个）。
- **信封（envelope）**：在设备与服务器之间携带一次文档更新、文档快照或流批次的加密且签名的帧。
- **租约（lease）**：执行某类工作的限时、单持有者权利（追加到某个会话、运行记忆维护、运行某个自动化）。

### 同步的内容

| 数据 | 原语 | 冲突规则 |
|---|---|---|
| 会话事件 | 每个会话一个流 | 通过会话租约同一时间只有一个写入者；`seq` 连续；接收方请求缺口 |
| 会话元数据（标题、置顶、归档、fork 父会话） | 文档 | 字段级合并 |
| 工作区注册表 | 文档；`path` 变为本地保存的按设备绑定 | 字段级合并；成员关系按集合 |
| 记忆行（trace、episode、MemOS session、policy、trace-policy 链接、world model、skill、skill 试验、反馈、决策修复、L2 候选池） | 按表以及行 id 的前几个字符分片的文档 | 字段级合并；遗忘墓碑优先于并发编辑 |
| 学到的能力 | 文档（按路径索引的文件内容） | 字段级合并 |
| 个性化、账户级设置 | 文档 | 字段级合并 |
| 自动化定义 | 文档；运行在每个自动化的租约下执行 | 字段级合并 |
| 消息反馈 | 每个会话一个文档 | 字段级合并 |
| 附件 | 加密的内容寻址数据块，按需获取 | 内容地址；无冲突 |
| 嵌入、FTS 索引、投影缓存、MemOS 的 `api_logs`、`audit_events`、`kv`、`embedding_retry_queue` 与 hub 表 | 不同步；重建或保留在本地 | — |
| 凭据、提供方密钥、连接器令牌 | 不同步；连接器已按账户保存在服务器上 | — |
| 设备专属设置（端口、路径、运行时、Chrome 配置文件、语音模型） | 不同步 | — |

这会复制原始记忆 trace，而[长期记忆路线图](../feature/2026-09-28-long-term-memory-roadmap.zh.md)第 10 行提议默认将其保留在本地。召回会读取 trace，因此没有 trace 的设备召回得更少，而一个作为网络的账户不能有按设备区分的记忆。

### 两种复制原语

**文档**使用 [Yjs](https://github.com/yjs/yjs)。一次 Yjs 更新是一个不透明的二进制值；更新可以任意顺序合并，重复应用不产生效果。因此每次更新可以单独加密，服务器存储和转发的是它既无法读取也无法合并的密文。对同一 map 键的并发写入按客户端 id 确定性地解决，而不是按挂钟时间，因此设备时钟不影响结果。每台设备在本地保存文档状态，只在消费方打开文档时加载它；按行 id 前缀给记忆表分片，使任何一个已加载的文档都小于一兆字节（[阶段 0 发现](#phase-0-findings)）。服务器为每个文档保存最新的加密快照以及其后的加密更新。持有该文档的任一设备会定期上传新的快照，之后服务器丢弃被快照覆盖的更新。加密 Yjs 的 [secsync](https://github.com/serenity-kit/secsync) 设计是快照与更新链的参考。

**流**携带会话事件。一个会话同一时间只有一个写入者，因此事件需要的是排序而不是合并。写入者把连续的事件按批次（100 ms 或达到大小上限时封闭）作为流信封发送，并标注首尾 `seq`。接收方只有在批次能连续接上本地日志时才追加，否则请求缺失的范围。以这种方式流式传输 `assistant/chunk` 事件，第二台设备可以在回复生成时实时观看。

两种原语使用相同的信封、密钥、传输和服务器存储。

### 拓扑与传输

每台在线设备为其账户与服务器的同步中继保持一条经过认证的 WebSocket，并与它在本地网络上发现的每个保管库对等方各保持一条 WebSocket。每个信封都会发往服务器，因为服务器是离线设备和新设备的备份与追赶来源。实时投递走先到达的路径；接收方按信封 id 去重。因此服务器是投递的最后手段，也是每次变更的存储路径。

本地网络对等方通过 mDNS（`_aeven-sync._tcp`）互相发现。通告携带由当前保管库密钥纪元派生的令牌，因此只有同一保管库的设备能识别它，通告也不会暴露账户名。对等方在交换信封之前，用各自的设备签名密钥对照设备链互相认证。监听器是一个只说同步协议的独立端口；Host API 仍留在回环地址上。

跨互联网的直接连接（WebRTC 或 QUIC 打洞）推迟实现。它们都需要在 Node Host 中为三个平台各引入原生模块，因此先测量经服务器中转的延迟。

### 加密与密钥

所有密码学操作都使用 `node:crypto` 内置能力：X25519、Ed25519、HKDF-SHA-256 和 AES-256-GCM。不新增原生或 WASM 密码学依赖。

- **保管库密钥纪元**：由第一台设备生成的随机 256 位密钥。移除设备时由新纪元替换。旧纪元对现有设备仍可用，以便读取旧密文。
- **按文档的密钥**：`HKDF(保管库密钥纪元, 文档或流 id)`，限制同一密钥下抽取的 AES-GCM nonce 数量。
- **不透明 id**：发往服务器的文档和流 id 是 `HMAC(保管库密钥, 逻辑名)`，因此服务器既看不到 "memory/traces/2026-10"，也看不到会话 id。
- **设备密钥**：每台设备在 `accounts/<hash>/sync/` 下一个权限为 0600 的文件中保存一个 Ed25519 签名密钥和一个 X25519 密钥协商密钥。按要求本地数据不加密，因此操作系统钥匙串只能保护密钥，而不能保护它解锁的数据；桌面应用可以改用 Electron `safeStorage` 保存它们。
- **信封**：协议版本、不透明 id、类型（更新、快照、流批次）、密钥纪元、发送设备 id、按设备递增的计数器、96 位随机 nonce、以前述所有字段作为关联数据的 AES-256-GCM 密文，以及发送方对整个帧的 Ed25519 签名。发送方不是设备链中的活动设备、计数器没有前进或签名失败的帧，接收方一律拒绝。
- **设备链**：只追加的签名条目列表（创世、添加设备、移除设备、设置恢复密钥）。第一台设备签署创世条目。之后的每个条目由一台活动设备或恢复签名密钥签署。服务器存储设备链但无法添加条目，因此它无法引入一台能接收密钥或加入对等连接的设备。

### 恢复与设备加入

账户本身不能作为恢复密钥，因为服务器能以用户身份完成认证。保持服务器无知的最接近形式是**带 WebAuthn PRF 扩展的 Aeven 账户通行密钥（passkey）**：

1. 加入时，持有保管库密钥的设备为 `aeven.io` 注册一个通行密钥，并用固定盐值计算其 PRF。对 PRF 输出做 HKDF 得到一个包装密钥和一对恢复签名密钥。设备在服务器上存储用包装密钥包装后的保管库密钥，并把恢复公钥追加到设备链。
2. 在新设备上，用该通行密钥登录既完成认证，也得到相同的 PRF 输出。设备在本地解开保管库密钥，用恢复签名密钥签署自己的添加设备条目，然后开始同步。不需要任何其他设备在线。
3. Apple、Google 以及密码管理器的通行密钥存储会在用户的设备之间同步通行密钥，因此通行密钥会如用户所期望的那样跟随账户。

第二种加入途径是**由已有设备批准**。新设备把它的公钥显示为一个短代码；用户在一台已加入的设备上确认相同的代码；该设备追加添加设备条目，并为新设备的 X25519 密钥包装保管库密钥。代码比对防止服务器替换成自己的密钥。

丢失通行密钥以及所有已加入的设备即丢失保管库。产品在创建通行密钥时说明这一点。删除账户会清除服务器上的每个信封、快照、包装密钥和设备链条目。

移除设备会追加一条移除设备条目，生成新的保管库密钥纪元，并为剩余设备和通行密钥包装它。被移除的设备保留它已经解密的内容；它无法读取移除之后的变更，对等方也会拒绝它的连接。

### 服务器存储与可见的内容

服务器存储设备链、包装后的保管库密钥、通行密钥凭据、加密快照、加密更新、加密流批次、加密附件数据块和租约记录。它能看到账户 id、设备 id、不透明的文档和流 id、大小、时间、IP 地址，以及哪台设备持有哪个租约。它看不到记忆文本、会话内容、文件名、标题、设置，也不知道哪个不透明 id 对应哪个逻辑文档。

同步之外还有两条路径会经 Aeven 基础设施传输明文，需要各自的承诺：

- **推理。** 本地 Host 的模型请求经过 Aeven 网关，因此每个轮次的提示词（包括召回的记忆）以明文经过它，调用模型的后台记忆工作也是如此。网关不得存储请求或响应正文，并且这一点要与同步承诺一并公开说明。
- **由 Aeven 托管的 Host。** 由 Aeven 运行的托管 Web 表面（[托管 Web 表面 Agent Note](2026-09-30-hosted-web-surface-and-sync.zh.md)）需要保管库密钥，这会打破承诺。通过浏览器访问保管库要经由用户自己的某台设备。

### 会话：单一运行者、任意设备输入与路径

会话仍然是单写入者日志——`seq` 连续，在每台设备上精确重放——而产品从不要求用户关心是哪台设备在写。同一时刻只有一台设备是会话的**运行者**；每台设备都列出该会话、渲染相同的事件，并接受输入。

- **实时查看。** 运行者在事件提交时即发布批次，而不是按固定间隔扫描：轮次进行中对发布做约 100 ms 的去抖。接收方通过持久化提供方按原始 `seq` 导入每个批次，而任何设备上连接的客户端本来就会把导入的追加当作实时帧接收（[`follow`](../../../../packages/api/session-controller/src/history.ts)），因此回复会在每台设备上流出。导入绝不因为事件到达而运行工具，导入的事件也从不进入活动的智能体循环。
- **任意设备输入。** 在本机未持有租约时提交的提示词会发布到会话的收件箱流；运行者把它作为普通用户消息追加并运行轮次。输入框在所有设备上可用，运行者唯一可见的痕迹是一行状态，标明当前轮次在哪台设备上运行。轮次进行中输入的消息按收件箱收到的顺序进入运行者的队列。
- **运行者租约与无感移交。** 会话租约由服务器授予，离线持有它的设备可以直接移交给局域网对等方。租约空闲或过期时，任何设备都可以认领会话，认领会把本地副本提升为可写日志：副本标记移入旁挂元数据，导入的日志头部保持逐字节不变，并且认领会等到导入游标到达 `next`，因此不会在缺口上开始轮次。随后由认领的设备写入后续事件。fork 不再是产品对“我在另一台电脑上”的回答：它只保留给本机根本无法读取日志的会话。
- **审批、停止与引导。** 请求批准的轮次会在日志中记录 `approval/asked`；请求与决定也走收件箱，因此用户手上的设备可以作答，停止与轮次中的引导同样如此。这些事件仍只由运行者写入，且只有账户所有者可以作答。
- **运行者不可达。** 没有任何持有可读日志的设备可达时，输入在收件箱中等待，而不是 fork 对话。被认领的设备在该工作区的本地绑定中运行轮次，因为记录的 `cwd` 指的是另一台机器的文件夹：目标不存在的路径相关工具会在对话记录中报告这一点，而不是让轮次失败。本机没有绑定的工作区会先要求绑定，这正是注册表已有的“不在本设备上”状态。
- **工作区与路径。** 同步的工作区记录保留其 UUID、标题和会话 id；`path` 变为本地保存的按设备绑定。在没有绑定的设备上，工作区及其会话可读，用户绑定一个文件夹。
- **延迟加载正文。** 新设备先下载会话元数据，在打开会话时或在限速的后台过程中下载会话正文，因此会话列表远在 686 MB 全部到达之前就可用。

### 记忆：捕获、物化与维护

- **变更捕获。** 打开核心时，`@aeven/memory-memos` 在每个复制的表上安装 `AFTER INSERT/UPDATE/DELETE` SQLite 触发器。每个触发器把 `(table, primary key, operation)` 写入同一数据库中的 `sync_changes` 表。无论现有还是将来的写入路径都会被捕获，且无需修改收录的 MemOS 代码。MemOS 迁移之后会检查并重新安装触发器。
- **发布。** 记忆同步消费方取出 `sync_changes`，读取当前行（不含向量列），写入其分片文档，并在同一事务中删除已处理的变更。
- **物化。** 远程行在一个设置标记行的事务中写入，触发器会检查该标记，因此应用的行不会被回传。应用的 trace 进入 MemOS 的 `embedding_retry_queue`，从而在本地计算向量；FTS 表通过它们自己的触发器更新。
- **遗忘。** 遗忘会写入一个优先于并发编辑且永不复活的墓碑。它还会请求该分片的新快照，使服务器丢弃包含被遗忘内容的更新。
- **维护租约。** 从已有记忆派生新记忆的后台工作只在账户维护租约的持有方上运行：MemOS 的 policy、world model 与 skill 归纳，Aeven 学习器的合并与整合，以及记忆画像构建。否则两台设备会从相同的 trace 派生出重复的 policy，并两次支付模型成本。如果持有方离线超过租约到期时间，另一台设备接管。一个轮次的捕获在运行该轮次的设备上进行。

### 包布局

| 包 | 角色 |

### 阶段 0 发现

在一台 Apple 芯片 Mac 上，以开发者本人的账户（21,887 条 trace）测得。

- **前置条件。** 工作区所有权和按 home 的会话写入锁已经存在；只剩设置作用域，它在阶段 3 落地。
- **行 id。** MemOS 的 id 是类型前缀加 12 个随机的 Crockford base-32 字符，即 60 个随机位（`vendor/memos-local-plugin/src/core/id.ts`）。MemOS `sessions` 行使用 Aeven 会话 id，`trace_policy_links` 以两个这样的 id 为键。不同设备上创建的行不会冲突。
- **复制的表与本地的表。** 复制：`traces`、`episodes`、`sessions`、`policies`、`trace_policy_links`、`world_model`、`skills`、`skill_trials`、`feedback`、`decision_repairs`，以及归纳工作集 `l2_candidate_pool`，使新的维护租约持有方从上一个持有方停下的地方继续。本地：`api_logs`、`audit_events`、`embedding_retry_queue`、`kv`（归纳重试记录）、hub 表、`schema_migrations` 和 FTS 表。
- **触发器。** MemOS 已经用触发器维护其 FTS 表，它的 14 个迁移都不删除或重建表，因此新增的触发器能在迁移后保留。触发器只记录表、键和操作，发布方读取整行，因此后续迁移新增的列无需修改触发器即可复制。接收方只写入其 schema 中存在的列，其余列保留在文档中。
- **分片键。** 仅 2026 年 10 月就有 21,878 条 trace，文本 56 MB，因此按月分片不可行。按 id 随机部分的前两个字符分片，每个表得到 1,024 个分片；最大的分片为 587 KB，加载耗时 3.7 ms。不含向量的全部 trace 行（71 MB）的 Yjs 编码与其 JSON 大小相同，修改一个字段产生 43 字节的更新。少于几千行的表使用一个字符（32 个分片）。
- **向量。** `Xenova/multilingual-e5-small`（q8，CPU）嵌入一条摘要需要 2.6 ms，为每条 trace 计算两个向量约需 2 分钟；超过 512 个 token 的文本会被拆成多段，耗时更长。向量在本地重算，不复制。
- **Electron 中的通行密钥。** Electron 内置的 WebAuthn 在 macOS 上无法使用平台通行密钥（[electron/electron#24573](https://github.com/electron/electron/issues/24573)）；拉取请求 [#51563](https://github.com/electron/electron/pull/51563) 提议 `app.configureWebAuthn()`，社区原生模块在 macOS 15 及以上版本提供 PRF。首个版本在系统浏览器中的 `aeven.io` 页面上运行通行密钥流程，页面在本地解开保管库密钥，并通过回环请求交给 Host。一旦某个已发布的 Electron 版本支持带 PRF 的平台通行密钥，就改用原生流程。

### 目前已构建的部分

[账户同步包](../../../../packages/sync/README.zh.md)与 `servers/node` 中转服务器实现了阶段 1–5，与上述计划有以下不同：

- **加入**只由打开了“添加设备”界面的设备回应，打开该界面时会请正在等待的设备重发请求，因此后台或无界面的设备不会接走本该由用户打开的界面处理的加入。
- **记忆向量随行传输**，并标注嵌入模型，而不是重新计算：MemOS 计算向量所用的文本是其内部实现。使用其他模型的设备保留自己的向量。
- **记忆行**按行复制，最后写入者胜出，墓碑优先于并发编辑；分片按 id 随机部分的前一到两个字符划分。
- **对话**由创建每个会话的设备发布，导入过某个会话的设备会实时渲染其新事件。运行者租约、来自另一台设备的输入与审批、无感移交，以及导入日志的提升尚未构建，因此另一台设备上的会话目前在那里是只读的。
- **设备**以主机名命名，在 设置 → 同步 中列出，移除时轮换密钥；被移除的设备会用新的密钥重新加入。
- 尚未构建：通行密钥恢复、维护租约、本地网络传输、附件、设置作用域声明，以及 aeven.io 上的生产 `/sync` 路由。

### 待定问题

1. 在 Windows 和 Linux 上，哪些浏览器和通行密钥提供方会在系统浏览器流程中返回 PRF 结果。没有 PRF 的设备通过另一台设备的批准加入。
2. 每个账户的服务器存储量，以及对拥有数 GB 会话的账户采用的配额策略。
3. 当一个表超出 1,024 个分片时如何重新分片，大约在当前最大账户的十倍规模时出现。

## 曾考虑的替代方案

**GUN。** GUN 中继依据图的 soul id、字段名和状态时间戳进行合并，因此这些对服务器保持可读；SEA 只加密值。冲突按字段以挂钟状态解决，因此设备时钟偏差会改变结果。图保存在内存中，不为只追加日志提供顺序保证，其存储适配器有数据丢失的报告，维护集中在一个人身上。它的主要优势是对等网状网络，而这里服务器无论如何都必须留在存储路径上。

**Automerge。** Automerge 支持同样的加密更新模式，工程质量也很好。它以 WebAssembly 形式发布，保留完整的变更历史，在实时使用中每次更新的成本更高；Yjs 是纯 JavaScript，更小，对频繁的小更新更快，并且已有公开的加密同步设计。

**服务器可读的同步。** 传输中和静态加密、由服务器持有密钥，恢复最简单，也允许服务器端搜索和由 Aeven 托管的 Web 应用。因服务器不得能够读取数据而被否决。

**由账户登录派生的密钥。** OAuth 登录和由 bcrypt 验证的密码都让服务器能以用户身份认证，因此由它们派生的密钥服务器也能派生。

**复制 home 文件夹或 SQLite 文件**（对 `$AVN_HOME` 做 Syncthing 式的文件同步）。两台设备对 SQLite 和 JSONL 文件的并发写入会损坏或交错它们，没有任何内容能实时合并，也没有比文件更小的单元。

**只用点对点，不用服务器存储。** 同一个人的两台设备很少同时在线，而剩下的那一台设备会成为唯一的副本。

**现在就做打洞直连。** 在 Node Host 中使用 WebRTC 或 QUIC 需要每个平台的原生模块。先测量中转延迟。

**从同步的会话重新派生记忆。** 每台设备都要再次支付捕获的模型成本，每次运行的结果不同，手动编辑、导入和反馈也不会被带过去。

**把会话日志做成 CRDT 文档**（每个会话一个 `Y.Array`）。一个会话只有一个写入者，因此从不需要合并，而把数 GB 的事件放进 CRDT 文档会白白耗费内存和存储。

**只读副本加 fork。** 允许每台设备读取另一台设备的会话，但只能通过创建关联副本来写入，会让用户去管理哪台机器持有自己的对话，而副本又会把回复历史与它的延续拆开。日志保持单写入者；流动的是输入与租约。

**基于托管 Web 表面的同步阶段构建。** 该 Agent Note 的阶段 4 提议先移动设置、能力和记忆，并在任何复制服务之前先导入会话；它因每个会话一个写入者未在多个 Host 之间强制而否决了日志复制。按会话的文件锁覆盖同一 home 上的 Host，本 Agent Note 的会话租约覆盖设备，账户同步由本 Agent Note 负责。

## 验收标准

- 两台设备经服务器在线时，一台设备上捕获的记忆在另一台设备上被召回的 95 百分位时间不超过 2 秒；在同一本地网络上不超过 1 秒。
- 在设备 A 上运行的会话出现在设备 B 上，回复实时流入；在 B 上输入的提示词进入 A 的轮次，该轮次请求的批准可以在 B 上作答，而在双方都没有轮次进行时于任一设备输入的提示词，由持有租约的设备运行。
- 用通行密钥登录的新设备在没有其他设备在线的情况下恢复记忆、能力、个性化、设置和会话列表。
- 没有通行密钥的新设备只有在用户于一台已加入的设备上确认代码一致之后才能加入。
- 在服务器的数据库和对象存储中搜索一句已知的记忆、一个会话标题和一个文件名，均无结果；服务器上没有任何文档或流 id 与其逻辑名相同。
- 被移除的设备无法解密移除之后的任何变更，本地网络对等方拒绝它。
- 在一台设备上遗忘某条记忆会在其他设备上将其移除，并且在下一次快照之后，服务器不再保存包含它的任何信封。
- 两台设备在都离线时所做的编辑在重新连接后收敛；同步过程中杀死 Host 不会丢失任何已在本地确认的变更。
- 同步被禁用或服务器不可达时，应用启动没有延迟，并在本地正常工作。
- 记忆归纳在一个账户中同一时间只在一台设备上运行。
- 启用同步后，Host 空闲内存最多增加 25 MB，安装大小最多增加 2 MB。

## 风险

- **永久丢失。** 丢失通行密钥和所有已加入的设备即丢失保管库。这是被接受的，必须在用户创建通行密钥的地方说明。
- **由服务器提供的解锁页面。** 在通行密钥流程于系统浏览器中运行期间，用户需要信任 `aeven.io` 为解锁页面提供的代码。
- **同步之外的明文。** 推理网关能看到每个轮次的提示词和召回的记忆；没有不记录正文的承诺，端到端同步并不能让产品变得私密。
- **元数据。** 服务器仍能得知设备数量、活动时间、大小和 IP 地址。
- **本地网络监听器。** 局域网传输会打开一个监听端口，这会触发 macOS 的入站连接提示，也是新的攻击面；它只说同步协议，并对照设备链认证每个对等方。
- **密码学错误。** nonce 处理、签名覆盖范围、设备链验证和纪元轮换都容易出现细微错误；这正是计划中包含外部审查的原因。
- **收录的 MemOS 变更。** 重命名或重构表的 MemOS 更新会破坏触发器；vendor 同步流程需增加一步重新检查它们。
- **服务器成本。** 拥有数 GB 会话的账户产生的存储成本需要由订阅覆盖。
- **维护暂停。** 当维护租约持有方离线且租约尚未到期时，没有设备会归纳新的 policy。
- **这项变更放弃了什么：** 针对账户数据的服务器端功能（服务器搜索、带有用户记忆的由 Aeven 托管的 Host 或 Web 应用），以及在通行密钥和设备都丢失后由 Aeven 客服恢复的可能。
