# Agent Note: 为会话索引赋予工作区身份

Status: proposed

[English](2026-09-21-workspace-identity-in-the-session-index.md) | 中文

## 问题

一个工作区拥有其会话的有序账目，而该记录是成员资格的唯一权威。`folder` 工作区要求 header 的规范化 `cwd` 等于工作区路径，以此接纳会话；`virtual` 工作区完全没有目录，因此其会话不携带 cwd，只通过记录本身加入。[types.ts](../../../../packages/workspace/workspace/src/types.ts) 中的 `WorkspaceKind` 与 `AttachSession` 陈述了这一约定，而 [index.ts](../../../../packages/workspace/workspace/src/index.ts) 中的 `adoptByCwd` 实现了仅适用于 folder 的恢复逻辑，用来重建持久记录丢失的成员资格。

由此产生两个后果，而且两者都体现在运行时而非纸面上。

会话索引无法回答工作区问题。`session-query-sqlite` 每行存储 `cwd`、`parent_session`、`seed_length`、`delegation_depth`、`agent_preset` 与 `revision`，因此它携带了列举所需的全部血统与配置事实，唯独缺少产品最先呈现的那项分组依据。因此按工作区筛选的列举必须查询注册表并在内存中连接，而 `virtual` 工作区的会话没有 cwd 可匹配，根本无法按位置查询。索引记录的是位置，而问题问的是身份。

会话日志存储以目录为键。[format.ts](../../../../packages/session/session-persistence-jsonl/src/format.ts) 中，`projectKey(cwd)` 对路径做哈希，`projectDir(root, cwd)` 选择桶，`undefined` 选择 `_no-cwd`。因此一台机器上每个无路径会话都共享同一个 `_no-cwd` 桶，无论它属于哪个 virtual 工作区；而移动一个目录会改变其会话的读取位置，工作区记录却不受影响。

路径身份已经需要修复机制。`claimLegacySessionWorkspace` 与 `repairRemoteSessionPaths` 之所以存在，是因为 `remote` 身份曾被写入目录或路径字段。两者都是窄范围、按 id 限定，且明确禁止批量迁移；当所存事实是一个后来被证明不稳定的位置时，workaround 就是这个形状。`WorkspaceKind` 保留了 `'remote'`，并声明不得假设它会一直缺席。

本组织内另一个 agent workbench 的对照促成了这次审查。该 workbench 直接把 `workspaceID` 存在会话行上，因此其索引可以把工作区作为一等列来分组。可迁移的是被索引的身份，而不是重复本身：该 workbench 不拥有账号体系，其 agent 运行在持有会话的机器上，因此它从来不需要把会话的位置与拥有它的工作区分开。

## 提案

为会话索引增加 `workspace_id` 列，并以该身份而非目录作为会话日志存储的键。工作区成员资格始终由工作区记录保持唯一权威；索引列与日志桶都是该权威的派生投影，永远不是第二个来源。

这正是本变更要守住的原则。`adoptByCwd` 之所以能*从 header* 恢复成员资格，只是因为 header 并非权威——权威是持久记录。把工作区字段加进 `SessionHeader` 会颠倒这一点：两条记录都会声称知道归属，而两者不一致时没有确定的胜出方。

把该列加到 `persisted_sessions` 上，与它已经持有的血统列并列，并在 `_reconcile()` 中依据注册表的会话账目填充。协调已经按 `revision` 检测变化；所属工作区改变的会话就是必须被替换的行，因此现有机制无需第二条同步路径即可承载这一新事实。注册表未认领的行读作无归属，而不是错误；这能避免一个尚未完成启动的注册表写入错误归属，也是唯一不会静默重新分组的失败方向。

对通过 `session.create` 带 `workspaceId` 创建的会话，以工作区身份作为日志桶的键。`projectDir` 从工作区派生桶，并把 `cwd` 保持为它本来的位置字段，因此 `virtual` 工作区获得自己的桶，而 folder 工作区在目录移动后其会话依然可读。未指明工作区的会话，以及磁盘上已存在的每个会话，都完全按现在的路径规则解析，这正是让该存储变更具备增量性而非成为一次迁移的原因。

只有当某个组合真正产出 `remote` 类型时，header 才获得工作区身份，并通过这个索引列接线，使它作为带唯一消费方的单个字段落地，而不是第二个权威。在此之前，header 的 `cwd` 仍然是位置，工作区记录仍然是归属方。

## 待决问题

**注册表未就绪时，派生值来自哪里？** 在协调时读取会话账目保持唯一权威，但会让索引依赖注册表的可用性。路径匹配的回退让索引保持独立，却无法用于 `virtual` 工作区，而后者正是该列存在的原因。本提案选择「由注册表派生并配以显式的无归属值」；另一种做法记录在下方，两者都未定论。

**`remote` 的 header 字段是否要在产出方存在之前就加入？** `WorkspaceKind` 保留了该类型并禁止假设它会一直缺席。提前加入该字段的代价是一个未使用的 header 元素，以及为不携带它的日志带来的迁移问题；延后加入的代价是同一格式的第二次变更。

**未指明工作区创建的会话归属谁？** `session.create` 接受 `workspaceId` 或 `cwd`，也可以两者都不给，此时位置回退到显式或部署默认的 cwd。这样的会话有位置而无归属，因此索引必须能表达无归属，而不能让它读作错误。

## 考虑过的其他做法

**照对照 workbench 的做法把 `workspaceID` 复制到 `SessionHeader` 上。** 让索引变得简单且无需派生，却重复了 [types.ts](../../../../packages/workspace/workspace/src/types.ts) 定义为工作区记录所有的权威，并制造出没有确定胜出方的不一致。对照 workbench 之所以能负担这一点，是因为它没有账号体系也没有 virtual 工作区：它的服务端就是这台机器，所以它的会话行与工作区是同一个对象。脱离这一语境采纳该字段，等于引入一个本仓库并不存在的问题的解决方案。

**在协调时从 `cwd` 派生归属。** 无需格式变更，也不依赖注册表，并且对每个 `folder` 工作区都正确。它恰好在需要该列的地方失效：`virtual` 工作区没有目录可匹配，其会话会被索引为无归属，既无法分组也无处分组。把 `adoptByCwd` 已声明为仅适用于 folder 的规则当作查询权威来复用，等于把一条恢复启发式扩展成查询权威。

**重新为既有会话的存储换键。** 能立刻让布局统一。被否决，因为它会重写 `jsonl.spec.ts` 所钉住、且 `repairRemoteSessionPaths` 正是为纠正而存在的已提交产物位置；增量规则对变更之后创建的每个会话都能达到同样的布局，同时不触碰已经持久化的内容。

**改为采纳对照 workbench 的标题来源记录。** 它的会话行记录一个标题来源和一个 message id。本仓库已经存储了 `SessionTitleSource`，用于区分回退、带 provider 与 model 的提供方，以及会钉住标题的显式用户重命名，并连同标题所依据的确切 `messageSeqs` 一起记录在 [types.ts](../../../../packages/session/session-title/src/types.ts)。既有记录严格更强，因此没有可采纳之处。

**用订阅驱动的索引同步替代基于 revision 的协调。** 对照 workbench 在每次会话变更时通知其索引。本仓库在 `_reconcile()` 中比较已存储的 `revision`，只重新载入有差异的行，因此漏掉一次通知不会让索引变旧。纯推送路径会在容错上倒退，却换不来任何时效性收益。

## 验收标准

- `persisted_sessions` 携带 `workspace_id`，原地迁移，既有行读作无归属。
- 按工作区筛选的会话列举仅凭索引即可作答，`virtual` 工作区返回其会话，`folder` 工作区返回与当前连接相同的集合。
- 带 `workspaceId` 创建的会话，其日志持久化在由该身份派生的桶中；仅带 cwd 创建的会话，持久化在今天使用的路径桶中。
- 移动 `folder` 工作区的目录后，其会话仍可读取且仍为成员。
- 对于 `folder` 与 `virtual` 类型，没有任何会话 header 携带工作区身份，且 `WorkspaceKind` 的成员资格约定不变。

## 风险

在索引中重复归属方是本设计最容易失守之处。该列是记录账目的缓存，因此一次漏掉解除关联的协调会留下过时的分组；让注册表的账目成为唯一写入来源、并让无归属成为唯一回退，能让错误保持可见而不是显得合理。

在协调期间读取注册表会让索引的可用性依赖注册表启动。尚未就绪的注册表必须产出无归属的行，并由后续协调纠正，否则会话会在该进程的整个生命周期内被索引为没有工作区。

存储变更是增量的，因此在所有变更前会话老化退出之前，存储会同时存在两套桶规则。读取路径按写入该会话的规则解析它，这既能防止它变成一次迁移，也意味着解析中会永久保留一个分支。

给索引加上工作区列会让按工作区分组便宜到足以成为默认查询。如果某个 `remote` 工作区的会话日后来自提供方，该列中的身份正是让本地与远程会话得以一起分组的事实，同时也是不得被当作「内容可达」之证明的事实。
