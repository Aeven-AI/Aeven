# Agent Note: 工作区文件随账户同步

Status: proposed

[English](2026-11-03-workspace-file-sync.md) | 中文

## 问题

[账户同步](2026-10-27-account-sync-network.zh.md)让对话、记忆、设置和工作区列表在账户的每台设备上保持一致，但工作区指向的文件不在其中。`@aeven/workspace` 通过账户的 `workspaces` 文档发布工作区的标题、顺序和所有者，从不发布其目录（[`sync.ts`](../../../../packages/workspace/workspace/src/sync.ts)）。收到该工作区的设备将其存为 `kind: 'remote'`（[`index.ts`](../../../../packages/workspace/workspace/src/index.ts)），导入其中的会话在本设备绑定目录之前解析不到任何目录（[本地绑定 Agent Note](../../implemented/architecture/2026-10-29-synced-session-directory-is-the-local-binding.zh.md)）。

目前绑定它的唯一方式是侧边栏的 **链接工作区** 操作，它会打开文件夹选择器（[`ui-workspace` `bindWorkspace`](../../../../packages/client/ui-workspace/src/client/index.ts)）；在此之前，新会话首屏显示通用的 **选择工作区** 标签。这假定用户已经把文件复制到第二台机器并能找到它们，而且没有任何检查确认所选文件夹是同一个项目。在新笔记本上登录的用户能看到自己的对话和记忆，却无法继续任何涉及文件的任务，而大多数任务都涉及文件。

工作区既可能是一个文档文件夹，也可能是完整的仓库：带 `.git` 目录、数 GB 的依赖、构建输出、被 Git 忽略的机密，以及只在一台机器上有意义的文件。单一的逐字节复制机制能很好地服务前者，却服务不好后者：两台机器都对同一个被复制的 `.git` 目录运行 Git、编辑器和代理时，会在 `index.lock`、packed refs 和对象库上发生竞争；复制 `node_modules` 或 `target/` 则为每台机器都会重新生成的文件消耗带宽。

普通用户不应该需要理解这些。产品承诺是：在任何已登录的电脑上，用户打开工作区时它的文件、机密和依赖都已就绪，无需设置，正常情况下不提任何问题，也不会明显影响电量或响应速度。

## 提案

每个工作区都携带一份同步的描述，说明其文件从何而来；账户的每台设备都能在本地取得这些文件，而无需用户选择方式。两种传输覆盖两类工作区，设备通过检查文件夹来选择，从不询问：

| 工作区 | 判定方式 | 传输 | 跨设备传递的内容 |
|---|---|---|---|
| **仓库** | 绑定的文件夹是 Git 工作树 | Git：从远程克隆；远程不可达时从另一台设备或云端副本克隆；工作状态检查点携带未提交和未推送的工作 | 不含凭据的远程 URL、分支、位置提示、加密的工作状态检查点、加密的环境文件 |
| **文件夹** | 其他所有情况 | [Syncthing](https://github.com/syncthing/syncthing)，在账户自己的设备之间点对点传输，外加 Aeven 服务器上的加密云端副本 | 文件夹 id、大小与文件数、位置提示、端到端加密的文件夹内容 |
| **仅对话** | 用户从本设备移除了文件，或拒绝了一次放不下的下载 | 无 | 账户同步已传递内容之外不再传递任何内容 |

四个默认行为让该功能开箱即用：

- **打开之前就已就绪。** 最近 `prefetch.recentDays` 天（默认 30）内在任何设备上用过的工作区在磁盘预算内于后台到达；其他工作区在首次打开时到达。
- **另一台电脑休眠时仍然可用。** Aeven 服务器上保存每个文件夹工作区的加密副本，服务器无法读取，在没有其他设备在线时提供文件（[云端副本](#cloud-copy)）。
- **新电脑上无需设置任何东西。** 电脑缺少 Git 时通过平台自己的安装器安装，被 Git 忽略的环境文件加密传递，依赖在后台安装（[全新电脑](#a-fresh-computer)）。
- **工作从不等待整个文件夹。** 用户或代理打开的文件优先获取；只有读取整个目录树的命令才会等待（[按需文件](#on-demand-files)）。

### 用户体验原则

1. **不选择模式。** 设备通过检查文件夹对工作区分类。"仓库"和"文件夹"都不会作为选项出现在界面中。
2. **不询问位置。** 设备根据位置提示和下面的放置规则得出本地文件夹，事后显示它，并在工作区菜单中提供 **使用其他文件夹…**。
3. **只问一个问题，且只在磁盘放不下时问。** 正常流程中唯一的确认是超出磁盘预算的下载。凭据失败、文件的两个版本、休眠的设备和缺失的工具都会被自动处理或作为状态报告，从不以模态框出现。
4. **不会悄无声息地丢失任何东西。** 被另一台设备删除或替换的文件在保留期内可以恢复；工作状态检查点在覆盖本地更改之前总是先保存它们；环境文件从不覆盖本地文件；冲突的编辑保留两个版本。
5. **没有传输术语。** 用户可见的文案从不出现 Syncthing、设备 id、文件夹 id、bundle、stash、中继、检查点或冲突。文案说的是*文件*、*你的 MacBook Pro*、*正在获取文件*、*两个版本*、*正在准备*。所有文案都经过 locale 字典（[locale 拥有的界面文案](../../implemented/architecture/2026-08-23-locale-owned-client-ui-copy.zh.md)）。
6. **从不碍事。** 后台工作以低优先级运行，在使用电池和按流量计费的网络时暂停批量传输，从不拖慢输入框、模型请求或用户打开的文件。

### 用户看到的内容

#### 设备 A：创建工作区

没有任何变化。绑定文件夹会在后台发布文件描述：设备检测该文件夹是否为 Git 工作树，对仓库记录远程 URL（去除凭据）和分支，对文件夹记录大小和文件数。一旦账户有了第二台设备，设备 A 在接通电源时于后台为其文件夹工作区建立索引并上传到云端副本，使另一台设备无需等待扫描即可开始接收（[调度](#indexing-and-transfer-scheduling)）。

#### 设备 B：首次登录

账户同步现有的进度照常运行。来自其他设备的工作区以正常标题、按账户顺序出现在侧边栏中。最近用过的工作区立即开始在后台到达，最近使用的优先；它们的行只显示一条细进度线。预取范围之外的工作区显示一个小的下载图标，提示文字为"打开此工作区时文件会到达。"

#### 设备 B：打开文件夹工作区

1. 用户点击工作区或它的某个对话。如果预取已经完成，文件已在本地，不会发生其他事情。
2. 否则设备选定本地文件夹（[放置](#placement)），并同时从所有拥有这些文件的来源接收：设备 A、账户的其他设备和云端副本，优先使用局域网。工作区行和对话标题显示"正在获取文件 · 34%"。文件侧边栏立即列出整个文件夹；尚未到达的文件一被打开就优先于其余文件到达。
3. 如果文件夹会超出磁盘预算（[配置](#configuration)），会先出现一张内联卡片询问："Notes 有 14 GB，这台电脑剩余 20 GB。要下载吗？"，提供 **下载** 和 **只要对话**。"只要对话"将该工作区在本设备上标记为仅对话；工作区菜单之后提供 **获取文件**。
4. 完成后指示消失。该工作区此时就是持续同步的普通已绑定文件夹。

#### 设备 B：打开仓库工作区

1. 用户点击工作区。如果预取已经完成，它已就绪。
2. 如果在常见位置已存在同一远程的检出（[检出发现](#checkout-discovery)），设备绑定它并显示提示："正在使用 ~/code/aeven"。不发生下载。
3. 否则设备把远程连同子模块和 Git LFS 对象克隆到选定的文件夹："正在获取 aeven · 60%"。它使用这台电脑自己的 Git 凭据（SSH agent、凭据助手、Git Credential Manager），电脑没有 Git 时先安装 Git。
4. 如果克隆因认证或网络原因失败，设备改为从另一台设备或云端副本复制仓库（[对等克隆](#peer-clone)），并将 `origin` 设为远程 URL。通知显示"已从你的 MacBook Pro 复制。要从这台电脑推送，请登录 github.com。"不出现对话框。
5. 设备恢复工作区的环境文件并应用最新的工作状态检查点，使用户在设备 A 上未提交的更改出现在本地。
6. 如果仓库有可识别的锁文件且对应工具链已安装，设备在后台安装依赖："正在准备 aeven…"。期间工作区照常可用。

#### 在另一台设备上继续对话

会话交接已经在设备之间移动运行者租约（[`@aeven/session-handoff`](../../../../packages/session/session-handoff/README.zh.md)）。文件同步让认领设备的文件在下一个回合执行操作之前与前一个运行者一致：

- **前一个运行者在线**：认领设备向它请求一个新的工作状态检查点（仓库）或对它写入的文件立即扫描（文件夹），并直接接收。更改小于 50 MB 时几秒内完成，只在进行期间显示"正在同步…"。
- **前一个运行者离线**：认领设备使用最新的检查点和云端副本。设备在每个改动了工作树的回合之后、系统休眠之前和应用退出之前写入检查点，因此最新的检查点反映运行者看到的最后状态。
- **认领设备上有本地更改的仓库**：这些更改先被保存为命名 stash，并以通知告知。

#### 一个文件的两个版本

当两台设备在交换之前都修改了同一个文件时，两个版本都会保留。版本字节相同或一方只改了元数据时，设备自动解决。否则工作区行显示"1 个文件有两个版本"；点击它会打开对比视图，提供 **保留这个**、**保留另一个** 和 **都保留**。文本文件显示差异；其他文件显示大小、时间和设备。显示该标记期间不阻塞任何工作。由于运行者租约保证同一时间只有一个代理写入，而交接在回合之前对齐文件，两个版本只会因两台设备上同时进行的人工编辑而产生。

#### 移除与删除

- **从这台电脑移除**（工作区菜单）停止本设备上的文件同步并保留本地文件；该工作区在此变为仅对话，在其他设备上保持不变。单独的 **移除并删除本地文件** 在一次确认后删除本地副本。
- 从账户中删除工作区（现有的删除操作）会停止每台设备上的文件同步，删除云端副本，且不删除任何设备上的文件。
- 删除已同步文件夹中的文件是普通更改，会传播出去；每台设备保留旧版本 `versionRetentionDays` 天（默认 30）。

#### 设置 → 同步 → 文件

在现有账户同步控件旁边增加一个分区（[`ui-settings-sync`](../../../../packages/client/ui-settings-sync/README.zh.md)）：

- **这台电脑上的文件**：**最近使用的工作区**（默认）、**所有工作区** 或 **仅在我打开时**。
- **在云端保留加密副本**（默认开启），显示已用存储和账户配额。
- 在这台电脑上 **暂停文件同步**。
- 这台电脑上已用的存储，以及工作区列表，显示其状态和本地文件夹，每项提供 **在访达/资源管理器中显示** 和 **从这台电脑移除**。

### 状态词汇

每个工作区在每台设备上有一个文件状态，显示在侧边栏行、对话标题和文件侧边栏中：

| 状态 | 文案（中文） | 含义 |
|---|---|---|
| `absent` | "打开此工作区时文件会到达" | 不在预取范围内，且未在此打开过 |
| `fetching` | "正在获取文件 · 34%" | 首次下载、克隆或对等克隆正在进行 |
| `preparing` | "正在准备 aeven…" | 克隆后正在安装依赖 |
| `current` | （无标识） | 其他设备拥有的每个文件都已在此 |
| `catching-up` | "正在同步…" | 首次下载后正在接收更改 |
| `waiting` | "正在等待你的 MacBook Pro" | 没有在线设备，也没有云端副本持有这些文件（云端副本关闭或超出配额） |
| `diverged` | "1 个文件有两个版本" | 存在未解决的冲突版本 |
| `paused` | "文件同步已暂停" | 用户暂停了同步，或批量传输在等待接通电源或非计费网络 |
| `chats-only` | "这台电脑上只有对话" | 用户在此拒绝或移除了文件 |
| `failed` | "无法获取文件 · 重试" | 磁盘已满、权限被拒绝，或没有可达的来源 |

<a id="placement"></a>
### 放置

设备按以下顺序选择本地文件夹，不询问用户：

1. **镜像来源位置。** 设备 A 发布位置提示：文件夹相对其主目录的路径（`Projects/aeven`）；文件夹位于主目录之外时不发布。设备 B 使用 `<home>/<hint>`，并按本平台转换分隔符和保留字符。
2. **复用已有的匹配。** 如果该路径存在且是同一个项目——具有相同规范化远程的 Git 工作树，或其 `.aeven-workspace` 标记文件指明同一工作区 id 的文件夹——设备直接绑定它，不下载。
3. **从不合并进无关文件夹。** 如果该路径存在、非空且不匹配，设备改用 `<root>/<title>`（默认根目录 `~/Aeven`），名称冲突时追加 ` 2`、` 3`。
4. **回退到根目录。** 没有提示时，设备使用 `<root>/<title>`。

位置提示从来不是绑定：绑定按[本地绑定 Agent Note](../../implemented/architecture/2026-10-29-synced-session-directory-is-the-local-binding.zh.md) 的要求保持设备本地。在 macOS 上，镜像到 `~/Documents`、`~/Desktop` 或 `~/Downloads` 下的路径会触发系统一次性的文件夹访问提示，该提示属于操作系统，每类文件夹至多出现一次。

<a id="checkout-discovery"></a>
### 检出发现

克隆之前，设备查找具有相同规范化远程 URL 的已有检出（scheme、主机和路径，去除 `.git` 和凭据，使 SSH 与 HTTPS 形式能够匹配）：

- 规则 1 选定的路径。
- 本设备上已绑定到其他工作区的文件夹的父目录。
- `discoveryRoots`（默认 `~/Projects`、`~/code`、`~/src`、`~/Developer`、`~/repos`、`~/git`、`~/workspace`，以及 `%USERPROFILE%` 下的 Windows 对应目录）下至多 `discoveryDepth`（默认 2）层。

发现过程只读取每个候选的 `.git/config`，在第一个匹配处停止，500 ms 后放弃，并按设备缓存候选列表。分支不同的匹配仍会被绑定；工作状态检查点步骤处理分支差异。

<a id="a-fresh-computer"></a>
### 全新电脑

新电脑往往没有 Git、没有机密，也没有已安装的依赖。每一项都无需用户处理：

- **Git。** 设备使用在 `PATH` 和各平台标准安装位置找到的 Git；应用不附带 Git。当仓库工作区在没有 Git 的电脑上需要 Git 时，设备运行一次平台的安装器，该行显示"正在安装 Git"：存在 Homebrew 时运行 `brew install git`；否则在 macOS 上运行 `xcode-select --install`，它会打开 Apple 的一键式命令行工具对话框；在 Windows 上运行 `winget install --id Git.Git --exact --silent`，可能会显示 Windows 管理员提示；在 Linux 上安装需要 root 权限，该行显示发行版的安装命令供复制。由于正在运行的进程看不到 `PATH` 的变化，设备通过探测标准位置来检测安装完成，然后继续克隆。缺少 Git LFS 时跳过 LFS 对象，并在该行列出它们。代理自己使用 Git 时解析到同一个可执行文件。
- **环境文件。** 被 Git 忽略但项目运行所需的文件——名称匹配 `envFiles.patterns`（默认 `.env`、`.env.*`、`.dev.vars`、`.envrc`，排除 `*.example`、`*.sample`、`*.template`）且每个小于 `envFiles.maxBytes`（默认 64 KB）——随工作区描述加密传递。设备只在不存在同名文件的位置恢复它，从不覆盖本地值；一台设备上的更改以同样方式更新其他设备。其他被忽略的文件从不传递。
- **依赖。** 克隆后，设备检测锁文件（`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock`、`bun.lock`、`uv.lock`、`poetry.lock`、`Pipfile.lock`、`Cargo.lock`、`go.sum`、`Gemfile.lock`），当对应工具链在 `PATH` 上时，通过 shell 能力在工作区的沙箱中以低优先级运行该锁文件的冻结安装命令。缺少工具链时静默跳过；任务需要时由代理安装。工作区中有打开的会话时，该步骤记录为会话事件，使模型知道依赖正在安装，不会再启动第二次安装。

<a id="on-demand-files"></a>
### 按需文件

文件夹工作区处于 `fetching` 状态时，设备已持有 Syncthing 关于其他设备拥有的每个文件的索引。文件侧边栏和代理的目录列表显示这棵完整的树。读取尚未到达的文件会把它移到下载队列最前面（Syncthing 的 `POST /rest/db/prio`）并只等待这一个文件，这通过文件同步 Consumer 在[文件系统能力](../../../../packages/fs/README.zh.md)上注册的读取前钩子实现。读取整个目录树的命令——shell 命令和内容搜索——会等待工作区变为 `current` 并显示进度，上限为 `handoffWaitMs`；超过上限后照常运行，并在对话记录中注明部分文件仍在到达。模型可见的说明是会话事件，因此日志能够重建它们。

<a id="indexing-and-transfer-scheduling"></a>
### 索引与传输调度

- **只在需要时运行 Syncthing。** 当账户至少有两台设备且至少有一个文件夹工作区或仅本地的仓库时，提供者启动 Syncthing。单设备账户，以及所有工作区都是有远程的仓库的账户，从不启动它。
- **提前索引，按需传输。** 账户一有第二台设备，设备 A 就在接通电源时以低进程优先级为其文件夹工作区建立索引，之后通过文件系统监视器跟踪更改。哈希成本在任何设备请求之前一次性付清，因此请求能立即开始传输。
- **邀请不花成本。** 设备 A 向账户的每台设备邀请每个文件夹工作区。接收设备只接受其预取范围内或用户打开过的工作区的邀请；未接受的邀请在双方都不消耗任何资源。
- **预取顺序与预算。** 接收设备按最近使用优先的顺序取得其预取范围，当下一个工作区会使各工作区总量超过剩余磁盘的 `prefetch.diskShare`（默认 20%），或单个工作区超过 `prefetch.maxBytes`（默认 5 GB）时停止；这些工作区等待用户明确打开。
- **电源与网络。** 使用电池时，初始索引、预取和超过 100 MB 的首次下载暂停；被请求的文件和持续的更改照常进行。在操作系统报告为按流量计费的连接上（Windows 网络成本、macOS 昂贵路径），批量传输同样暂停，该信息通过桌面应用提供的一个小型平台查询读取。

<a id="continuing-work-across-devices"></a>
### 跨设备继续工作

仓库工作区未提交和未推送的工作以**工作状态检查点**传递，由仓库 Consumer 负责：

- **内容**：基础提交和分支；从 `HEAD` 可达而远程跟踪分支中没有的提交组成的 `git bundle`；已跟踪更改相对 `HEAD` 的二进制 diff；以及未被 `.gitignore` 排除的未跟踪文件的归档。环境文件单独传递（[全新电脑](#a-fresh-computer)）；其他被忽略的文件从不传递。
- **时机**：运行者在线时应认领设备的请求生成；在改动了工作树的回合之后生成（防抖为每 30 秒至多一次，并在回合结束后计算，从不拖延回合）；系统休眠之前；应用退出之前。内容地址与上一个相同的检查点不会写入。
- **位置**：两台设备都在线时，通过只在两者之间共享的传输文件夹直接传递。否则作为会话同步已在使用的附件路径中的一个加密、按内容寻址的 blob，`workspace-git/<workspace id>` 文档中的每工作区条目指向每个会话、每台设备的最新检查点。中继既看不到内容也看不到名称。
- **大小**：大于 `checkpointMaxBytes`（默认 50 MB）的检查点只走直接路径，运行者离线时走云端副本的传输文件夹。
- **应用**：认领设备获取基础提交（从远程获取，否则从 bundle 获取）；如果其工作树有本地更改，先将其保存为命名 stash（`aeven: before continuing from MacBook Pro`）并以通知告知；然后检出该分支，应用 bundle 和 diff，并解出未跟踪文件。它从不 reset、强制检出或删除分支。应用失败时 stash 和工作树保持原样，失败会在对话中报告。

<a id="peer-clone"></a>
### 对等克隆

本设备无法访问其远程的仓库——仅本地的仓库、本设备无法认证的私有主机，或离线的远程——从某台设备或云端副本复制：持有方把 `git bundle create --all`（含已检出修订的 LFS 对象）写入一个只与请求方共享的传输文件夹，请求方从中克隆，在存在记录的远程 URL 时将 `origin` 设为它，随后持有方删除该 bundle。仅本地的仓库在其云端副本传输文件夹中保留一个增量刷新的 bundle，有新提交后至多每 `peerBundleIntervalMs` 更新一次，使其在其他设备都休眠时仍然可用。仓库从不通过复制其 `.git` 目录来同步。

<a id="cloud-copy"></a>
### 云端副本

Aeven 服务器使用 Syncthing 的不受信任设备模式，为每个文件夹工作区和仅本地仓库的 bundle 保存加密副本：服务器存储并提供加密的块、名称和元数据，从不收到文件夹密码。

- **密码。** 每个文件夹的密码在设备上按 `HKDF(vault key, "file-sync/folder" ‖ folder id)` 派生，从不显示，也无需输入。
- **分配。** 服务器运行一个 Syncthing 实例池，并为每个账户分配其中一个。设备从经过认证的服务器端点读取所分配实例的设备 id，并将其作为每个文件夹的不受信任对等设备添加。由于该对等设备只收到密文，分配错误不会暴露任何内容。
- **用途。** 接收设备从云端副本拉取块，与其在线对等设备并行，因此它也能加快下载；没有对等设备在线时由它单独提供。
- **配额。** 云端副本计入账户的同步存储配额。超出配额时，最大的文件夹只在对等设备之间同步，设置页面会指明是哪些。
- **生命周期。** 删除工作区会删除其云端副本；删除账户会清除所有副本。
- **密钥模式。** 使用通行密钥持有的密钥时，服务器无法派生密码。使用中继持有的密钥时，中继持有保险库密钥，因此能够派生，这与该模式下其他每个账户文档已有的暴露相同；设置页面像说明其余内容一样说明这一点。

### 文件夹同步细节

- **忽略规则。** 提供者根据内置默认集合（`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build`、`target`、`.next`、`.turbo`、`.cache`、`.DS_Store`、`Thumbs.db`、`*.tmp`）写入 `.stignore`，文件夹有 `.gitignore` 时再加上转换为 Syncthing 忽略语法的规则。`defaultIgnores` 替换内置集合。设置列表为每个工作区提供高级编辑器；普通用户永远看不到它。
- **版本保留。** 每个文件夹使用 Syncthing 的分级版本保留，保留期为 `versionRetentionDays`，因此来自另一台设备的删除或覆盖可以恢复。
- **冲突。** 提供者检测 Syncthing 的 `*.sync-conflict-*` 副本，将其从代理的文件列表和搜索中隐藏，并通过 `diverged` 状态呈现；解决时通过提供者重命名或删除它们。
- **平台限制。** Syncthing 会报告它无法在接收平台上创建的文件（仅大小写不同的名称冲突、Windows 保留名、过长路径、Windows 上的符号链接）；提供者将其作为列出这些文件的 `failed` 条目呈现，而不是整个工作区失败。
- **对话工作区。** 代理从虚拟的对话工作区写入的文件作为附件传递，会话同步已经加密发布附件并按需获取，而不作为文件夹传递。

### 性能

机制：

- **快速传播。** 工作区文件夹使用 `watcherDelayS`（默认 1 秒）的文件系统监视器延迟。文件同步 Consumer 还会在代理的文件工具完成时请求扫描它写入的每个路径，使更改无需等待监视器即可到达在线的对等设备。
- **多来源的块级传输。** Syncthing 只传输变化的块，检测重命名和移动而不重新传输，并从每台拥有这些块的设备和云端副本拉取，优先使用局域网。
- **低优先级。** Syncthing 以其低优先级设置和有限数量的哈希线程运行（使用电池时为一个），因此从不与代理、模型流或界面争夺资源。
- **完整克隆。** 仓库以完整历史克隆，代理使用 Git 时会读取它；浅克隆和部分克隆以更快的首次克隆换来后续工作中的网络往返。
- **低成本检查点。** 检查点使用 Git 的索引（`git diff`、`git ls-files --others --exclude-standard`），在回合结束后运行，进行防抖，并按地址跳过未变化的内容。

预算在第 0 阶段设定，并在最后一个阶段于 macOS、Windows 和 Linux 上验证：

| 指标 | 目标 |
|---|---|
| 小于 10 MB 的文件更改在同一局域网的在线对等设备上可见 | 3 秒以内 |
| 同上，跨互联网 | 10 秒以内 |
| 运行者在线且更改小于 50 MB 时的交接 | 下一个回合开始前 5 秒以内 |
| `fetching` 期间被请求文件的首字节 | 2 秒以内 |
| Syncthing 空闲 CPU，已索引 100,000 个文件 | 平均低于 1% |
| Syncthing 常驻内存，已索引 100,000 个文件 | 低于 200 MB |
| 检查点给回合增加的延迟 | 无：在回合结束后运行 |

### 架构

该功能是一个用于文件传输的[能力接缝](../../../../docs/glossary.zh.md#capability-seam)，外加两个 Consumer：

| 包 | 角色 |
|---|---|
| `packages/sync/file-sync`（`@aeven/file-sync`） | Service Definition `ctx.fileSync`：本设备的传输对等 id、与对等设备和云端副本共享和取消共享文件夹、文件夹状态及其变更事件、全局文件索引、文件优先级、定向扫描、冲突及其解决，以及用于交接的 `awaitCurrent(owner, folder, deadline)` |
| `packages/sync/file-sync-syncthing`（`@aeven/file-sync-syncthing`） | Service Provider：通过 subprocess 能力监管打包的 Syncthing 进程，通过其回环 REST API 配置它，跟随 `/rest/events`，将文件夹映射到工作区，写入忽略、版本保留、监视器和优先级设置，并执行电源与网络策略 |
| `packages/workspace/workspace` | Consumer：在现有 `workspaces` 文档中发布每个工作区的文件描述、位置提示、请求方和持有方；运行放置、预取和状态投影；注册读取前钩子以及 shell 和搜索的等待闸门 |
| `packages/workspace/workspace-git-sync`（`@aeven/workspace-git-sync`） | Consumer：Git 解析与安装、仓库检测、远程规范化、检出发现、含子模块和 LFS 的克隆、对等克隆、环境文件、依赖准备、工作状态检查点，以及注册在会话交接认领上的应用步骤 |
| `packages/api/file-sync-controller` | Remote：为 Client 提供状态、取得、移除、冲突和设置 |
| `packages/client/ui-workspace`、`ui-sidebar-files`、`ui-settings-sync` | 行状态与进度、`fetching` 期间的完整目录树、设置 → 同步 → 文件、两个版本的对比视图 |

`workspaces` 文档的每条记录增加以下字段，全部位于账户的端到端加密之内：

```ts
interface SyncedWorkspaceFiles {
  /** How a device materializes the workspace's files. */
  source:
    | { kind: 'repository'; remote?: string; branch?: string }
    | { kind: 'folder'; folder: FileSyncFolderId; bytes: number; files: number }
  /** Path relative to the publishing device's home directory; a placement hint, never a binding. */
  hint?: string
  /** Devices that asked for the files, and devices that hold them. */
  wants: Record<DeviceId, true>
  holders: Record<DeviceId, true>
  /** Last time any device used the workspace, which orders prefetch. */
  usedAt: string
}
```

环境文件位于单独的 `workspace-env/<workspace id>` 文档中，使其内容只在持有该工作区的设备上加载。`FileSyncFolderId` 和 `DeviceId` 是品牌类型（[`avn-brand`](../../../../packages/util/brand/README.zh.md)）；文件夹 id 是随机的，从不由标题或路径派生。

#### 无需用户参与的设备配对

每台设备的 Syncthing 设备 id 发布在账户现有的 `devices` 文档中，该文档目前保存每台设备的名称（[`sync-yjs`](../../../../packages/sync/sync-yjs/README.zh.md)）。提供者只把该文档为本账户列出的 Syncthing 对等设备添加为受信任对等设备，把分配的云端实例添加为不受信任对等设备，移除其设备已离开文档的对等设备；只有当账户的 `workspaces` 文档列出该文件夹 id 时才自动接受文件夹邀请，其他一律拒绝。Syncthing GUI 绑定在回环地址并使用随机 API 密钥，使用情况报告和崩溃报告关闭，自动升级关闭，任何 Syncthing 界面都不会显示。

信任随账户密钥模式而定。使用通行密钥持有的密钥时，只有账户的设备能写入 `devices` 文档，因此没有其他人能添加受信任对等设备。使用中继持有的密钥时，中继可以写入该文档并添加自己的对等设备，这与该模式下其他每个账户文档已有的暴露相同。

#### 网络

当设备处于同一网络或能穿透 NAT 时，Syncthing 通过 TLS 直接连接它们。对于发现和中继，Aeven 在 aeven.io 上运行自己的 `stdiscosrv` 和 `strelaysrv`，并配置每台设备使用它们，因此可用性和元数据不依赖公共 Syncthing 服务池；本地发现对局域网对等设备保持开启。中继在设备之间转发 TLS 流，无法读取其内容。发现和中继服务器能看到设备 id、IP 地址和流量大小，与账户中继对其自身帧已能看到的内容相同。

#### 进程与打包

- 桌面构建为每个平台和架构下载固定版本的 Syncthing 发布包（压缩后约 14 MB，解压后 36 MB），校验其校验和，并作为嵌套可执行文件发布，与 [`prepare-runtime.ts`](../../../../apps/desktop/scripts/prepare-runtime.ts) 处理 Cua Driver 的路径相同，因此它随应用一起签名和公证。
- 提供者在每个 Host 上运行一个 Syncthing 进程，其主目录位于 `$AVN_HOME/file-sync/syncthing/`；崩溃后按退避策略重启，并随 Host 停止。文件夹标记其所属账户；文件夹只与该账户的对等设备和云端实例共享。
- 桌面配置补丁挂载这些插件；基础和 Web bundle 以禁用状态挂载它们。浏览器无法运行 Syncthing，因此 Web 端对文件的访问经由用户的某台设备，与[托管 Web 界面 Agent Note](2026-09-30-hosted-web-surface-and-sync.zh.md) 一致。
- Syncthing 采用 MPL-2.0。发布其未修改的二进制文件需要附带许可声明和对应源代码的链接；本地补丁将会公开。

对计划的修改：

- **`pullerDelayS: 0`** 应用于每个工作区文件夹；仅 Syncthing 默认的 1 s 就超过同网络预算的三分之一。
- **批量首次获取。** 首次下载受限于大量小文件而非字节数：即使调优后，100,000 个文件的文件夹也需要约 4 分钟。处于 `fetching` 的文件夹关闭 fsync，使用 16 路并发写入以及 4 个复制器和哈希器，并在 `current` 时恢复默认设置；此时其他设备仍持有断电可能中断的每个文件。仓库工作区通过 Git 克隆，因此不受此限制。
- **获取期间的优先级。** 2 KB 请求被正在传输的大块阻塞，未达到 2 s 预算。第 1 阶段在有优先请求待处理时降低 `pullerMaxPendingKiB` 并重新测量。
- **向云端副本的重命名会重新上传。** 加密名称决定每个文件的加密方式，因此移动的大文件会再次发送到云端副本；对等设备之间的重命名仍然无需传输。云端副本的配额会计入这部分。
- **Git 不随安装器附带。** 通过 dugite 打包 Git 的实测大小为每个平台解压后 150 MB，去掉 Git Credential Manager 后 40 MB；设备改为运行平台的 Git 安装器（[全新电脑](#a-fresh-computer)）。
- **密度结果倾向对象存储。** 每个账户约 7 MB 和 0.05% 的空闲 CPU，每秒每次编辑占一个核心的 2.2%，使一个实例只能承载数百而非数千个账户；第 4 阶段从[未决问题 1](#open-questions) 中的中继对象存储方案开始。

<a id="open-questions"></a>
### 未决问题

1. **云端实例密度。** 一个不受信任设备模式的 Syncthing 实例在其内存和连接限制内能为多少账户的文件夹提供服务，决定了实例池的规模和成本。首次探索测得每个实例可承载数百个账户（[结果](#phase-0-results)）；由于密度较低，云端副本改为通过账户中继的对象存储保存同样的加密块，仍在同一个 `ctx.fileSync` 提供者之后。
2. **不受信任设备模式的成熟度。** Syncthing 的文档将不受信任设备模式标为比协议其余部分更新的功能。首次探索发现崩溃恢复、源设备离线时的恢复以及通过云端副本中转的编辑均正确，而重命名会重新上传（[结果](#phase-0-results)）；在云端副本成为默认之前，还需在 Windows 和 Linux 上完成大型文件夹测试。

## 考虑过的替代方案

**对每个工作区都使用 Syncthing，包括 `.git`。** 单一传输更容易构建。被否决，因为两台设备对同一个被复制的 `.git` 运行 Git 和代理时会在锁文件、refs 和 pack 上竞争，而被复制的依赖和构建目录为每台机器都会重新生成的文件消耗带宽。Git 本身已经能正确复制仓库。

**只用 Git，要求有远程。** 对开发者最简单。被否决，因为许多工作区是没有仓库的文档文件夹，而要求用户创建远程正是本提案要消除的那类问题。

**让用户选择模式和位置。** 明确且容易实现。因用户体验目标而被否决：设备判断这两者比普通用户更准确，剩下的唯一问题是为了保护磁盘。

**只在打开工作区时下载。** 节省第二台设备的磁盘。作为默认行为被否决，因为首次打开时需要等待整个传输；在磁盘预算内预取最近使用的工作区既保护了磁盘，又让常见情况即时可用。设置页面保留它作为 **仅在我打开时**。

**登录时下载每个工作区。** 文件总是就绪。作为默认行为被否决，因为开发者账户可能有数十 GB 第二台设备从不使用的内容。设置页面保留它作为 **所有工作区**。

**只在另一台设备请求后才建立索引。** 不在无人请求的文件夹上花费任何资源。被否决，因为首次请求需要等待设备 A 对文件夹进行完整哈希，并且在设备 A 休眠时完全失败；在接通电源时提前索引，一次性付出成本，且不在关键路径上。

**只用对等设备，不要云端副本。** 每个字节都不经过 Aeven 服务器。作为默认行为被否决，因为最常见的第二台设备场景——笔记本合上了，用户坐在台式机前——会显示"正在等待你的 MacBook Pro"。云端副本使用服务器在通行密钥模式下永远收不到的密码加密，设置页面可以关闭它。

**服务器能读取的云端副本。** 运维更简单且可搜索。被否决，因为服务器不得能够读取数据。

**让代理等待整个文件夹。** 简单且一致。被否决，因为文件工具能在几秒内获取所需的那一个文件；只有输出会不完整的整树命令才需要等待。

**让用户自己处理 `.env` 文件。** 机密不经过网络。被否决，因为新电脑上的第一个回合在大多数 Web 和后端仓库中会因此失败，这与开箱即用正好相反；这些文件很小，端到端加密，且从不覆盖本地值。

**通过 dugite 打包 Git。** 在没有 Git 的电脑上省去安装步骤。被否决：每个平台解压后 150 MB，去掉 Git Credential Manager 后仍有 40 MB，另需签名和公证 37 个可执行文件，并承担 GPL-2.0 源代码义务，而缺少 Git 的电脑只占少数，平台安装器即可覆盖。

**浅克隆或部分克隆。** 首次克隆更快。被否决，因为代理会读取历史和 blame，而部分克隆会在代理需要时通过网络获取缺失的对象，这更慢且离线时会失败。

**通过 Syncthing 实时镜像仓库工作树并排除 `.git`。** 能让文件在设备间即时更新。被否决，因为每台设备的索引和 `HEAD` 与被镜像的文件不一致，导致一台设备上的 `git status` 把另一台的编辑报告为自己的更改。认领时生成的新检查点在需要的那一刻传递同样的工作，没有这种歧义。

**在账户中继上构建文件传输。** 通过现有中继进行分块、加密、按内容寻址的传输可以复用保险库，并只有一个网络身份。被否决，因为它要重建 Syncthing 经过十年打磨的块哈希、重命名检测、部分传输、文件监视、NAT 穿透、多来源下载和局域网直连传输。如果实例密度过低，它仍是云端副本的后备存储。

**Mutagen。** 对代码很强且速度快，但它通过 SSH 或自己的 agent 同步成对的端点，而不是一组设备，也没有发现或中继。

**Unison 和 rclone bisync。** 成对的双向同步，按需或按计划运行而非持续运行；两者都不发现对等设备，也不穿透 NAT。

**Resilio Sync。** 点对点且功能完善，但是专有软件，因此无法打包和审计。

**iroh。** 一个现代的点对点库，具备按内容寻址的 blob 和 NAT 穿透，但它是 Rust 库，需要在每个平台上提供原生 Node 插件，而文件夹同步语义（监视、忽略、冲突、版本保留）仍需自行编写。

**iCloud Drive、OneDrive、Dropbox 或 Google Drive。** 用户可以把工作区放在消费级云文件夹中。被否决，因为服务提供方能读取文件，这些服务为仅在线保存的文件创建的占位文件会破坏工具和构建，而且这些服务与原始复制一样会损坏 `.git` 目录。

## 验收标准

- 用户在第二台电脑上登录，无需回答任何问题，即可发现最近使用的文件夹工作区已经在本地，其他符合磁盘预算的文件夹工作区在打开后也在本地。
- 账户的其他每台设备都在休眠时，上述情况同样成立，由云端副本提供。
- 在第二台电脑上打开仓库工作区时，如果发现根目录中存在同一远程的检出则绑定它，否则连同子模块和 LFS 克隆；克隆失败时回退到对等克隆，全程不提问，且无需安装系统 Git。
- 克隆后，仓库的环境文件已就位且从不覆盖本地文件；工具链存在时依赖在后台安装。
- 在另一台设备上继续对话时，在下一个回合执行操作之前，带来前一个运行者在仓库工作区中未提交和未推送的更改，以及它在文件夹工作区中写入的每个文件；运行者在线且更改小于 50 MB 时，在 5 秒以内完成。
- `fetching` 期间列出完整目录树，代理读取的文件优先到达；shell 命令和搜索等待工作区变为 `current` 或达到上限。
- 每当检查点被应用到认领设备的本地更改之上时，这些更改都保存在命名 stash 中；冲突的编辑保留两个版本；删除在保留期内可以恢复。
- 单设备账户，以及所有工作区都是有远程的仓库的账户，从不启动 Syncthing。
- 性能预算在 macOS、Windows 和 Linux 上成立。
- 没有任何用户可见字符串出现 Syncthing、设备 id、文件夹 id、bundle、stash、检查点或中继；`verify-client-ui-i18n` 通过。
- 模型可见的效果（检查点说明、仍在到达的文件、依赖准备）以会话事件出现，因此会话日志能够重建它们。
- 录制会话快照，以及单元、e2e 和 SDK 期望输出覆盖文件取得、带检查点的交接、按需读取和状态词汇。

## 风险

- **第二个网络身份。** Syncthing 设备 id 与账户同步的设备密钥并存。配对从 `devices` 文档派生它们，因此该文档写入者（中继持有密钥模式下的中继）的失陷会延伸到文件对等设备。这与每种密钥模式已声明的信任一致。
- **机密经过网络。** 环境文件现在会传递。它们端到端加密，在通行密钥模式下只有账户的设备能读取；在中继持有密钥模式下中继能够读取，正如它能读取经常引用这些机密的对话一样。
- **克隆后运行仓库代码。** 依赖准备在没有明确点击的情况下运行用户自己仓库中的安装脚本。它在工作区的沙箱中运行，且只针对账户已经在使用的仓库；`prepareDependencies` 可以关闭它。
- **云端成本。** 云端副本增加每个账户的存储和一个实例池。配额按账户限制它；在其成为默认之前，第 0 阶段测量密度。
- **打包的原生可执行文件。** 签名、公证、Windows 上杀毒软件的误报，以及保持固定版本及时打补丁都是持续成本，与 Cua Driver 的路径共享。
- **资源使用。** 提前索引会在可能永远不被请求的文件夹上花费 CPU 和磁盘。它在接通电源时以低优先级运行，预算限制稳定状态。
- **在用户自己的编辑之上应用工作。** 应用检查点会改动用户可能正在编辑器中打开的文件。stash、通知以及从不 reset 使更改可撤销；用户仍会看到文件在编辑器下发生变化。
- **放置出乎意料。** 镜像路径可能落在第二台机器上用户未预期的位置。位置会在事后显示，**使用其他文件夹…** 可以移动绑定。
- **明知放弃的内容。** 仅使用 Web 和托管的用户得不到文件；不提供仓库工作树的逐键实时镜像；环境文件之外的被忽略文件不会传递；超出磁盘预算的工作区仍需询问一次。
