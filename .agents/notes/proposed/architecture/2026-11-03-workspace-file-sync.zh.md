# Agent Note: 工作区文件随账户同步

Status: proposed

[English](2026-11-03-workspace-file-sync.md) | 中文

## 问题

[账户同步](2026-10-27-account-sync-network.zh.md)让对话、记忆、设置和工作区列表在账户的每台设备上保持一致，但工作区指向的文件不在其中。`@aeven/workspace` 通过账户的 `workspaces` 文档发布工作区的标题、顺序和所有者，从不发布其目录（[`sync.ts`](../../../../packages/workspace/workspace/src/sync.ts)）。收到该工作区的设备将其存为 `kind: 'remote'`（[`index.ts`](../../../../packages/workspace/workspace/src/index.ts)），导入其中的会话在本设备绑定目录之前解析不到任何目录（[本地绑定 Agent Note](../../implemented/architecture/2026-10-29-synced-session-directory-is-the-local-binding.zh.md)）。

目前绑定它的唯一方式是侧边栏的 **链接工作区** 操作，它会打开文件夹选择器（[`ui-workspace` `bindWorkspace`](../../../../packages/client/ui-workspace/src/client/index.ts)）；在此之前，新会话首屏显示通用的 **选择工作区** 标签。这假定用户已经把文件复制到第二台机器并能找到它们，而且没有任何检查确认所选文件夹是同一个项目。在新笔记本上登录的用户能看到自己的对话和记忆，却无法继续任何涉及文件的任务，而大多数任务都涉及文件。

工作区既可能是一个文档文件夹，也可能是完整的仓库：带 `.git` 目录、数 GB 的依赖、构建输出，以及只在一台机器上有意义的文件。单一的逐字节复制机制能很好地服务前者，却服务不好后者：两台机器都对同一个被复制的 `.git` 目录运行 Git、编辑器和代理时，会在 `index.lock`、packed refs 和对象库上发生竞争；复制 `node_modules` 或 `target/` 则为每台机器都会重新生成的文件消耗带宽。

普通用户不应该需要理解这些。产品承诺是：在任何已登录的电脑上打开工作区都能看到它的文件，正常情况下不会询问传输方式、模式、文件夹或密钥。

## 提案

每个工作区都携带一份同步的描述，说明其文件从何而来；账户的每台设备都能在本地取得这些文件，而无需用户选择方式。两种传输覆盖两类工作区，设备通过检查文件夹来选择，从不询问：

| 工作区 | 判定方式 | 传输 | 跨设备传递的内容 |
|---|---|---|---|
| **仓库** | 绑定的文件夹是 Git 工作树 | Git：从远程克隆；没有可达远程时从另一台设备克隆；工作状态检查点携带未提交和未推送的工作 | 不含凭据的远程 URL、分支、相对主目录的位置提示、加密的工作状态检查点 |
| **文件夹** | 其他所有情况 | [Syncthing](https://github.com/syncthing/syncthing)，在账户自己的设备之间点对点传输 | 文件夹 id、大小与文件数、相对主目录的位置提示，文件夹内容在传输中端到端加密 |
| **仅对话** | 用户从本设备移除了文件，或拒绝了大文件下载 | 无 | 账户同步已传递内容之外不再传递任何内容 |

取得文件在用户表现出意图时开始——打开工作区、打开它的某个对话，或在其中开始会话——而从不在登录时开始，因此新设备不会被无人在此打开的工作区占满磁盘。

### 用户体验原则

1. **不选择模式。** 设备通过检查文件夹对工作区分类。"仓库"和"文件夹"都不会作为选项出现在界面中。
2. **不询问位置。** 设备根据位置提示和下面的放置规则得出本地文件夹，事后将其显示为可编辑文本，并在工作区菜单中为少数在意的用户提供 **使用其他文件夹…**。
3. **只问一个问题，且只在保护用户时问。** 正常流程中唯一的确认是体积很大或会导致磁盘空间不足的下载。凭据失败、冲突和离线的对等设备都会被自动处理或作为状态报告，从不以模态框出现。
4. **不会悄无声息地丢失任何东西。** 被另一台设备删除的文件会在可配置的保留期内进入版本文件夹；工作状态检查点在覆盖本地更改之前总是先将其暂存；冲突的编辑保留两个版本。
5. **没有传输术语。** 用户可见的文案从不出现 Syncthing、设备 id、文件夹 id、bundle、stash、中继或冲突。文案说的是*文件*、*你的 MacBook Pro*、*正在获取文件*、*两个版本*。所有文案都经过 locale 字典（[locale 拥有的界面文案](../../implemented/architecture/2026-08-23-locale-owned-client-ui-copy.zh.md)）。
6. **对话从不等待文件。** 文件到达期间输入框照常可用。只有会作用于文件夹的回合才会等待，并以进度和 **仍然开始** 操作告知。

### 用户看到的内容

#### 设备 A：创建工作区

没有任何变化。绑定文件夹会在后台发布文件描述：设备检测该文件夹是否为 Git 工作树，对仓库记录远程 URL（去除凭据）和分支，对文件夹记录大小和文件数。在另一台设备请求该文件夹之前，设备 A 不运行任何 Syncthing 扫描（见[按需共享](#lazy-sharing)）。

#### 设备 B：首次登录

账户同步现有的进度照常运行。来自其他设备的工作区以正常标题、按账户顺序出现在侧边栏中，带一个小的下载图标，取代当前的 "remote" 处理。悬停图标显示"文件在 MacBook Pro 上。打开即可获取。"文件不在任何在线设备上且没有远程的工作区显示"文件在 MacBook Pro 上，它当前离线。"

#### 设备 B：打开文件夹工作区

1. 用户点击工作区或它的某个对话。
2. 设备选定本地文件夹（[放置](#placement)）并开始接收。工作区行和对话标题显示"正在从 MacBook Pro 获取文件 · 34%"。文件侧边栏随文件到达而列出它们。
3. 如果文件夹大于 `fileSync.confirmAboveBytes`（默认 5 GB），或会使剩余空间低于 `fileSync.minFreeDiskRatio`（默认 10%），会先出现一张内联卡片询问："Notes 有 14 GB。要下载到这台电脑吗？"，提供 **下载** 和 **只要对话**。"只要对话"将该工作区在本设备上标记为仅对话；工作区菜单之后提供 **获取文件**。
4. 完成后图标消失。该工作区此时就是普通的已绑定文件夹，两台设备在线时持续保持同步。

#### 设备 B：打开仓库工作区

1. 用户点击工作区。
2. 如果在常见位置已存在同一远程的检出（[检出发现](#checkout-discovery)），设备绑定它并显示提示："正在使用 ~/code/aeven"。不发生下载。
3. 否则设备把远程克隆到选定的文件夹："正在从 github.com 获取 aeven · 60%"。克隆使用这台电脑自己的 Git 凭据（SSH agent、凭据助手、Git Credential Manager），因此可能出现系统登录提示，那是 Git 自己的，不是 Aeven 的。
4. 如果克隆因认证或网络原因失败，且持有该仓库的设备在线，设备改为从那台设备复制仓库（[对等克隆](#peer-clone)），并将 `origin` 设为远程 URL。通知显示"已从 MacBook Pro 复制。要从这台电脑推送，请用 Git 登录 github.com。"如果没有设备在线，该行显示"无法从 github.com 获取 aeven"并提供 **重试**。
5. 如果用户打开的对话有工作状态检查点（[跨设备继续工作](#continuing-work-across-devices)），设备在克隆后应用它，使设备 A 上未提交的更改出现在本地："已从 MacBook Pro 带来 3 个更改的文件"。

#### 在另一台设备上继续对话

会话交接已经在设备之间移动运行者租约（[`@aeven/session-handoff`](../../../../packages/session/session-handoff/README.zh.md)）。文件同步在认领设备开始回合之前增加一步：

- **文件夹工作区**：认领会等待，直到本设备持有前一个运行者写入的每个文件（"正在同步 12 个文件…"），上限为 `fileSync.handoffWaitMs`；超过上限后回合照常开始，并在对话记录中注明部分文件仍在到达。
- **仓库工作区**：认领会应用该工作区最新的工作状态检查点（"已从 MacBook Pro 带来 3 个更改的文件"）。

#### 一个文件的两个版本

当两台设备在交换之前都修改了同一个文件时，两个版本都会保留。版本字节相同或一方只改了元数据时，设备自动解决。否则工作区行显示"1 个文件有两个版本"；点击它会打开对比视图，提供 **保留这个**、**保留另一个** 和 **都保留**。文本文件显示差异；其他文件显示大小、时间和设备。显示该标记期间不阻塞任何工作。

#### 移除与删除

- **从这台电脑移除**（工作区菜单）停止本设备上的文件同步并保留本地文件；该工作区在此变为仅对话，在其他设备上保持不变。单独的 **移除并删除本地文件** 在一次确认后删除本地副本。
- 从账户中删除工作区（现有的删除操作）会停止每台设备上的文件同步，且不删除任何地方的文件。
- 删除已同步文件夹中的文件是普通更改，会传播出去；其他设备在版本文件夹中保留旧版本 `fileSync.versionRetentionDays` 天（默认 30）。

#### 设置 → 同步 → 文件

在现有账户同步控件旁边增加一个分区（[`ui-settings-sync`](../../../../packages/client/ui-settings-sync/README.zh.md)）：

- 已同步工作区在这台电脑上占用的存储。
- **自动获取每个工作区的文件**（默认关闭）：在大小限制内于后台取得每个工作区。
- 在这台电脑上 **暂停文件同步**。
- 工作区列表，显示其状态和本地文件夹，每项提供 **在访达/资源管理器中显示** 和 **从这台电脑移除**。

### 状态词汇

每个工作区在每台设备上有一个文件状态，显示在侧边栏行、对话标题和文件侧边栏中：

| 状态 | 文案（中文） | 含义 |
|---|---|---|
| `absent` | "文件在 MacBook Pro 上" | 尚未在此取得；打开即开始 |
| `waiting` | "正在等待 MacBook Pro" | 已请求，但没有持有文件的设备在线 |
| `fetching` | "正在获取文件 · 34%" | 首次下载、克隆或对等克隆正在进行 |
| `current` | （无标识） | 其他设备拥有的每个文件都已在此 |
| `catching-up` | "正在同步 12 个文件" | 首次下载后的持续同步 |
| `diverged` | "1 个文件有两个版本" | 存在未解决的冲突版本 |
| `paused` | "文件同步已暂停" | 用户暂停了同步或设备离线 |
| `chats-only` | "这台电脑上只有对话" | 用户在此拒绝或移除了文件 |
| `failed` | "无法获取文件 · 重试" | 无对等设备时克隆失败、磁盘已满或权限被拒绝 |

<a id="placement"></a>
### 放置

设备按以下顺序选择本地文件夹，不询问用户：

1. **镜像来源位置。** 设备 A 发布位置提示：文件夹相对其主目录的路径（`Projects/aeven`）；文件夹位于主目录之外时不发布。设备 B 使用 `<home>/<hint>`，并按本平台转换分隔符和保留字符。
2. **复用已有的匹配。** 如果该路径存在且是同一个项目——具有相同规范化远程的 Git 工作树，或其 `.aeven-workspace` 标记文件指明同一工作区 id 的文件夹——设备直接绑定它，不下载。
3. **从不合并进无关文件夹。** 如果该路径存在、非空且不匹配，设备改用 `<fileSync.root>/<title>`（默认根目录 `~/Aeven`），名称冲突时追加 ` 2`、` 3`。
4. **回退到根目录。** 没有提示时，设备使用 `<fileSync.root>/<title>`。

位置提示从来不是绑定：绑定按[本地绑定 Agent Note](../../implemented/architecture/2026-10-29-synced-session-directory-is-the-local-binding.zh.md) 的要求保持设备本地。在 macOS 上，`~/Documents`、`~/Desktop` 或 `~/Downloads` 下的路径会触发系统一次性的文件夹访问提示；默认根目录因此位于这些文件夹之外。

<a id="checkout-discovery"></a>
### 检出发现

克隆之前，设备查找具有相同规范化远程 URL 的已有检出（scheme、主机和路径，去除 `.git` 和凭据，使 SSH 与 HTTPS 形式能够匹配）：

- 规则 1 选定的路径。
- 本设备上已绑定到其他工作区的文件夹的父目录。
- 配置的 `fileSync.discoveryRoots`（默认 `~/Projects`、`~/code`、`~/src`、`~/Developer`、`~/repos`、`~/git`、`~/workspace`，以及 `%USERPROFILE%` 下的 Windows 对应目录）下至多 `fileSync.discoveryDepth`（默认 2）层。

发现过程只读取每个候选的 `.git/config`，并在第一个匹配处停止。分支不同的匹配仍会被绑定；工作状态检查点步骤处理分支差异。

<a id="lazy-sharing"></a>
### 按需共享

在另一台设备需要之前，设备 A 不为任何文件夹建立索引。设备 B 在账户的 `workspaces` 文档中记录请求（`wants: { <device>: true }`）；设备 A 看到它持有的文件夹有请求时，将该文件夹加入 Syncthing、扫描，并与请求设备共享。文件夹一旦被共享，设备 A 会继续与账户中每台请求它的设备共享。持有文件但从未收到请求的设备不会为它们消耗 CPU 或磁盘。

<a id="continuing-work-across-devices"></a>
### 跨设备继续工作

仓库工作区未提交和未推送的工作以**工作状态检查点**传递，由仓库 Consumer 负责：

- **内容**：基础提交和分支；从 `HEAD` 可达而远程跟踪分支中没有的提交组成的 `git bundle`；已跟踪更改相对 `HEAD` 的二进制 diff；以及未被 `.gitignore` 排除的未跟踪文件的归档。被忽略的文件从不传递。
- **时机**：运行者在每个改动了工作树的回合之后、以及释放运行者租约时写入检查点。内容与上一个相同的检查点不会写入。
- **位置**：负载是会话同步已在使用的附件路径中的一个加密、按内容寻址的 blob；`workspace-git/<workspace id>` 文档中的每工作区条目指向每个会话、每台设备的最新检查点。与其他每个账户文档一样，中继既看不到内容也看不到名称。
- **大小**：大于 `fileSync.checkpointMaxBytes`（默认 50 MB）的检查点不上传；运行者在线时认领设备直接从运行者获取，否则回合照常开始，并在对话记录中注明无法带来另一台设备的更改。
- **应用**：认领设备获取基础提交（从远程获取，否则从 bundle 获取）；如果其工作树有本地更改，先将其保存为命名 stash（`aeven: before continuing from MacBook Pro`）并以通知告知；然后检出该分支，应用 bundle 和 diff，并解出未跟踪文件。它从不 reset、强制检出或删除分支。应用失败时 stash 和工作树保持原样，失败会在对话中报告。

<a id="peer-clone"></a>
### 对等克隆

没有可达远程的仓库——仅本地的仓库、本设备无法认证的私有主机，或离线的远程——从持有它的设备复制：持有方把 `git bundle create --all` 写入一个只与请求设备共享的专用 Syncthing 文件夹，请求方从 bundle 克隆，在存在记录的远程 URL 时将 `origin` 设为它，随后持有方删除该 bundle。仅本地仓库的后续更新通过同一路径使用增量 bundle。仓库从不通过复制其 `.git` 目录来同步。

### 文件夹同步细节

- **忽略规则。** 提供者根据内置默认集合（`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build`、`target`、`.next`、`.turbo`、`.cache`、`.DS_Store`、`Thumbs.db`、`*.tmp`）写入 `.stignore`，文件夹有 `.gitignore` 时再加上转换为 Syncthing 忽略语法的规则。`fileSync.defaultIgnores` 替换内置集合。设置列表为每个工作区提供高级编辑器；普通用户永远看不到它。
- **版本保留。** 每个文件夹使用 Syncthing 的分级或回收站版本保留，保留期为 `fileSync.versionRetentionDays`，因此来自另一台设备的删除或覆盖可以恢复。
- **冲突。** 提供者检测 Syncthing 的 `*.sync-conflict-*` 副本，将其从代理的文件列表和搜索中隐藏，并通过 `diverged` 状态呈现；解决时通过提供者重命名或删除它们。
- **同步期间的代理写入。** 状态为 `fetching` 的文件夹工作区中的回合会等待 `current` 或用户的 **仍然开始**；`catching-up` 工作区中的回合立即开始，因为运行者租约保证同一时间只有一个代理写入。
- **平台限制。** Syncthing 会报告它无法在接收平台上创建的文件（仅大小写不同的名称冲突、Windows 保留名、过长路径、Windows 上的符号链接）；提供者将其作为列出这些文件的 `failed` 条目呈现，而不是整个工作区失败。

### 架构

该功能是一个用于文件传输的[能力接缝](../../../../docs/glossary.zh.md#capability-seam)，外加一个仓库 Consumer：

| 包 | 角色 |
|---|---|
| `packages/sync/file-sync`（`@aeven/file-sync`） | Service Definition `ctx.fileSync`：本设备的传输对等 id、与对等设备共享和取消共享文件夹、文件夹状态及其变更事件、冲突及其解决，以及用于交接的 `awaitCurrent(owner, folder, deadline)` |
| `packages/sync/file-sync-syncthing`（`@aeven/file-sync-syncthing`） | Service Provider：通过 subprocess 能力监管打包的 Syncthing 进程，通过其回环 REST API 配置它，跟随 `/rest/events`，将文件夹映射到工作区，写入忽略和版本保留设置 |
| `packages/workspace/workspace` | Consumer：在现有 `workspaces` 文档中发布每个工作区的文件描述、位置提示和每设备请求；在用户表现意图时取得文件；负责放置和状态投影 |
| `packages/workspace/workspace-git-sync`（`@aeven/workspace-git-sync`） | Consumer：仓库检测、远程规范化、检出发现、克隆、对等克隆、工作状态检查点，以及注册在会话交接认领上的应用步骤 |
| `packages/api/file-sync-controller` | Remote：为 Client 提供状态、取得、移除、冲突和设置 |
| `packages/client/ui-workspace`、`ui-sidebar-files`、`ui-settings-sync` | 行图标与状态、文件侧边栏进度、设置 → 同步 → 文件、两个版本的对比视图 |

`workspaces` 文档的每条记录增加三个字段，全部位于账户的端到端加密之内：

```ts
interface SyncedWorkspaceFiles {
  /** How a device materializes the workspace's files. */
  source:
    | { kind: 'repository'; remote?: string; branch?: string }
    | { kind: 'folder'; folder: FileSyncFolderId; bytes: number; files: number }
  /** Path relative to the publishing device's home directory; a placement hint, never a binding. */
  hint?: string
  /** Devices that asked for the files, and devices that hold them. */
  wants: Record<DeviceId, true>
  holders: Record<DeviceId, true>
}
```

`FileSyncFolderId` 和 `DeviceId` 是品牌类型（[`avn-brand`](../../../../packages/util/brand/README.zh.md)）；文件夹 id 是随机的，从不由标题或路径派生。

#### 无需用户参与的设备配对

每台设备的 Syncthing 设备 id 发布在账户现有的 `devices` 文档中，该文档目前保存每台设备的名称（[`sync-yjs`](../../../../packages/sync/sync-yjs/README.zh.md)）。提供者只添加该文档为本账户列出的 Syncthing 对等设备，移除其设备已离开文档的对等设备；只有当账户的 `workspaces` 文档列出该文件夹 id 且本设备请求了它时，才自动接受文件夹邀请，其他一律拒绝。Syncthing GUI 绑定在回环地址并使用随机 API 密钥，使用情况报告和崩溃报告关闭，自动升级关闭，任何 Syncthing 界面都不会显示。

信任随账户密钥模式而定。使用通行密钥持有的密钥时，只有账户的设备能写入 `devices` 文档，因此没有其他人能添加对等设备。使用中继持有的密钥时，中继可以写入该文档并添加自己的对等设备，这与该模式下其他每个账户文档已有的暴露相同；设置页面像说明其余内容一样说明这一点。

#### 网络

当设备处于同一网络或能穿透 NAT 时，Syncthing 通过 TLS 直接连接它们。对于发现和中继，Aeven 在 aeven.io 上运行自己的 `stdiscosrv` 和 `strelaysrv`，并配置每台设备使用它们，因此可用性和元数据不依赖公共 Syncthing 服务池；本地发现对局域网对等设备保持开启。中继在设备之间转发 TLS 流，无法读取其内容。发现和中继服务器能看到设备 id、IP 地址和流量大小，与账户中继对其自身帧已能看到的内容相同。

#### 进程与打包

- 桌面构建为每个平台和架构下载固定版本的 Syncthing 发布包，校验其校验和，并作为嵌套可执行文件发布，与 [`prepare-runtime.ts`](../../../../apps/desktop/scripts/prepare-runtime.ts) 处理 Cua Driver 的路径相同，因此它随应用一起签名和公证。
- 提供者在每个 Host 上运行一个 Syncthing 进程，其主目录位于 `$AVN_HOME/file-sync/syncthing/`；在第一个启用文件同步的账户就绪时启动它，崩溃后按退避策略重启，并随 Host 停止。文件夹标记其所属账户；文件夹只与该账户的对等设备共享。
- 桌面配置补丁挂载这些插件；基础和 Web bundle 以禁用状态挂载它们。浏览器无法运行 Syncthing，因此 Web 端对文件的访问经由用户的某台设备，与[托管 Web 界面 Agent Note](2026-09-30-hosted-web-surface-and-sync.zh.md) 一致。
- Syncthing 采用 MPL-2.0。发布未修改的二进制文件需要附带其许可声明和对应源代码的链接；本地补丁将会公开。

### 未决问题

1. **被忽略的机密。** 仓库的 `.env` 被忽略，因此新设备上的第一个回合可能因缺少它而失败。在工作状态检查点中携带一小份被忽略文件的允许列表（例如 64 KB 以下的 `.env*`）可以省去这一步，代价是在设备之间移动机密；在做出决定之前默认保持关闭。
2. **始终可用的文件。** Syncthing 的不受信任（加密）设备模式可以让 Aeven 服务器充当始终在线的对等设备，存储它无法读取的文件夹内容，使设备 A 休眠时设备 B 仍能获取文件。它会为每个账户消耗服务器存储，而且该模式比 Syncthing 其余部分更新；它是探索阶段测量之后的第 6 阶段候选。
3. **按流量计费的网络和电池。** Electron 并未在所有平台上提供按流量计费网络的信号；是否在电量低于阈值时暂停文件夹同步需要第 0 阶段的测量。
4. **Git LFS 和子模块。** 只有设备安装了 Git LFS 并能访问子模块远程时，克隆才会获取 LFS 对象和子模块；对等克隆的 bundle 两者都不包含。首个版本将缺失的 LFS 对象和子模块作为状态报告。
5. **对话工作区的文件。** 代理从虚拟的对话工作区写入的文件不属于任何文件夹工作区；它们是通过附件还是专用文件夹同步，尚未决定。

## 考虑过的替代方案

**对每个工作区都使用 Syncthing，包括 `.git`。** 单一传输更容易构建。被否决，因为两台设备对同一个被复制的 `.git` 运行 Git 和代理时会在锁文件、refs 和 pack 上竞争，而被复制的依赖和构建目录为每台机器都会重新生成的文件消耗带宽。Git 本身已经能正确复制仓库。

**只用 Git，要求有远程。** 对开发者最简单。被否决，因为许多工作区是没有仓库的文档文件夹，而要求用户创建远程正是本提案要消除的那类问题。

**让用户选择模式和位置。** 明确且容易实现。因用户体验目标而被否决：设备判断这两者的准确度高于普通用户，剩下的两个决定（大文件下载、两个版本）只在保护用户时才询问。

**通过 Syncthing 实时镜像仓库工作树并排除 `.git`。** 能让文件在设备间即时更新。首个版本中被否决，因为每台设备的索引和 `HEAD` 与被镜像的文件不一致，导致一台设备上的 `git status` 把另一台的编辑报告为自己的更改。工作状态检查点在回合边界传递同样的工作，没有这种歧义。检查点发布后，它可以作为可选项回归。

**登录时下载每个工作区。** 文件会在用户请求之前就绪。作为默认行为被否决，因为开发者账户可能有数十 GB 第二台设备从不使用的内容；设置开关提供了这一选项。

**在账户中继上构建文件传输。** 通过现有中继进行分块、加密、按内容寻址的传输可以复用保险库，并只有一个网络身份。被否决，因为它要重建 Syncthing 经过十年打磨的块哈希、重命名检测、部分传输、文件监视、NAT 穿透和局域网直连传输，并让每个字节都经过 Aeven 的存储。

**Mutagen。** 对代码很强且速度快，但它通过 SSH 或自己的 agent 同步成对的端点，而不是一组设备，也没有发现或中继。

**Unison 和 rclone bisync。** 成对的双向同步，按需或按计划运行而非持续运行；两者都不发现对等设备，也不穿透 NAT。

**Resilio Sync。** 点对点且功能完善，但是专有软件，因此无法打包和审计。

**iroh。** 一个现代的点对点库，具备按内容寻址的 blob 和 NAT 穿透，但它是 Rust 库，需要在每个平台上提供原生 Node 插件，而文件夹同步语义（监视、忽略、冲突、版本保留）仍需自行编写。

**iCloud Drive、OneDrive、Dropbox 或 Google Drive。** 用户可以把工作区放在消费级云文件夹中。被否决，因为服务提供方能读取文件，这些服务为仅在线保存的文件创建的占位文件会破坏工具和构建，而且这些服务与原始复制一样会损坏 `.git` 目录。

## 验收标准

- 用户在第二台电脑上登录，打开在第一台电脑上创建的文件夹工作区，在文件夹未超过大小限制时无需回答任何问题即可看到其文件。
- 在第二台电脑上打开仓库工作区时，如果发现根目录中存在同一远程的检出则绑定它，否则克隆；克隆失败且有持有设备在线时回退到对等克隆，全程不提问。
- 在另一台设备上继续对话时，在下一个回合执行操作之前，带来前一个运行者在仓库工作区中未提交和未推送的更改，以及它在文件夹工作区中写入的每个文件。
- 每当工作状态检查点被应用到认领设备的本地更改之上时，这些本地更改都保存在命名 stash 中。
- 冲突的编辑保留两个版本，来自另一台设备的删除在配置的保留期内可以恢复。
- 没有任何用户可见字符串出现 Syncthing、设备 id、文件夹 id、bundle、stash 或中继；`verify-client-ui-i18n` 通过。
- 从不打开某工作区的设备不为其文件消耗磁盘或 CPU，持有文件的设备只在另一台设备请求后才为其建立索引。
- 发现和中继流量只发往配置的服务器；Syncthing 的 GUI 只能在回环地址上用提供者的密钥访问。
- 模型可见的效果（检查点说明、仍在到达的文件、缺失的更改）以会话事件出现，因此会话日志能够重建它们。
- 录制会话快照，以及单元、e2e 和 SDK 期望输出覆盖文件取得、带检查点的交接和状态词汇。

## 风险

- **第二个网络身份。** Syncthing 设备 id 与账户同步的设备密钥并存。配对从 `devices` 文档派生它们，因此该文档写入者（中继持有密钥模式下的中继）的失陷会延伸到文件对等设备。这与每种密钥模式已声明的信任一致。
- **打包的原生可执行文件。** 签名、公证、Windows 上杀毒软件的误报，以及保持固定版本及时打补丁都是持续成本。Syncthing 的发布节奏规律，版本像 Cua Driver 一样固定。
- **资源使用。** 大文件夹的首次哈希消耗 CPU 和电量，Syncthing 的数据库随文件数增长。按需共享把它限制在有人请求的文件夹上；第 0 阶段设定预算。
- **在用户自己的编辑之上应用工作。** 应用检查点会改动用户可能正在编辑器中打开的文件。stash、通知以及从不 reset 使更改可撤销；用户仍会看到文件在编辑器下发生变化。
- **放置出乎意料。** 镜像路径可能落在第二台机器上用户未预期的位置。位置会在事后显示，**使用其他文件夹…** 可以移动绑定。
- **明知放弃的内容。** 仅使用 Web 和托管的用户得不到文件；不提供仓库工作树的逐键实时镜像；被忽略的文件（包括机密）不会传递；非常大的文件夹仍需一次确认。
