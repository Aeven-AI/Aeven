# Agent Note: 多参与者会话

Status: proposed

[English](2026-09-30-multi-participant-sessions.md) | 中文

## 问题

按账号隔离让「已登录账号」成为归属单位：会话 header 携带一个 `owner` 账号 id（`packages/core/session/src/types.ts:136`），它由创建该会话的调用方决定（`packages/api/session-controller/src/agent.ts:549-556`），而可达性是 `IdentityUsers.mayAccess(owner, caller)` 的严格相等（`packages/identity/user/src/index.ts:121-124`）。[按账号隔离](../../implemented/architecture/2026-09-30-per-account-isolation-on-a-shared-host.zh.md)是有意这样选的，包括它锋利的一面：不记录 owner 的状态对任何已登录调用方都不可达，而另一个账号的会话所给出的回答与「状态不存在」完全一致，因此调用方无法探测哪些身份存在。

该模型回答的是「这是谁的」，无法回答「还有谁可以加入」。`SessionHeader`（`types.ts:99-137`）和 `CreateSessionOptions.meta`（`types.ts:156-165`）上都没有成员、参与者、角色或共享字段，没有任何把某个调用方加入既有会话的操作，transcript 也无法说明哪句话是哪个人说的。因此，「一个助手能否与多个人进行一段对话」不是可以在客户端补上的功能缺口；这是当前的持久化模型没有容身之处的问题。托管部署是另一个问题，另有注记：[从远端提供 Web 表面](2026-09-30-hosted-web-surface-and-sync.zh.md)。

## 当前会话模型提供的部分

| 关注点 | 现状 | 位置 |
|---|---|---|
| 归属 | header 上一个账号 id，只写一次，由 fork 与 subagent 子会话继承 | `packages/core/session/src/types.ts:136`、`packages/core/session/src/index.ts:1189` |
| 可达性 | 一个二元谓词 `owner === caller.id`，约二十余处调用 | `packages/identity/user/src/index.ts:121`、`packages/api/session-controller/src/agent.ts:212-220` |
| 作者身份 | 不持久：用户消息的来源是 `{ kind: 'user' }`，外加 RPC 关联 id 与客户端时区 | `packages/llm/llm/src/message.ts:103`、`packages/api/session-controller/src/types.ts:444-449` |
| 轮次驱动 | 每个 `SessionId` 一个 Agent，经 Inbox 排队，而 `edit` 会取消活动轮次并为调用者回退 | `packages/core/agent/src/index.ts:252`、`packages/api/session-controller/src/commands.ts:427-455` |

## 共享会话所需的部分

- **作为持久化状态的成员关系**，并带角色而非一个布尔值：读取、提交、审批、管理。替换 `mayAccess` 的谓词必须保持 fail-closed，因此空或缺席的成员关系不加入任何人。
- **日志中的作者身份。** 某个人的消息必须可持久归属，这意味着一项新的或扩展的会话事件：凡模型可见者都必须能从日志重建，而模型可见的 `user/message` 目前不携带任何行为者。
- **轮次仲裁。** 两个人向同一个会话提问，需要顺序、需要打断活动轮次的规则，也需要决定谁可以通过 `edit` 改写历史。
- **审批策略。** 传输层已经把同一个请求送达多个客户端并让第一个回答胜出；缺的是谁有权回答、单个参与者的审批是否足够，以及谁批准过的持久记录。
- **按用户状态的规则。** 模型凭据由会话 owner 解析（`packages/llm/llm-aeven/src/index.ts:420-425`），记忆与学到的能力按账号键控，因此共享轮次必须说明它读取谁的记忆、向谁计费。
- **客户端工作。** 参与者名册、transcript 中的逐消息作者、邀请与移除、在线状态、审批的通知路由，以及上述一切由 locale 拥有的文案。

## 提案

**P0 —— 先决定产品问题。** 谁可以被邀请、谁可以审批、用谁的账号付费，以及参与者是否看得见在 owner 机器上产生的工具输出。共享 transcript 会暴露文件内容与命令输出，因此这个决定先于任何代码。

**P1 —— 成员关系与带范围的授权判断。** 为会话加入持久化的成员记录（owner 加带角色的参与者），并把二元谓词替换为带范围的谓词：改动集中在唯一咽喉点 `ApiSessionAgentController.resolve`（`agent.ts:212-220`），加上那些直接读取归属的位置。对不记录 owner 的状态保持现有的 fail-closed 规则。

**P2 —— 持久的作者身份。** 扩展会话词汇，使用户消息能指明作者：既要改提交路径（`packages/api/session-controller/src/commands.ts:67-78`），也要改 agent loop 对 `user/message` 的追加（`packages/core/agent-loop/src/agent.ts:292`），并决定模型是否把作者身份作为提示词输入看到。

**P3 —— 仲裁与审批。** 定义参与者之间的排队顺序、谁可以打断，以及 `edit` 是否仅限 owner；然后在现有的「第一个回答即结算」投递之上实现审批策略，并追加一条写明应答账号的审计记录。

**P4 —— 客户端。** 参与者名册、逐消息归属、邀请与移除、在线状态，以及审批通知路由，全部文案走 locale 字典。

**P5 —— 重新审视隔离注记中保持共享的部分。** 明确共享会话是否改变按账号的计费与记忆键，或者共享会话中的每个轮次是否仍由 owner 的账号付费并提供记忆。

## 验收标准

- 两个已登录账号可以抵达同一个会话，而第三个非成员账号所得到的回答与「会话不存在」完全一致。
- 持久化日志能回答每条人类消息的作者，且重放或导出的会话保留该归属信息。
- 轮次进行中到达的第二条提示遵循既定顺序而不是相互竞争；不被允许的 `edit` 由执行侧拒绝，而不是由 UI 拒绝。
- 审批送达策略指定的参与者，且审计记录写明是哪个账号应答的。
- 移除某个参与者对读取、提交与审批即时生效，无需重启 Host。
- 针对双账号 transcript 存在快照与端到端覆盖，包括隔离场景。

## 风险

- **共享 transcript 是数据外泄面。** 工具结果携带 owner 机器上的文件内容、命令输出与路径，因此只加成员关系而不决定可见性，会把宿主状态泄露给每个参与者。
- **作者身份是一次格式变更。** 日志成员默认按「读到即必需」处理，因此新增事件类型或新增必需字段是一个持久化格式决策，旧版本必须拒绝该日志，而不是误读它。
- **仲裁很容易在细节上出错。** 现有的单写入者规则没有跨进程强制手段，因此两个客户端本来就会经由同一个 Inbox 竞争；再加入第二个账号只会增加场景，而不会增加机制。
- **计费与记忆变得含糊。** 今天由拥有会话的人提供模型凭据与记忆键；在共享会话中这是令人意外、而非错误的安排，必须在创建会话处写明。
- **客户端不是边界。** 上述每条规则都必须在 Host 的执行侧强制执行，因为浏览器可以被任何参与者修改。
- **本次改动放弃了什么：** 单 owner 规则是一行毫无歧义的代码，而每一个替代谓词都是一处可达性可能倒退的地方。隔离工作那个干净的性质——另一个账号的状态回答与不存在一致——只有在成员关系显式且非空时才能保留。

## 曾考虑的替代方案

**多人共用一个账号。** 让每个参与者使用同一份 Aeven 凭据，这样完全不需要代码。否决，因为模型给出的回答本身就在描述这种安排：transcript 中没有归属、一个钱包为所有人付费，而撤销会让所有参与者一起失效。它还会让「谁批准了某次破坏性工具调用」无法审计。

**共享工作区、每人各自一个会话。** 让每个人保留自己的会话，并加一个能看到其他人的共享位置。作为默认方案否决，因为所要求的结果是「与同一个助手的一段对话」，而助手的上下文就是会话：分开的会话会让每个参与者拿到不同的对话并重复工作。如果仲裁与审批策略的代价超出预期，它值得作为更便宜的第一步保留。

**把成员关系放在会话 header 上。** 把参与者列表放在 `SessionHeader` 上紧邻 `owner`，而不放在单独记录里。就持久化格式而言否决：header 是每个日志带版本号的物理首记录（`packages/session/session-persistence-jsonl/src/format.ts:52-105`），而成员关系在运行时变化并有自己的生命周期。把成员关系移出该记录，使格式决策与共享决策彼此独立。

**让助手来仲裁。** 接受所有人的提示，让模型决定轮到谁。否决，因为它把安全与顺序决策交到模型手中，既不可审计也不可强制，而且 agent loop 的单写入者队列在调用模型之前就已经需要一个由 Host 给出的答案。
