# Agent Note: 桌面发布重试自己的运行时下载

Status: implemented

[English](2026-10-25-desktop-release-retries-runtime-downloads.md) | 中文

## 问题

`v0.3.14-alpha` 的 `Release desktop` 运行在 `Build mac-x64` 的 `prepare:runtime` 处失败，报 `[TypeError: fetch failed]`，其中包裹着 `getaddrinfo ENOTFOUND nodejs.org`。该作业此前已完成依赖安装并打包好原生包；是运行器的域名解析短暂停止应答，构建本身无可指责。`prepare-runtime.ts` 对每个归档只抓取一次，于是这一次打嗝就丢弃了一个已完成的 macOS 目标，并且因为 release 作业需要每个目标都成功，整个发布也随之作废。下载还是直接写入缓存读取的那个路径，因此一次中途中断的传输会留下一个文件，后续运行把它当作完整的缓存归档，随即在校验和处拒绝，让此后的每次构建都失败。

## 决定

- **`downloadFile` 只重试下一次尝试能清除的失败。** 一个上游文件获得四次尝试，第二次之前等待 2 秒，之后逐次翻倍，上限 30 秒。每次尝试都带有 5 分钟的 `AbortSignal.timeout`，因为停止应答的套接字永远不会 reject，否则它会在根本不进入重试的情况下一直占住发布作业。除限流之外的客户端应答会抛出 `MissingUpstreamFileError` 并立刻失败：上游说该文件不在那个地址发布，这件事不会改变。
- **下载原子落盘。** 字节先写入同级的 `.part` 文件再改名到位，尝试失败时删除该 `.part` 文件，因此缓存路径上只可能出现完整的传输结果。
- **`verifiedArchive` 重新抓取，而不是相信缓存。** 缓存归档的 SHA-256 与校验和文件中的那一行不符时，先删除再重新抓取，然后才判定构建失败；校验和文件没有列出该归档时，也会重新抓取一次，因为中断的下载会留下被截断的校验和文件。
- **工作流按目标缓存这些固定版本的归档。** `Release desktop` 以 `desktop-runtime-<target>-<prepare-runtime.ts 的哈希>` 为键缓存 `apps/desktop/.desktop-build/downloads`，正如该工作流已经缓存固定版本的 ffmpeg 源码。同一 macOS 架构的签名与未签名两个变体共用该键，因此签名构建会复用旁边未签名构建已抓取的内容，而每个缓存归档在使用前仍要对照它的校验和文件验证。

## 考虑过的替代方案

**重跑失败的作业，不改脚本。** 重跑会重放同一次单发抓取，所以下一次 DNS 打嗝又要付出一个 40 分钟的 macOS 目标以及其后的整个发布；单个作业里这种失败很罕见，但每个标签要构建八个目标。

**重试整个 `Package` 步骤。** 到抓取的时候，它之前的每个步骤都已成功，重复该步骤意味着为了恢复一次 50 MB 的下载而重装依赖、重建原生包。

**把所有非 2xx 应答、或所有失败都视为值得重试。** 上游不再发布的归档在四次尝试里会以同样方式答复；立刻失败可以避免一次错误的版本固定耗尽重试预算，并留下读起来像网络故障的日志。

**把 Node.js 与 Cua Driver 的归档纳入仓库。** 六个目标合计约 200 MB 的第三方二进制，而用于验证它们的校验和文件本身也是上游产物，必须一并纳入。

## 后果

- 一次 DNS 打嗝、一次连接重置或一次停滞的套接字，代价是几秒到几分钟的重试，而不是重建一个目标；日志会指出第几次尝试以及它包裹的网络故障。
- 上游停止发布的固定归档、以及字节与校验和不符的归档，仍然会让构建失败；后者给出归档名，并且不会重试一次重试也修不好的不匹配。
- 校验和的重新抓取意味着损坏的下载缓存会自行修复，因此任何发布运行都不需要先手工清空缓存才能开始。
- 工作流缓存能在一次运行内、以及同一标签的重跑之间省下某个目标的归档；它不会从一个标签延续到下一个标签，因为 GitHub 把在 tag ref 上保存的缓存限定在该 ref。
