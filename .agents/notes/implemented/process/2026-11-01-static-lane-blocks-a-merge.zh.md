# Agent Note: 静态通道阻断合并

Status: implemented

[English](2026-11-01-static-lane-blocks-a-merge.md) | 中文

## 问题

`static` 运行四十四个仓库卫生检查，却带着 `continue-on-error: true`，因此无论发现什么，作业都报告成功。有一个发布周期里，`main` 仍然需要这个作业名，这让必需的检查形同虚设：过期的 `docs/config-catalog.md` 报告为绿色，一次运行可以在其内部通道失败的情况下通过。

这条通道曾被降级，起因是一个单元测试、类型检查与构建全部通过的拉取请求被它挡住：它声称 `docs/config-catalog.md` 在运行器上已过期，而同一个提交在开发机上重新生成没有任何改动，并以零退出。那处漂移来自生成链接里的行号锚点，现已在生成器处修好——目录的标签只写文件，声明上方的无关改动不再改变生成内容。

## 决策

静态通道阻断。它的步骤不再带 `continue-on-error`，`main` 要求 `test`、`static`、`types-lint`、`build-verify` 以及 `owner-only`。任何一项处于等待或红色时，合并被拒绝；管理员仍可刻意绕过，这是针对被宿主环境而非改动本身弄坏的通道的逃生口。

一个无法失败的必需检查比没有更糟：它花掉这次运行的时间，却产出读起来像「通过」的证据。

## 考虑过的替代方案

**让通道保持只报告。** 被否决：`main` 本来就需要该作业名，只报告等于这项要求什么都没度量。要么通道阻断，要么去掉要求。

**去掉通道，把它的检查放进单独的只报告工作流。** 暂时否决：这些检查能拦住真正的破坏——过期的生成文件、许可证漂移、清单错误——而让它们显得不稳定的那处漂移已在源头修好。

## 后果

生成文件或清单的错误现在会拦住引入它的那个拉取请求。当失败来自宿主而非改动时，它会被明确修复或明确绕过，而不是被悄悄吸收。
