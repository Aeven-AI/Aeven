# Agent Note：生成器拥有目录的双语两侧，检查按改动包限定范围

Status: implemented

[English](2026-10-26-generated-catalog-locales.md) | 中文

## 问题

有两项开销主导了文档工作，而它们都没有产出一份文档。

第一项是生成目录的双语配对。`gen-config-catalog` 与 `gen-persistence-catalog` 写出英文文件；中文文件是手工维护的对侧，逐节翻译，再用 `verify-translation-pairing --write` 重新记录。每次重新生成都会重新打开同一份工作：`来源：` 行、`需要：` 行、`Source:` 链接里的一处行号偏移。这些文件里的散文是一套固定词汇——一个标题、三段引言、五个标签、两个标题层级——其余全是标识符、路径或原样粘贴的声明文本。为一套固定词汇在每次重新生成时手工翻译一遍，再为一段过期章节付出失败重试的循环，就是一个只改动一个插件的变更里绝大部分文档时间的来源。

第二项是检查循环。`tsc -b` 覆盖整个解决方案，只要增量状态不在了就重建每个项目，而一次用于链接新工作区包的 `pnpm install` 正会丢弃它；于是改一行代码要付出一次冷启动的多分钟重建。门禁与测试套件覆盖整个语料库有其正当理由，但内层循环并不需要整个语料库。

## 决策

### 渲染器接收一个 locale，并自行产出两侧

`gen-config-catalog` 与 `gen-persistence-catalog` 现在通过一次 `render(entries, locale)` 调用渲染每一侧。`Locale` 恰好命名一侧所贡献的散文：生成横幅、语言切换器、标题、引言段落、标签前缀、章节标题，以及译文页面需要的两处路径投影——`.md` 页面链接与外部类型引用形式。`LOCALES` 是 `[EN, ZH]`，两侧在同一次运行中写出，`--check` 失败时会指出过期的那一侧。

这遵循 Cordis 子系统区域生成器已有的契约：同时拥有两侧的生成器把成对的文档路径投影到每个输出 locale，同时保持其余每个生成字节相等。配对契约没有任何削弱——两个文件仍然由 `verify-translation-pairing` 记录，结构签名仍然能抓住漂移的一侧。改变的是散文由谁书写：生成器把它持有一份，评审者读到的是固定词汇的 diff，而不是再翻译一次。

生成横幅在两侧都说明了这一点：本文件由生成器产出，请勿手动编辑，重新运行生成器即可。

### 内层循环把改动文件映射到所属包

`scripts/check-changed.ts`（`pnpm run check:changed`，或 `typecheck:changed` / `test:changed` / `docs:changed`）读取工作区——已暂存、未暂存与未跟踪——把每个路径映射到最近的 `package.json`，然后把各包的工程文件交给 `tsc -b`、把各包的 `tests/` 目录交给 vitest、把触及的文档配对交给 `verify-translation-pairing`。落在包之外（`scripts/`、根配置、`docs/`）的改动，会在那一步回退到覆盖语料库的命令，因为那正是该改动实际的影响半径。

它是一个驱动器，不是门禁。`typecheck`、`test` 与 `doc-sync` 保留覆盖语料库的含义，CI 仍然运行它们。

### 文档聚合先询问 Git，再遍历语料库

当门禁本身成为仅剩的成本，聚合就需要停止重复工作。`doc-sync` 与 `doc-quick` 仍运行它们的十七个门禁，只要有文档输入变脏就全部运行。它们不再做的，是重读一份没有任何脏路径能改变的语料库：只改动了应用源码的工作区会让每个门禁输入保持逐字节相同，于是聚合读取 `git status --porcelain`，发现没有 Markdown、配对记录、生成器或包清单，就报告跳过，而不是花半分钟去确认上一次绿色运行已经确立的事实。`AVN_GATE_CACHE=0` 关闭该跳过，而 CI 会设置它，因此已推送的 diff 始终被完整检查。

`verify-md-links` 在门禁层面承载同一思路：它对读取的每个文件内容做哈希，当重复运行看到相同字节时跳过——也就是一份文档改动、其余 2 982 份没有改动的情形。

## 考虑过的替代方案

**继续手工翻译并接受开销。** 否决：反复出现的工作对象是一套固定词汇，因此它什么也换不来，而失败模式比开销更糟——一段过期的中文章节（英文侧已删掉的一个服务键、它新增的 `systemPrompt`）会一直留在文件里，因为除结构之外没有任何东西在比较两侧。

**在构建时用机器翻译生成中文侧。** 否决：`docs/i18n/README.md` 赋予两种语言同等的权威，而把翻译模型放进构建路径，会把未经评审的散文写进读者有权信任的文档里。把散文持有在生成器中是一套固定、可评审的词汇；一次模型调用不是。

**只保留一种语言，为生成目录放弃配对。** 否决：生成目录恰恰是最需要照顾读不懂引言段落的读者的地方，而一旦渲染器接收 locale，成对路径投影的代价很低。

**让 `typecheck` 自身按范围执行。** 否决：它会悄悄削弱 CI 与每位读者都视为完备的那条命令。独立的 `check:changed` 会说明自己做了什么。

**为每个门禁加路径过滤。** 目前否决：只有配对检查接受具名配对，其余门禁回答的是语料级问题（每个包 README 是否满足骨架；模块图是否最新），过滤只能回答其中一部分。把 typecheck、测试与配对限定到改动范围，覆盖了时间实际流失的地方。

## 影响

- 目录重新生成现在是一条命令、一份 diff 的操作，不再有翻译步骤。剩下的成本是阅读生成器已经持有的中文散文 diff。
- 中文目录现在包含手工翻译曾经漂移掉的内容；与本笔记同批落地的 diff 修正了一个被丢掉的服务键、一条过期的 `subprocess` 条目，以及多个偏移的源码链接。
- 同时拥有两个 locale 的生成器必须把语言切换器放在 H1 标题之后，因为配对检查在该处读取切换器。两个生成器都这样做了，而一个 locale 数组使下一个生成器在构造上就如此。
- `check:changed` 是没有 spec 也没有 CI 角色的便利工具；映射中的缺陷会表现为回退到覆盖语料库的命令，而不是一次错误的通过。
- `check:changed` 只读取工作区。已在其他分支上提交的内容不是它的输入；对已推送的 diff，`check:all` 与 CI 仍然是权威。
- 聚合跳过信任 HEAD 是绿色的——合并规则与 CI 为 `main` 确立了这一点，主题分支从其基线继承。基线从未通过门禁的分支，可以改动任意文档输入或设置 `AVN_GATE_CACHE=0` 来重新运行它们。
- 文档改动仍然要付出一次完整聚合——十七个门禁共 32 秒。跳过消除的是不可能影响文档的改动所带来的成本，而不是真正文档改动的成本。
