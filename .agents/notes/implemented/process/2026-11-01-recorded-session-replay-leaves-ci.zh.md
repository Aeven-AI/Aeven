# 录制会话回放退出 CI

## 问题

`build-verify` 把录制会话回放当作 `{ ...snapshotGate(['build']), allowFailure: true }` 来运行。带 `allowFailure` 的门禁会打印 `NON-BLOCKING FAILED`，而作业仍然判定成功，因此 41340242556 号运行在内部九个场景失败的情况下报告为绿色。那一行上方的注释写明了原因：若干 fixture 早于工作目录提示段落，需要一次带密钥的 `test:snapshot:record`，而没有人跑过。

结果是一个永远无法说「不」的门禁。它对坏掉的回放和正常的回放给出同一个结论，于是它检测到的漂移——同一周里一次复核提示改动破坏了十一个场景——就这样悄无声息地进了 `main`。

## 决定

回放不再是 CI 门禁。`ciBuildVerifyGates()` 只返回构建与产物门禁，模式列表里不再有 `ci-snapshot`，`package.json` 里不再有 `check:ci:snapshot`，`webSnapshotGate` 的排序也不再等待它。`pnpm run test:snapshot` 仍可在工作树中运行该套件，供想把自己改动的提示与录制语料做比对的人使用。

门禁的价值在于它检查的东西坏掉时会失败。一个打印 `NON-BLOCKING FAILED` 却以零退出的门禁比没有更糟：它花掉这次运行的时间，却产出读起来像「通过」的证据。

## 备选方案

**把它改成阻塞门禁并重新录制 fixture。** 这是这项检查诚实的形态，暂时被否决，因为语料需要 DeepSeek 密钥，并且需要为录制模式会跳过的场景手工编写替代。等有人愿意接手这次重新录制时，它可以以那种形态回归。

**只修那十一个过期 fixture，不动门禁。** 这修好了今天的漂移，却留下了掩盖下一次漂移的机制。

## 后果

回放回归不再悄无声息地进入 `main`——因为回放根本不再在那里运行。拉取请求通道中其他一切未变：单元测试、类型检查、构建与产物门禁仍然决定一次改动能否落地。

`ciWindowsCompleteGates()` 保留它的 `allowFailure` 映射。那些是明确命名的观察性 Windows 门禁，保持可见而不阻塞；本决定针对的是一条声称在检查什么、却无法失败的门禁。
