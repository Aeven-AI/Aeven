# Agent Note：工具调用占住循环期间为提示缓存保温

状态：已实现

[English](2026-10-26-prompt-cache-warming.md) | 中文

## 问题

提供方只在缓存条目存活期间对缓存前缀计费。一次长时间的工具调用——构建、测试套件、浏览器会话、子代理——让循环在对话毫无变化的情况下等待数分钟；若缓存条目在此期间过期，紧随其后的请求就要按全价读取前缀。DeepSeek 未公布缓存存活时长（"数小时到数天内清除"），而 `@earendil-works/pi-ai` 0.84.2 根本不携带提示缓存元数据，因此本仓库中没有任何适配器能判断一次保温是否值得发送。

支持该功能的度量来自本仓库之外：`dsh-warm` 0.2.0——一个正为此问题发布的 DeepSeek harness 宿主插件——报告在"工具结果阻塞保温"的配置下，50 天内空闲保温节省 $6.91，而该配置下多花 $7.15。本插件沿用这一试点，并按 Aeven 的接缝重新塑形。

## 决定

### 只在工具阻塞点内保温，绝不在会话等待人类时保温

`llm/stream` 记录保温将要重放的请求。`tools/execute` 在一次工具调用期间打开保温窗口，并在该调用落定时关闭；嵌套子调用递增深度计数，因此一段 `run_code` 程序只维护一个窗口，而不是按每个绑定调用重启；`ask_user_question` 默认排除，因为它的阻塞点是人类在做决定，而不是工作在进行中。

插件不为空闲会话保温，即使空闲往往是最长的等待。dsh-warm 自己的数据表明，在后续没有请求时，空闲保温可能得不偿失，因此这里先交付试点证明有利的一半，另一半留给愿意自行度量的部署。

### 重放的请求就是捕获到的请求，仅去掉输出上限

保温发送捕获的 `GenerateOptions`，除 `maxTokens: 1` 与自身取消信号外原样不变，因此提供方看到的前缀逐字节一致——这正是整件事的意义。有两个字段被刻意丢弃：`sessionId`，因为手工构造的调用一旦带上会话名就会触发一次持久化 flush，而保温没有任何理由造成它；以及任何附件永不被重放，因为带 `file` 或 `image` 区块的捕获请求可能在每次 ping 时重新上传文件。

`purpose` 保持未设置。新增 purpose 值要求每个适配器与扩展要么支持、要么忽略它，而任何把 purpose 变成 wire 字段的扩展都会改变保温本要保住的前缀。

### 支出被记录，也被计量

每次保温在分发前追加 `cache-warm/start`，之后追加 `cache-warm/result`，携带提供方上报的用量或使其终止的失败。`@aeven/token-meter` 把 `cache-warm/result` 的用量折叠进会话的 `tokenUsage` 总计，于是保温支出与回合支出并列可见，而不是与"什么都没有"并列；这正是辅助调用今日的缺口——一次 review 或标题调用会计费却不被计数。

三个上限让支出事先可界：每次工具阻塞点的 `maxPings`、跨会话的 `maxConcurrentPings`、每个 UTC 日的 `dailyPingBudget`。`dryRun` 只记录 start 事件而不分发任何请求，部署因此可以先在自己的流量上给该功能定价。

### 缓存存活时长属于配置

DeepSeek 未公布 TTL，pi-ai 也不暴露，因此 `providers` 逐项列出要保温的提供方及其 `intervalMs` 与可选 `maxPings`。不在表中的提供方永不被保温。插件在 `aeven` preset 中以 `disabled: true` 发布，附一条 240000 ms 的 DeepSeek 行作为示例而非推荐：部署应根据提供方文档中的存活时长设定，并留出一次请求的往返余量。

### 不会干扰通用助手的行为

保温经同一条 `llm/stream` waterfall 分发，因此路由、重试与提供方鉴权原样生效；但它的响应在插件内部被耗尽：没有助手消息、没有工具调用、没有提示文本、没有引导。没有任何模型可见的变化，因此对话、压缩路径与 turn review 看到的与从前完全相同。工具自身的 signal 会取消进行中的保温，提前结束的阻塞点立刻停止付费。

## 考虑过的替代方案

**等待提供方自行刷新条目。** DeepSeek 只在条目存活期间按命中计费，也不提供 keep-alive，因此一次长时间工具调用造成的中断会按全价读取前缀，除非有东西自行重放前缀。

**除工具区块之外，再用空闲计时器保温。** 最长的等待通常是人类在读回复，而这恰恰是没有测量支撑的情形：`dsh-warm` 的空闲模式依据的是一次本仓库并未记录的流式运行。在部署报告该时间窗口之前，插件只在工具区块内部工作。

**在工具返回之前同步保温。** 前缀在区块开始时已知，但那时发送会把一次提供方往返放在工具与其结果之间，并让并行调用排队等同一个 ping。把保温追加在工具结果之后，会话顺序不变。

**从提供方元数据读取缓存 TTL。** 此处没有适配器暴露该值，而新增按适配器的字段会把部署判断塞进一个无法观察它的客户端。改为用 `intervalMs` 配置。

**只在插件自己的日志里记录花费。** 保温花费就会孤零零地存在：审查或标题调用今天计费却不进入 `tokenUsage`，把这一缺口复制到频率更高的调用上，会掩盖那些上限本要控制的成本。

## 影响

- 两个只进日志的事件，以及用量投影的 `stateVersion: 3` 提升；没有任何模型可见的变化，因此没有快照场景记录该功能。
- 插件以 `disabled: true` 交付。部署通过为提供方指定 `intervalMs` 来启用，示例行不是推荐值。
- 前缀只要逐字节不同，保温就会被抑制，而不是去支付第二个缓存条目；因此在会话中途改变系统提示或工具 schema 的部署，只会在前缀稳定后才保温。
- 花费在单个工具区块、每日以及跨会话三个层面都有上限，`dryRun` 让部署在真正派发之前用真实流量为该功能定价。

## 验证

`packages/llm/llm-cache-warm/tests/warmer.spec.ts` 双向覆盖该窗口：在未配置提供方、辅助 purpose、带附件、前缀过小或不在工具阻塞点内时不保温；在窗口内每个间隔一次保温并被记录；ping、每日预算、dry-run 与并发上限；以及失败路径。`packages/llm/token-meter` 在把该事件折叠进用量投影后通过类型检查，`stateVersion: 3`。

未覆盖：录制快照场景。插件以停用状态发布，因此没有任何随附 profile 会产生 `cache-warm/start` 事件，而按设计保温在模型可见表面上本就不可见。
