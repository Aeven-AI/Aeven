# Agent Note: 已学流程的合并与在 Settings 中显示

Status: implemented

[English](2026-10-19-learned-procedures-merge-and-settings.md) | 中文

## 问题

使用 `store: memory` 时，学习器通过对该轮次请求的一次记忆召回来寻找可以合并进去的流程。MemOS 默认返回五条轨迹，而刚被捕获的那个轮次与该会话更早的轮次与这个请求最接近，因此提炼通常看不到任何既有流程，于是创建一个新名称。一个账户在 692 个名称下存有 706 套流程，其中许多只是同一类任务的单个实例。替换一套流程时只遗忘召回恰好返回的副本，因此同一名称会被存两次。Settings → Memory → Capabilities 读取的是能力注册表，而 memory 存储从不写入它，因此它一直为空。MemOS 的轨迹仓库还把单次 `list` 调用限制在 500 行，因此按文本或领域过滤的记忆列表只能看到最新的 500 条轨迹。

## 决定

`ctx.memory.procedures({ owner, cwd? })` 从记忆文本形式 `Learned procedure <name>: <description>` 加 Markdown 流程中列出所有者的每套已学流程，这种形式现在由 `@aeven/memory` 通过 `LEARNED_PROCEDURE_PREFIX` 与 `learnedProcedureOf` 拥有。`list` 接受 `cwd`，它像召回一样略去其他工作区的项目记忆，因此学习器只看到它的会话能召回的流程。

每次提炼之前，学习器列出该会话的流程，按一次请求 30 条轨迹的召回与共有词为它们排序，并发送最多 120 个名称及描述，以及其中三套的全文。回复可以在 `replaces` 中点名它现在涵盖的其他流程；存储的流程会替换其名称下的每条记忆以及每套被涵盖的流程。当被学习轮次的会话看到的不同流程超过 `consolidateAbove`（40）时，无论该轮次教出什么，学习器都会遗忘每个名称的较早副本，以每批最多 150 个名称把同一类任务的流程分组，并以一次模型调用合并每一组，每个进程中每个所有者与工作区只做一次。合并在它们自己的队列中运行，因此会话的学习与它的 `session/settle` 都不会等待它们。

`memoryManager` 去掉了能力注册表的各个端点，改为提供 `procedures()`、`procedure(id)` 与 `editProcedure(id, summary)`；遗忘使用 `forgetMemory`。Capabilities 标签页带搜索框列出这些流程，并位于 Standing facts 之前。收录的 MemOS `listTraces` 与 `countTraces` 按页遍历仓库（vendor 修改 26）。

## 考虑过的替代方案

**只提高召回上限。** 被拒绝，因为召回会为所有者的每条记忆排序，同一工作的对话轨迹仍会挤掉流程；完整清单让既有流程无论排名如何都可见。

**每次提炼都发送全部流程。** 被拒绝，因为数百条描述会在每个被学习的轮次中占去大部分输入预算；排序后的清单有上限，而后台合并让数量保持较小。

**在流程面板旁保留能力注册表面板。** 被拒绝，因为随附的预设只学习进记忆，注册表面板会一直为空。

## 后果

- 重启后第一个其会话看到超过 40 套流程的合格轮次会启动后台合并，它在该会话的路由上消耗模型调用：几次分组调用，以及每组一次调用。
- 落在不同分组批次中的同类流程会保持分开，直到之后的一次合并或某个被学习的轮次在 `replaces` 中点名它们。
- Memory 各标签页与文本搜索可以看到比最新 500 条轨迹更早的记忆。
