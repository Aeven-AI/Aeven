# Agent Note：会话搜索匹配任意顺序的全部词，并把最后一个词作为前缀

Status: implemented

[English](2026-11-10-session-search-all-words-and-prefix.md) | 中文

## 问题

`avn-session-query-sqlite` 把查询当作一个字面短语来匹配：`memory sync bug` 只能找到这三个词相邻且按此顺序出现的文本。2026-11-10 在托管索引的副本（42.6 万个文档）上，尽管分别有 836 和 308 个文档包含全部词语，`memory sync bug` 和 `session search warning` 却没有任何结果；`install pnpm` 找到 733 个文档，而同时包含这两个词的文档有 3,379 个。正在输入的词在输入完整之前匹配不到任何内容。

## 决策

查询匹配包含其全部 token 的每个文档，顺序不限。最后一个 token 达到 `prefixMinChars` 个字符（默认 3，`0` 关闭）后，也匹配以它开头的更长 token，因此 `rele` 能找到 `release`。每个 token 都被单独加引号，查询语法保持为惰性数据。

FTS5 通过求 token 文档列表的交集来找出候选文档（`MATCH "a" "b" "c"*`），再由实例词表统计每个候选文档的 token 命中数及其合并后的完全短语 span，两者都把最后一个 token 当作前缀。排序依次为短语 span、token 命中数、更短的文档，然后是时间、会话 id 和 seq；高亮会标出每个匹配到的 token。`packages/client/connection/src/client/fixture.ts` 中的浏览器 fixture 镜像了这套匹配方式和排序键。

在把会话限定给其所属账户的 Host 上，会话控制器把调用者作为新的 `owner` 会话过滤器传入，引擎在统计命中之前丢弃其他账户的候选文档。此前，控制器搜索所有账户的会话，事后才丢弃别人的命中，并反复调用提供方直到凑满一页，因此其他账户的匹配结果可能把调用者的结果挤出页面，并耗尽控制器 100 次调用的工作预算。

改动只涉及 TEMP 查询表和查询路径：持久化索引、其结构版本以及搜索请求和响应的字段都没有变化，因此每个客户端无需重建索引就能得到新的匹配方式。

## 考虑过的替代方案

FTS5 `bm25()` 按词的稀有程度和文档长度排序，但它的统计是按表计算的，因此实时会话的分数与持久化会话的分数无法比较；引擎的排序约定要求两者处于同一可比尺度。

在求交集之前为包含任一 token 的每个文档统计命中数，需要读取每个 token 的完整实例列表：在托管副本上每个多词查询需 70–215 毫秒，而先由 FTS5 缩小候选范围时只需 49–93 毫秒。

trigram 分词器可以增加子串和中日韩文字的匹配，但会让索引大小翻倍并需要提升结构版本；这是另一个决定。

## 影响

自然的多词查询能找到结果，并且在输入最后一个词时结果就会更新。搜索比原来的短语查找更耗时：在托管副本上，单个词需 10–50 毫秒，多词查询需 50–90 毫秒，前缀 `rel` 约 130 毫秒，像 `the` 这样的停用词超过一秒，而之前为 446 毫秒。FTS5 的候选步骤仍会读取整个索引；一旦应用 `owner` 过滤器，命中统计只读取调用者的候选文档。最后一个 token 短于 `prefixMinChars` 的查询仍只匹配完整 token，因此 `AI` 找不到 `AIM`。

## 验证

`packages/session-query/session-query-sqlite/tests/sqlite.spec.ts` 固定了：`alpha beta` 把完全短语排在 `alpha middle beta` 之前，`beta alpha` 能找到全部四个，`alpha bet` 的排序与完整短语相同，`alpha be` 什么也找不到；`tests/query.spec.ts` 固定了每个 token 的加引号方式和前缀标记。会话查询测试通过（262 个），使用新匹配方式的 fixture 让连接测试通过（148 个）。上述托管环境耗时是在 pink 搜索索引的副本上测得的。
