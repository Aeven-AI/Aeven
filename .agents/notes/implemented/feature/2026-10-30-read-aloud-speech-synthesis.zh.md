# Agent Note: 朗读作为语音合成 seam

Status: implemented

[English](2026-10-30-read-aloud-speech-synthesis.md) | 中文

## 问题

Aeven 不会朗读任何回复，也不存在可添加该能力的 seam：模型没有办法请求朗读，Host 没有合成提供方，Web 客户端没有地方存放读者对语音的选择。语音识别已经拥有 definition/provider/Remote/tool 一整套栈，因此语音合成需要同样的形状，而不是一条定制的路径。构建它暴露了三个朴素实现会直接带上线的产品问题：一个没有配置语音的语言会落到提供方列出的第一个语音上，对日语而言那是一个男声；开关在读者打开另一个会话的瞬间就忘了自己；留在朗读文本里的 Markdown 让读者在词与词之间念出「asterisk」。

## 决策

**合成是一个三项角色全部交付的能力 seam。** `@aeven/text-to-speech` 拥有定义：具名提供方注册并附带可释放的接纳、一个保留的 voice id 空间使同一个 id 在各提供方之间只命名一个语音，以及一个显式的 `resolve(request): TtsSpec` 步骤，把一种语言或一个精确的 voice id 变成实际使用的语音。`@aeven/text-to-speech-edge` 通过 Aeven 自己的 Edge 客户端 `src/edge-tts.ts` 提供它：它对 `api.msedgeservices.com` 讲朗读 WebSocket 协议，在仍会应答的旧主机上列出名册，并回退到已配置的语音。`@aeven/api-text-to-speech` 是客户端消费方：`tts` 命名空间下的一个 Remote 控制器，带字符上限、通过请求信号取消，并且不产生会话事件，因为音频属于展示，而不是模型可见的上下文。`@aeven/tool-read-aloud` 是模型消费方，一个 agent 在语言练习期间调用的 `enabled` 开关。

**一种语言的默认语音是女声，在回退原本就已到达的那一档上决定。** 提供方列表携带每个语音自报的音色，目录保留它，而 `resolve` 在每一档都优先女声：先是该语言的主导 locale（`zh-CN` 优先于 `zh-HK`，`ja-JP` 优先于各 `ja-JP` 变体），然后是精确语言的任一语音，再是语言族，最后是多语言语音。已配置的 `voiceByLanguage` 条目仍然直接胜出，而已配置的行在该行省略音色时保留提供方报告的音色，因此为语言做映射永远不会重新引入男性默认值。选择器读取同一规则来命名一种语言回退到的语音。

**读者是一个流式引擎，而不是每条回复一次请求。** `@aeven/client-ui-tts` 在增长的回复文本到达时从中切出可朗读的分句，预取四个片段，保持提前排定十二秒的音频，并把解码后的缓冲区背靠背播放，使拼接的片段之间不出现间隙。之后到达的文本继续队列，而不是切断已经在朗读的句子，而一次档位变化只冲刷未终止的尾部。Markdown 在合成之前被压平：围栏代码、表格、链接目标，以及每一个残留的 `*`、`_`、`~`、反引号或竖线都被移除，因此没有读者会念出标记的名称。

**朗读是一项常驻偏好，而且单条消息可以单独朗读。** 打开开关会把选择存进浏览器，之后打开的会话会恢复它一次，但不会重新打开读者已经关掉的那个；agent 的 `read_aloud` 调用持久化同一个标志，因为它移动的是同一个开关。`Branch into a new session` 旁边的逐消息操作在它自己的通道上朗读一条已定稿的助手消息，因此它既不打扰也不依赖会话通道：它显示 spinner 直到第一个片段可听，播放时显示停止字形，第二次请求时从头重新开始。被停止打断的排空会把任何仍在排队的工作交给一次新的排空，这正是让那次第二次请求得以发声的原因。

## 验证

服务、Edge 提供方和 Remote 控制器各自通过自己的套件接受检验，客户端引擎、句子切分器和选择器则通过 GUI 层。语音规则对着线上 Edge 名册测量过：全部 75 种语言都解析到女声，`ja` 解析到 `ja-JP-NanamiNeural`（早先的回退产生的是男声），`zh` 解析到普通话语音而不是粤语语音，已配置的 `en`/`nl`/`es` 条目仍然胜出。在浏览器中，朗读开关带着它存储的标志在一次重新加载后依然存在，逐消息操作先报告准备中、随后报告朗读中，一次停止之后紧跟一次新的请求能在大约一秒内重新到达音频，而一条包含粗体文本、项目符号、行内代码和表格的回复在朗读时不带任何标记名称。

## 曾考虑的替代方案

**通过一次合成请求朗读每条回复。** 不予采纳，因为等待第一批词的时间等于回复的长度，而且被停止的朗读不重新合成全部内容就无法继续。

**让提供方决定默认语音。** 不予采纳，因为提供方的列出顺序不是一项产品决策：它产生了日语男声，以及 `zh` 的粤语默认值。

**按会话保留读者的选择。** 不予采纳，因为朗读是读者希望 Aeven 如何行事的偏好，而不是某一段对话的属性；语言练习与免手使用都会跨会话延续。

**在朗读之前用更严格的解析器剥离 Markdown。** 目前不予采纳：切分器运行在仍在到达的字符串上，而真正的解析器需要一份完整文档。先移除成对标记、再处理残留标记，用一条额外的规则覆盖了流式情形。

## 后果

- 添加一个提供方意味着实现定义并传入它报告的音色；不报告音色的提供方不产生女性偏好，它的语言按列出顺序回退。
- 朗读文本在客户端派生，因此回复渲染为 Markdown 的方式一旦改变，`toSpeechText` 必须随之同步。
- 逐消息操作与会话通道共享引擎的通道映射；一个与会话 id 冲突的通道 id 会混合两个读者的队列，因此消息通道保持命名空间隔离。
- 音频从不进入会话日志，因此回放中没有关于朗读过什么的记录。
