# Agent Note: 能力生命周期

Status: implemented

[English](2026-09-29-capability-lifecycle.md) | 中文

## 问题

一项已确认的能力，对其用户之后每个会话都是受信指令。流程会过时：工具变了、机器不同了，或者流程本来就不对。信任必须跟随能力运行时的实际情况，而不由模型生成的置信度数字决定任何事情。

## 决策

`@aeven/capability` 为每项能力保留每个修订的流程（`versions/<revision>.md`）与一份仅追加的证据日志（`executions.jsonl`）。`@aeven/tool-capability` 为每个加载了已确认能力的轮次记录一次执行：修订、模型路由、环境、加载之后调用的工具、提供方重试、token、轮次结束原因，以及模型的 `report`（结果与验证）。下一轮次中的直接用户纠正与该轮次回复上的评分作为修正记录追加。

一项确定性策略判定每一次执行，并在每次写入之后推导状态：

- **判定。** 纠正、负向评分、失败的报告或验证、或失败的轮次都会使一次执行判定为失败。正向评分使其得到验证，一次报告的通过验证加上一次成功的工具调用同样如此；仅有报告永远不算验证。
- **状态。** 只有用户能让一项能力可执行，或把它退役。在可执行状态中，`trusted` 要求当前修订有 `trustAfter` 次成功，且至少一次已验证、最后一次没有失败；`degraded` 跟随 `degradeAfter` 次连续失败；已受信流程发生变更后，在出现新修订的一次已验证运行之前保持 `needs-validation`；其余情况为 `learned`。
- **模型视图。** 受信与已学能力按原样加载。`degraded`、`needs-validation` 以及当前环境中从未成功过的能力会带着一段简短的证据说明加载，要求模型验证并报告。

## 考虑过的替代方案

**由模型生成的置信度数字决定信任。** 已否决，因为一项确定性策略判定每一次执行，并在每次写入之后推导状态，因此信任跟随已记录的证据，仅有模型的数字永远不能提升一项能力。

**继续让用户决定是否保存每套学到的流程。** 已否决，因为这使学习层变成用户要维护的一项功能；学习现在自动且静默，首次成功执行使候选成为 `learned`，`degradeAfter` 次失败执行使其退役。

**继续把记忆管理器做成 MemOS Viewer。** 已否决，因为 Settings → Memory 是 Aeven 自己的界面，其 Remote 只为发起当前请求的调用方行事，而 Viewer 仍是开发期的临时手段。

## 后果

- 一次浏览器运行让 `check-node-toolchain` 在三次已验证运行后从已学变为受信，在一次纠正后回到已学，并在一次已确认的编辑后变为 `needs-validation`；一个新会话带着验证说明加载了它，运行了新步骤，并在改动环境之前询问用户。
- 纠正通过开头短语识别，与轮次捕获使用同一套做法；隐式的不满不会被检测到。
- 证据留在能力运行所在的 Host 上；可移植性稍后决定其中哪些内容同步。

## Settings → Memory（PR9）

记忆管理器是 Aeven 自己的页面，而不是 MemOS Viewer：`@aeven/api-memory-manager` 提供一个 `memoryManager` Remote，它只为发起当前请求的调用方行事，`@aeven/client-ui-settings-memory` 把它渲染为 Settings → Memory。`MemoryProvider.list`、`edit` 与 `forget` 接受 `owner`，而不是会话范围，因为该页面在任何会话之外运行。能力出处条目现在只在变更来自某个会话时才携带会话；证据结算与从页面做出的变更都不记录会话。`@aeven/memory` 与 `@aeven/capability` 发布 `./types`，使 Remote 边界类型来自公开的非根类型子路径，并且 `@aeven/memory/types` 从 `@aeven/session/types` 读取 `SessionId`，这样 Client 面永远不会合并 Host 的 `ctx.sessions` 声明。

## 自动学习，不再发问

让用户决定是否保存一套流程，会使学习层变成用户要维护的一项功能，因此学习现在自动且静默。`@aeven/tool-capability` 运行一个学习器：一次以至少 `minSteps` 次真实工具调用完成的轮次会保留到用户的下一封消息，在纠正时丢弃，否则由一次后台模型调用提炼为新的候选，或合并进已有能力。候选会立即发布，并附上提醒检查每个步骤的说明；首次成功执行使其成为 `learned`，`degradeAfter` 次失败执行使其退役，在 `candidateTtlDays` 内从未执行过的候选会离开目录。一次未报告结果、但轮次以最后一次成功的工具调用结束的执行计为 `succeeded`。每项已学能力存储它的来源（请求、工具与该轮次的成本），Settings → Memory 把该基线与此前成功运行的中位数比较。模型被告知绝不要询问或宣告保存；`capability_manage` 去掉了 `delete` 与所有确认，删除留在 Settings 中。学习一套流程不授予任何权限：它引出的每一次工具调用仍要通过会话的访问模式与审批，后者仍是同意边界。在一次浏览器检查中，一个存储报告请求（7 次工具调用、27 秒、28.6K token）在后续消息之后产出了 `aeven-storage-report`；一个新会话中改写过的请求被指向它，加载后以 4 次工具调用、20 秒与 10.8K token 完成，并把它提升为 `learned`。

## 学习基准

`pnpm run benchmark:learning` 衡量学习是否让一项固定任务更快、更好。它通过随附的 `headless` 预设运行同一个清单任务（体积、最大的文件、`.log` 计数、CSV 行数，以隐藏目录、CSV 表头与相似的文件名作为陷阱），每种条件各用一个一次性 `$AVN_HOME`：`baseline` 挂载能力注册表但关闭学习，`learning` 则开启；两种条件都关闭记忆，因此唯一差别就是能力学习。每次运行都会得到一份结构相同、取值新生成的 fixture（测试前置数据），因此它无法靠重复早先的数字通过；脚本把 `inventory.json` 与由 fixture 计算出的真值比较，并从会话日志读取时间、工具调用、失败与 token。两项产品改动使之成为可能：headless 运行器接受 `owner`（`$AVN_OWNER`），即路线图第 11 步中已配置所有者的那一切片，并在退出前等待新的 `session/settle` 检查点，学习器用它在该运行结束后完成学习，因为一次性进程否则会在五秒关闭宽限期内退出，而学习调用仍在运行。

首次测量（2026-09-29，`--task release --runs 5`，aeven-cloud/Aeven-1.0-Flash，high effort）：十次运行都产出了正确验证的产物。未挂载能力层的基线中位数为 18 秒与 18 次工具调用。开启学习后，首次运行学会了流程；第 2–5 次运行分别耗时 19、15、12、10 秒，工具调用为 12、15、7、7 次（中位数 13 秒与 9.5 次），能力自行修订一次并达到 `trusted`。首次 `inventory` 测量没有显示差异，因为一次冷启动运行已经毫无错误地解决了它。过程中发现并修复了两个基准缺陷：在基线中挂载能力工具会让模型自己保存流程，因此基线现在不挂载任何能力层；学习器曾把顺利的首次运行当作一次性情况，因此它现在从第一次成功的多步骤操作任务开始学习。
