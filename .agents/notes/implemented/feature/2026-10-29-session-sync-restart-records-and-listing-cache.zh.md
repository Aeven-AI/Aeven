# Agent Note：会话同步的重启记录、列表缓存与运行标记

Status: implemented

[English](2026-10-29-session-sync-restart-records-and-listing-cache.md) | 中文

## Problem

账户同步每启动一次都会重新构造同样的事实。`importAll` 先列出本机会话，再从偏移 0 读取每个日志来统计事件数，因此重启会重读本机持有的每个会话日志。列出一个会话时，每一轮都要通过一次有界首行读取取它的头部。`SessionMirror.catalog()` 为每个会话向工作区注册表询问它位于哪里，也就是每个会话一次注册表扫描。

通过局域网认领会话的设备也永远不会释放：在没有租约持有者时，`holdRunner(id, false)` 在发布之前就返回，于是共享索引条目保留 `running: true`。账户的其他设备因此认为有一轮正在运行而拒绝接管，用户看到的就是输入被拒，提示“agent busy”，而该会话上其实什么都没有运行。

## Decision

每台设备在账户的同步存储里保留自己的会话记录，位于 `session-sync/<id>`，从不参与同步：它最后发布的日志修订号、它导入到的流位置，以及在给定修订号下统计出的一处“最后一个已存 `seq` 的下一位置”。只要日志的修订号未变，`SessionMirror.next()` 就用该记录作答，因此重启只读取发生变化的日志。

列表按日志路径缓存每个工件，在该日志及其副本标记保持读取时的修订号期间有效，并交出头部的副本，因为调用方拥有它收到的头部。重写头部会替换文件，所以变化的头部总伴随变化的修订号。`SessionMirror.importAll` 从该列表取得修订号。

`WorkspaceRegistry.sessionHomes()` 一次遍历就命名每个已归档会话的工作区，目录改用该方法，而不再为每个会话调用一次 `sessionHome`。`PersistenceCoordinator.load` 直接采用 `loadStored` 返回的图，而不再次克隆，因为该图是新建且未被保留的。

`holdRunner(id, false)` 无论有没有租约都会先发布再释放，只有本设备持有租约时才处置它。通过局域网认领会话的设备因此会清除那个告诉账户“这里有一轮在运行”的标记。

## Alternatives considered

**每次启动仍然通过 `readFrom` 统计日志事件。** 否决：这是有历史账户的主要启动开销，而计数只在日志变化时才改变。

**让记录在设备之间同步。** 否决：它们描述的是某台设备读到了什么，不是共享状态；另一台设备的游标与本机日志无关。

**不带修订号键缓存头部。** 否决：被重写的头部行将再也看不到。

**通过局域网直接询问写入设备是否正在运行。** 暂缓：本机链路只承载实时更新，这需要该传输层尚不具备的请求/响应帧；在释放时清除标记已经解决了卡住的问题。

## Consequences

- 对于修订号未变的日志，重启不发布任何内容，也完全不读这些日志的事件。
- 在中继不可达期间错过实时索引更新的设备，仍会在中继恢复时得知它；本机链路只承载实时帧。
- 该记录是存活于账户存储中的设备本地状态；删除它只需一次完整发布或一次流读取，别无其他代价。
