# Agent Note: 重新链接已移动的工作区目录会保留其会话

Status: implemented

[English](2026-10-30-relinking-a-moved-workspace-directory.md) | 中文

## Problem

文件夹工作区就是它的目录：成员资格通过比较会话记录的规范 cwd 与工作区路径来判定，而 `bindDirectory` 会拒绝任何已经带有路径的记录。当读者的项目文件夹移动了——被重命名、重新组织、从备份恢复或重新检出——就没有任何办法把工作区指向新目录。旧路径继续命名一个已不存在的目录，记录在那个路径下的每个会话都不再是成员，而唯一可用的补救是重建工作区（失去分组）或把文件夹放回去。

行菜单提供"在此设备上选择文件夹"，但只对从另一台设备到达且没有路径的工作区显示，所以拥有该文件夹的设备根本没有可点击的入口。

## Decision

为工作区选择文件夹在两种情况下是同一个动作，注册表的 `bind(id, path)` 按记录分派：无路径的记录获得它的第一个目录，文件夹记录则被重新链接到新目录。

重新链接会把它离开的目录记入新的持久字段 `anchorPaths`（最新的在前），而每个成员资格判定——`member()`、`mutate()` 中的剪除、准入、启动时重新准入，以及采纳刚宣告的会话——都把当前目录与每个锚点视为该工作区拥有的目录。因此记录在旧路径下的会话会继续留在工作区里，而不是从一个从它们脚下移走的工作区中掉出去。

`anchorPaths` 属于设备本地。账户文档仍然只携带工作区的标题与顺序，因为路径在另一台机器上没有意义；一台设备上的重新链接不会改变账户其他设备上的任何东西，每台设备各自选择自己的文件夹。

解析遵循同一列表：本设备写入的会话解析到它记录的目录，而当该目录位于某个锚点之下时，它会被转换为工作区当前目录内的同一位置，因此在子目录中工作的会话在移动后仍保留该子目录。

行菜单在除内置工作区之外的每一行提供该动作，名称为 **选择工作区**，位于删除工作区之上——无论工作区在本设备上无路径还是已经有文件夹，入口都是同一个。

## Alternatives considered

**重写会话记录的目录。** 它能让头部在本地再次为真，但会摧毁可移植的记录、需要对既有日志做迁移、并重写不可变的头部元数据——而其他设备上的副本每台都还要再做一次。

**把会话分离出去，再按新路径重新归档。** 成员资格是与会话无法更改的记录路径做比较，所以没有任何东西会把它们重新归档：工作区只会变空，会话则处于未分组状态且没有回头路。

**在新目录重建工作区。** 实现成本最低，也是读者此前不得不做的事：它丢失标题、位置与归档状态，并把旧记录留成一条命名着没人拥有的目录的重复记录。

**在 `bind` 之外再加一个"relink"动词。** 两者的差别只在于同一个生命周期的不同阶段，而在"为这个工作区选择文件夹"和"为这个工作区选择文件夹"之间给读者一个可见区分，是读者无法据此行动的文案。面向仓库的名称仍为 `bind`，并在文档中说明它覆盖两种情况。

## Consequences

- 移动后的项目保留它的工作区、标题、位置与会话；不重建任何东西，也不写入任何会话日志。
- `anchorPaths` 每次重新链接增加一项且从不裁剪；反复重新链接同一工作区的设备会积累一小串失效目录。每个条目在每个成员资格判定中多一次比较。
- 记录在既非当前目录也非锚点的目录下的会话不受本决定影响：它仍跟随命名它的工作区，而对于本设备从未得知的移动，那仍是失效的绑定。
- 两个工作区也不能通过锚点认领同一个目录，因此重新链接不会悄悄夺走另一个工作区的会话。
