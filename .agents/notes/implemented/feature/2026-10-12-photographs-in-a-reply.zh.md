# Agent Note：回复中的照片

Status: implemented

## 问题

关于某样东西实际长什么样的问题，此前只用散文回答。“Crystal palace. Did it ever exist?” 会给出不错的文字答案，却没有任何配图；而同样的问题在 chatgpt.com 上会得到一行带来源的照片。

harness 里没有任何东西能取回照片。`web` 能力下的各个 provider 只返回文本；`find`／`fetch` 也只返回文本；唯一会产出 image 块的工具是图片生成，它凭空造图，而不是展示真实事物。因此缺口在于检索，而不在于渲染：Markdown 引擎本来就能渲染图片，客户端本来也会把工具返回的图片画成一行。

## 决定

`@aeven/tool-image-search` 注册一个面向模型的工具 `find_images(query, count?)`。它在 Wikimedia Commons 的 `File:` 命名空间中检索，只保留位图，下载每条匹配结果 1600px 的缩略图，通过 `ctx.attachments.saveImage` 存储字节，并返回普通的 image 内容块，外加一段写明每个文件页面与许可的文本摘要。首个来源选 Commons，是因为它的 API 为每条匹配结果同时返回许可与文件页、不需要任何凭据，且其中的历史摄影属于开放许可或公有领域——缺少这些字段的来源无法被引用。

图片以 image 块的形式传递，因此客户端会把它们画在生成图片所用的同一条通道里，会话日志也以相同方式保存。工具的结果文本会告知模型图片已经展示，不要再重复写出。

该工具通过 `aeven` preset 为每个会话挂载，preset 提示词也写明了行为：当主题真实存在且被拍摄过时，直接展示照片，而不是描述它们，且无需等待用户提出。

随之而来的还有两处渲染改动，因为一行照片必须看起来像生成器产出的那一行：

- 引擎会把写在连续区块上的一串图片——包括同一段落内的多张图片，模型用软换行就会产生这种写法——合并为一个带 `data-count` 的 `div.markdown-image-grid`。合并只负责结构，并在净化之后进行：图块长什么样仍归宿主。
- 渲染出的图片在加载完成后会报告自身方向（`data-orientation`），宿主据此把横向图块做成 3:2、竖向图块做成 2:3，且单独的一张竖图永远不会占满整列。

## 考虑过的替代方案

**让模型自己写 Markdown 图片链接。** 既没有检索也没有许可：模型得先知道某个 URL，回复还要热链一个可能拒绝请求的主机，而且没有任何东西能验证那张图存在或确实拍的是该主题。

**像 ChatGPT 的可视化那样增加模型自撰 HTML 的界面。** 这会带来新的沙箱、CSP 允许清单，以及一套需要同步维护的第二套设计系统——而这一切都用在本已可用的那一半上，因为引擎与客户端本来就已能显示图片。

**让模型描述它所知道的照片。** 无法验证、内容过时，而且它什么也展示不出来。

## 影响

干净的新会话现在会用来自 Commons 的带来源照片回答该问题，并按生成器通道自身的几何排布。

Commons 收录的当代素材很少，因此新闻、产品与在世人物来自 `web` 缝的结果页，新闻则以模型选定文章生成的卡片呈现（[视频与新闻卡片](2026-10-13-videos-in-a-reply-and-news-cards-from-articles.zh.md)）；检索、抓取、下载与工具本身仍放在同一个包里，而没有拆分到各自的能力缝上。

该包不带 spec 交付：其 wire 边界解析、超时与体积上限均未被测量，这一行的排布也只在真实会话中验证过。preset 行要到下一次 Host 启动才会生效，因此已在运行的服务端在重启前仍只会用散文回答。
