# Agent Note: 轮次复核与 bash 编辑守卫

Status: implemented

[English](2026-10-21-turn-review-and-bash-edit-guard.md) | 中文

## 问题

在一个九轮的 CSS 会话中，智能体的 `edit` 调用因文件未读取而被拒绝后，改用 `bash` 运行了 28 个 Python heredoc 来改动 `ProducedFiles.module.css` 与 `ProducedFiles.tsx`。`str.replace` 在文本不存在时不改动任何内容却报告成功，于是若干所要求的值从未落地。这些改动没有留下产出文件卡片所读取的任何 `tool/call`，因此第 3 至第 9 轮都没有显示已编辑的文件。最终回复在轮次自身的工具结果恰恰相反时声称「已完成」「已验证」「与表格一致」：一次 DevTools 读取在回复之前就发现参考表头是透明的，回复却把不透明表头称为「表格卡片的做法」；一个被观察到不可见的胶囊在回复中被称为「模糊」；一次只匹配到 `-webkit-backdrop-filter` 的打包搜索被当作 `backdrop-filter` 的证据呈现。有一项请求（「表头的字重是 400 而不是 500」）被反着执行。

## 决策

`@aeven/bash-edit-guard` 注册一个 `tools.guard`，拒绝这样的 `bash` 命令：它指名一个携带源码扩展名的现有文件，并就地编辑该文件（`sed -i`、`perl -i`）、通过脚本调用写入（`open(…, 'w')`、`write_text`、`writeFileSync` 等），或重定向进该文件（`>`、`>>`、`tee`）。路径按调用的 `workdir`、会话 cwd 以及命令中每个 `cd` 目标解析。创建文件、写入系统临时目录以及运行程序都不会被拒绝，因此用 `cat > package.json` 搭建新项目仍然可行。回放该 CSS 会话时，守卫恰好拒绝它的 28 个编辑脚本；回放一个单轮网站构建时，它没有拒绝按原样运行的 12 条命令中的任何一条。

`@aeven/turn-review` 监听 `agent/turn-stopping`。当一个轮次以文本回复结束、且其中一次 `write`、`edit` 或 `str_replace_editor` 调用成功时，一次使用该轮次自身路由的辅助调用把该轮次当作 JSON 读取（用户消息、工具调用、裁剪后的工具结果、回复），并只针对三个问题回答 `{"complete", "issues"}`：请求未做或做得与要求不同、没有任何工具结果支持或被工具结果否定的断言（包括只读到经过筛选、被截断或不完整视图的结果时，断言某物不存在、缺失或不受支持），以及在最后一次编辑之后没有任何观测却被说成可用的改动。问题通过一条来源为 `plugin` 的 user 消息把智能体送入另一个步骤；干净的判定、失败或超时的调用，或用完的 `maxReviewsPerTurn` 配额（2）都会允许轮次结束。`turn-review/request` 记录确切的请求，`turn-review/verdict` 记录解析后的结果，`turn-review/failure` 记录两者皆无的调用及其原因。

## 考虑过的替代方案

**在角色设定或系统提示词中加入规则。** 否决：会话提示词已经告诉模型用 `edit` 做定点修改，而模型在遭到一次拒绝后就绕开了它。在操作中执行的守卫才是强制；散文不是。

**在每次 bash 调用前后快照工作区。** 暂时否决：每次调用都做一次 `git status` 会让每条命令都付出时间成本，而且仍然区分不出格式化器运行与手工编辑。

**复核每一个轮次。** 否决：不改动文件的轮次没有编辑断言可查，而额外的调用会给对话与调研轮次增加延迟。

## 后果

- 一个改动文件的轮次在结束前多花一次模型调用；当第一次复核发现问题时是两次。
- 守卫读取命令文本，因此它不认识的写入（例如自行计算路径的自定义脚本）会通过。
- 在一次脚本调用中读取现有源文件的同时又向别处写入的命令会被拒绝；模型改用 `read` 读取该文件。
