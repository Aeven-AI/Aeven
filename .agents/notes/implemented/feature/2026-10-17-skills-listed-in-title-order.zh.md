# Agent Note: 设置页面按标题顺序列出技能

Status: implemented

[English](2026-10-17-skills-listed-in-title-order.md) | 中文

## 问题

技能页面按上游安装次数排列目录，而账户自己的技能库则保持宿主返回的原有顺序。安装次数是目录内置仓库带来的热度信号，而页面的职责并不是它：读者要么按名字找一个技能，要么扫一遍分类看看有什么。按热度排序恰好把最需要被找到的条目埋了起来——本仓库编写的每个技能都以 `downloads: 0` 出现并排在最后，于是一个新的一手技能卡在自己分类的底部，而与它并列的、安装量九千的第三方技能却在顶部。技能库那一半则完全没有顺序，导入进来就按到达顺序待着。

## 决策

`IntegrationsSection` 用同一个比较器把每份技能列表按标题排序，比较的是每行显示出来的名字：目录条目有 `displayName` 就用它，否则用安装名，并且忽略大小写与变音符号。

技能库列表、目录的单一列表、以及每个目录分类，都走这个比较器。显示方式菜单仍是两种排布——一份包含全部技能的列表，或按分类分组——两者都按标题顺序阅读，因此这个选项现在决定的是“怎么分组”，而不是“怎么排名”；它的第一个标签从 `按热度` 改为 `全部`。安装次数仍作为文本显示在每条目录行旁，它依然是读者可能想要的信号，只是不再决定位置。

## 考虑过的替代方案

**保留按热度排序，另加一个排序控件。** 为一份只读一次的列表加三向排序菜单，换来的是实打实的成本——多一份状态、多一个待翻译的标签、多一个测试——换取的却是几乎没人会做的选择。标题顺序不需要控件，而且正是读者自己的搜索所预设的顺序。

**目录按标题排序，技能库保持到达顺序。** 同一个页面的两半依照两种顺序，而从目录装进去的技能会在技能库里出现在另一处。两半共用一条规则，切换时才会像把技能挪进了同一份列表，而不是挪进了另一份。

**单一列表先按分类名、再按标题。** 分组本来就是第二种排布，想要的人可以选。先按分类排序的单一列表，反而藏起了读者用来快速扫描的那段字母顺序。

## 后果

本仓库编写的技能在发行当天就能按名字被找到，这正是 `reverse-engineering` 需要的性质：该分类里只有一个条目，而列表也不再暗示拿一个尚未安装的热度数字去比较两个技能。

热度退出了排序，但仍留在数据里：`downloads` 依然存在于每个目录条目上，依然作为安装次数显示在行旁，而目录包自己的文档不再声称设置页面按它排序。想要排行榜的部署可以从这个数字自行构建，索引也仍然带着它。

技能页面的文案随行为一起改了：目录说明不再描述“与之并列固定的仓库”，显示选项的标签是 `全部`。
