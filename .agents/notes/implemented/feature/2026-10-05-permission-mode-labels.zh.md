# Agent Note: 权限模式按边界命名，而不是按背后的沙箱旋钮

Status: implemented

[English](2026-10-05-permission-mode-labels.md) | 中文

## 问题

GUI 此前用三个模式背后的强制旋钮来命名它们：`Read Only`、`Workspace Write` 和 `Full access`。其中 `Workspace Write` 命名的是一个 `sandbox/mode` 取值，因此用户必须选择的那一行描述的是实现设置，却没有说明他们真正要决定的事——智能体可以自主走多远，以及在什么位置停下来询问。已交付的 base bundle 预设表不携带任何客户端标签，所以这三个名称就是用户能得到的全部解释。`Full access` 的风险对话框同样只描述「减少确认步骤」，没有点名谨慎的用户应当改选哪个模式。

审批提示有对应的缺口。它的按钮已经是 `Reject` / `Allow once`，但卡片上没有任何地方说明这次授权覆盖什么范围，因此在下一个请求出现之前，一次性应答与持久的策略变更看起来并无区别。

## 决策

内置权限模式在所有列出它们的弹窗中都以按边界命名的产品标签呈现，除此之外不显示别的：一行就是模式的名称，因此这个表面始终是在模式之间做选择。

| 机器取值 | 产品标签（en / zh） | 该模式边界的一句话（标签的含义，而非渲染文案） |
| --- | --- | --- |
| `read-only` | `Read only` / 仅可查看 | Looks at files and runs read-only commands. Nothing can be changed. |
| `workspace-write` | `Ask for approval` / 需要时先询问 | Works inside your workspace and asks before going beyond it. |
| `danger-full-access` | `Full access` / 完全权限 | No sandbox and no approval prompts: the agent can change anything on this machine. |

`Workspace Write` 变为 `Ask for approval`，与它作为组合默认值的含义一致：智能体在工作区内工作，`ask` 审批策略在边界处让它暂停。机器取值、预设表键名、`/permission` 命令参数，以及 `permission/preset`、`sandbox/mode`、`approval/policy` 事件都不变——这属于呈现层，因此没有任何持久化或线上事实移动，重放也不受影响。

标签在两个呈现它的包中都是 locale 所有的客户端文案。两个包各自携带文案，是因为两个 bundle 独立加载——这是既有的标签映射重复。行渲染标签，并且在选择器支持时渲染部署自己提供的 `description`；任何地方都不再渲染内置解释。

被部署改名的模式不显示内置标签。两个包只在宿主仍以取值本身或内置英文标签呈现该取值时解析内置标签；否则原样呈现部署自己的 `name`。该规则存在的原因是：内置文案点名的是部署可能已不再配置的行为——被改名的模式绝不能继承这一层无法核实、关于沙箱语义的断言。

审批提示保留两个一次性应答，并新增一行说明它们的覆盖范围：允许只作用于这一次调用，权限模式不会改变。该句子只是既有封闭结果词汇之上的文案——`allowed-once` 仍是唯一的授予，也没有引入任何持久化审批状态。

## 曾考虑的替代方案

**在同一次改动中把 `danger-full-access` 改名为 Codex 的三模式组合，并加入 `Approve for me`。** Codex 的 `Approve for me` 保留沙箱、只替换审核者：跨越边界的请求交给自动审核，而不是交给用户。Aeven 没有审核者这一维度——`approval/policy` 只有 `ask | never`，而 `allowed-once` 是按请求授予的——因此该模式需要一个全新的持久旋钮，以及挂在 `approval/request` 瀑布上的自动审核应答者。在能力落地之前先交付标签，等于承诺一种没有任何东西会去执行的自动审核；所以这次改名停留在既有三个模式之内，审核者维度另作一项工作。

**保留沙箱名称，把解释放到别处。** 名称是用户最先读到、也会自己重复的部分；把 `Workspace Write` 留在原位，等于让实现词汇继续占据权威位置，却要求其他文案去抵消它。模式自己的名称是说明其含义最省的位置，也是用户会转述给同事的那个名称。

**按审批策略命名模式（`Ask` / `Never ask`）。** `read-only` 与 `workspace-write` 都带 `ask` 策略，因此按审批策略命名会把两个不同模式压成一行，并隐藏真正有区别的那条边界。

**在 chip 菜单的每个模式下渲染一句后果说明。** 每一行下面配一句话，不必悬停也能看出边界在哪里。它先被实现，随后被移除：模式的名称本身已经承载了决定（「需要时先询问」用三个字说明了边界），因此第二行只是用更长的形式重复标签，把一个三行弹窗的高度变成三倍，并把两个词的选择变成一段要读的文字。后果属于风险对话框与面向模型的策略上下文；弹窗显示的是可以选什么。

**把解释做成共享 `Menu` 原语里正式支持的第二行。** 该原语的 `description` 槽是右对齐的单行文本，尺寸是为命令行准备的，放在那里句子会被省略号截断；而一个可换行的第二行会成为一个只服务一个弹窗的通用菜单能力。行仍是在原语既有座位上渲染的单行标签，原语保持不变。

## 后果

选择模式的用户读到的是智能体可以做什么，而不是哪个旋钮在移动；改名的部署完全掌握自己模式的含义，代价是失去内置解释——这与标签映射此前已经做出的取舍相同。`Full access` 对话框现在会点名推荐 `Ask for approval`，因此从风险被说出的那一刻起，更安全的选择就是可达的。

固定 chip 无障碍名称、模式标签与设置行文案的 Web UI 快照会随文案变化，permission-presets 浏览器 spec 的标签列表同样如此。两个客户端包必须手工保持各自的标签键同步；没有任何检查跨包核对它们，因此某个模式只在一个表面改名、另一个没有，属于评审时才能抓住的问题。弹窗宽度不变：一行就是按原语自身字号排版的单行。

审批提示新增的那一行只是文案：composer 接管、待处理交互注册表、审计事件对，以及单一授予规则都未被改动。
