# Agent Note: 沙箱升权的会话授权

Status: implemented

[English](2026-10-12-sandbox-escalation-session-grant.md) | 中文

## Problem

受限调用被拒绝后可以用 `sandbox_permissions` 重试，但每一次放宽都会再次询问用户，即使他们在同一会话中几分钟前刚刚允许过相同的放宽。写入工作区之外且需要重复执行的工作——在应用程序包旁边解包归档、连续导出——因此变成每条命令一次提示；而请求方唯一的替代做法是在编辑器中提升会话的访问模式，这比「再次允许这次放宽」表达了更大的范围。

## Decision

`approveEscalation` 在每次升权询问中都提供会话授权：范围为 `sandbox:<effectiveMode>-><requestedMode>`，覆盖类别为 `'sandbox'`。审批能力把该范围和会话 ID 记入 `approval/decided`，并在后续工具名与范围都匹配的询问中复用该授权，因此提示里的「本会话允许」选项覆盖本会话余下时间。范围记录了授权来源的既有模式，因此用户在把会话切换到另一种模式之后提出的询问会重新询问。bash、pwsh 与文件系统变更都通过共享的升权编排走到这里，并各自以自身的工具名提供该授权。

`allowSessionCoverage` 是请求方对自身授权覆盖范围的声明，面板据此选择同意文案。连接器询问声明 `'account'`（该账户上同类操作，包括其他收件人和内容），升权询问声明 `'sandbox'`（后续取得同一放宽访问权限的任何调用），未声明的请求方得到 `'action'`（重复同一操作），它不主张超出提示上该动作的范围。

该授权既不改变会话的访问模式，也不改变模型可见的沙箱叙述：被允许的升权仍然只把授予的模式打到提出询问的那一次调用上，编辑器中的访问模式控件仍是放宽会话的唯一途径。

## Alternatives considered

**在审批提示中提升会话的沙箱模式**（会话授权时写入 `sandbox/mode`）可以让模型免于为后续每条命令继续支付「先拒绝、再重试」的循环。它未被采纳，因为访问模式控件已经拥有该决定；审批卡片静默地把会话切到完全访问所表达的内容超过卡片所示；而且该能力有意向消费方返回一次性结果，而不是工具层必须据此行动的授权。

**为所有请求方使用一句通用会话说明**（不声明覆盖类别）未被采纳，因为诚实的覆盖范围因请求方而异：连接器授权会触达卡片从未展示的收件人和内容，而升权授权会触达其他命令。单一措辞要么低估连接器授权，要么对升权说不出有用的信息。

**在面板中根据工具名推导说明**（在客户端维护沙箱相关工具清单）未被采纳，因为范围由请求方发明，只有请求方知道其授权覆盖什么；这样的清单会随下一个执行族出现而过时。

## Consequences

用户可以让自己的一次放宽覆盖整个工作会话，而且提示会在用户同意之前用请求方自己的说法解释该授权覆盖什么。升权授权与其他授权一样持久且可重放，没有撤销界面，也不会带给分叉。模型永远不会得知授权的存在，因此它仍会带着理由请求放宽，也仍会执行那一次产生拒绝的受限尝试。
