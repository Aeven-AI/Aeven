# Agent Note: 能力学习

Status: implemented

[English](2026-09-29-capability-learning.md) | 中文

## 问题

一个 agent（智能体）摸索出一套多步骤流程，往往是在出错或得到纠正之后，却会在会话结束时丢掉它。Hermes 表明，一份平实的书面流程（由 agent 创建的 `SKILL.md` 加配套文件）已经能让 agent 随时间推移为它的用户做得更好。直接照搬会带来两个风险：skill（技能）正文以受信指令的形式加载，因此 agent 依据工具输出写出的流程会成为一条持久的提示词注入路径；而学习系统也可能谨慎到什么都不留下。

## 决策

能力学习遵循三条规则：

- **复杂的学习，简单的执行。** 可执行产物是一个与 agentskills 兼容的目录：`SKILL.md` 含流程，另加可选的配套文件。状态、修订、来源与出处放在旁边的 `capability.json` 中，永不进入模型。
- **立即记住，逐步信任。** agent 学到的任何东西都立刻以 `candidate` 形式持久保存。只有在用户确认之后，它才成为 `learned`，从而可执行。证据决定一项能力被信任到什么程度（路线图的下一步），而从不决定它是否被记住。
- **执行从不依赖记忆。** 能力存放在 Aeven 拥有的注册表（`ctx.capabilities`，本地文件位于 `$AVN_HOME/capabilities/<owner>/`）中。记忆提供方可以帮忙找到它们；运行一项能力只需要注册表与 skill 目录。

`@aeven/capability` 按已登录所有者存储能力，并把每个所有者的已学能力发布为 `learned-capabilities` skill 提供方。`SkillLookupOptions` 新增 `owner`，由 skill 工具、面向模型的目录与 Web skill 目录设置，并成为注册表目录缓存键的一部分。

`@aeven/tool-capability` 给模型提供 `capability_manage`。`learn` 保存一个候选，随后通过 `ctx.userQuestions` 询问用户；由工具发问，模型便无法跳过确认。这里不使用 `ctx.approval`，因为它的 `never` 策略（完全访问预设）会拒绝每一个请求，而不是允许它。修改或删除一项已学能力同样会发问。系统提示词中一段简短文字（仅在会话有所有者时显示）说明何时学习：应要求时，或在通过错误、死胡同或纠正摸索出一套重复流程之后。与请求匹配的未确认草稿每会话召回一次，作为带标签的 `<capability_drafts>` 块。

## 考虑过的替代方案

**agent 一写出流程就信任它。** 已否决，因为 skill 正文以受信指令的形式加载：由工具输出提炼出的流程会成为一条持久的提示词注入路径，只有用户的确认才能让一项能力可执行。

**让证据决定一套流程是否被记住。** 已否决，因为证据决定一项能力被信任到什么程度，而从不决定它是否被保留；agent 学到的任何东西都立刻作为候选持久保存。

**通过记忆提供方运行能力。** 已否决，因为执行不能依赖记忆：注册表与 skill 目录足以运行一项能力，记忆提供方只帮忙找到它们。

**通过 `ctx.approval` 确认保存。** 已否决，因为它的 `never` 策略（完全访问预设）会拒绝每一个请求，而不是允许它；学习器改为通过 `ctx.userQuestions` 发问，因此模型无法跳过该问题。

## 后果

- 一次浏览器检查在一个会话里用一次确认教会了 `check-node-toolchain`；一个新会话在 skill 目录中找到了它，用 `skill` 工具加载并照做。
- 用户确认过的能力，对该用户之后每个会话都是受信指令。执行记录、校验与降级随后在能力生命周期步骤中定义。
- 目前还不会从已记录的证据自动生成提案；模型依据学习指引提出候选。
