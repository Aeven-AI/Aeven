# Agent Note: The account menu reads the plan with the page

Status: implemented

[English](2026-10-17-account-plan-read-with-the-page.md) | 中文

## Problem

[账户菜单的方案行](2026-10-17-account-picture-and-plan-menu.zh.md)原本在面板首次打开时才读取。因此点击头像的读者先看到读者、设置与登出，方案行则在订阅路由回答之后才出现在它们下方——面板已经打开、正在被阅读，而其中最新的一条事实还在路上。头像从首帧起就站在常驻导航条里，因此这次读取完全可以随页面一同开始，在任何打开之前就已有结果。

## Decision

`AccountMenu` 一旦绘制出已登录读者就询问方案，而不是等到面板打开。这次读取由以“读者是否存在”为依赖的 effect 发起，因此请求随文档一同发出，面板在打开的那一帧就画出方案行。

答案仍是组件状态。方案从本菜单所通向的账户页变更，频率远低于面板打开的次数，也没有其它界面绘制它，因此不需要 store，`shell.corner` 的注册保持原状。

若某次打开时仍无方案——页面的读取仍在途，或已经失败——第二个以 `open` 为依赖的 effect 会再次询问。两次询问都经由同一个 `accountType` 注入，而插件 `apply` 与账号页共用的 `createReadCache` 会把第二次折进已在途的请求，而不是再发一条。未登录的读者不会发起任何请求。

## Alternatives considered

**在 `apply` 中预热读取，让菜单同步读缓存。** 否决：这需要在注入面上、`accountType` 之外再加一个同步访问器，而组件会在渲染期读取可变快照。以读者为依赖的 effect 通过组件已有的注入面达到了同样的延迟。

**在 boot kernel 中读取订阅。** 否决：认证 gate 链接进 boot，因此 boot 确实可以发起该调用，但方案属于账户呈现，boot 既不拥有账户，也不拥有这一行。没有挂载账户菜单的部署也会照付这次请求。

**保留首次打开时读取，接受迟到的方案行。** 否决：面板是由读者自己点击打开的，而他们正看着它，因此绘制之后才出现的方案行读起来像“缺少一条事实”，而不是“它还在路上”。前一份笔记要保护的是：从不打开菜单的读者不产生任何请求；而面板打开的时长远超这次请求所需。

## Consequences

已登录的页面上，无论读者是否打开菜单，都会多出一次 `/api/cloud/subscription` 请求；在方案仍未知期间，每次打开还会再多一次。读取落定之后，打开菜单本身不再产生请求。

菜单保留它读到的方案，因此在账户页或另一客户端做出的方案变更，要到下次文档加载后才在此出现，而不是下次打开时；账号页自身的视图不受影响。

## Testing

`tests/account-menu.client.spec.tsx` 固定的是时机，而不只是文本：面板仍关闭时发生一次读取、方案行与打开出现在同一次渲染中且不再产生调用，以及首次读取未得到方案时再次询问。
