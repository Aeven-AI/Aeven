# Agent Note: 一次 read 或 edit 调用处理多个文件

Status: implemented

[English](2026-10-27-multi-file-read-and-edit.md) | 中文

## 问题

一个已记录的会话在 161 个模型步骤中执行了 161 次工具调用。模型推理中计划了“一条消息中 3 个 read 调用”和“一条消息中三次编辑”，但每次响应都在第一个调用后结束，因此读取并编辑三个文件花费了六次模型往返，每次约三秒。在近期会话中，路由模型约每六个步骤中有一个批量发出原生调用，几乎都是 `bash` 或 web 调用；`read` 只批量过两次，`edit` 从未批量过，尽管 persona 已要求分组调用。

## 决策

`read` 和 `edit` 接受 `files` 列表，使批量处理不再依赖模型发出多个调用。每个条目采用单文件参数：`read` 条目接受 `file_path`、`offset` 和 `limit`；`edit` 条目接受 `file_path` 加 `old_string`/`new_string`/`replace_all` 或 `edits` 列表。单文件形式、其结果文本和展示元数据保持不变。

多文件 `read` 并发读取各文件，原地报告失败的文件，仅当所有文件都失败时才失败。多文件 `edit` 先解析所有路径，拒绝重复文件，然后按顺序应用各文件，每个文件使用自己的观察守卫；失败会停在该文件，其错误列出已修改的文件。工具描述、提示指导和 persona 都引导模型使用这两种列表。

从调用参数读取 `file_path` 的消费者随列表一起处理：嵌套 agent 指令为每个被触及的路径加载，turn deliverables 以各自的行数记录每个被编辑的文件，Web diff 卡片和行摘要覆盖每个文件。diff 卡片和 deliverables 现在也接受此前被跳过的单文件 `edits` 列表。

## 考虑过的替代方案

仅靠提示措辞的方案早已存在，并在文件工具上被忽略。跨文件原子编辑需要任何后端都不提供的文件系统事务。单独的多文件工具会重复守卫、展示和消费者。

## 后果

多文件 `read` 没有 read 卡片；Web 将其显示为带包络的通用行。部分应用的多文件 `edit` 报告错误，因此 Web 不显示其已应用文件的 diff。`scripts/bench/agent-efficiency.ts` 按任务测量调用数和步骤数，用于前后对比。
