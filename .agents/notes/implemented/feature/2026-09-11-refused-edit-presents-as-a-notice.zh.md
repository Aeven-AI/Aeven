# Agent Note: 被拒绝的编辑呈现为提示，而不是告警

Status: implemented

[English](2026-09-11-refused-edit-presents-as-a-notice.md) | 中文

## 问题

`@deepseek-ai/dsh-fs-observation-policy` 会对本会话尚未读取的目标的 `edit` 以 `FS_NOT_OBSERVED` 拒绝，`@deepseek-ai/dsh-tool-fs` 则把该拒绝呈现为 `cannot modify "<path>": file has not been read — read the file, then retry`。按设计，这类拒绝是常态：它正是门禁在起作用，而消息里点名的读取就是全部补救办法。但对话行却穿着整套错误外衣——错误配色的状态点加上错误配色的失败行——于是一个会话自己就能消除的步骤，看起来与一次事故毫无区别。先编辑后读取的会话会连续产生多条这样的行，而每一条读起来都像 harness 的缺陷，而不是某个策略在履行职责。另一种诱惑是把它压掉，那是更糟的选择：渲染出的对话记录就是模型看到的上下文，隐藏一次拒绝，也就抹掉了紧随其后那次读取的唯一解释。

## 决定

补救办法已有明文记载的失败结果，以提示而非告警呈现。`toolRowModel` 依据结构化错误码作出判定，绝不依据消息文本：工具会把所有未读取来源统一成同一句话，因此按文本匹配还会连带认领本分类并未声明的失败。按错误码判定还有一个好处——提供方一侧的拒绝与策略一侧的拒绝落入同一类，而这是正确的：同一步补救能消除两者。`NOTICE_ERROR_CODES` 包含 `FS_NOT_OBSERVED`，并且自[陈旧目标笔记](2026-09-12-stale-target-refusal-presents-as-a-notice.zh.md)起也包含 `FS_STALE_VERSION`——后者自身的诊断写明了同样的重新读取补救办法。

该行保留使其成为失败的一切。状态仍为 `error`，因此运行状态契约、行外观与无障碍朗读状态（“failed”）都不变；消息仍是折叠后的摘要；展开后的输出保留其错误配色。真正弱化的只有两处——前置指示符改用 `StateDot` 的 `warning` 状态，折叠行改挂 `.noticeSummary`（次级标签色）而不再是 `.errorSummary`（错误色）。行上的 `data-notice` 把这一区分带给 CSS 与测试。

`ToolRow.notice` 为可选属性，缺省即普通错误行。只有可能报告该失败的行才传递它：拥有 `edit` 与 `write` 的 `FileMutationRow`，以及这些调用在未注册该视图时落入的键控派发回退 `GenericToolCard`。不可能报告未读取目标的工具行保持不接线，而不是传递一个恒为 false 的字段。

## 考虑过的替代方案

**在对话视图中压掉该行。** 引发本次改动的抱怨正是噪声，而针对那句被统一过的文案加一个过滤器，是回答它最省事的办法。已否决：渲染出的对话记录就是模型自身的上下文，隐藏一次拒绝会让视图与智能体实际依据的内容不一致——紧随拒绝之后的那次读取会显得毫无来由——而以那句话为键的过滤器，还会一并隐藏本分类从未认领的失败。

**由工具代模型读取目标并重试编辑。** 已否决：它消除的是门禁本要施加的纪律，而不是噪声。模型仍会在看不见内容的情况下写出 `old_string`，一旦这个字面量恰好唯一次匹配在非预期之处，编辑就会被静默应用。一个通用的“读取后重试”还会顺带吞掉 `FS_STALE_VERSION`——那正是模型对文件的认知确定已经过时、需要重新读取内容而不只是刷新版本的场合。若收窄为只处理 `FS_NOT_OBSERVED`，它修好的只是较少见的那类成因，而更常见的那类（会话从未读过该文件）原封不动。

**在同一路径成功读取或编辑之后折叠该行。** 已否决，因为这是空动作：工具行在读者展开之前本就是折叠的，所以“已恢复”不会带来任何可见变化，而检测它却需要把同辈调用上下文穿过工具槽契约，传递给该轮中的每一行。

**在 `ToolRowState` 上新增 `notice` 取值。** 已否决：该状态驱动运行状态契约与无障碍朗读状态，而本次改动刻意两者都不动。弱化的是呈现，因此由呈现层承载这个标记。

## 后果

常态拒绝现在读起来是信息：该行仍可见、仍可展开、仍被朗读为失败，但不再与真正的失败争夺注意力。代价是行上多出一个呈现维度，以及一份必须刻意维护的分类清单——下一个加入其中的错误码会让每一位读者的告警变轻，因此每次新增都需要与本次相同的论证。门禁本身没有任何变化：未读取的目标仍被拒绝，文件系统工具仍报告同一个错误码、同一条消息与同一个状态。

想要恢复原有强调的读者，只需点开一次：展开后的输出保留着错误配色。

## 验证

`packages/client/ui-tool/tests/tool-row.client.spec.tsx` 固定分类结果：`FS_NOT_OBSERVED` 结果为提示，任何其他错误码的失败都不是，运行中或成功的调用永远不是。`packages/client/ui-tool/tests/diff-card.client.spec.tsx` 固定渲染结果：该拒绝在保留 `data-state="error"` 的同时获得 `data-notice` 与 `.noticeSummary` 类，其消息在折叠状态下仍可读，而补救办法无明文记载的失败仍保持错误呈现。客户端库与 Web 产物已重建，运行中的 Web URL 所服务的 bundle 携带 `warning`/`error` 状态点分支、提示类与 `data-notice`。
