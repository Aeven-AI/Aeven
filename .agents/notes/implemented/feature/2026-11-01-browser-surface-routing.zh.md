# Agent Note: Browser surface routing

Status: implemented

[English](2026-11-01-browser-surface-routing.md) | 中文

## Problem

所有面向模型的说明都把开发工作指向侧边栏浏览器。第一步浏览器上下文写着 `localhost` 页面要“在用户能看到的浏览器 —— 也就是这个窗格 —— 里验证”，应用内浏览器技能要求优先使用该窗格而非外部 Chrome/CDP，`web_fetch` 的升级路径把任务留在窗格内，而 `preview_navigate` 自称适用于“本地开发服务器 URL”。`preview_status` 又加重了这一点：只要会话旁打开了任何页面，`nextStep` 就让模型去驱动那个页面，从不区分用户想看的站点与正在开发的应用。结果是窗格被当成开发浏览器使用 —— 重新构建的页面被重载进用户正在阅读的窗格，而为开发而存在的 Chrome DevTools 只有在什么都没打开时才被提及。

## Decision

两个可见浏览器按任务分工，每一处路由浏览器工作的说明都写明这个分工：

- 打开、访问或阅读网站的请求属于侧边栏浏览器：`preview_navigate` 打开窗格，`preview_*` 工具驱动它直到任务结束。
- 开发与调试属于 Chrome DevTools 浏览器（`mcp__chrome_devtools__*`）：`localhost` 或 `127.0.0.1` 页面，以及任何改变页面背后代码的任务。窗格只有在 Chrome DevTools 不可用时才服务于这类页面，且绝不作为检查模型自己工作结果的方式。
- `nextStep` 在同一句话里既指明分工也指明浏览器：`nextStepFor` 在页面已打开与页面可打开两个分支中都报告站点访问用窗格、开发用 Chrome DevTools，并在组合挂载了工具服务器时写出已注册的 `toolPrefix`。
- 分工在执行导航的地方强制执行，而不只是写出来。只要 Host 的 Chrome DevTools 工具已注册，且用户最新的一条消息没有点名该地址，`preview_navigate` 就拒绝本机提供的地址 —— `localhost`、其子域名、`[::1]`、`0.0.0.0` 以及任何回环 IPv4 地址 —— 以 `BROWSER_DEVELOPMENT_TARGET` 失败，并指明应当改用的 `new_page` 调用。用户在自己的请求里点名该地址、其主机名或其端口，它就留在窗格，要求查看本机页面的用户所得到的与之前完全一样。没有 Chrome DevTools 工具的部署仍把窗格当作唯一的可见浏览器，那里永远不触发该拒绝。
- 技能的目录描述承载同一分工，因此即使某个会话从不打开页面，只要目录列出 `in-app-browser` 就能读到这条规则。

## Alternatives considered

- **只保留窗格一个浏览器并改进它对 DevTools 的访问。** 窗格是 `webview` 客体；它自己的 DevTools 打开在模型无法读取的窗口里，而一次重载就会替换用户选择观看的页面。
- **仅按页面地址路由** —— 把任何 `localhost` 页面都当作开发。这已很接近，但用户要求查看自己正在运行的站点时会被拉出他正在观看的窗格，因此请求的意图仍是首要信号，地址只用来判断歧义情形。
- **保持 `nextStep` 不变，只在技能里写明分工。** 技能是按需加载的，而第一步上下文与工具描述不是，恰恰是后者赢得了执行。
- **只用文字强制执行分工。** 提示文本只是建议：模型读了它却仍然导航窗格，harness 没有任何可以拒绝的动作，而用户正在观看的页面已经被替换。拒绝只在说明未能阻止的那种情形里多花一个往返。

## Consequences

窗格不再是页面检查的默认选择，开发任务因此会打开 Host 调试端口上的可见 Chrome。没有挂载 Chrome DevTools 服务器的组合就没有开发浏览器：说明按前缀写出这些工具，好让 `tool_search` 找到它们；而无法注册它们的模型会如实报告，而不是悄悄在窗格的浏览器里开发。被拒绝的一次导航在记录里多出一条工具结果，且只发生在用户请求没有点名该页面的情况下，因此用户要求查看的东西绝不会被挡在窗格之外。页面打开期间，第一步上下文每轮多出一句话。
