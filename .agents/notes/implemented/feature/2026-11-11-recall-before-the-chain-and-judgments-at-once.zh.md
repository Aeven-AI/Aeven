# Agent Note：召回在 pre-step 链之前开始，后续轮次的两次判定同时进行

Status: implemented

[English](2026-11-11-recall-before-the-chain-and-judgments-at-once.md) | 中文

## 问题

在桌面端，一个轮次的第一个模型请求在轮次开始后中位 4.2 秒、最长 17 秒才发出（2026-11-11 测量了 110 个轮次），几乎全部花在轮次开始时的召回上。召回要等后面所有 `agent/pre-step` 监听器都完成后才开始。在后续的个人话题轮次中，[最近记忆召回](2026-10-23-recall-what-the-person-is-living-through.zh.md)会在第一次相关性判定之后再进行第二次，因此该轮次要依次等待两次模型往返。

## 决策

- `@aeven/memory-context` 在一个前置到 `agent/pre-step` 链开头的监听器中，从已认领的输入开始召回和画像读取，因此这项工作也与召回监听器之前运行的 Host 监听器重叠，例如 `@aeven/host-account-integrations` 的连接器登录、工作区同步和检查点落盘。召回监听器在链中的位置不变并接手已开始的工作，因此它追加的消息顺序不变；链在到达它之前结束时会取消这项工作。当链的决定携带相同的请求文本时，轮次使用这项工作。当决定携带不同的请求或拒绝该步骤时，提前的工作被取消，召回像以前一样针对决定的请求运行。
- `MemosMemory` 让后续轮次不带此人最近记忆的判定与带有它们的判定同时进行。只有当第一次判定发现此人在分享且第二次未降级时才采用带有它们的判定，这正是顺序执行时的规则，因此召回的记忆相同，而轮次只需等待较慢的那次调用，而不是两次之和。
- 相关性判定在 `relevanceHedgeMs`（2000 毫秒）后仍未答复时，会用相同提示词再发送一次；在此之前失败或答复不可用的请求会立即重发；第一个可用答复胜出，另一个请求被取消。桌面端路由上的小型 JSON 调用在 14 天内测得第 95 百分位为 1.6 秒，因此只有少数百分比的判定会发出第二个请求。
- 即使检索用掉了召回预算的大部分，判定也至少获得 `relevanceMinMs`（3500 毫秒，以 `relevanceTimeoutMs` 为上限），因此召回最多可在 `recallTimeoutMs` 之后这么久才结束。`ctx.memory` 的召回请求说明了这一上限。
- 人物画像刷新是同一路由上的一次长蒸馏调用，它在该所有者的轮次开始召回结束之后才开始，而不是与轮次所等待的判定并行。
- 每次判定都通过 `MemoryCore.logApiCall` 向所有者的 MemOS `api_logs` 追加一行 `recall_judgment`：候选数量、输入大小、检索时间、窗口、结果（`judged`、`unusable`、`failed`、`timeout`、`no-time`），以及每个请求的开始时间、耗时和状态。这些行不含记忆文本。
- 在托管 Host 上，共享嵌入工作线程会先处理等待中的查询嵌入，再处理排队的文档批次。

## 考虑过的替代方案

- **始终把最近记忆放进同一次判定的候选中**：不增加模型调用，但工作轮次会看到以前从未看到的个人经历，从而改变召回保留的内容。
- **缩短判定或召回的时限**：更快，但较慢的判定会退回到未经判定的结果，降低召回质量。
- **嵌入优先级与批处理**：2026-11-11 测得一个轮次的查询需 15 毫秒，排在完整文档批次之后约 0.5 秒，因此不会缩短桌面端的等待。

## 后果

2026-11-16，在 250 个桌面召回轮次中，有 143 个只交付了一到两条记忆，中位等待 5.7 秒，多数落在 5 秒召回截止时间上，而经过判定的召回在 3.5 秒内完成：这正是判定超时后退回未判定结果的模式。第二个请求与最短窗口旨在让这些轮次得到经过判定的结果；`recall_judgment` 行用来衡量是否做到，并作为之后调整预算的依据。检索较慢时，召回最多可在预算之外再等待 `relevanceMinMs`。

拥有最近个人记忆的后续轮次会比以前多发送一次相关性判定，这是一次计入账户的小型 Flash 调用。针对被链改写的请求而提前开始的召回工作会被取消，而不会交付。
