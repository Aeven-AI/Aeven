# Agent Note: Slack is a plugin over Slack's MCP server, one workspace per row

Status: implemented

English | [中文](2026-10-07-slack-connector.zh.md)

## Problem

Settings named Slack in its connector catalogue and sent the reader to the custom MCP form with a provider-issued token, because no `slack` member existed in `ConnectorProvider`, no skill shipped, and nothing in the product knew what a Slack workspace was. The useful Slack operation is not reading one channel but finding the decision, the file, or the person anywhere in a workspace, and that operation needs a user token: [`search.messages`](https://docs.slack.dev/reference/methods/search.messages) lists `search:read` under **User token** only, and the [Real-Time Search API](https://docs.slack.dev/apis/web-api/real-time-search-api) that replaces it needs an `action_token` on every bot-token call, which exists only inside a Slack interaction. Any design whose credential is a bot token therefore cannot do the one thing worth connecting Slack for.

The rest of the connector was not new work. Slack serves the surface itself: the [Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server/) speaks JSON-RPC 2.0 over Streamable HTTP at `https://mcp.slack.com/mcp` and authenticates with an ordinary Slack user token. Every harness that already integrates Slack does it the same way, and the shape is public: OpenAI's plugin catalogue carried Slack as a [`.mcp.json`](https://github.com/openai/plugins/blob/main/plugins/slack/.mcp.json) naming the endpoint, `type: "http"`, and a public `oauth.client_id`. This repository already lifts that catalogue's connector assets for its icons. Claude Code, Codex, Cursor, and Pi connect the same endpoint with a public client and no secret; Slack's [PKCE documentation](https://docs.slack.dev/authentication/using-pkce/) states that a desktop redirect exchanges the code with `code_verifier` and **without** `client_secret`, and that a refresh needs no secret either.

## Decision

`slack` is a `ConnectorProvider` whose connector is a descriptor: the endpoint `https://mcp.slack.com/mcp`, the deployment's Slack application client id, one row per workspace, one icon, one description in two languages, and one skill bundle. Nothing was added to the Aeven API, no proxy mediates a call, and no bot exists. The deployment configures `slackClientId` — public, and the only Slack value it holds — plus `slackCallbackPort`, `slackDirectMessages`, `maxSlackWorkspaces`, and `slackVerifyIntervalMs`.

Aeven registers its own Slack application rather than borrowing a client id from another harness. Slack ties rate limits, logging, and workspace-administrator approval to the application behind the client, so another product's id would make this connector indistinguishable from that product in the places a workspace administrator decides whether to allow it. The reference implementations are evidence of the shape, not a credential to reuse.

The login runs on this Host, in `packages/host/account-integrations/src/slack-login.ts`. `authorize('slack')` starts it: mint an S256 verifier and challenge, bind `127.0.0.1:<slackCallbackPort>`, build `https://slack.com/oauth/v2_user/authorize` with the workspace scopes, return that URL for Settings to open, and settle when Slack redirects back to the callback with a state the login minted. The exchange posts to `https://slack.com/api/oauth.v2.user.access` with `code_verifier` and no client secret, and Slack's own `auth.test` names the workspace and the account the row records. Every failure carries a fixed reason — `port`, `state`, `denied`, `approval`, `exchange`, `response`, `unauthorized`, `timeout`, `cancelled` — and only `unauthorized` and a spent consent count as the consent being gone, which is what turns a row into one the reader has to connect again.

The callback port is the registered redirect `http://127.0.0.1:<slackCallbackPort>/callback`, which Slack matches exactly, so a port already in use fails with that fact rather than drifting to a port the application did not register. The token bundle — access token, refresh token, expiry, granted scopes — is that connector's own `grant` record in the account's credential provider, refreshed on this Host before use, and it never appears in the row, a Remote response, a tool schema, a model request, or a log. Disconnecting revokes the token at Slack.

The unit of connection is one workspace, as [Discord's unit is one guild](../../implemented/architecture/2026-10-07-discord-connector-guilds.md): one connector row, one connector id derived from the Aeven account and the Slack team id so tool names survive reconnecting, one `mcp__account_<id>__` namespace, and one enable, disable, and remove switch. `maxSlackWorkspaces` bounds the rows one account may hold. The row mounts through the existing remote Streamable HTTP path with the stored user token as its bearer — the same path a GitHub row uses — and a workspace is stored only after Slack's MCP server accepts that token, so a workspace whose administrator has not approved the application is refused instead of saved broken.

Slack owns the served tool names, so `isSlackReadTool` classifies by the name's own verbs and answers false for anything it does not recognize: searching, reading, listing, getting, fetching, downloading, looking up, finding, and resolving run directly unless another word in the name is itself a write — which is what keeps `slack_get_file_upload_url`, the first half of an upload, behind the approval gate with its second half. Any other name asks for approval, naming itself, and the copy says the message will appear as the reader rather than as a labelled bot.

Slack's server renders what those tools return, so message text arrives as Slack renders it, without the nonce fencing `native/discord-mcp` applies to Discord's own records; the preset's `slack` skill carries that instruction instead. The skill also names how to pick a connection when several workspaces are connected, that search runs under the reader's own permissions and a per-user rate limit, and that a posted message appears as them. Settings gains the Slack row with a brand icon from Simple Icons, an English and a Chinese description, the sign-in action, the reconnect state after a revoked token or an expired refresh, and the administrator-approval state.

## Alternatives considered

**No code at all: leave the catalogue entry pointing at the custom MCP form.** The endpoint half of this decision is already the plugin the catalogue asked the reader to assemble by hand, so the alternative was one line of copy rather than an implementation. Rejected because it makes every reader a Slack app developer, and because nothing in the product can then know which workspace a row belongs to, show whether Slack still accepts it, or revoke it on removal.

**A vendored bot connector under `native/`, as Discord has.** One Aeven-owned Slack app, a bot token, one row per workspace, a curated surface, and — unlike Discord — no proxy needed, since Slack's server enforces permissions itself. Rejected because it cannot search: `search.messages` is user-token-only and the Real-Time Search API needs an `action_token` from a Slack interaction, so a bot surface reads only the channels it was invited to and finds nothing on demand. Kept as the deferred route if a posting identity separate from the reader is ever wanted.

**Brokering the login through the Aeven API with a client secret, as Google, Microsoft, GitHub, and Discord do.** This was the first version of this proposal, and it is the right shape when the deployment holds a secret that must not reach a machine it does not own. Rejected because there is no such secret here: Slack's PKCE client is public, the token being protected belongs to the reader who consented on their own machine, and the Host already stores a reader's own bearer for its custom MCP connections. The broker would add API routes, environment variables, and a registered server callback to buy back exactly what it costs, and its one real advantage — refresh tokens that do not expire after 30 idle days — does not justify a subsystem for the first release.

**A third-party Slack MCP server, kept as a dependency.** [`korotovsky/slack-mcp-server`](https://github.com/korotovsky/slack-mcp-server) and its relatives serve a wider surface, and the maintained ones authenticate with the browser session cookies (`xoxc`/`xoxd`) of the reader's own Slack client. Rejected: that path treats a person's session as a client, which Slack's terms do not allow, and it puts a long-lived session credential in a deployment's hands.

**A bot token with the Real-Time Search API instead of a user token.** Rejected: every bot-token call to `assistant.search.context` requires an `action_token` sent as it was received in a message event, and a harness that is not answering a Slack interaction cannot produce one.

**Dynamic client registration, the usual MCP OAuth path.** Slack does not support dynamic client registration and requires MCP clients to be backed by a registered app with a fixed app id. Rejected: the Aeven application is the client, and its identity is deployment configuration, not a discovery result.

**Running the Slack tools on the API.** Discord needs an API-side proxy because the bot token must not leave the API and Discord has no way to act as one user. Slack's server already receives a per-user token and enforces that user's permissions, so there is nothing for a proxy to enforce. Rejected: it would move the tool surface into another codebase for no security gain.

**One row for Slack with a workspace argument on every tool.** Fewer rows, one namespace for every workspace. Rejected on the same grounds as Discord's: one enable switch for every workspace, ids a model can carry across a boundary it cannot verify, and no structural answer to reading the wrong workspace.

## Consequences

The connector bought a workspace-shaped row, a permission-aware surface, and no deployment secret to protect: a deployment needs a Slack application with PKCE enabled and the callback registered, and nothing else. It gave up three things in exchange. Enabling PKCE is a one-way setting on the application, so the client can never return to a confidential one without Slack support. Slack expires a PKCE refresh token after 30 days without use, so a workspace used a few times a year has to be connected again. And the redirect is an exact match on a configured port, which is a narrower tolerance than a scan would give: a busy port is a failed connection that names the port.

Acting as the reader is the deliberate behaviour and the sharpest consequence: a message sent through this connector comes from the person, not from a bot with Aeven's name on it, and search returns exactly what that person is allowed to see. Direct-message search and history are the most sensitive part of the surface, so they are absent from the default request and from the application's registered scopes; `slackDirectMessages` adds them at consent time, and a workspace connected before it was turned on has to be connected again to gain them.

Slack gates the server rather than the code: only marketplace-published or internal applications may use MCP, and a workspace administrator can refuse the integration, so the first connection of a workspace can need an administrator. A refusal from the consent screen or the exchange reports as the administrator-approval state; a token Slack has stopped accepting reports as a row that has to be connected again. A workspace left idle past its refresh window is discovered the same way, by the probe that re-asks Slack at most once per `slackVerifyIntervalMs`.

The tool surface belongs to Slack and can move under us. A renamed tool or a new one reaches the approval gate as an unrecognized name, which asks rather than posting unreviewed; the read classification and the skill are written against the surface Slack publishes, not against an enumeration taken from a live workspace. Results are not fenced by us, because Slack renders them, so the skill tells the model to treat message text as other people's words and nothing mechanical enforces that the way `native/discord-mcp` does for Discord.

## Testing

`packages/host/account-integrations/tests/slack-login.spec.ts` drives the login against a fixture Slack: the consent URL's challenge matching the verifier it sends, the exchange and the refresh carrying no `client_secret`, the workspace read, a mismatched state, a refused consent, an administrator refusal, a spent consent, an exchange that answers without JSON or without a token, a workspace Slack does not name, a busy callback port, a timeout, cancellation during the exchange, a revocation, and the token probe. `slack.spec.ts` pins the connector id derivation, the redirect, the scope sets, and the read/write classification. Both `slack.ts` and `slack-login.ts` are at 100% statements, branches, and functions.

A connector skill is part of the preset, so it reaches every session request: the keyless recorded-session snapshot that enumerates those skills is re-recorded with a key in the same change that adds one.

No test connects to a real Slack workspace, and none can: a workspace has to approve the application first. The served tool names, the scopes each of them needs, and the exact errors a workspace that has not approved the application returns are therefore the one part of this decision that a live pass still has to confirm; the classification's asking default is what keeps an unconfirmed name safe until then.

## Deferred

A bot-token surface for posting as a labelled Aeven application; a listener for Slack events, which is what would make the connector proactive rather than read-on-demand; org-wide Enterprise Grid tokens with `team_id` on every call; and the API-brokered confidential client if the 30-day refresh expiry turns out to be the failure readers hit.
