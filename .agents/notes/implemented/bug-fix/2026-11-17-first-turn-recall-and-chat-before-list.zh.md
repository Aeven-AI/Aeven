# Agent Note: 首个轮次的记忆召回，以及等待 Session 列表的聊天

Status: implemented

[English](2026-11-17-first-turn-recall-and-chat-before-list.md) | 中文

## 问题

一个 Desktop home 的会话日志与 MemOS `api_logs` 审计行显示，Host 启动后的首个轮次在发出模型请求之前等待了 5.6 s 和 7.3 s，两次都以“召回未在 5000 ms 内完成”的提示结束，因此回复在没有召回记忆的情况下运行。在 Desktop 上，账户的 MemOS 核心、本地嵌入模型、轨迹向量索引以及 person 记忆列表都在这第一次召回内部加载：针对同一个 1 GB 数据库的副本，一个新进程打开核心用了 0.4 s，首次检索用了 2.6 s（之后的检索为 40 ms），列表用了 0.7 s，而在 Host 内部仅模型加载就用了 1.5–4.8 s。托管组合已经在一个启动时加载模型的工作线程中运行嵌入；Desktop 使用的是进程内提供方。另外，窗口自身的加载计时显示打开的聊天在 1.24 s 绘制：门控在启动前等待 Aeven 的 `/get-profile` 153 ms，Session 列表在 704 ms 才被请求，而恢复的聊天的历史（一次 4 ms 的读取）要等 1.76 MB 的列表到达并应用之后才被请求。

## 决策

- **Desktop 与 Web 在工作线程中运行嵌入**（`avn-bundle-web-app`）：`memory-memos` 设置 `embeddingExecution: worker`，因此模型在提供方启动时加载，加载与嵌入批次都不占用 Host 的事件循环。这样的 Host 归一个账户所有，因此 `embeddingQueuePerAccount` 等于 `embeddingQueueTotal`；进程内提供方原本没有可触及的队列上限。
- **账户的记忆在登录时加载**（`avn-memory-memos`）：启用 `warmOnSignIn` 时，提供方响应 `credentials/session-updated`，打开该账户的核心并调用 `MemosMemory.prime`，它以固定查询运行显式记忆搜索所用的检索、丢弃命中，并列出 person 记忆。它只加载数据库已存在的账户，每次运行一次，且不调用模型。该字段默认为 `false`；托管补丁重述其 `memory-memos` 配置时不含它，因为服务众多账户的 Host 会把每个已登录账户的向量索引都留在内存中。
- **门控从保留的 profile 恢复**（`avn-client-ui-auth-aeven`）：当浏览器持有带已选名称的保留 profile 以及同一账户未过期的 bearer 时，`restoreSession` 立即采用该 profile，并在启动的同时读取 `/get-profile`。应答会替换保留的 profile；拒绝则通过 `leaveForSignIn` 结束会话。待处理的语言选择、Host 的拒绝，或缺失、过期的 bearer 仍走等待路径。
- **恢复的选择与列表拉取同时打开**（`avn-api-session-controller`）：持久化的选择单元保留所选 Session 的显示标题，在首个列表基线尚未到达时，投影把该选择发布为 `current`，并用保留的标题构造其行。因此它的窗口在连接建立时打开，而不是在列表之后。空白 Session 不保留标题，等待携带其 `blank` 位的列表；基线未列出的选择照旧被屏蔽。

## 考虑过的替代方案

**在插件挂载时请求 Session 列表。** 门控不再等待之后，列表在首批挂载时读取之后约 200 ms 开始。更早的拉取在事件连接建立时仍在进行，因此要么其间新增的 Session 在下一次拉取之前被漏掉，要么每次启动都执行第二次拉取：约 300 ms 的 Host 工作和第二次 1.76 MB 解析，换来的行已不再推迟聊天。未采用。

**缩短或跳过相关性判断。** 在已预热的 Host 上，一个轮次的召回是 0.35–0.9 s 的检索加上会话路由上一次 1.0–1.6 s 的判断。该判断决定哪些候选到达模型，去掉它是用召回精度换时间。未改动。

**在 Host 启动时打开找到的每个账户数据库。** 账户目录名是账户 id 的哈希，因此 Host 无法从目录得出所有者，而一个 home 可能保存着无人登录的账户的数据库。登录指明了即将聊天的账户。

## 影响

启动后的首个轮次面对的是已加载的核心、模型与索引，与之后任何轮次一样。每次 Host 启动为每个登录的账户增加一条 `memos_search` 审计行。在开发版 Desktop 窗口中，打开的聊天文本在 680 ms 而不是 1,236 ms 绘制，其历史在 626 ms 而不是 1,192 ms 被请求，Session 列表在 361 ms 而不是 704 ms 被请求。在另一台设备上更改的 profile 在后台读取应答时到达恢复的页面，而不是在启动之前。其 Session 已在别处被移除的恢复选择会显示失败的窗口，直到列表基线到达并将其屏蔽。在上一轮次 10 分钟或更久之后开始的轮次，日志中仍显示其请求之前有 5–8 s；这些加载无法解释该延迟，问题仍未解决。
