# Agent Note: Overlay scrollbars return the scrollport's gutter

Status: implemented

English | [中文](2026-09-13-overlay-scrollbars-return-the-gutter.zh.md)

## Problem

Every scrolling box in the web client lost 8px of its own width to its scrollbar, and the transcript lost it where it shows most. `ConversationRoot`'s scrollport reserved the band unconditionally with `scrollbar-gutter: stable`, the message column centred inside the narrower box, and the composer seat and `.viewChrome` bought the band back with `--dsh-scrollbar-width` so that the input card stayed on the column's axis. Measured in the running GUI before this change (chromium 151, macOS 26.5): `.scrollBody` reported `offsetWidth - clientWidth` = 8, `scrollbar-gutter: stable`, `scrollbar-width: auto`.

The band was a property of the skin, not of the palette. [Themed scrollbars and reserved gutter](2026-07-28-themed-scrollbars-and-reserved-gutter.md) split one skin across two rendering paths and gated them apart — the standard properties to the engines without `::-webkit-scrollbar`, the pseudo-elements to the engines with it — because a non-`auto` `scrollbar-color` or `scrollbar-width` makes chromium and Safari discard the pseudo-element rules for that element, `::-webkit-scrollbar-thumb:hover` included. That split also decided the layout, which was not its stated purpose: a `::-webkit-scrollbar` width is what makes chromium draw the bar in a gutter rather than floating it over the content, so the engines on the pseudo-element path (chromium, Safari) each paid 8px per scrolling box while the engines on the standard path (Firefox) did not. Only one of the two paths could ever give the width back, and it was not the one most readers run. The split was also the reason the sidebar's list needed the reservation in the first place.

## Decision

`packages/client/ui-theme/src/styles/scrollbar.css` declares `scrollbar-width: thin` on `body *` unconditionally, and every engine that implements it takes that path. The pair's other half is gone: the iOS/Safari 14.5 baseline that [every client stylesheet is held to](../process/2026-09-16-css-baseline-pairs-and-breakpoint-scope.md) cannot parse `scrollbar-color`, which arrives in Safari 18.2, so the sheet states none and the `::-webkit-scrollbar-thumb` skin is the only themed path on WebKit. The selector is `body *` rather than `body, body *` because the root element draws no scrollbar and `scrollbar-width` is not inherited: a declaration on `body` is one no element reads, while `body *` matches every scrolling element in the client. That property is the only one that can ask for a bar which does not take a gutter: measured on the running app in chromium 151, one scroller stated the pseudo-element width first and then `scrollbar-width: thin` — with a `scrollbar-color` this sheet stated at the time — instead, and `offsetWidth - clientWidth` went 8 → 0 while the themed thumb kept painting at the content's inline edge (read out of a screenshot as an 11 × 40 device-pixel band at the scrollport's right edge, with 0 layout width), and `scrollbar-gutter: stable` reserved nothing for the overlay bar that replaced it. `thin` rather than the initial `auto` keeps the bar near the 8px the pseudo-element path drew, and it is the narrower of the two reservations on the engines that still reserve one.

The pseudo-element skin is not deleted; it moves inside `@supports not (scrollbar-width: thin)`, which is true exactly for the engines that cannot honor the standard properties (caniuse records the first supporting release as chromium 121 and Safari 26.2, with 26.0 and 26.1 partial). Their reach is then stated by the at-rule rather than left to the suppression above: an ungated copy would be discarded by every engine that parses the property — the engines the gate is keeping it away from — and would read as dead CSS at review time. The two facts agree anyway, because the suppression is keyed on the same non-`auto` values the gate tests for, which is the property that makes one gate sufficient.

The hover tokens render only on that fallback path. `--dsw-alias-scrollbar-hover-l1`/`-l2` and the pair-rebinding contract every elevated surface follows exist because `::-webkit-scrollbar-thumb:hover` can name a second colour; `scrollbar-color` states one colour and the engine derives its own hover treatment, so the standard path has no counterpart to render. The pair stays bound and rebindable, and the sheet contract that every scrolling elevated surface rebinds a complete pair stays green, because the fallback path still reads both halves — a surface that drops its rebind is now wrong on those engines and correct on the rest.

`.no-scrollbar` keeps both of its halves, outside the gate. `scrollbar-width: none` serves the engines that parse the property, and the pseudo-element `display: none` serves the engines that do not — exactly the engines the fallback skin is for — so neither half needs to be gated away from the other. The vendored sheet (`ui-auth-aeven/src/vendor/aeven-auth.css`) states the same class for its own consumers and loads app-wide, so the two spellings stay equal.

`--dsh-scrollbar-width` is deleted along with its two readers. A scrollport that reserves a gutter cannot hand the seat a number for it any more: the reservation is symmetric, `scrollbar-gutter: stable both-edges`, so the content column's axis is the scrollport box's own axis and the seat — which sits outside that box, in Chat and under a view's composer overlay alike — centres on the same axis with no compensation. Measured against a classic 15px bar, `stable` leaves a centred child 7.5px off the box's centre and `both-edges` leaves it exactly on it; with an overlay bar both reserve 0. The overlay-view branch keeps `scrollbar-gutter: auto`, since that box never scrolls and a symmetric reservation there would narrow the view's content twice over.

## Alternatives considered

**Keep the fixed 8px compensation and give the standard properties only to the engines that lack the pseudo-element path.** Rejected: that is the shipped shape, and it is what costs the band. It also cannot be fixed by any value of the token, because the band is 0 on the engines this change is about and an engine value no sheet knows on the engines that still reserve one.

**Reserve the end edge only and publish the measured band at runtime to feed the compensation.** Rejected: a measured custom property is a new contract — when it publishes, on which element, and what the seat renders before first paint — carried to preserve an alignment CSS can express by symmetry, and it would keep reserving the 8px this change exists to give back.

**Symmetric reservation plus the existing 8px compensation.** Rejected: the two would double-count. `both-edges` already puts the column on the box's axis, so the padding would move the card off it by half the band.

**Declare the standard properties and leave the pseudo-element rules ungated.** Rejected: the skin's reach would then depend on each engine's suppression behavior instead of on one testable fact, and an engine that parses the standard properties while still honoring the pseudo-elements would draw the gutter this change removes. The gate makes which engines own the skin a stated fact.

**Delete the pseudo-element path and let the fallback engines render the UA bar.** Rejected: `.no-scrollbar` would stop hiding bars on exactly those engines, so the sidebar session list's rows would run under a UA bar — the symptom the [2026-07-28 decision](2026-07-28-themed-scrollbars-and-reserved-gutter.md) exists for — and the hover tokens would lose their last consumer, which would pull the pair-rebinding contract out of every elevated surface in the client.

**Leave the band and document it.** Rejected: it is 8px off every scrolling box, and the transcript and its composer are the surfaces where a reader sees it — the column and the input card sat 4px left of the box's centre together, which is what the compensation was buying.

## Consequences

- No scrolling box reserves width for its bar on an engine that implements the standard properties. In the reported configuration the transcript scroller goes from 1112px to 1120px of usable width inside a 1400px viewport, its column and the composer card both re-centre from 836 to 840, and the seat needs no padding to sit on that axis.
- The bar is still drawn, still themed, and still hover-thickened by the engine; what changed is that it is painted over the content instead of beside it. A surface that wants no bar at all still says `.no-scrollbar`, now through the standard property on chromium as well as Firefox, which is also what makes the sidebar's list and the composer's overlays consistent across engines.
- `scrollbar-width: thin` is a request, not a measurement: an engine that draws a classic bar still takes that bar's width out of the scrolling box — just a narrower one than the `auto` bar — and the symmetric reservation is what keeps the composer on the transcript's axis there. Only the engines that paint the bar as an overlay give the whole band back, and on macOS that overlay is what chromium draws for the initial scrollbar styling too: the 8px was the `::-webkit-scrollbar` skin's doing, not the platform's.
- WebKit keeps a space-consuming themed bar until Safari 26.2, where the standard properties arrive; the symmetric reservation keeps the composer on the transcript's axis there (WebKit implements `scrollbar-gutter` from Safari 18.2). An engine that implements neither the standard properties nor `scrollbar-gutter` — Safari before 18.2 — centres the transcript up to half the fallback bar's width (4px) off the composer, because the compensation that used to cover it is gone. Accepted rather than carried: the only value the token could hold is the one that is wrong everywhere else.
- Sheet contracts move with the decision: `scrollbar-styles.client.spec.ts` now pins the standard property outside the gate while asserting the baseline-unparsed half absent, the skin and every read of the hover indirection inside it, and the opt-out's two halves outside; `scroll-surface-styles.client.spec.ts` pins the symmetric reservation and the absence of a seat or view-chrome compensation.

## Testing

`packages/client/ui-theme/tests/scrollbar-styles.client.spec.ts` reads the sheet as text and pins the split by source offset, because its rule parser flattens through at-rules: deleting the gate or moving a declaration across it leaves every other assertion in that file green. It also keeps the token-consumer, pair-rebinding, and elevated-surface checks that the [2026-07-28 decision](2026-07-28-themed-scrollbars-and-reserved-gutter.md) introduced. `packages/client/ui-conversation/tests/scroll-surface-styles.client.spec.ts` pins the symmetric reservation, the seat's missing `padding-right`, and the view chrome's symmetric inset.

The layout claims were measured, not reasoned, because the two facts that decide them are engine behavior: the band (8 → 0 on one scroller, the same element, with a screenshot confirming the thumb paints at the inline edge and the pixel band is 11 × 40 device pixels wide at the scrollport's right edge), and the centring (a classic 15px bar beside `stable` and beside `stable both-edges`, 7.5px off the box's centre versus exactly on it, with an overlay bar at 0 for both).

`apps/web/tests/composer-tab-geometry.e2e.ts` covers the same geometry in a real browser and records it in `expected/composer-tab-geometry/geometry.expected.md`, which now reads `stable both-edges` and a 0px band. Its control — the assertion that the equal-rectangle checks can still fail — was rebuilt for this change: with no compensation left in the sheet, forcing the old one moves nothing, so the control instead states a layout-consuming bar on the Chat scrollport and drops its reservation.
