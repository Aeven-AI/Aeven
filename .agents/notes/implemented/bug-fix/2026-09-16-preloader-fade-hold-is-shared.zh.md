# Agent Note：首屏预加载器的淡出等待时长是共享值，因此只应有一处定义

Status: implemented

[English](2026-09-16-preloader-fade-hold-is-shared.md) | 中文

## 问题

首屏遮挡层播放两个淡出动画——`opacity` 与 `filter`——它们必须同时开始，而一个兜底定时器必须比两者都晚结束，这样即使 shell 始终没有报告就绪，应用仍会显示出来。这两个时长由两个文件掌控：内联样式表 `apps/web/src/preloader.css` 负责播放动画，`packages/client/web/src/preloader.ts` 中的 `FADE_DELAY_MS` 与 `FADE_MS` 供兜底定时器相加使用。

`00147ac181` 把样式表的等待时长与该常量一同设为 500 ms。`56264f4338` 之后只改了常量，改为 300 ms，且未在任何地方记录原因。于是两侧不再一致，而依据这些常量推导期望值的 `packages/client/web/tests/preloader-styles.client.spec.ts` 与线上样式表不符而失败。样式表本身声明它是权威：两个淡出都等待 500 ms，其注释也指明 `FADE_DELAY_MS` 是对该等待时长的重复表述。

## 决定

`FADE_DELAY_MS` 恢复为 500，与样式表及其注释一致。等待时长是播放该动画的一方所拥有的一个数值；TypeScript 常量为了兜底定时器重复它，因此必须与它一同修改。

可见的后果是「无信号」兜底窗口从 `300 + 400 + 100` ms 变为 `500 + 400 + 100` ms。该窗口只在 shell 始终未报告就绪时才会走完——正常路径由 shell 自身的信号触发显示——而现在它会等完样式表实际播放的淡出，而不是在淡出进行到 200 ms 时就撤掉遮挡。

## 考虑过的其他方案

**改为把样式表调到 300 ms。** 否决，因为这是无声的产品变更：它缩短了遮挡层设计时所依据的等待时长，而且是对所有用户缩短，而不只是兜底路径；引入 300 ms 的那次提交并未记录任何修改动画的意图。若确实想要更短的等待，那是一项设计决策，应在同一次改动中同时调整样式表、其注释与两个常量。

**在构建期由样式表推导该常量。** 可消除这类漂移，但样式表在客户端 bundle 生成之前就已内联进启动 HTML，而该常量由 shell 入口读取；为得到一个数值，推导必须与内联发生在同一构建步骤中。

**保留 300 ms 并放宽测试。** 该测试的存在意义就是把两侧绑定在一起；放宽它等于在淡出进行中就撤掉遮挡并宣称已通过验证。

## 后果

控件与动画重新一致，因此同时读取两者的测试无需被削弱即可通过。今后若要改动等待时长，必须同时修改 `FADE_DELAY_MS` 与样式表中的两条 `transition` 声明——这正是样式表的注释已经要求、本笔记也记录下来的做法。

## 测试

`packages/client/web/tests/preloader-styles.client.spec.ts` 把样式表的等待时长钉在 `FADE_DELAY_MS`、把时长钉在 `FADE_MS`，因此只改动样式表或只改动常量的情况都会导致该门禁失败。
