# Agent Note: 命名步骤不因 MFA 状态接口缺失而失败

Status: implemented

[English](2026-10-15-naming-step-outlives-a-missing-mfa-status-route.md) | 中文

## 问题

命名步骤保存读者姓名后，会请求 `GET /mfa/status`，以决定是否提供身份验证器设置。该第二次调用的任何失败都会置位该步骤的失败状态，因此对于不提供 `/mfa` 路由的 Aeven API——即尚未上线身份验证器工作的部署——已保存的姓名会得到「我无法保存这个名字。请重试」，并让读者停留在该步骤，因为命名关卡在步骤报告姓名之前不会启动应用。该失败还以按钮下方一行文字呈现，而此界面上的其他失败都以弹窗呈现。

## 决策

该步骤只报告姓名的结果。`/set-display-name` 被拒绝时抛出此界面的弹窗——携带 `modal.oops` 与 `name.saveFailed` 的 `show:modal` 事件——并让读者留在该步骤。API 无法回应的 `/mfa/status` 会直接启动应用，与未启用双重验证的账号完全一致：状态调用只在「提供设置引导」与「启动应用」之间选择，绝不在「成功」与「失败」之间选择。设置页面仍可开启该保护。

两次调用保持先后顺序而非并发，因此应用绝不会在姓名保存之前启动。

## 考虑过的替代方案

**保留按钮下方那行文字，只是不再由状态调用置位。** 这行文字与该界面不一致：登录与注册的失败都以弹窗报告，而按钮下方的一行会被读作字段错误。

**状态无法回应时提供设置引导。** 设置引导界面自身的设置调用会以同样方式失败，读者会被带到一个无法完成的界面；而引导文案已经承诺之后可在设置中开启该保护。

**要求状态接口必须可用，否则不启动。** 双重验证是可选功能，因此一次无法回应的状态调用不应成为应用的关卡。

## 后果

早于身份验证器工作的 API 现在可以正常为读者命名，状态调用期间的中断只会让该读者失去本次设置引导，而不会失去会话。该步骤不再区分「未开启保护」与「无法判断」：若账号已开启保护而状态接口不可达，读者会进入应用，并在下次登录时被要求提供第二个因素，这与开启保护之前就已存在的会话一致。

## 验证

`packages/client/ui-auth-aeven/tests/name-check.client.spec.tsx` 覆盖两条路径：姓名被拒绝时抛出弹窗并让读者留在该步骤；`/mfa/status` 返回 404 时以已保存的姓名启动应用。该界面另外在浏览器中以 1728x997 渲染，并用同样的三种回应驱动——姓名被拒绝、缺少状态接口、账号未开启保护——提示语经测量居中于姓名输入框之上。
