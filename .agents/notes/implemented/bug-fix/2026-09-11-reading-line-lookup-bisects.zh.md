# Agent Note: 阅读行查找改为二分，不再逐行扫描

Status: implemented

[English](2026-09-11-reading-line-lookup-bisects.md) | 中文

## 问题

`ChatView` 的 `turnAtLine` 通过 `document.elementsFromPoint` 命中测试阅读行来解析该行所属的 Turn，命中失败时回退为对每个带 `[data-chat-turn]` 的行做线性扫描：

```ts ignore-check
for (const row of list.querySelectorAll<HTMLElement>('[data-chat-turn]')) {
  if (row.getBoundingClientRect().top > line) break
  ...
}
```

每次迭代读取一个 rect，而在尚未 flush 的 transcript 上读取几何信息会强制整列重新布局。只要该行落在行与行之间的空隙或非滚动的列装饰上，命中测试就会失败——在真实会话中约占四分之一的情况——而 `syncActiveTurn` 每帧可能执行不止一次查找。该扫描还与**已渲染**的行数成线性关系，因此开销随读者已载入的历史增长：在 512 行、11,569 个节点的会话上实测，单次查找最多读取 781 行，滚动平均每帧产生 113.6 次几何读取，其中 105.7 次发生在该扫描内部。

这段代码还带着一个看似多余的兜底：扫描自身的 `break` 是隐藏行不至于出错的唯一原因，而代码里没有任何地方说明这一点。

## 决定

`turnAtLine` 保留命中测试，并将回退扫描替换为二分查找。

二分查找会前进到最近的*可见*行，而不是比较探测下标处的行。这不是防御性写法，而是必要条件：带 `[data-chat-turn]` 的行与隐藏行交错分布（在真实会话上实测跨越下标 2–497），而隐藏行不渲染盒子，因此返回全零 rect、其 `y` 为 0，排在所有可见行之前。只有可见行按文档位置有序——实测 457 个可见行零逆序，且 turn 编号递增。跳过零高度行即可恢复二分查找所需的单调谓词；首次探测越过最后一个可见行时，搜索以无匹配结束。

二分查找保持了原有契约：位于该行或其上方、且最靠下的可见行拥有该阅读行；`data-chat-turn` 不是安全整数的行返回 `null`；没有任何可见行的列表返回 `null`。它只读取约 10 行，且与窗口深度无关。

`usePrimitives` 的 `useAnchoredPosition` 补上了同类 hook 早已具备的同一性保护。`place` 被注册为捕获阶段的 `window` 滚动监听器，因此滚动产生的每一帧都会执行——包括滚动页面中其他元素、锚点位置完全未变的那些帧。它每次都返回新的 `{ left, top }`，为与屏幕上完全相同的坐标重新渲染面板。现在当位置未变化时保留原对象，与 `AttachmentRail` 既有的保护一致。

## 验证

回退逻辑是在一个真实的 512 行会话上替换的：重新实现新旧两套算法，并在阅读行可能取到的每个位置逐一比对——滚动容器跨 y 0–739，而阅读行位于 `top + min(96, 0.2 * height)`，故可达范围为 0–739。740 次比对，零处不一致；该范围内平均读取次数从 321.0 降至 20.0。仅有的分歧出现在 `line < 0`，此时没有任何行能覆盖该行，两种答案都无意义。

在同一个 11,569 节点的窗口上用真实 CDP 滚轮输入滚动，改动前后对比：每帧几何读取 113.6 → 14.0，每帧回退行读取 105.7 → 6.1，每次扫描读取行数 423 → 25，60 帧内 `turnAtLine` 读取次数 6,322 → 195。

在统一方法下（真实滚轮输入、相同距离与相同埋点）的端到端结果：应用从 3 帧超过 16.7 ms 且有 1 个 95 ms 长任务，变为 0 帧、0 长任务，`median 8.3 / p90 9.1 / p99 9.4 / worst 9.4` ms——与同样方法测得的 Aeven 参考客户端一致（`8.3 / 9.1 / 9.3 / 9.4`，0 与 0），而应用渲染 4,370 个节点、参考为 9,574 个。

`packages/client/ui-chat` 与 `packages/client/ui-primitives` 通过，共 900 个测试。客户端构建（`tsc -b tsconfig.client.json && tsdown`）退出码为 0。

## 备选方案

**照搬 `pagingAnchor` 已有的二分查找。** 它对 `[data-chat-flow] > [data-chat-flow-key]:not(:empty):not([hidden])` 做二分，该选择器已排除零高度行，所以其谓词在所读内容上单调。`turnAtLine` 的选择器无法排除它们：隐藏行同样带 `[data-chat-turn]`，它们正是 prepend 留下的 Tombstone，而该查找必须与线性扫描对"哪一行拥有该行"的判断保持一致。改用那个选择器会改变轨道所标记的 Turn。

**改为修好命中测试，采样多个 x 坐标。** 在真实 flow 上实测，采样左、中、右三点在同一位置全部落空：未命中的原因是行间空隙与列装饰，而不是两侧留白。没有任何 x 坐标能让单行命中测试在存在空隙的 flow 上变得可靠，因此回退路径本身必须足够便宜。

**保留扫描，并用围绕上次答案的窗口加以限制。** 平稳滚动时正确，但在跳转或 prepend 之后错误——那时答案的移动会超出任何窗口。而且它在每个滚动帧都保留与窗口大小成正比的开销，而二分查找稳定为约 10 次读取。

**改为对 transcript 做虚拟化。** 列的 CSS 已经为此预留（`ChatView.module.css`：flow item 是"虚拟化器天然的测量/挂载单元"）。虚拟化能降低节点绝对数量，但不会让本次查找变得正确或有界：虚拟窗口仍然需要定位拥有某一行的行，而扫描在窗口内依然是线性的。两项改动彼此独立，二分查找是让该查找在任意窗口大小下都保持廉价的前提。

**为 flow 行加上 `content-visibility: auto` 或 `contain: layout paint` 以降低滚动开销。** 将两者分别应用到真实 flow 行实测：一次分页突发中的长任务总量在未改动时为 241 ms，加 `content-visibility` 为 249 ms，加 containment 为 231 ms——变化不足 4%，落在运行间噪声之内。剩余开销并不在绘制。

## 后果

滚动开销不再随读者已载入的历史增长。无论窗口多深，该查找都是约 10 次几何读取，因此已载入 900 行的会话与只有 90 行的会话开销相同——这正是此前缺失的性质，也是长会话退化的原因。`syncActiveTurn` 每帧仍可能执行多次，但每次执行都是有界的，而不是与 transcript 成正比。

二分查找比较的是可见性而非位置，因此它依赖一个此前扫描未曾言明的事实：隐藏行高度为零，且与可见行交错分布。上文已记录该事实，而 `visible` 谓词是唯一承载它的地方。若将来出现"标记为 `hidden` 却渲染非零盒子"的行，或带有布局的隐藏行，该排序假设就会被破坏——届时回退路径会返回错误的 Turn 而不会抛错，所以这正是在阅读行标记出现异常时需要重新测量的假设。

另有一个约 90 ms 的卡顿仍然存在，本次改动未涉及。它按历史页触发而非按帧触发：`loadOlder` 拉取 `PAGE_MESSAGES = 50`（`packages/api/session-controller/src/client/sessions/session.ts`），在一次 React 提交中写入约 100 行、5,000 个节点，在窗口填充期间产生 3–4 个 85–102 ms 的长任务。React 仅占约 100 ms 任务中的约 38 ms，其余是插入子树的浏览器布局。可用的手段是分页大小或虚拟化，两者都属于设计改动而非局部修补。
