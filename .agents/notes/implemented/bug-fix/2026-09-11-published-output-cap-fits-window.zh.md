# Agent Note: 已发布的输出上限必须能装进模型的窗口

Status: implemented

[English](2026-09-11-published-output-cap-fits-window.md) | 中文

## 问题

`deepinfra` 路由上的每一轮都在任何 token 流出之前失败：`max_tokens: 974872 > 128000, which is the maximum allowed number of output tokens for claude-opus-5`，而同一个模型 id 在 `openrouter` 路由上正常。没有任何地方配置过 974,872。DeepInfra 的模型文档把 `metadata.max_tokens` 写成了 `metadata.context_length` 的副本——同时携带这两个字段的全部 131 个条目都如此——于是实时刷新从 `anthropic/claude-opus-5` 读出了 1,000,000 的输出能力。该路由未配置任何请求上限，而调用方不指定时 pi-ai 会回退到 `model.maxTokens`，并把它夹到 `contextWindow - estimatedPromptTokens - 4096`：对那次请求即 1,000,000 − 21,032 − 4,096 = 974,872。能容忍超大上限的提供方接受了它，因此只有 Anthropic 后端的 id 暴露了这个失败。`catalog.ts` 与 `config.ts` 的契约都声称目录的 `maxTokens` "只为模型定尺寸，到此为止"；pi-ai 却把它提升为请求的上限，因此从提供方文档到线上请求之间，没有任何环节把它与窗口作比较。

## 决定

输出上限必须小于它所受约束的窗口，每一个成为上限的值都会与窗口比对。

已发布的上限只有在小于该条目最终采用的窗口时才算数——该窗口是它自己发布的上下文窗口，否则是路由的 `defaultContextWindow`。其余情况一律读作"未发布上限"。

文档给不出可用上限时，先由模型自己的厂商作答，再轮到路由默认值。已发布 id 带有厂商前缀，当该前缀正是一个已安装提供方、且其余部分（大小写除外）正是该提供方某个模型的 id 时，就采用该条目的输出上限。这一匹配刻意收得很窄，因为网关的上限只有在网关正是服务该模型的厂商时才等于厂商的上限：DeepInfra 以 1,000,000 的窗口服务 `anthropic/claude-opus-5`，两份文档都未陈述任何输出上限，并且恰好如 `anthropic` 条目所述的 128,000 那样拒绝 128,001 个输出 token。若改为在整个目录中查找模型 id，就会得到某个恰好服务同名模型的提供方，而那些值彼此矛盾——目录对某个 DeepSeek id 陈述 384,000，而 DeepInfra 自身把它限制在 65,536；对 DeepInfra 以 131,072 服务的 `gpt-oss-120b`，目录陈述 40,960。

已物化的上限若高于其 `contextWindow`，则改由路由的 `defaultMaxTokens` 取代——无论是模型的能力，还是显式条目本会设置的请求默认值。相等仍然合法：`maxTokens` 等于其窗口，正是模型没有独立输出上限时的陈述方式——已安装的 pi-ai 目录在 1267 个同时携带两个字段的条目中有 197 个如此，手写设置也如此。无论如何，pi-ai 都会把它发出的每个上限夹到窗口之下，因此这两种替换都不会放宽任何请求。

## 验证

`packages/llm/llm-pi-ai` 的 334 个测试通过，其源码保持逐文件 100% 覆盖率。`tests/live-catalog.spec.ts` 固定了四种情形：由上下文长度复制而来的上限读作没有上限；更小的已发布上限被保留；条目未发布窗口时该上限按路由窗口判定；只有在文档给不出可用上限时厂商上限才作答。`tests/catalog.spec.ts` 固定了厂商查找——id 精确匹配、大小写除外，且对"厂商并非该提供方"与"该提供方并未提供此 id"都不作答——以及高于窗口时的替换和保留其值的"等于窗口"条目。

厂商层采用的每个值在采用之前都对照线上 API 校验过。把 DeepInfra 的线上文档交由 `resolveRouteModels` 解析，`anthropic/claude-opus-5` 得到 128,000（主机拒绝 128,001 并接受 128,000），`anthropic/claude-haiku-4-5` 得到 64,000，`google/gemini-*` 得到 65,536（主机的支持区间到此为止），`moonshotai/Kimi-K3` 得到 131,072，`google/gemma-4-*` 得到 32,768；该层覆盖的 17 个 id 中，每一项要么被主机以"目录值加一"拒绝，要么被接受，因此没有任何被采用的上限超出实际。该路由上其余 93 个模型保留 32,768 的路由默认值。

## 考虑过的替代方案

**在整个已安装目录中查找每个已发布 id。** 丢掉厂商前缀只按裸模型 id 匹配，能覆盖 DeepInfra 106 个 chat 模型中的 33 个，而收窄规则只覆盖 17 个；但它会取用某个恰好服务同名模型的提供方的值。在 DeepInfra 同时陈述自己 `max_output_tokens` 的地方，两者 11 次中有 8 次不一致，且方向各异：65,536 对目录的 384,000，512,000 对目录的 128,000。采用这些值会使今天可用的一些模型重新陷入本次报告的故障。

**在刷新时读取 DeepInfra 的逐模型 `max_output_tokens`。** `GET /models/<id>` 对许多开放权重模型确实陈述了真实上限——`DeepSeek-V4.1-Flash` 与 `GLM-5.3-Flash` 为 131,072，`gemma-4-31B-it-Ultra` 为 8,192——但对每个被代理的模型都是 `null`，包括全部七个 Anthropic 条目，而批量文档反而在该处陈述上下文窗口。读取它意味着每次刷新、每个模型一次请求，却仍然答不出最需要它的那些模型。

**在刷新时探测该上限。** 主机在拒绝超量请求时会给出该上限，上面那些被采用的值正是这样手工校验出来的。把它放进刷新，意味着每次挂载都为每个模型发送一次故意无效的请求；而主机对开放模型本就公布了参数区间——这是测试框架不应制造的流量。

**拒绝高于窗口的已声明上限。** 一条坏条目会让整条路由被拒绝，而同样的设置文件里本来就存在必须保持合法的"等于窗口"条目，因此这种拒绝会为一个 pi-ai 本就会夹成可用请求的值，把正常工作的路由一并停掉。

**在所有地方都把相等视作没有上限。** 这正是 DeepInfra 文档需要的行为，但若施加到目录与手写设置上，就会改写 197 个已安装条目以及每一个"等于窗口"的手写条目，砍掉今天可用的路由的长输出上限。只有当一份文档自称陈述输出上限时，其中的相等才意味着"没有上限"。

**在每条 pi-ai 路由上都物化一个请求上限。** 把每个未配置的请求都限制在路由默认值，会改变每条 pi-ai 路由所请求的内容，而这发生在一个并不掌握任何容量数据的层次，并且会掩盖同类缺陷而不是修正它。

**改 pi-ai 自身的回退。** `options?.maxTokens ?? model.maxTokens` 位于本仓库并不拥有的已安装依赖中；而那个已发布的值仍必须在到达任何消费者之前接受窗口的判定。

**完全丢弃 `openai-models` 布局中的 `metadata.max_tokens`。** 这能修好 DeepInfra，同时也会丢弃真正发布了该上限的提供方所给出的真实值，让每一条这样的路由都停在路由默认值上。

## 后果

`deepinfra` 路由的模型在已知厂商上限时请求该上限：六个 Anthropic 模型为 128,000，五个 Google 模型为 65,536，`claude-haiku-4-5` 为 64,000，`moonshotai/Kimi-K3` 为 131,072，其余 93 个保留 32,768 的路由默认值。对于文档与厂商都没有尺寸的模型，需要更多的部署自行陈述：路由上的 `defaultMaxTokens`，或 `models`／`modelOverrides` 条目上的 `maxTokens`，后者仍是请求默认值，并且仍会被夹到窗口之下。

厂商层信任厂商对网关所服务模型给出的上限。当网关以自己的更低上限服务同一模型并且陈述了该上限时，文档的值胜出，网关的上限绝不会被覆盖；当网关未作陈述而其自身上限更低时，被采用的值可能超出实际——这正是逐模型探测在该层覆盖的全部 17 个 id 上所检查的内容。厂商不在已安装目录中的模型保留路由默认值。

`maxTokens` 等于其窗口的已安装目录条目仍会发出整窗上限，这是上面相等决定的代价。只有会拒绝它的提供方才能推翻该声称，补救办法是在该路由上写一条 `modelOverrides` 上限。

该防护是天花板而非知识：一份发布了看似合理却偏低的错误上限的文档仍会被采信，而模型文档中没有任何内容能揭示提供方真实的输出上限更低。
