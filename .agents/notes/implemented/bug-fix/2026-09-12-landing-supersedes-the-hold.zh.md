# Agent Note: 落点会取代前插保持锚点

Status: implemented

[English](2026-09-12-landing-supersedes-the-hold.md) | 中文

## 问题

跳转到尚未加载的回合时，轨道导航会先落到目标，随后又滑走：目标行确实到达过，但几秒后读者已经回到会话末尾，目标行远在视口上方。在一个 52 回合的会话中，点击最上方的标记会让 `scrollTop` 从 8970 变为 0，随后又变为 78,956——也就是底部——把第 1 回合留在 −78,899 px 处。

对真实会话中每一次程序化偏移写入做插桩后，可以看到它的形态：

```
30120  184975  83295  86477  87215  87953  …  91643  92381
```

在落点写入 `0` 之后，偏移量按每次写入 **恒定 +738 px** 递增，直到抵达底部。每一步的最后写入者都是 `ResizeObserver.<anonymous>`——`ChatView` 的重排补偿——而不是落点路径本身。

该补偿解析锚点的方式是 `prependHoldRef.current ?? reflowAnchorRef.current`，而按设计"落定保持"的优先级高于推导出的锚点（`prepend-settle-hold` 笔记）。该保持锚点是依据补偿写入*之前*的窗口校准的，而它只被两件事清除：读者的滚动（滚动采样中的 `movedByReader`）与 `toBottom`。`landOnRow` 清除了 `reflowAnchorRef`，却让该保持锚点继续保持生效。

落点并不是前插，因此也没有任何东西会针对落点后的位置重新设置该保持锚点：它仍然保留跳转前持有的那一行以及跳转前的偏移。于是之后每一次重排都会把 `flowTop(heldRow) - heldTop` 重新应用到刚刚落定的偏移上——跳转到原点后，读者所在行位于顶部以下数百 px，因此每次回调都会再把读者往下推同样的距离。只有到底部时才会停止。

## 决定

`landOnRow` 在清除推导锚点的同一位置清除落定保持锚点：

- 在 `landOnRowRef.current` 中、落点写入的旁边设置 `prependHoldRef.current = null`，使一次落点同时让两个补偿锚点失效。
- 推导出的 `reflowAnchorRef` 仍在其后依据落点位置设置，因此常规重排路径依然会保持读者当前正在看的那一行。

这两个锚点的唯一用途就是在异步分页期间保持某一行。落点正是该分页目的达成之时，因此两者一并丢弃，而不是让其中一个残留到没有任何东西会重新设置它的状态。

## 考虑过的替代方案

**只在最终落定（`settle: true` 的调用）时清除保持锚点。** 跳转途中的落点仍会朝自己的目标做补偿，而这些补偿正是同一个缺陷：它们写入的是依据落点前窗口校准的偏移。跳转途中的落点还会为下一块重新设置 `anchorRef`，那才是真正带着读者前进的机制，因此保持锚点并不是让多块跳转保持正确的原因。

**让滚动采样在落点后重新推导保持锚点。** 采样依据"观测偏移与账本之间的差值"来推断归属；落点写入会把自己记入账本，因此采样看不到读者输入，也就无法区分落点与补偿。在那里重新推导还会在页面仍在落定的若干帧里与落点本身相互争夺。

**给补偿加上上限，使其无法越过落点偏移。** 这是只治症状：该补偿在方向上就是错的，而不仅仅是幅度过大；加上限只会留下残差，并在每次重排时累加。

**维持原状。** 跳转本身就是这个功能；一次"落下又丢失目标"的跳转比一次缓慢的跳转更糟，而且该故障与分页进来的页面大小成正比，因此恰好在最需要跳转的场景中最严重。

## 后果

轨道跳转会落下并停留在落点：在真实会话上实测，`scrollTop` 到达 0，此后观测到的最大偏移为 0，目标回合所在行位于滚动视口顶部以下 56 px，并在 2.5 秒后保持不变。修复前，同样的测量最终停在底部。

落点现在对两个补偿锚点都具有权威性，因此在跳转落定时仍在到达的页面不会在之后再移动读者。这正是"落点"应有的语义：读者要的是某一个特定回合，而他们所要的那一行就在阅读线上。

覆盖的路径包括：未加载回合的轨道跳转、跳转途中分块之后的同一次落定，以及来自内容搜索的精确事件导航——即 `landOnRow` 的所有调用方，而那里正是如今丢弃这两个锚点的唯一位置。
