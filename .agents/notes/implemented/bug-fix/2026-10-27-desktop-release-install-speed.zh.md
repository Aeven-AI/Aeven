# Agent Note: Desktop 版本安装速度与启动屏

Status: implemented

[English](2026-10-27-desktop-release-install-speed.md) | 中文

## 问题

在 0.3.15-alpha profile 之上启动 Windows 0.3.18-alpha 安装包后，启动屏停留约四分钟，并且全程显示“正在安装更新”，即使在完全没有 profile 的主目录中也是如此。根据时间戳，以及在报告问题的机器上（arm64 Windows，620 MB 分片中共 19,612 个存储文件）用内置 Node.js 对各阶段计时，结果如下：

| 阶段 | 耗时 |
| --- | --- |
| 对每个 seed 文件计算哈希（`verifySeedIntegrity`），每次启动都执行 | 6.7 秒 |
| 对 seed 与 profile 中的 311 个本地 tarball 计算哈希（`verifyDesktopCorePackageSet`），每次启动都在主进程中同步执行 | 1.5 秒 |
| 列出并验证分片 | 1.7 秒 |
| 把全部分片解包到 staging | 75 秒 |
| 把解包结果复制进持久存储 | 约 75 秒 |
| 在新的 staging profile 中执行 `pnpm install --offline` | 约 60 秒 |
| 健康检查与切换 | 约 7 秒 |

在 Windows 上，启动屏也不显示菜单条：preload 会在每个页面向 shell 请求菜单标签，而 shell 直到启动完成后才注册该处理器。

存储中几乎已经包含所有文件：pnpm 内容寻址路径由其字节的 SHA-512 命名，macOS seed 也会把每个重新签名的内容写到新的摘要路径，因此同一路径上的文件内容相同。解包步骤却仍把 620 MB 写了两遍。

## 决策

- `extractPnpmStoreArchives` 接收持久存储，并跳过存储中已有同路径、同大小文件的每个条目；大小比较会替换被中断写入截断的文件。索引数据库总是解包，因为它们需要合并，而不是内容寻址。
- `mergePnpmStore` 通过重命名而非复制把解包结果移入存储。存储中缺少的目录整体移动，除非其中包含索引；文件替换存储中同一路径的文件。每次重命名都经过 `renameRetryingWindowsLocks`（现位于 `rename-retry.ts`），因为 Windows 扫描程序会占用刚写入的文件。staging 目录与存储都位于 `$AVN_HOME/desktop` 下，因此重命名不会跨卷。
- `applyRelease` 只在快速路径发现 profile 过期之后才对 seed 计算哈希并验证 seed 的包集，快速路径也不再对 profile 的 tarball 计算哈希。验证保护的是进入可写状态的 seed 内容，而快速路径不写入任何内容；已是最新的 profile 从其 `node_modules` 运行，之后不会再读取它的 tarball，因为 staging 从 seed 复制 tarball。profile 已是最新的启动只读取 seed 的包集描述文件，不计算任何哈希。
- 启动屏会说明当前步骤以及是否为首次安装：没有活跃 profile 时显示“正在设置 Aeven：…”，否则显示“正在更新 Aeven：…”，分别对应解压软件包、安装软件包与健康检查。
- 标题栏菜单条的 IPC 处理器在启动屏加载之前注册，因此 Windows 与 Linux 的菜单条会出现在启动屏上。

在报告问题的机器的 seed 与存储上，升级的解包步骤耗时 13.8 秒，只写入一个文件。首次安装仍会把每个文件解包一次，但不再复制第二遍。

## 考虑过的替代方案

**直接解包到持久存储。** 中断的解包会在内容寻址路径上留下被截断的文件，而之后的启动会信任这些文件。先解包到 staging 再重命名，能保证存储收到的每个文件都是完整的。

**缓存一次成功的 seed 验证。** 以文件大小和时间为键的标记仍需要自己的信任规则；而在不写入任何内容的路径上跳过验证则不需要。

**复用活跃 profile 的包。** 这会让 staging 依赖上一次安装的包布局。Windows 改为从已验证的 seed 存储重建发布的[预计算 profile 布局](2026-10-29-windows-precomputed-profile-layout.zh.md)，无需读取旧包目录树即可跳过初始 pnpm 安装。

## 后果

Windows `tar` 在每个解包器中为所有文件保留同一个路径，使写入串行执行。Windows 最多并发解包十六个独立且已验证的分片；POSIX 保持单个解包器，因为它已经能并发写入独立文件。所有分片的结果确定后，解包才会拒绝，因此事务清理不会与写入器竞争。在报告问题的 Windows 机器上，使用已安装的 0.3.28-alpha seed 解包到空目录，串行耗时 30.3 秒，并发耗时 15.4 秒。这些测量仅覆盖解包，不包括安装或 Host 启动。分片测试验证共享父目录中的文件内容完整，并证明拒绝会等待其余写入器。

存储合并现在会消耗其解包结果，因此只有在重命名最终放弃时，解包目录中才会剩下未能移动的内容。与 seed 条目路径和大小都相同的存储文件会直接被信任，而不比较字节；pnpm 自身的存储完整性检查仍会在安装时覆盖它。
