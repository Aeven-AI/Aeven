# Agent Note: 听写在流关闭与工作进程冷启动后仍可使用

Status: implemented

## Problem

听写曾以两种读者无法与「应用坏了」区分的方式失败。

Composer 的就绪状态来自一条 Host 流（`speech.follow`）。`RemoteStream` 把静默结束报告为终止错误，而其载体重试在客户端仍认为连接存活时、第二次失败后就放弃；两种结果都会终结消费者。`ui-voice-input` 只在插件挂载时打开一次该流，且从不监听 `connection/reset`，因此一次套接字丢失或 Host 重启之后，麦克风在整页重新启动之前都无法录音。其他 Client 域（设置、模型选择、会话）会在该事件上重启各自的流；语音没有。

识别器的冷启动很昂贵。macOS 工作进程构建内嵌 Metal 内核源码并在进程启动时编译——大约二十秒后才打印 `{"ready":true}`。`idleTimeoutMs` 为五分钟时，工作进程会在两次听写之间被停止，于是稍作停顿的读者把这段编译付在一次看起来卡住的转写里。如果录制开始时工作进程正被回收，录制就在等待一个尚不存在的进程。

## Decision

就绪镜像在插件生命周期内持有自己的流，并重新打开它。任何一次结束后，它以指数退避等待（两秒起，逐次翻倍至三十秒）；`connection/reset` 会中断等待、重置退避并重启当前代次；新代次打开期间，UI 已有的目录保持发布。释放会中断等待并汇合循环，因此插件 effect 仍释放全部资源。

应用组合在激活期间启动一个已校验的工作进程（`warmOnActivation`）并保留它（`idleTimeoutMs: 0`）。`warm()` 等待激活检查结束，在模型未校验时拒绝启动——未校验的模型仍然等待设置页的显式下载——否则走普通准备路径，像任何一次启动那样发布 `waking` 再发布 `ready`。代价从读者的首次录音移到 Host 启动。

麦克风绝不采集它无法转写的音频。识别器不可用时，控件的提示会说明原因（流已关闭、模型未准备、准备失败、准备进行中），并在阶段为 `unprepared`、`failed` 或 `cancelled` 时重新开始准备，同时打开语音设置；在此变更之前，`failed` 的模型会让按钮完全无反应。

加速始终自动且可选。`use_gpu` 向 whisper.cpp 请求该构建提供的任何 GPU 或集成 GPU 设备，并始终追加 CPU 缓冲列表，因此没有这类设备的机器在 CPU 上运行。原生构建决定提供什么：macOS 用 Metal，x64 用 AVX2/FMA，Windows ARM64 用 dotprod，Linux 仅 CPU。组合中没有任何部分依赖 GPU。

## Alternatives considered

**在重置时重启整个就绪插件** — 插件的注册、字典与采集体都是一个 fiber 的 effect；为一次传输失败而重挂它，会重建 UI 注册。

**保留空闲回收，按需重开工作进程** — 这不保留任何东西，只留下旧账：编译发生在读者正在等待的路径上。

**仅在页面订阅目录时才预热** — 订阅在每次页面加载时到达，包括读者从不听写的重载，因此它比激活更频繁地支付编译，而且仍会漏掉直接启动进入会话的应用。

**在构建时预编译 Metal 库** — 这是消除那二十秒的正解，但它需要每个平台包各自的 metallib 产物、面向贡献者的构建工具链依赖，以及一次新的原生发布；预热工作进程今天就把延迟移出读者的路径，并把构建改动留作待办。

**检测 GPU 并据此选择模型或线程数** — whisper.cpp 已在加载时选择设备，而录制是一条串行作业，因此再叠一层选择只会多出一种与它不一致的方式。

## Consequences

关闭或失败的流不再以整页重载为代价：麦克风会在三十秒内自行恢复，而客户端看到新的 Host 代次时立即恢复。作为交换，镜像可能对持续失败的 Host 反复重开，因此故障的语音 Remote 现在会产生重复错误而不再是一条死流；退避把该流量限制为每三十秒一次尝试。

应用在 Host 进程存活期间持有一个常驻工作进程——小模型权重及其运行时——而不是在五分钟后释放它。启动会在后台承担这部分内存与平台编译开销；从不听写的机器两者都要付。`warmOnActivation` 默认 false、`idleTimeoutMs` 默认五分钟，因此只有主动选择的组合（web 应用 bundle 已选择）才承担这笔交易。

录音现在不可能再被误认为一个坏按钮：麦克风要么开始，要么说明为何不能。
