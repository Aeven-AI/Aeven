# Agent Note：语义记忆召回覆盖每一条轨迹

Status: implemented

[English](2026-11-10-memory-recall-covers-every-trace.md) | 中文

## 问题

回合开始时的召回通过 `traces.vec_summary` 和 `traces.vec_action` 上的向量通道查找记忆（内置 MemOS 核心中的 `tier2-trace.ts`）。`traces.searchByVector` 运行 `scanAndTopK`，其默认的 `LIMIT 5000` 没有 `ORDER BY`，因此语义召回只为 SQLite 先返回的 5,000 条轨迹打分。2026-11-10 托管环境中最大的账户里，这是 41,901 条中的 5,000 条，时间从 2026-10-14 到 2026-11-04：最新的 5,615 条轨迹以及该区间之前的所有轨迹只能通过关键词搜索被召回。长期记忆是产品的核心承诺，而它会随着账户变大而悄悄退化。

只提高上限会在每次召回时读取并解码每一个向量 BLOB：在该账户上每列约 650 毫秒，因为向量存放在 6.7 KB 的行里。窄表（448 毫秒）或覆盖索引（626 毫秒）几乎没有帮助，因为主要开销是解码 64 MB 的向量。

## 决策

不带上限的轨迹向量搜索改走内存中的余弦索引（`vendor/memos-local-plugin/src/core/storage/vector-index.ts`），每个数据库、表和向量列一个。它把所有非空向量放在一个 `Float32Array` 中，每次搜索为整列打分，用有界堆取出最佳候选，再对它们运行调用方的 SQL 过滤条件，并逐步扩大范围直到有 `k` 行通过——因此结果正是过滤条件允许的行中精确的前 K 个。它在每次搜索时读取超过其最大 rowid 的行、并复查向量为 NULL 的行来保持最新；当其最大 rowid 指向另一行、在 `traces.updateVector` 之后，或另一个连接（例如记忆同步）有提交且索引已建立十分钟时，它会重建。所有索引合计不超过 512 MiB，超出时丢弃最久未用的。

轨迹仍保留各自的向量；索引是派生的内存数据，因此数据库文件、其结构以及记忆同步交换的行都没有变化，旧版本和旧设备读取和同步的是同样的数据。该修改作为第 35 条记录在 `vendor/README.md` 中。

## 考虑过的替代方案

按时间排序有上限的扫描能保留新记忆，但会丢掉旧记忆，这违背长期召回的承诺。

窄向量表或覆盖索引会改变旧版本打开的数据库结构，而且每列仍需 450–630 毫秒。

近似最近邻库（HNSW）会引入原生依赖并给出近似结果；以目前的规模，在连续数组上做精确暴力搜索已经足够快。

## 影响

语义召回能触及账户的每一条轨迹。Host 启动后的第一次召回会建立索引（最大账户约 0.7 秒）；之后的召回只需读取增量并打分。被另一个连接原地改写的轨迹向量，在下一次重建之前（最多十分钟）仍以旧向量参与搜索。`policies`、`skills` 和 `world_model` 保留有上限的扫描：它们远低于 5,000 行，并且通过许多更新路径改写向量。

## 验证

一个脚本在 50,000 条随机 384 维的行上运行，每次查询都与精确全量扫描的前 20 个结果一致，无论有无过滤条件，包括只允许 100 行通过的过滤条件；它能找到新行、在行之后才到达的向量、被改写的向量，并会丢掉已删除的行；一次搜索约 18 毫秒，而精确扫描需 150–200 毫秒。在最大托管账户的副本上，抽样的五次查询返回的前 20 个结果与对全部 41,901 条轨迹的精确扫描相同，耗时 50–75 毫秒，而精确扫描需 615–655 毫秒。memory-memos 的测试全部通过（68 个）。
