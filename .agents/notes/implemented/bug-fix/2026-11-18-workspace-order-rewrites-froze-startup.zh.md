# Agent Note：重写同步的工作区顺序会冻结每次 Host 启动

Status: implemented

[English](2026-11-18-workspace-order-rewrites-froze-startup.md) | 中文

## 问题

对一个启动三分钟后仍无响应的桌面 Host 做 CPU 分析，显示其主线程全部耗在 `sync-yjs` 的 `openDocument` 中，重放某个同步文档已存储的更新。该文档 `workspaces` 在桌面端有 158 个更新共 644 MB，在托管 Host 上为 406 MB；每次重放需要四到六分钟，而且文档的最后一个句柄关闭后再次打开时会重新重放。

这是两个缺陷共同造成的。`WorkspaceSync.publish` 在每次发布时都删除并重新插入整个 `order` 数组，无论是否有变化；两台设备同时替换它时各自保留了自己的副本，于是数组积累了没有任何代码会移除的重复项：约 92,000 个条目，每次发布 3.6 MB。而 `sync-yjs` 只在文档的已存储更新超过 200 个之后才合并它们，因此 158 个大更新从未被合并。

## 决定

- `WorkspaceSync.publish` 让每个工作区只列出一次，并且只在顺序与文档中的不同时才写入；读取顺序时也会去除重复项。此改动之后的第一次发布会用短列表替换重复的列表。
- `sync-yjs` 在文档自上次合并以来的更新超过 `compactBytes`（默认 8 MiB）时也会合并。
- `openDocument` 会先在同步工作线程上合并到期的文档，因此在关闭期间超出阈值的文档不会再在 Host 线程上被完整重放。

## 考虑过的替代方案

- **保持文档打开，而不是在最后一次关闭时销毁。** 已推迟：它消除的是重复重放，而不是第一次重放。
- **用位置映射替换顺序数组。** 已推迟：这是每台设备都必须理解的格式变更；去除重复项和无变化的写入已能终止增长。

## 影响

此改动之后第一次打开超大文档时，要等待它在同步工作线程上完成合并，对 644 MB 的文档需要数分钟，每台设备一次。存储保留合并后的状态，其中以墓碑形式保存已删除的历史。
