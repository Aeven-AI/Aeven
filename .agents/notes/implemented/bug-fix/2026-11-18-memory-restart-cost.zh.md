# Agent Note：账户记忆不再在每次 Host 启动时耗费数分钟

Status: implemented

[English](2026-11-18-memory-restart-cost.md) | 中文

## 问题

从 0.3.58 起，桌面端会在登录时加载账户的记忆（`warmOnSignIn`）。在一个拥有 45,781 条 trace、数据库 1.1 GB 的账户上，这次加载在 Host 主线程上做全表读取，堆增长到约 6 GB，垃圾回收占满，Host 在每次启动后约十分钟内不响应任何请求；桌面端随后拒绝启动第二个 Host。在 2026-11-18 的列表修复和核心工作线程之后仍有两项成本：每次启动都从所有行重建向量索引，每次启动都要先列出人物记忆才能提供画像块。

## 决定

- **保存的向量索引。** 内置的索引把每个已构建的列保存在数据库旁，并在下次启动时恢复，然后只读取此后新增的行。一个 `AFTER UPDATE OF <column>` 触发器统计来自每个连接（包括记忆同步的连接）的原地向量写入，计数或最高行不一致的保存文件会被重建。在上述账户的副本上，启动后对两列的第一次搜索耗时 103 毫秒，而不是 698 毫秒。
- **保存的人物列表。** `@aeven/memory-memos` 把每次人物记忆列表写入 `person-facts.json`；启动后的第一次画像读取直接使用它，同时在后台重新列出。之后过期的列表仍像以前一样等待。
- **延迟预热。** `warmDelayMs` 让登录加载在窗口提供之后才开始；Web 与 Desktop 使用十秒。

## 考虑过的替代方案

- **关闭登录加载。** 已否决：那样启动后的第一个轮次会在召回上超时，而这正是该加载要解决的问题。
- **裁剪已存储的数据（审计行、旧工具输出和思考内容）。** 被所有者否决：已存储的记忆保持捕获时的样子。

## 影响

每个账户为每个向量列保留一个保存的索引文件，在 45,000 条 trace 时每列约 70 MB。数据库随记忆继续增长；它的大小不再决定一次启动的成本。
