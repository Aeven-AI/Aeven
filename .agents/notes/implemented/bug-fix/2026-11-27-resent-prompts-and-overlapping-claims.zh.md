# Agent Note: 再次发送的提示与重叠的认领

Status: implemented

[English](2026-11-27-resent-prompts-and-overlapping-claims.md) | 中文

## 问题

2026-11-27，用户已经发送过的一条提示在桌面端重新显示为“排队中”，随后作为单独的一轮运行。桌面端的同步收件箱中只有一条对应条目，由桌面端自己写入，没有目标设备，并保留了提示原来的 `rpcId`；Aeven Cloud 从未收到或转发它。这正是 [`SessionMirror.rewrite`](../../../../packages/session/session-sync/src/mirror.ts) 的形态：桌面端接手一个对话时，如果发现账号历史从未接受它自己的日志尾部，就会丢弃该尾部，并再次提出其中用户的提示。排队气泡没有任何迹象表明这是第二次发送。

同一次排查还发现 `SessionMirror.claim` 中的第二个缺陷。在没有认领时到达同一设备的两个输入都会进入该会话的操作队列；第二个运行时会再次获取中继租约（中继会把设备自己的租约再授予它），并释放第一个认领的持有者，从而在第一个认领的轮次运行期间放弃中继租约。新的持有者从未启动，因此在 `runnerLease.ttlMs` 之后不再算作持有。

## 决定

- **`claim` 在会话操作内部再次检查。** 排在另一个认领之后的认领，在本设备的认领仍然成立（本地正在运行一轮，或认领的租约被持有且未被拒绝）时返回 `{ claimed: true }`，与排队前快速路径的检查相同。
- **再次提出的提示带有 `resent: true`。** `droppedPrompts` 在每个 `prompt` 请求上设置它；[`@aeven/api-session-controller`](../../../../packages/api/session-controller/README.zh.md) 只从转发的输入中读取它，记录到已写入日志的消息的 `user-rpc` 来源上，在提示继续转发时保留它，并投影为 `SessionQueuedItem.resent` 和 `QueuedMessage.resent`。客户端的提示请求无法设置它。
- **排队气泡显示“再次发送”。** [`@aeven/ui-chat`](../../../../packages/client/ui-chat/README.zh.md) 把再次发送的队列行标为“再次发送”（en Sent again，es Enviado de nuevo），用提示框说明原因，并保留队列操作。

## 考虑过的替代方案

**不再次提出被丢弃的提示** 被否决：账号历史已不再包含该提示，用户的消息会从对话中消失。**让再次提出的提示先于触发认领的输入运行** 暂被否决：重写在该输入的认领内部运行，在那里应用这些提示会重新进入认领所持有的会话操作。

## 影响

账号同步再次发送的提示在等待期间会被标明；一旦它的轮次开始，它会显示为普通的用户消息，因为该标记位于消息来源中，没有转录界面读取它。重叠的首次认领会为开始的轮次保留中继租约。2026-11-27 桌面端日志尾部为何被拒绝仍未确认：没有读取该对话的中继帧日志。
