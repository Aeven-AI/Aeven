# Agent Note：设备的计数器重新开始后，其他设备拒绝了它的更新

Status: implemented

[English](2026-11-18-refused-sync-frames-and-lost-index-entries.md) | 中文

## 问题

2026-11-18，一台 Mac 上有托管 Host 未列出的对话，而托管 Host 上保存的是 Mac 已继续的对话的旧副本。Mac 对会话索引的发送方计数器为 162，而托管 Host 已从同一设备 id 接受过计数器 84,489：Mac 的存储丢弃后又取回了同一个账户密钥，丢弃密钥时的清空删除了 `counters` 表。文档 id 由密钥派生，因此保持不变；此后 Mac 发送的每个文档更新（会话索引条目、转发的输入、工作区）都没有通过其他设备的重放检查。之后托管 Host 的一个快照让中转服务器删除了这些帧，因此只有 Mac 还保存着它们。流批次不做计数器检查，因此对话正文到达了中转服务器。

会话索引还以计数器无法解释的两种方式丢失条目。十个对话以副本形式存放在 Mac 上，没有任何索引条目列出它们，而副本从不发布。三个对话的副本中保存着超出其索引条目的事件：整理阶段跳过已整理的副本，因此在释放完成发布之前写下的尾部留在本地，落后于流的条目也从不调高。

## 决定

- 发送方计数器比已存储的计数器大一，且不低于以微秒计的当前时间（`counterFloor`），Host 和同步 worker 都如此。丢弃账户密钥时保留计数器。
- 每个存储在追赶完成后执行一次：vault 把它写过的每个文档与中转服务器的副本比较，并发布其他设备从未收到的内容（`missingFrom`）。中转服务器的副本是其他设备的帧；当没有其他设备为该文档生成快照时，再加上本设备自己的帧，直到第一个计数器不大于之前某个计数器的本设备帧为止。
- 会话整理阶段把索引未列出的副本从头发布，发布已存储日志超出其条目的副本的尾部，并调高落后于流头部的条目。历史发布对索引未列出的对话，即使修订已记录也会再次发布。

## 考虑过的替代方案

- **对每个写过的文档生成一次快照。** 已否决：托管 Host 会为它从未丢失的 3,665 个文档重新发送约 500 MB。
- **由接收方从中转服务器取回被拒绝的帧。** 已否决：快照覆盖后中转服务器已删除这些帧。
- **按密钥模式选出需要修复的设备。** 已否决：托管账户也使用通行密钥模式。

## 影响

更新后的第一次连接会下载该设备写过的每个文档在中转服务器上的副本；托管 Host 从同一台机器上的中转服务器读取。若某设备在重新开始之前的自身帧已被裁剪、而被拒绝的帧仍在，且没有其他设备为该文档生成快照，它会把被拒绝的帧算作已收到；该文档在下一次快照时恢复。索引列出 18,466 个事件而两台设备都只存储一个事件的对话 `c5caed39`，不在本次变更的解释范围内。
