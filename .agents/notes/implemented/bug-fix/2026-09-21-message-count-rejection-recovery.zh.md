# Agent Note：从消息条数拒绝中恢复

Status: implemented

[English](2026-09-21-message-count-rejection-recovery.md) | 中文

## 问题

超过 400 条消息的会话，其回合会永久失败。网关返回 `400`，客户端把这次拒绝归类为 `INVALID_REQUEST`，而下游没有任何东西能对它采取行动：`INVALID_REQUEST` 不在默认可重试集合中，因此 `llm-retry` 从不重试；而 `compaction-basic` 的溢出恢复以 `CONTEXT_WINDOW_EXCEEDED_CODE` 为闸门，因此也不会尝试任何缩减。该会话之后的每条消息都会撞上同一堵墙，因为那个已经越过上限的请求无法自行缩小。

这次拒绝以 `` `messages` may contain at most 400 entries `` 的形式到达，并指明了 `messages` 参数。它不匹配 `packages/llm/llm/src/error.ts` 中任何识别器——那些识别器描述的是 token 预算：上下文长度、窗口、"too large for model context"——于是一个「按既定形态被接受、随后超出条数上限」的请求，被报告成了一个模型在任何形态下都不会接受的请求。恢复路径所依赖的正是这个分类，而它从未得到正确的分类。

这个上限本身是本部署自己发明的。DeepSeek 的 chat-completions schema 只给出 `messages` 的下界（`>= 1`），没有规定上界；而在条数真正有意义之前，模型上下文窗口早就先一步约束了对话，因此条数上限会拒绝提供方本会应答的请求。只有那种由大量小条目构成的长尾会话——每条工具结果占一行，这正是本 harness 的序列化方式——才会在 token 仍然很少时触及它。

## 决策

取消条数上限，并让保留该上限的部署能够从条数拒绝中恢复。

`INFERENCE_MAX_MESSAGES` 不再有默认值。`services/inference/config.js` 在部署未设置时将其解析为 `null`，`RequestNormalizer` 对 `null` 上限完全跳过检查。端点已经具备的保护是 `maxBodyBytes`，它在请求体被解析之前生效；条数上限则是提供方从未要求的限制。希望保留上限的部署把 `INFERENCE_MAX_MESSAGES` 设为正整数；而一个不可用的值会解析为「无上限」，而不是解析为零上限——后者会拒绝每一个请求。

确实指明条数上限的拒绝，现在属于它自己的失败类别，而不再是无效请求。`MESSAGE_COUNT_EXCEEDED_CODE` 是 `packages/llm/llm/src/error.ts` 中的规范代码，`isMessageCountExceededError` 识别网关陈述该上限时使用的措辞。该识别器要求条数旁边出现 `messages` 参数名，因为数字与“entries”一词也会出现在关于其他数组的拒绝中；缺少这个锚点的匹配会把一次无关的拒绝变成无休止的“压缩并重试”循环。两条投递路径都执行它：非 2xx 响应上的 `httpErrorCode`，以及响应开始之后带内错误帧上的 `mapStreamError`。

`compaction-basic` 对新代码的处理与对上下文溢出相同。它的 `agent/request-error` 监听器从同一个集合中接受两者，让它们共享 `maxOverflowRetries` 预算，并在日志中标明它恢复自哪个上限，使运维人员能区分 token 上限与条数上限。一次缩减会用单个检查点替换一段 surface 节点，因此它同时降低条数与此前的 token 数；只有在缩减确实推进了 surface 时才授权重试——持续拒绝的端点和无法再缩小的 surface 会像以前一样结束该回合，而不是空转。

## 考虑过的替代方案

**不删除网关上限，只把它调大。** 更大的数字仍是本部署选定的数字，仍会拒绝提供方本会应答的对话，只是把墙挪了个位置，而不是拆掉它。

**声明按路由的行数上限，让客户端在发送前自行缩减。** 本 harness 统计的是 token，不是 wire 行；行数只有在适配器序列化请求之后才存在，而且条数上限是适配器背后端点的属性，不是模型的属性。让客户端携带它将新增一个必须与网关保持一致的值，而一旦两者不一致，回合仍然失败——只不过现在是在用户还没被告知任何信息之前就失败。

**依赖 `maxBodyBytes` 并跳过恢复路径。** 对默认配置而言这是对的，对其他每一种配置都是错的：设置了 `INFERENCE_MAX_MESSAGES` 的部署，以及在本客户端之前的任何自行强制条数的网关，产生的正是这个无法恢复的拒绝。

**把新代码加入默认可重试集合。** 重试只是把同一个超限请求再发一次；只有缩减对话才会改变答案，而缩减归压缩负责。

## 后果

超出条数上限的会话现在可以继续：客户端缩减被替换的区域，写入摘要检查点，并重试该请求一次。默认部署没有这样的上限，因此根本不会因这个原因触发压缩。

这个失败代码是会话日志中的新代码，因此在此变更之前构建的客户端会把 `MESSAGE_COUNT_EXCEEDED` 读作无法识别的代码，而不是读作 `INVALID_REQUEST`。恢复受 `maxOverflowRetries` 限制，并与上下文溢出共享该预算；因此，在缩减之后仍然持续的拒绝依旧会让回合失败，而不是循环下去。

条数上限不是 token 上限，两者现在被分开报告；阅读某个已恢复回合日志的运维人员可以判断对话触及的是哪个上限。该识别器也会匹配 DeepSeek 自家 API 某些版本并不使用的措辞，这是刻意为之——条数上限是网关的规则，因此客户端识别的是规则，而不是厂商。
