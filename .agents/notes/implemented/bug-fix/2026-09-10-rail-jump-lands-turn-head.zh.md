# Agent Note: 轮次导航跳转落在轮次最早的行

Status: implemented

[English](2026-09-10-rail-jump-lands-turn-head.md) | 中文

## 问题

从 Chat 轮次导航跳转到第 1 轮时，视图从不显示对话的开头。在每个测量过的 Session 中，视图都停在 `scrollTop = 90`，第 1 轮自己的 `System prompt` 行完全位于视口上方。导航项的锚点是该轮次第一个已加载的用户节点，`ChatView` 把这个锚点行放在 24px 阅读线上。渲染器可以把同一轮次的行放在用户节点之前：每当一次请求显示其系统提示词时，request-prompt Definition 就会把一个 `system-prompt` 行锚定在轮次开头，第一次请求总是如此，系统提示词变化时也会再次出现。因此这种落点裁掉了目标轮次自己的前导行。对于没有这种行的后续轮次，锚点之上的行属于更早的轮次，没有丢失任何内容。已加载路径与加载并跳转路径最终落在同一位置，因为两者都通过同一个辅助函数落点。

## 决定

导航跳转在滚动之前，把锚点行解析为其轮次最早的已渲染行。`turnHead` 沿锚点之前的 flow 兄弟节点向前遍历，只要它们带有相同的 `data-chat-turn` 就继续，并跳过隐藏和空的 seat，因为它们不渲染任何盒子。该行落在阅读线上。当它之前没有任何已渲染行，且 Session 没有更早的历史可分页（`hasMore` 为 false）时，该行就是对话的开头，视图落在滚动原点，使 flow 的前导空白也一并显示。导航项的 `anchorKey` 保持不变。它仍然作为分页锚点、结算校正和 outline 合并的键，因此只有落点位置发生变化。内容搜索导航仍落在其精确的持久行上，因为它定位的是一条消息而不是一个轮次。

## 验证

`chat-view.client.spec.tsx` 跳转到一个完整的两轮对话记录的第 1 轮，其第一轮带有 System prompt 行，并要求 `scrollTop` 为 0。第二个用例让第 2 轮在其用户锚点之前带有一个 System prompt 行，并要求该行位于阅读线上。针对先前的落点，两个用例分别停在 676 和 236，而不是 0 和 176。现有的跳转用例的目标是不完整历史中第一个已加载的行，仍落在阅读线上。

## 考虑过的替代方案

**把导航项锚定在轮次第一个可见节点上。** 这会移动落点，但 `anchorKey` 还标识跳转期间分页补偿所保持的行。System prompt 行会随提示词变化出现和消失，为了修正一个滚动偏移而把键从用户节点移开，会改变每个消费者看到的导航投影。

**把第 1 轮作为特例钳制到原点。** 这修复了所报告的症状，但对系统提示词发生变化的任何后续轮次，仍会裁掉其前导行。

## 后果

跳转到任何轮次都会显示该轮次的前导行，跳转到完全分页的 Session 的第 1 轮与手动滚动到顶部的结果一致。目标是仍有更早历史的窗口头部时，跳转仍像以前一样把该头部落在阅读线上。
