# Agent Note：发布运行中的会话会重读整个日志

Status: implemented

[English](2026-11-18-running-session-publication-reread-its-log.md) | 中文

## 问题

对托管 Host 的 CPU 分析显示，一个账户的九个轮次花了 12.8 秒主线程时间解码它自己的会话日志：十分钟内对一个 2.5 MB 的日志做了 106 次全量读取，每次最长 1.15 秒。账户同步在每次提交后 `liveMs` 发布运行中的会话，并向会话持久化请求其已发布位置之后的事件。JSONL 后端存储的是没有后缀读取的顺序日志，因此每次发布都要解压并解析整个日志，成本随对话增长。

同一份分析还显示 `deepFreeze` 占了 2.3 秒：`Session.requestHeader()` 在每次有新事件之后的读取中都重新冻结折叠后的 header，尽管当新事件不含 `request/header` 时，折叠返回的就是已冻结的输入。

## 决定

- 会话镜像保留每次提交交给它的事件，每个会话至多 `tailEvents` 条（默认 2,000 条），并从这些事件发布。只有当保留的事件不是从已发布位置开始时，它才读取已存储的日志：重启之后、溢出之后，或日志由其他进程写入时。没有新事件、只更新索引元数据的发布不读取任何内容。
- `Session.requestHeader()` 只在折叠产生新 header 时才冻结。

## 考虑过的替代方案

- **在 JSONL 后端实现后缀读取。** 已推迟：Zstandard 帧不带事件索引，因此需要在持久格式代码内维护每个日志的位置缓存，而镜像本来就收到了它要请求的事件。

## 影响

镜像在提交与发布之间的几百毫秒内持有未发布事件的引用；会话本身已持有同样的对象。其他在 JSONL 日志上调用 `SessionPersistence.readFrom` 的调用方仍会读取整个日志。
