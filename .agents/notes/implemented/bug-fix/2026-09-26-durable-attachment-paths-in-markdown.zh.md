# Agent Note: Markdown 图片中的持久化附件路径

Status: implemented

[English](2026-09-26-durable-attachment-paths-in-markdown.md) | 中文

## 问题

图片附件保存在以摘要命名、没有扩展名的持久化路径下。Web Markdown 渲染器接受绝对路径，并通过 `/api/file` 加载，但该路由只根据扩展名选择响应媒体类型。其 `nosniff` 响应头使附件对象以 `application/octet-stream` 返回。某个 Agent 为了展示设备截图，把对象复制到带 `.webp` 后缀的 `/tmp` 文件，并把临时路径嵌入持久化回复。副本消失后，图片就无法显示。

## 决定

当已解析文件没有可识别的扩展名时，`/api/file` 通过文件签名识别 PNG、JPEG、WebP 和 GIF。它继续使用已组合的文件系统提供者实施路径授权和字节上限，带扩展名的文件仍使用其声明的媒体类型。当附件提供者能够给出持久化主机路径时，`device_screenshot` 在文本结果中提供该路径，并提示直接嵌入它。附件引用与对象存储布局不变。[模型可读图片路径记录](../feature/2026-08-21-model-readable-image-paths.zh.md)仍负责模型的路径披露；[无扩展名 read_image 记录](2026-08-28-read-image-extensionless-paths.zh.md)仍负责该工具的图片接纳。

## 考虑过的替代方案

**复制到有文件名的临时文件。** 后缀让文件路由取得媒体类型，但副本的生命周期不与会话日志绑定。持久化回复必须引用持久化字节。

**为附件对象加扩展名并重命名。** 这会为了一个路由的显示问题而改变内容寻址存储布局和每个现有对象路径。

## 后果

回复能够直接嵌入持久化对象路径，无需建立第二个文件。文件路由会读取无扩展名文件以判定响应类型，`HEAD` 请求也一样；无法识别的字节仍以 `application/octet-stream` 返回。指向已删除临时副本的现有回复仍无法显示，因为会话日志记录的是该路径，而不是附件 ID。
