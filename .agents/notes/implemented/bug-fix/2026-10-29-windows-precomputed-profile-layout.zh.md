# Agent Note: Windows 预计算 profile 布局

Status: implemented

English | [中文](2026-10-29-windows-precomputed-profile-layout.md)

## 问题

全新的 Windows 0.3.28-alpha profile 在存储解包后，内置 pnpm 安装仍耗时 104 秒。并发归档解包只解决了[解包开销](2026-10-27-desktop-release-install-speed.zh.md)。发布打包过程已经安装过完全相同的依赖图，包括原生构建和下载的可执行文件副作用。

## 决策

Windows 打包过程在删除已验证的 hoisted `node_modules` 之前记录其布局。每个文件引用 seed 存储中的一个 SHA-512 内容对象；存储中尚不存在的生成文件，会在归档与完整性清单生成之前加入同一存储。描述文件只增加路径与 pnpm 元数据，不增加第二份依赖树内容。

安装过程验证描述文件和架构、创建目录，再以有界批次把完整的存储对象硬链接进 staging profile。刚从完整性已验证的归档中解包的对象，在事务内同卷重命名后仍保持该验证；复用的可写存储对象则在链接前接受 SHA-512 检查。解包结果只记录实际写入的文件，不包括跳过的已有文件。安装过程会按安装后的 home 重写 pnpm 存储与虚拟存储位置，并省略构建主机的工作区状态缓存。包含符号链接的 Windows hoisted 布局会使打包失败，而不是保留指向构建主机的目录联接。存在但无效的描述文件会在链接任何包文件之前使安装失败。

完整 seed 清单会在执行此路径之前验证。staging、后端健康检查、激活日志、回滚与用户插件的精确版本恢复，仍由项目管理器负责。携带布局的发布跳过初始 pnpm 安装；插件恢复仍使用 pnpm。POSIX 发布沿用现有离线安装路径。

## 考虑过的替代方案

**额外提供一份预安装依赖归档。** 这会重复存储中已为升级和插件操作保留的包内容。布局描述文件复用这些字节，不需要额外解包归档。

**禁用 pnpm 存储完整性检查。** 这会削弱对持久可写存储的验证，而且仍然重复依赖安装。重建已验证的打包布局可以移除这项工作，而无需改变 pnpm 的完整性策略。

## 后果

在报告问题的 Windows 机器上，当存储对象刚完成验证时，重建真实的 22,541 个文件的依赖树耗时 20.4 秒，而 pnpm 安装耗时 104 秒。链接前重新检查全部内容摘要则耗时 33.9 秒。重建的后端能够成功启动，随后通过内置 pnpm 执行离线安装耗时 4.7 秒。这些是单个阶段的测量，不是重建安装包后的端到端启动时间。

打包过程负责昂贵的安装与布局哈希。首次启动仍验证并解包 seed、启动 staging 后端，但不解析依赖或重新运行构建脚本。存储和 staging 必须位于同一卷，Desktop 管理的 home 满足此条件；硬链接失败会拒绝事务，而不会静默复制每个文件。每批写入全部结束后，清理过程才能删除 staging。单元测试覆盖内容去重、元数据重定位、无效路径、架构不匹配与内容缺失。项目管理器测试证明无需可执行的 pnpm 入口也能完成激活和健康检查。
