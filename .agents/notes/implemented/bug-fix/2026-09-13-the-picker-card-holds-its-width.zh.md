# Agent Note: 选择器卡片在过滤时保持宽度

Status: implemented

[English](2026-09-13-the-picker-card-holds-its-width.md) | 中文

## Problem

`popupSelect` 卡片按内容定宽——`max-content` 盒子外加 `min-width: min(220px, 100%)` 与 `max-width: min(420px, 100%)`——因此可搜索的模型列表和它最宽的那一行一样宽。在搜索框里输入会过滤掉行，卡片随之在光标下方变窄：盒子、输入框与行在每一次匹配更少的按键上都会移动，而匹配重新变多时又把它们推回去。

来自运行中 GUI 的反馈，针对模型列表——人们真正会去输入的那个选择器：该列表动辄数百行、宽度各异，因此收缩恰恰发生在搜索最有用的地方，且幅度最大。

## Decision

卡片在同一次打开期间保持它已展示过的最宽宽度。`PopupSelectView` 在每次可能改变内容的渲染之后（搜索文本、已加载选项、加载状态）用 layout effect 测量卡片，并把见过的最大宽度保存在 state 中，以内联 `min-width` 应用。测量会收敛，因为内联最小宽度只会抬高盒子的宽度，下一次测量不可能更小；外壳关闭时重置，因此下一次打开重新开始测量。

宽度仍然由内容决定：两行的选择器依旧窄着打开，模型列表按其最宽的一行所需展开，上限是 composer 卡片自身的宽度。

## Alternatives considered

**给卡片固定宽度。** 之所以拒绝：外壳服务于所有 `popupSelect` 贡献项——主题列表、权限列表、模型目录——固定 420px 会让其中大多数被撑到它们永远用不到的宽度，而更窄的固定值又会截断弹性宽度本就是为了容纳的长模型名。

**只测量未过滤的行一次并冻结该宽度。** 对第一次按键而言与当前实现等价，但它忽略了上面这套测量天然覆盖的情形：重试后加载到更长的目录，或行在卡片已经显示之后才到达，都会再次改变尺寸。

**允许卡片收缩，但加上动画。** 之所以拒绝：动效并不能消除问题。读者的光标就在卡片内部，一个在它下方移动的目标比一个暂时偏宽的盒子更糟。

**跨打开保持宽度（按会话）。** 之所以拒绝：之后为另一份列表（其他贡献项的行）打开的选择器会继承一个与之无关的宽度。测量很廉价且按次打开进行，因此每次重新测量。

## Consequences

- 在外壳的搜索框里输入不再移动卡片、输入框或行；过滤到只剩一行时盒子仍是整份列表给出的尺寸，清空搜索后也保持不变。
- 在同一次打开的持续时间内，卡片可能比当前行更宽。这是有意接受的：另一种选择是让盒子在光标下移动，而超出的部分以读者刚看到的最宽一行为界。
- 每次内容变化多跑一个 layout effect。它只读一个数字，并且仅在该数字增长超过一像素时才写 state，因此不改变宽度的按键没有额外代价。

## Testing

`packages/client/ui-commands/tests/popup-view.client.spec.tsx` 把卡片的 rect 打桩为行数的函数（jsdom 不做布局），并断言在过滤到一行之后、以及清空搜索之后，内联 `min-width` 仍保持三行时的宽度——若测量不再被应用，这条断言就会失败。
