# Agent Note: 内容遮罩从输入区背后穿过

Status: implemented

[English](2026-09-09-content-cover-behind-composer.md) | 中文

## 问题

切换 Session 时，输入区看起来像是被卸载又重新挂载。它从未如此：`session-maybe` 在切换之间保留同一个化身，输入区座位的 DOM 节点在前后是同一个节点。是内容遮罩盖在了它上面。`.contentLoader` 带着 `z-index: 20`，而输入区座位是 `7`，因此只要遮罩还立着，其不透明的 `--dsw-alias-bg-base` 底板就覆盖着输入卡片，随后又在 400ms 淡出中把它重新露出来。读者看到输入闪没再闪回，这读起来像是重新挂载，而不像是加载。

## 决定

遮罩保留其几何，只改变它在层叠中的位置。它仍是从 `top: 0` 到 `bottom: 0`、宽 `100cqi` 的 fixed 图层，因此依旧横跨整个会话列，而现在它从输入区座位*背后*穿过，而不是盖在其上。`.contentLoader` 降到 `z-index: 6`，`.scrollArea` 以 `z-index: 5` 成为一个层叠上下文，这把转录、其中位于 `6` 的 CodeBlock 粘性横幅，以及视图自己的浮动装饰都收进一个层级，遮罩用一个数字即可越过。座位的 `7` 因此胜过遮罩，而头部的 `30` 仍旧胜过二者。这仅取代[内容加载器决定](2026-09-08-conversation-content-loader.zh.md)中让遮罩覆盖列*直至输入区*的那一条；该记录继续拥有遮罩何时出现、显示什么，以及如何与页面预加载器交接。

## 验证

`ui-conversation` 中的样式规格读取该模块的声明，要求遮罩排在输入区座位之下、压过持有其所遮内容的 `.scrollArea` 组，并保持 `position: fixed` 与 `top: 0`、`bottom: 0`，使其不被限制在滚动视口内。Chrome DevTools 对一次真实 Session 切换的观测印证了这一点：座位全程留在文档中且矩形不变，遮罩在 `z-index: 6` 上量得完整的 `997px` 列高，而在遮罩完全不透明时横跨输入区带取的三十个采样点中，没有一个解析到加载器——那里最上层被绘制的元素是输入行，而此前是遮罩的背景底板。

## 考虑过的替代方案

**把遮罩限制在滚动视口内。** 让它在 `.scrollArea` 内成为 `position: absolute; inset: 0` 会使其止于座位上缘，确实能阻止它覆盖输入，但那是把遮罩缩小而非重新层叠：输入区背后的那条带子随之失去覆盖，修复变成了更小的遮罩而不是正确的绘制次序。

**把输入区座位抬到遮罩之上。** 座位刻意位于 `7`，在 ChatView 的回到底部控件 `8` 之下，好让该控件绘制在输入卡片之上。为越过 `20` 的遮罩而抬升座位，会为一个与这两个控件都无关的理由颠倒该关系。

**让遮罩留在 `6` 并依赖文档次序。** 那样遮罩与 CodeBlock 粘性横幅会在 `6` 上打平，绘制次序将取决于哪个元素在树中更靠后。这在今天成立，而一旦任一子树移动便会无声地失效。

## 后果

一次 Session 切换会遮住转录，同时全程让输入区保持可见可读，因此切换读起来是内容在加载，而不是输入被拆掉重建。`.scrollArea` 内的一切现在都被压在座位之下，这与该图层本就被限制在滚动视口内、在几何上无法与输入区重叠是一致的。遮罩仍横跨完整列高，因此在转录被隐藏时，输入背后的那条带子保持其底色。
