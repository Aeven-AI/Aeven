# Agent Note：监视器启动期间写入的用户 patch 仍会被应用

Status: implemented

[English](2026-11-10-user-patch-watch-arming.md) | 中文

## 问题

`packages/boot/app-boot/src/index.ts` 中的 `watchUserPatches` 在 Cordis HMR 的 chokidar 监视器报告 `ready`、且一次对账读取已应用磁盘上的文件后才返回。chokidar 在其目录监视真正开始投递之前就发出 `ready`：一个在 `ready` 时创建被监视文件的探针，在十二路并发下 480 次运行中有 28 次丢失了这次创建，且丢失的创建之后都没有被通报；在 `ready` 之后 50 毫秒再创建，480 次全部被通报。在这一窗口内创建或编辑的用户 patch 文件，在整个进程生命周期内都不会被应用。同一竞态让 `user-patches.spec.ts` 的 “watches add, failure, recovery, and removal” 在 48 次并发运行中失败 2 次，都发生在第一次写入，并在 2026-11-10 让完整单元测试超时一次。

## 决策

在 `ready` 之后的一秒内（`WATCH_ARMING_WINDOW_MS`，是测得的启动时间的二十倍），`watchUserPatches` 还会每 25 毫秒轮询一次 patch 文件的标识（inode、大小和修改时间）。它记录每次刷新（无论是通报触发还是对账触发）读取到的标识，只有当变化后的标识在 300 毫秒（`WATCH_ARMING_GRACE_MS`）内都没有被通报时才应用它，因此已启动的监视器通报的写入只应用一次，失败的候选也只广播一次。窗口结束且没有待处理的变化时，或监视被释放时，轮询停止。

测试中 `eventually` 每一步的期限从 120 秒降到 20 秒，低于用例超时，因此丢失的写入会指明是哪一步，而不是表现为用例超时。

## 考虑过的替代方案

更长的测试超时或在第一次写入前 sleep，会掩盖让真实用户的编辑无法生效的产品竞态。

在被监视目录中写入一个哨兵文件并等待其 `add`，可以证明监视已启动，但监视根目录可能是一个缺失的 profile 目录的祖先目录，哨兵文件会落在用户拥有的目录中。

在整个进程生命周期内轮询会与监视器重复；竞态只存在于监视启动期间。

## 影响

启动后立即创建或编辑的 patch 文件会在宽限时间内被应用。每次注册的监视器最多增加四十次 `stat` 调用。窗口期间被监视器延迟超过 300 毫秒才通报的写入可能被应用两次；文件有效时第二次应用不做任何事。

## 验证

上述 chokidar 探针测得了丢失率和启动时间。改动之后，`user-patches.spec.ts` 在十二个并发进程中整文件运行 96 次全部通过，而同一测试工具在改动前 48 次中失败 2 次；app-boot 测试全部通过（141 个）。
