# Agent Note: 未给出判定的自查保留原回复

Status: implemented

[English](2026-11-01-inconclusive-review-keeps-the-reply.md) | 中文

## Problem

`turn-review` 在轮次停止时发起一次辅助模型调用；当这次调用失败——判定被截断、请求了工具、传输错误或超时——只要之前某一轮记录过问题，插件就会让整个轮次失败。读者看到的是泛化的「Aeven 没能完成这次回复。请再试一次。」，而回复其实已经写好了，重试还会重现：六十个会话中轮次失败十六次，其中十二次是 `review output reached maxOutputTokens`。

失败被归到了回复身上，但它发生在复核者那边。被截断的复核并不能说明被复核的工作有什么问题。

## Decision

没有给出判定的复核调用会追加带原因的 `turn-review/failure`、记录一条警告并返回：轮次保留已有的回答并正常结束。取消仍然向上传播。`maxReviewsPerTurn` 之后仍有未解决问题的轮次会以同样的失败记录写入这些问题，并同样带着回复结束——任何复核结果都无法让轮次失败。

复核者同时被要求最多列出五个问题、每条不超过 200 字符，并且不引用工具输出，这让判定保持为「要修什么」的清单。

最后，复核调用请求 `reviewReasoningEffort`（默认 `low`），不再继承路由的默认推理强度。把判定撑到 `maxOutputTokens` 的正是思考：`llm-aeven` 默认 `high`，而上限约束的是包含推理在内的输出，六万字符的记录又给了复核者大量可推演的素材——它才开始写那四个词的 JSON。该强度会对照路由自身的推理元数据解析，路由未声明时便略去，因此不常见的路由用自己的默认值跑复核，而不是让它失败：服务会拒绝声称不支持强度的请求。

## Alternatives considered

**把 `maxOutputTokens` 提到 12000** — 它只是移动了失败阈值而不是原因，而且每个录制场景都钉住了请求里的 `maxTokens`，十一个 fixture 得为此重新推导，读者在仍然触顶时看到的东西却没变。限制推理强度比提高上限花更少的 token。

**把每次失败的复核都当作轮次失败** — 这正是要移除的行为：它告诉读者回复失败了，而实际失败的只是检查。

**重试复核调用** — 成功的重试会掩盖一个反复无法作答的复核者，还推迟了读者正在等的回复。

## Consequences

坏掉或过载的复核者只带来一条警告和一条 `turn-review/failure` 记录，绝不会拿走用户的回复；轮次在配额内没能解决的问题同样如此。留下来的只是有用的那部分：还有剩余轮次时，问题会作为引导消息到达，agent 仍能补上它遗漏的东西。

未被复核的轮次是可观测的而非静默的：每次失败都被记录且持久化，因此停止作答的复核者在会话日志里依然可见，只是不再打断任何人。
