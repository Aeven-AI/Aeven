# Agent Note: 未给出判定的自查保留原回复

Status: implemented

[English](2026-11-01-inconclusive-review-keeps-the-reply.md) | 中文

## Problem

`turn-review` 在轮次停止时发起一次辅助模型调用；当这次调用失败——判定被截断、请求了工具、传输错误或超时——只要之前某一轮记录过问题，插件就会让整个轮次失败。读者看到的是泛化的「Aeven 没能完成这次回复。请再试一次。」，而回复其实已经写好了，重试还会重现：六十个会话中轮次失败十六次，其中十二次是 `review output reached maxOutputTokens`。

失败被归到了回复身上，但它发生在复核者那边。被截断的复核并不能说明被复核的工作有什么问题。

## Decision

没有给出判定的复核调用会追加带原因的 `turn-review/failure`、记录一条警告并返回：轮次保留已有的回答并正常结束。取消仍然向上传播；`maxReviewsPerTurn` 之后仍有未解决问题的轮次依旧失败，但改用 `TURN_REVIEW_UNRESOLVED`，客户端因此可以说明是 Aeven 自己的检查拦下了回复，而不是显示泛化错误。

复核者同时被要求最多列出五个问题、每条不超过 200 字符，并且不引用工具输出。这让判定落在现有的 `maxOutputTokens: 4000` 上限之内——实测的截断来自冗长散文，而不是预算定得太小——也让问题保持为「要修什么」的清单。

## Alternatives considered

**把 `maxOutputTokens` 提到 12000** — 它只是移动了失败阈值，而没有改变归因；而且每个录制场景都钉住了请求里的 `maxTokens`，十一个 fixture 得为此重新推导，读者在仍然触顶时看到的东西却没变。

**把每次失败的复核都当作轮次失败** — 这正是要移除的行为：它告诉读者回复失败了，而实际失败的只是检查。

**重试复核调用** — 成功的重试会掩盖一个反复无法作答的复核者，还推迟了读者正在等的回复。

## Consequences

坏掉或过载的复核者只带来一条警告和一条 `turn-review/failure` 记录，绝不会拿走用户的回复。剩余的致命路径只有复核轮次用尽后仍存在的真实问题，它现在有自己的错误码和自己的文案。

未被复核的轮次是可观测的而非静默的：每次失败都被记录且持久化，因此停止作答的复核者在会话日志里依然可见，只是不再打断任何人。
