# Agent Note：其他会话持续变化时会话搜索照常作答

Status: implemented

[English](2026-11-10-session-search-answers-under-churn.md) | 中文

## 问题

每次搜索以及启动后的后台刷新都会运行 `packages/session-query/session-query-sqlite/src/index.ts` 中的 `_observeStable`。它列出持久化的会话，为有变化的会话建立索引，再列出一次，并要求两次列举和实时会话集合一致。重试一次后它会抛出 `SESSION_QUERY_PERSISTENCE_FAILED`。托管 Host 为所有账户的会话建立索引，因此任何账户在两次列举之间的写入都算作变化。启动刷新要为上次运行以来变化的所有会话建立索引，在 pink 每次重启后都会失败（`background index refresh failed`，2026-11-08 至 2026-11-10 期间四次），同样的规则也可能让繁忙 Host 上的用户搜索失败。

## 决策

持久化快照或实时会话集合的变化仍然获得一次重试，最后一次尝试时搜索以该次尝试作答，而不是失败。行按修订版本存储，因此该观察截至其第一次列举是正确的；之后变化的会话由下一次对账建立索引。持久化绑定本身的变化仍然先重试再失败，因为来自已被替换的存储的观察不是有效答案。

派生索引还以 `synchronous = NORMAL` 和 `temp_store = MEMORY` 运行。每个被索引的会话在各自的事务中提交，`FULL` 在启动刷新时每个会话同步一次，延长了发生变化的窗口。索引可以从会话日志重建，因此因断电丢失的提交会被重新计算。

## 考虑过的替代方案

更多次重试只会降低失败概率：服务多个账户的 Host 在持续写入，而每次重试都要重复完整的列举。

把列举限定在发起搜索的账户可以缩小窗口，但会改变持久化查询的接口；按修订版本存储的行已经让尽力而为的观察是正确的。

## 影响

搜索可能漏掉在它运行期间写入的会话，直到下一次搜索。后台刷新在重启后不再失败。

## 验证

`packages/session-query/session-query-sqlite/tests/sqlite.spec.ts` 固定了持续的快照变化在四次列举后返回最后一次尝试中的会话；会话查询的测试全部通过（262 个）。在 pink 上，搜索索引包含 1,233 个持久化会话、42.6 万个文档，在副本上 FTS5 MATCH 查询耗时 2–4 毫秒。
