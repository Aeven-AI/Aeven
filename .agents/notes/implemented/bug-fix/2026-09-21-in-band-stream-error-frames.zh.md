# Agent Note：流内错误帧

Status: implemented

[English](2026-09-21-in-band-stream-error-frames.md) | 中文

## Problem

`@aeven/llm-deepseek` 中的 `translate()` 逐条读取 SSE 载荷，且只看 `choices`、`usage` 与 `system_fingerprint` 三个字段。一个 OpenAI 兼容网关若在响应**已经开始之后**才失败，就无法把已经发出的 200 改写为 4xx 或 5xx，于是它把失败写在流内——用 `{"error":{"message":…,"type":…,"param":null,"code":…}}` 取代下一个分块——然后在不发送 `[DONE]` 哨兵的情况下关闭流。该响应体不匹配任何被读取的字段，因此无声地穿了过去，而未到的哨兵触发了读取端自己的兜底错误：`SSE stream ended without [DONE]`，代码 `STREAM_CLOSED`。

这两者并不是同一种失败。`STREAM_CLOSED` 说的是连接断了；那个帧说的是提供方已经作答、随后失败，并用网关自己的代码为这次失败命名。调用方无法区分二者，于是「提供方消失」的这一回合读起来像一起传输事故——既无可着手之处，也无可报告之物。

这一形态在 2026-09-21 被端到端地观察到：Web GUI 中会话 `1c671b68` 的第 3 回合于 18:06:34Z 在第 9 步失败，报的正是这条 `STREAM_CLOSED` 文案，而此前的增量文本已经抵达页面。本地网关的用量账本把同一请求记录为 18:06:31.989Z 的 `provider_unavailable`——送到客户端的那个帧正是由同一个失败对象序列化而来，所以它携带的代码就是 `provider_unavailable`，而账本是它唯一留存下来的地方。客户端当时握着它，却把它丢掉了。

## Decision

现在，一个帧被解码为它可能属于的两种形态的联合。`WireFrame` 同时继承 `WireChunk` 与 `WireError`，因此 `error` 与 `choices` 一并被读取；读取端在查看该帧可能携带的任何其他内容之前，先用新增的 `mapStreamError` 构造出的 `LlmError` 抛出。

`mapStreamError` 只按一种顺序分类，从最具体的事实到最不具体的事实。账户额度耗尽与请求超出模型窗口这两种情况——它们到达这里时都没有状态码可供说明——走的是非 2xx 路径已经在用的那两个识别器 `isQuotaExceededError` 与 `isContextWindowExceededError`，于是一次失败无论以何种方式送达，分类都完全一致。除此之外，网关自己的 `code` 会被原样转为大写后透传，而不是被压平成 `SERVER`，因为调用方路由所依据的正是这套词汇。完全没有代码的帧是 `SERVER`；而既没有消息也没有代码的响应体，会直说这一点，而不是在冒号后面留下一条悬空的消息。

消息命名的是送达方式而非请求本身——「the provider failed after the response began」——因为读者面对的正是这件事：一个停下来的回答，而不是一个从未开始的请求。

`WireError['error']` 的每个成员都被声明为可空，与 `content`、`finish_reason` 已经遵循的约定一致。该类型是对远端编码器的断言，而一个把「此处无内容」写成显式 `null` 的网关，绝不能让我们在通往诊断的路上把一次分类变成 `TypeError`。

## Alternatives considered

**就让截断作为答案。** 跳过该帧、让缺失的哨兵抛出 `STREAM_CLOSED`，这正是原代码的做法，而且作为传输层面的事实也说得过去。拒绝：这是调用方唯一剩下的事实，而它对提供方的描述是错的。网关已经判定该请求失败并说明了原因；丢掉它等于选择知道得更少。

**把所有流内代码都折进 `SERVER`。** 用测试框架自己的通用桶只需一行代码，也不必引入新词汇。拒绝：`SERVER` 是在什么都不知情时才给出的东西，而这里恰恰是知情的。路由的重试策略是对这些代码所做的配置，而一个能标识网关自身故障的代码，正是最值得被指名的那一个。

**同时对已经输出增量的流拒绝重试。** 重试策略纯按失败代码判断，因此在一个会重试该代码的路由上，`PROVIDER_UNAVAILABLE` 帧会重放一个读者已经看过前半段的回合。此处不做：本框架的默认路由并不重试该代码，而部分输出防护是对 `@aeven/llm-retry` 契约的改动，它属于重试策略，而不属于读取端。这里把它留作可见的问题，而不是悄悄替它做决定。

**改为通过 `finish` 呈现失败，而不是抛出。** 流协议中已经存在 `{kind: 'error'}` 结束原因，因此该帧本可以翻译成它。拒绝：该帧在流结束之前到达，而一个先产出 finish 再继续读取的生成器必须决定剩下的载荷怎么办——网关关闭时不发哨兵，因此接下来被破坏的就会是哨兵自己的契约。

## Consequences

抵达应用的那次失败现在会带上网关自己的代码。[translate.spec.ts](../../../../packages/llm/llm-deepseek/tests/translate.spec.ts) 对此加以固定：在该帧之前到达的增量照旧送达，具名错误紧随其后，而额度、上下文、裸上游失败与未命名响应体各自归入其所属的类别。没有错误帧的流仍然是 `STREAM_CLOSED`，因为它确实就是如此。

同一缺陷在上一层——也就是发出这些帧的网关——同样存在：`servers/node` 的 `DeepSeekProvider` 同样只读取 `choices`，于是来自 DeepSeek 的流内错误帧被换成了它自己的通用文案「the response stream ended before it completed」。该适配器现在会用其非 2xx 路径已在使用的识别器来分类该帧；网关也会记录代码、消息以及已经转发的字符数，因此服务器对某个被截断回合的自述，不再需要客户端来重建。
