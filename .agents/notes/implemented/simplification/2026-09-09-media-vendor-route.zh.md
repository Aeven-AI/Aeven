# Agent Note: 媒体适配器背后的同一条厂商路由

Status: implemented

[English](2026-09-09-media-vendor-route.md) | 中文

## 问题

DeepInfra 与 OpenRouter 两个媒体适配器各自独立写成，却收敛到了同样的代码。凭据解析、对固定 origin 的 JSON 调用、在体积上限下的字节取回，以及作业体的翻译，在两者之间重复，`available()` 判定与视频 provider 本身的形状也是如此。克隆检测在这两个文件之间报出六处重叠区域。这种重复并非偶然：视频 provider 四个方法中的三个仅在路由路径上不同，因此对其中任何一个的修复都必须做两遍，而且可能悄悄只做了一遍。

## 决定

`@aeven/media` 发布其 provider 所依托的共享管道。给定注册键、凭据引用、origin 与显示名，`vendorRoute(ctx, config)` 为一个厂商给出 `available`、`apiKey`、`json` 与 `bytes`。`vendorJob` 依据厂商提供的状态表，把作业体映射到该 seam 的状态联合上。`vendorVideoProvider` 由三个路由路径、体积上限、状态表，以及塑造启动请求的那一个函数，组装出完整的 `MediaVideoProvider`。每个适配器只保留其路由确实塑造得不同的部分：它的 origin、它的状态词汇、它的模型列举过滤、它的图像请求与响应处理，以及它的启动请求体。该 seam 包把 `@aeven/credentials` 作为 peer dependency，这正是共享凭据解析所需要的。

该路由的操作以属性函数类型而非方法声明，因为适配器会把它们直接交给 provider 的字段，而脱离对象的方法不会带着接收者。

## 验证

两个适配器既有的测试套件均原样通过，只有一处期望改变：DeepInfra 对于没有错误正文的终态状态所给的失败文本现在会写明厂商名，与 OpenRouter 既有的措辞一致，因为这两条消息合成了一条。共享模块通过这些套件达到完整的语句、分支与函数覆盖，克隆检测在这两个包之间不再报出任何重复。

## 考虑过的替代方案

**新建一个 `media-http` 包。** 一个包会带来 README、tsconfig、注册以及在布局中的位置，而这里只是一把函数，恰好只有两个消费者，且二者本就依赖该 seam 包。

**保留重复并抑制克隆报告。** 那些标记是给必须与其移植来源保持可 diff 的代码用的，而这两个适配器并非如此：它们是自有源码，凭据或上限规则的修复必须同时落到两处。

**只共享 HTTP 调用。** 那会把视频 provider 三个近乎相同的方法留在两个文件里，而重复行的大部分、以及全部由路径带来的风险，恰恰就在那里。

## 后果

对凭据解析、上游失败文本、体积上限或作业状态处理的改动只做一次，两个厂商随之跟进。第三个厂商适配器只需说明自己的 origin、路径、状态表与请求体，而不必重述传输层。作为这一份单一实现的代价，DeepInfra 的终态状态消息措辞发生了变化。
