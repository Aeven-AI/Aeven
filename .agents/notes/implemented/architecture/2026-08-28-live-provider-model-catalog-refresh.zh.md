# Agent Note：路由可从提供方增补式刷新其模型列表

Status: implemented

[English](2026-08-28-live-provider-model-catalog-refresh.md) | 中文

## 问题

pi-ai 目录路由提供的是 `getBuiltinModels`——`@earendil-works/pi-ai` 内部一份按其维护者节奏重新生成的静态快照。因此它会滞后于提供方当前列出的内容，而 harness 中没有任何机制能弥合这一差距。

以 2026-08-28 对 OpenRouter 线上 `GET /api/v1/models` 的测量为准：已发布 387 个模型，已安装快照中有 346 个，撇开 `:batch` 变体后**缺失 81 个**，另有 46 个快照条目已不再列于上游。缺失的并非冷门条目——`deepseek/deepseek-v4-flash-vision-exp`、`z-ai/glm-5.3`、`qwen/qwen3.8-flash`、`x-ai/grok-4.20-multi-agent`，以及整个 `perplexity/sonar*` 系列。一个被要求切换到具备图像能力模型的会话无法选中任何一个，因为 OpenRouter 上唯一这样的 DeepSeek 路由恰好不在快照中。

升级依赖并非解法。当前最新的 pi-ai 0.84.3 附带 351 个模型，仍然缺失 78 个。

## 决策

**路由可以写明用于刷新的模型文档。** provider profile 上的 `catalogRefresh: { url, format?, requireTags?, timeoutMs? }` 会在挂载时抓取提供方的 OpenRouter 风格 `GET /models` 一次，材料化快照未描述的已发布条目，并重新解析，使新增模型进入每个选择器。这些模型在任何读取发生之前就并入已安装默认值，因此 `models`、`modelOverrides` 及其诊断对待刷新得到的模型，与对待随附模型完全一致。

**该刷新按契约只做增补；已发布条目从不替换已安装条目。** 快照携带了该文档并不表达的手工调校值 `compat` 与 `thinkingLevelMap`——推理方言、developer 角色支持、逐等级的过线拼写。从 `supported_parameters` 推导这些值会静默降级今天可用的模型，等于用一个正确性回归换取一个列表缺口的弥合。修正已安装条目仍然是 `modelOverrides` 的职责，其诊断已能指名未命中项。新增模型只声明该文档所蕴含的内容：容量、接受的模态，以及——当它公布推理参数时——带 low/medium/high 的 OpenRouter 方言。其余一切保持缺省，而非猜测。

**刷新失败不等于路由失败。** 无法访问、缓慢或格式错误的文档会记录一条警告，并让路由继续提供快照：提供方的列表短暂不可用，不得连带让该路由下线。配置错误则是相反的情形，会在解析时大声失败——未写明 `url` 的 `catalogRefresh` 块会被拒绝，因为 profile 中没有别的东西能提供该文档的位置。

**pi-ai 未附带的提供方同样可以是第一方。** `KNOWN_ROUTES` 是一张本包知道如何配置的提供方表——目前是 DeepInfra——携带 profile 本来必须陈述的协议、端点、凭据引用与刷新配置。这些条目与 pi-ai 自身的路由并列进入可配置提供方目录，并被标记为 `declared: false`，因为那里存下的 profile 是一份凭据，而非某人不得不描述出来的路由。表中没有任何内容会注册路由：存在哪些适配器仍属编排，运行哪些提供方仍属用户的设置文档——正如随发行的 `llm-pi-ai` 行所述。

只有当某条路由的模型无需任何人编辑配置即可维持时——也就是提供方发布了本包能够读取的文档时——它才配进入该表。模型必须手工列出的提供方属于部署自身的设置，那里的列表归属清晰，而不属于随发行的表——否则它会像 pi-ai 快照一样陈旧。

**文档存在多种布局，而非单一形状。** `format` 在 `openrouter`（容量、模态与所接受的参数位于每个条目顶层）与 `openai-models`（朴素的 OpenAI 列表，在 `metadata` 下扩展，即 DeepInfra 所发布的形式）之间选择。`requireTags` 只接纳带有全部指定标签的条目，因为 DeepInfra 会在 chat 路由读取的同一份文档中列出图像、视频、语音与嵌入模型——190 个条目中有 106 个是 chat。

**已知路由会恰好一次地以空目录解析，而不是被拒绝。** 解析在挂载时同步进行，而首次抓取在其之后应答，因此模型只来自该文档的路由本会在刷新得以填充之前被拒绝，并因此永不注册。空路由无法服务任何请求，并在其模型到达之前不出现在浏览器目录中。既非目录路由、也非已知路由且未列出模型的路由仍会被拒绝——没有任何东西会去填充它。

**对其余每条路由而言，刷新是选择性启用的。** 没有任何随发行编排启用它。想要它的部署需写明端点，而这也是陈述端点的唯一方式：没有哪个 URL 是安全的猜测，而设默认值会让每条路由在挂载时都访问网络。

## 验证

`live-catalog.spec.ts` 覆盖了映射（协议、端点、容量、由逐 token 十进制字符串换算的每百万成本、按 pi-ai 词汇过滤模态、仅对公布推理的条目给出推理等级，以及对未公布者不作任何猜测）、增补式合并（跳过已安装 id、重复的已发布 id 保留首个、跳过不可用条目而不使整份文档失败）、抓取的失败模式（非 OK、超时、调用方取消），以及配置解析（超时默认值、缺省块，以及被拒绝的无 url 块）。

路由材料化被端到端断言：刷新得到的模型与整个已安装目录一并出现在 `piProvider.getModels()` 中；未配置刷新的路由原样提供快照；与已调校的已安装 id 冲突的已发布条目，不会改动该条目的名称与容量。

对照真实端点，OpenRouter 路由从 346 个模型增至 433 个，且 `deepseek/deepseek-v4-flash-vision-exp` 以 `["text", "image"]`、1,048,576 的上下文窗口与 384,000 的输出上限被材料化。

DeepInfra 以同样方式验证，起点是一份只带 `apiKeyEnv` 的 profile：在 190 个已发布条目中材料化出 106 个 chat 模型；该路由解析为对 `https://api.deepinfra.com/v1/openai` 使用 `openai-completions`；`Qwen/Qwen3.5-27B` 从 `metadata` 读到其真实的 262,144 上下文窗口，而非路由回退值；其 vision 标签成为 `["text", "image"]`；且没有任何图像、嵌入或语音模型进入该路由。

## 影响

启用刷新的路由会在挂载时发出一次出站请求。该请求不带认证，并在 fiber 销毁时取消，但它终究是启动期的网络访问，这也正是它选择性启用的原因。

新增模型不携带任何调校后的兼容性值。若某个刷新得到的模型需要该文档并不表达的推理方言，就需要一个 `models` 条目来陈述它——而其随附的同类模型从不需要这一步编辑。这是拒绝猜测所付出的、有意为之的代价。

已发布文档属于外部输入，因此刷新以防御方式读取它：条目在结构上按 `unknown` 定型并逐字段校验，且单个不可用条目绝不会使整份文档失败。

`ResolvedPiAiProviderProfile` 现在以一个 `url`、`format`、`requireTags` 与 `timeoutMs` 均已存在的已解析形态覆盖 `catalogRefresh`，因此运行时不会重新检查解析阶段已经确定的事情。

DeepInfra 现在会对每个部署出现在可配置提供方目录中。在有人存入凭据之前它不会运行任何东西，但它确实是该列表中多出的一个提供方，且其条目断言了本仓库如今所拥有的协议与端点：若 DeepInfra 变更其中任何一项，需要更新的正是这张表。

加入第二种文档布局使 `format` 成为一个兼容性面。第三个列表形式又不相同的提供方，将是同一批读取器中的第三个分支，而非一个新模块；若该表增长到超出少数几个条目，这些读取器应当拆为按格式划分的模块，而不是继续加宽条件判断。

## 考虑过的替代方案

**升级 pi-ai 后就此了事。** 依据测量被否决：当前最新版本只弥合了 87 个缺口中的 5 个。该滞后是结构性的，而非依赖版本陈旧。

**用线上文档整体替换快照。** 被否决：这恰恰丢弃了让推理模型得以工作的手工调校，且该回归会表现为微妙错误的请求，而非缺失的模型。

**按请求抓取文档，或按 TTL 抓取。** 暂时否决：挂载时抓取一次已经回答了所陈述的问题，而带过期策略的缓存是需要拥有的状态——失效、并发刷新、退避——目前没有消费者要求会话中途的新鲜度。

**从 `supported_parameters` 推导 `compat`。** 被否决：该字段说明端点接受哪些参数，而非它讲哪种方言。接受 `reasoning_effort` 完全不能说明推理是否以 `reasoning_content` 形式出现在 assistant 消息上，而猜错的结果是一个坏掉的请求，而非一项缺失的功能。
