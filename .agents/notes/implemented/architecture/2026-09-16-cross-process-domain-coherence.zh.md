# Agent Note: 跨进程的领域一致性

Status: implemented

[English](2026-09-16-cross-process-domain-coherence.md) | 中文

## 问题

存储领域层假定 `~/.aeven` 由一个进程独占。让两个 harness 实例跑在同一个 home 上——已发布的 web 应用与一份桌面构建，或者两个 dev server——会让会话标题从会话列表中消失，并静默地摧毁工作区分组。

原因不在介质。设施打开一个领域时只调用一次 `unit.loadAll()` 并构建 `Map`；此后 `KvTableImpl.get()` 的每一次读取都由该 `Map` 提供。`put()` 先写穿单元，再改动同一个 `Map`。因此每个进程都持有一份在打开时刻取得的私有快照，而两个进程会在任意一方做第一次写入时分叉。把 JSON 后端换成 `storage-sqlite` 也解决不了：它的 `loadAll()` 同样是一次批量读进同一批 `Map`，因此 WAL 会让并发写入变安全，而读取同样陈旧。

有两种机制把这种陈旧变成了用户可见的丢失：

- **标题被读作不存在。** `session_projcache` 是 `per-record` 布局，而 `parseRecord` 把 `version` 戳落在 `[version, ...compatibleVersions]` 之外的文档当作*不存在*，而不是当作错误（[storage-json/src/format.ts](../../../../packages/storage/storage-json/src/format.ts)）。处于领域版本 5 的构建读不了更新构建写下的版本 7 记录，而 `ApiSessionList.summarizeCold` 又只靠缓存提供冷行，于是一条被丢弃的行被渲染成「Untitled session」。底层的 `session/title` 事件在会话 JSONL 中完好无损；丢失它们的只是派生的读取路径。
- **工作区分组被覆盖。** `workspace` 领域用的是整单元布局，因此一份 `workspace.json` 同时承载每条 workspace 记录和全局的 `archivedSessionIds`，而每次写入都会重新发布写入进程的整份内存快照。与标题不同，这里没有任何东西可以重建它。

值得点明的不对称之处：`session-persistence-jsonl` 早已正确地解决了多进程问题。它为每个会话目录取得内核 `flock(2)`，该锁即使进程死亡也会被 OS 释放，并通过 `link()`+`unlink()` 发布——选择它而不选 `rename()`，是因为 link 会以 `EEXIST` 失败，而不是覆盖。会话数据本就是多写入方安全的。只有派生的领域层不是，因为它当初被建成进程内缓存，随后又被赋予对 UI 展示内容的权威。

## 决策

当另一个进程写入某个已打开的领域时，该领域会向介质收敛，而这些变更以普通的 `domain/changed` 事件到达消费方。

事件之所以是载体，是因为它的消费链已经存在，并且已经能正确处理增量：`WorkspaceFeed` 订阅 `domain/changed`，并向已连接的客户端推送有序增量（[workspace-controller/src/feed.ts](../../../../packages/api/workspace-controller/src/feed.ts)）。一条到达该事件的外部变更无需改动即可驱动整条流水线。`events.ts` 早已把它命名为「后续阶段中跨进程变更推送（RPC 帧）的事件源」；本 note 就是那个阶段，只是以文件系统而非 RPC 作为传输。

### 归属

检测属于后端，因为只有后端了解自己的介质。`KvUnit` 携带一个可选成员 `watchExternal(onExternal)`（[storage/src/backend.ts](../../../../packages/storage/storage/src/backend.ts)），与既有的可选成员 `backupRecord` 并列。它报告的是*位置*——`{ table, key }`，其中 `table: ''` 与 `key: ''` 指称全局单例——而绝不上报值：介质具有权威，领域会重新读取它。无法观察外部写入的后端省略该成员，其领域则保留打开时刻的快照，也就是此前每个调用方的行为。

`DomainImpl.applyExternal` 是消费方。设施在构造之后调用一次 `observeExternal()`，而 `runClose()` 在排空写入链之前停止观察。

不存在单独的一致性包。只有当各角色独立演化时才值得设一个能力 seam；在这里，检测与后端本就拥有的介质不可分割，因此这个可选的 `KvUnit` 成员就是全部约定，而一个独立服务只会在没有第二个实现者的情况下多出一次跳转。

### 检测外部写入

`ExternalWatcher`（[storage-json/src/external-watch.ts](../../../../packages/storage/storage-json/src/external-watch.ts)）只持有一项事实：它已观察过的每份文档的 stat 身份（`mtimeMs`、`size`、`ino`）。只要该身份与它记录的不同，它就上报一个位置，因此检测绝不依赖文件系统事件的内容。

它监视后端根目录、单元目录以及每个已存在的表目录。监视根目录是承重的，而非防御性的：单元目录与每个表目录都由各自的第一次写入惰性创建，`fs.watch` 无法观察不存在的目录，而后端根目录是唯一保证存在的一层，因为后端在打开时创建它。没有根目录监视器，一个从未被写入过的单元会在该进程的整个生命周期里停留在仅清扫状态。每次对账都会重新执行安装，因此后来才创建的目录会在第一次看到它的那一趟取得自己的监视器。

自身写入靠戳记排除，而不是靠路径记账：`writeDocument` 在每次 durable 写入之后记录得到的 stat 身份，因此下一次对账找不到任何要上报的东西。自身写入与外部写入竞速同一份文档时会被上报，这是正确的——介质上的字节已不再是本进程写下的那些。

### 监视漏掉事件时

`fs.watch` 会丢事件：队列溢出、网络挂载、什么都不投递的平台。把「无事件」当作「无变化」会在新的地方重新引入同样的静默陈旧，因此监视只是加速器，绝不是权威。

守住这条线靠两条性质。对账过程重新 stat 目录，而不信任任何事件负载，因此漏掉一个事件付出的是延迟，而不是一个错值。又因为对账是幂等的且开销很低，周期性清扫会运行同一趟对账：监视事件负责延迟，清扫充当下限。在 `fs.watch` 不可用的地方，单元只跑清扫，收敛得更慢，而不是完全不收敛。

节奏（`debounceMs: 50`、`sweepIntervalMs: 5_000`）是常量，不是配置。防抖只是把一批文件系统事件合并起来，而清扫的存在是为了给丢事件造成的损害设一个上界；两者都不是随部署而变的取舍，部署方若想要不同的收敛上界，改变的是自己读取的频率。

### 应用外部变更

`applyExternal` 在领域既有的写入链上作为单个任务运行。这正是它安全的原因：该链本就是一切变更的串行化点，因此外部应用不会与本地 `put` 交错，而进程之间的后写胜出仍和以前一样在介质上解决。在该任务内，每个被上报的位置都从介质重新读取，用表自身的 schema 校验，写入 `Map`，然后才发出。

这个顺序是强制的。包不变式断言所发出的值与内存已经持有的值完全相同（[storage-domain/src/invariant.ts](../../../../packages/storage/storage-domain/src/invariant.ts)），因此在变更之前发出就会让它失败。

外部变更与本地变更携带同一个 `DomainChanged` 联合类型，没有来源判别字段。一个对外部写入采取不同行为的消费方，就是在推断是哪个进程写下了某个值，而那正是本次改动所消除的脑裂。

未通过 schema 校验、或其版本戳不被本构建接受的记录会被记日志，并让当前值留在原处：这与打开时加载所做的判断相同，也正是外部写入不可能演变成损坏的原因。

### 版本门控

跨版本读取保持单向：领域版本是兼容性承诺，不是协调机制。变化的是后果。读不了更新记录的构建不再把它呈现为缺失数据——`ApiSessionList` 从 durable 日志重新折叠无标题的行，因此缓存提供不了的标题仍会被展示。

## 考虑过的替代方案

**每次读取都重新校验。** `get()` 对底层文档做 stat，并在它变化时重新读取。更简单，也不需要监视。不予采纳，因为 `get()` 在整个读取面上都是同步的，而会话列表路径在每次列出时逐行调用它；把它改成异步或在 stat 上阻塞，要么改动每个调用方，要么把文件系统 I/O 放进列表渲染路径——而那正是只有缓存的列表当初要避免的开销。

**带 WAL 的 SQLite 后端。** 真正的并发写入安全，也是显而易见的选择。它是作为不充分而非错误被否决的：它修好了写入，而 `loadAll()` 让读取同样陈旧，因此标题仍会消失。它的 README 写明「跨进程协调属于范围外」，它也没有忙等待重试。它仍然是本设计之下合理的介质，这也是检测为什么活在一个可选的 `KvUnit` 成员背后，而不是假定文件。

这也不是一个性能论证。在真实 home 上对 176 条 projcache 记录、合计 1.68 MiB 的实测：一次等价于 `loadAll()` 的完整读取加解析耗时 42 ms，一次整记录原子写入在中位数 7 KiB 记录上耗时 0.21 ms、在最大的 106 KiB 记录上耗时 0.51 ms，而整单元的 `workspace.json` 重写耗时 0.21 ms。占主导的是 fsync 系统调用，而不是序列化：体积增大 15 倍只让耗时变为 2.4 倍，而 SQLite 在每次 durable 提交时付出同样的 fsync。

**用一个锁文件让第二个实例只读。** 便宜且安全。不予采纳，因为它让在 web 应用旁边运行桌面应用变成一种降级模式，而不是受支持的用法。

**用一个 broker 进程拥有 `~/.aeven`。** 构造上只有一个写入方，无需对账。不予采纳，理由是它不成比例：它引入了生命周期、协议格式和一个 broker 死亡的失败模式，都比问题本身更大，而且它仍然需要本方案所用的 `domain/changed` 路径。

**按间隔轮询 stat。** 可移植，没有 `fs.watch` 的各种怪癖。作为主要机制不予采纳，理由是延迟与空闲开销都不划算，并保留下来作为支撑监视的清扫。

## 后果

共享同一个 home 的两个 harness 进程会收敛：在真实 157 条记录的 projcache 上，一个进程写入的记录大约 95 ms 内对另一个进程可见，而 workspace 全局——承载展示顺序与 `archivedSessionIds` 的那个槽位——以同样的方式收敛。让 web 应用与一份桌面构建跑在同一个 `~/.aeven` 上，现在是受支持的配置。

代价是：`domain/changed` 的扇出现在跨进程承重，因此那些隐含「只收自己的写入」的监听器会看到外部写入。这是预期语义，任何消费方都不应该区分二者，但这扩大了该事件的影响面。一个启用了监视的后端上每个已打开的领域还会携带一个间隔定时器与几个目录监视器。

它没有换来的是：收敛是最终一致的，不是事务性的。两个进程写入同一条记录仍然在介质上按后写胜出解决；它们是收敛并察觉，而不是串行化。跨进程的读-改-写竞态仍可能丢失一次更新，任何需要真正原子性的东西都必须按 `SessionWriteLease` 的方式取锁。

整单元（`single` 布局）的领域没有变化：那里的外部写入会作为整份文档替换落地。`workspace` 在同一次改动中迁到了 `per-record`，因此促成这次改动的那个领域已不再属于这一类。

## 相关

让缓存未命中能从 durable 日志恢复的冷列表重折叠，以及 `workspace` 的布局迁移，都与本 note 一同落地。`bootstrapLegacyUnit` 在同一次改动中获得了全局迁移：它此前只复制表记录，因此在一个全局承载权威状态的单元上采用 `per-record` 会丢掉那个全局。
