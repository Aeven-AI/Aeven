# Agent Note: 提供方登录遵循部署所声明的方式

Status: implemented

[English](2026-09-21-provider-sign-in-flow.md) | 中文

## Problem

使用 Google、X 或 Apple 登录时，总是把页面自身的文档导航到提供方（`Authenticate.signInOauth` 中的 `location.href = oauthUrl`）。随后提供方把该文档送回 `<origin>/oauth-result/<session>/<challenge>`，这会让整个 kernel 再次启动，只为抵达那次交换。

这种形式正是公开 web 客户端所要的：提供方注册就是按它书写的，落地点也是应用的普通页面。但对于从自定义 scheme 或 loopback origin 提供自身页面的应用，它是错误的形式——被跳转的文档会替换读者正在使用的外壳，而在桌面上还会打开一个外壳随后必须拦截并关闭的窗口。桌面外壳此前正是如此：它把 `will-navigate` 按提供方 URL 作为键，打开自己加固过的窗口，并在读者返回时用 `loadURL` 丢弃自己的应用窗口。

页面中没有任何东西说明部署要哪一种形式，因此客户端无法区分公开站点与已安装的应用。

## Decision

**形式是部署事实，由 Host 声明，并在提供提供方时为必填。** `identity-user-aeven` 新增经过校验的 `oauthFlow: 'redirect' | 'window'` 字段，并与各提供方 URL 一起写入 `__AVN_AEVEN__`。`apply()` 在加载时解析它，并在配置了提供方 URL 却未声明该字段时抛错：默认为某一种，会把一个无法离开自身文档的页面交给那种会离开文档的形式，而声明该提供方的部署才是唯一知道它服务哪一种的一方。声明了形式却没有提供方 URL 时，它被忽略而非拒绝——没有任何登录可供它描述。

`packages/bundle/web-app/cordis.patch.yml` 声明 `redirect`（公开页面），可由 `AEVEN_OAUTH_FLOW` 覆盖。`apps/desktop-host` 声明 `window`，因为外壳的页面从 `avn-app://` 提供自身，而在那里，被跳转的文档会替换 Electron 正持有的外壳。

**外壳不必被告知它渲染的是哪一种形式，就能服务两者。** 打开提供方的页面会得到外壳自己加固过的窗口——清理过的 user agent、无 preload、沙箱内——而该窗口返回时的落地在那里完成交换，经由持有 API refresh cookie 的那个会话，而不是被加载进应用窗口。改为导航到提供方的页面则保留原本就在服务它的拦截，其落地被载回它来自的那个窗口，也就是该页面所期望的形式。被接管的 Host 是一个外壳并不声明其形式的部署，而它的两种情况都能工作。

**在 `window` 下，提供方由独立窗口抵达，页面本身永不移动。** `openProviderSignIn(url)` 以固定名称打开该窗口，因此读者第二次按下提供方按钮时替换第一个窗口，而不是在其后叠出第二个。

**交接靠的是会话，而不是文档之间的消息。** 落地窗口就是本应用自己的 `/oauth-result`，因此它自行交换提供方的回答——与跳转文档所运行的同一套 `checkOauthToken` 与 `getProfile`——从而在该 origin 的 cookie 中建立会话，两个窗口共享它。随后 `OauthResult` 以关闭窗口来报告：由本应用打开的窗口中的落地，是登录完成之处，而不是应用该存在之处（否则[启动 gate](../bug-fix/2026-09-21-auth-gate-boots-in-place.zh.md) 会在其中启动一个外壳，而打开它的那个文档已经在等待了）。打开该窗口的文档用 `awaitProviderSession()` 等待该会话，反复读取 profile 直到 API 给出一个，随后完全按邮件表单之后的方式继续：读取 profile、离开认证界面，并让 gate 启动。

**被拒绝仍在被拒绝登录所在之处呈现。** 携带错误的落地，或交换失败的落地，会把致歉留在打开它的那个窗口中，与 `redirect` 的呈现一致；本文档继续等待，而读者关闭那个窗口后，仍停留在登录界面、按钮就在手边。

## Alternatives considered

**保留单一形式，让桌面端自行适配。** 外壳可以对每个部署都继续拦截渲染进程的导航，也就是它今天的做法。已否决：这使应用窗口的文档成为一次登录所消耗的东西，读者的页面成为所失去的东西，而且恰恰发生在最承受不起的那一类部署上。形式是关于部署的事实，只有部署能声明它。

**由页面被服务的位置推断形式。** 客户端可以读取 `window.location.protocol`，把非 `http(s)` scheme 视为 `window`。已否决：它让一项与安全相邻的路由决策躲在运行时猜测背后，无法在真实桌面上区分 loopback 提供的页面与浏览器中的同一页面，也违背仓库规则——因部署而异的选择是经过校验的配置字段，而不是回退值。

**在窗口之间传递结果。** 落地可以把 `session/challenge` 这对值报告给它的 opener，由后者去交换。已否决：为了同样的结果引入更多机制——落地本来就是本应用自己的页面，它能自行交换这对值，而它留下的会话与其它任何登录路径留下的完全一致。于是 opener 读取的是会话，而不是相信一条消息。

**永久轮询会话。** 这次等待没有上限，也没有取消：放弃提供方窗口的读者会让它一直保持待命，登录界面也留在那里。这是有意保留的——那正是中断登录一改之后 gate 所建模的同一种未完成状态，而读者的下一步动作就是那个提供方按钮。桌面外壳是唯一会察觉到被放弃窗口的部署，而那个窗口归它所有。

## Consequences

一个无法离开自身文档的页面现在可以提供提供方登录，而这是桌面部署在外壳不再为登录重新加载之前所需要的。公开部署不变：它声明 `redirect`，抵达提供方的方式与从前完全一致，而这个开关把这一点从隐含变为显式。

只要部署提供提供方，`oauthFlow` 就是必填，因此现有 `cordis.yml` 若配置了提供方 URL 却没有它，现在会加载失败。这是上述选择的预期代价——声明了提供方的部署就是服务提供方登录的部署，而形式现在是它所服务内容的一部分。

落地的 `<title>` 与窗口尺寸归提供方所有；应用只声明会打开一个窗口、它的名称与尺寸。

`packages/client/ui-auth-aeven/src/client/auth/views/*.tsx` 被排除在逐文件覆盖率之外，并保持与 Aeven 客户端源版本可 diff，因此这两处界面改动——`Authenticate.tsx` 中的形式分支与 `OauthResult.tsx` 中的关闭——没有覆盖率证据。`auth/services/oauth.ts` 在门禁之内，覆盖率为 100%。

## Testing

- `oauth.client.spec.ts` 覆盖该窗口：打开它所用的 URL、名称与特性；只有当另一个文档打开了本文档时它才是落地；以及那次等待——会话已存在时立刻返回，API 尚无会话时继续等待，API 完全无法抵达时也继续等待，而不是把它读成已完成。
- `config.client.spec.ts` 覆盖解析器：声明过的形式，以及没有提供方的页面所抵达的回退值。
- `packages/identity/user-aeven/tests/resolver.spec.ts` 覆盖 Host 一侧：页面被服务时携带的形式；提供提供方却未声明形式时拒绝加载；以及没有提供方时声明过的形式被忽略。
- 在 `redirect` 之下，组装后的浏览器没有变化，而 web 车道所运行的每个部署都是如此：gate、预加载页与启动路径由已经负责它们的测试套件覆盖。

## Deferred

`redirect` 部署所经历的那些文档加载是该形式自身所声明的，并非缺口，而为它们保留的外壳拦截继续存在。既非提供方也非部署所选择的加载已不再存在：[会话结束会把页面交还给 gate](../bug-fix/2026-09-22-session-end-hands-the-page-back.zh.md)，且就在读者身处的文档中完成。
