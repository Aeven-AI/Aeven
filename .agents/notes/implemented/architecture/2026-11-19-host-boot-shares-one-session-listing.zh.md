# Agent Note：Host 启动共享一次会话列举，会话列表分两次请求返回

Status: implemented

[English](2026-11-19-host-boot-shares-one-session-listing.md) | 中文

## 问题

在一个有 1,339 个会话、八个已登录账户的主目录上对桌面 Host 做性能分析，结果显示 Host 在启动后约 2.57 秒才报告就绪（开发构建，热启动中位数），最后完成的插件是工作区注册表，比几乎所有其他插件晚约一秒。原因如下：

- 九个调用方同时列举全部已存储会话：每个账户一个 session-sync 镜像，加上工作区注册表。每个调用方都对所有会话目录各自执行一遍 `readdir` 和 `stat`。
- `indexHeaders` 对每个会话的工作目录单独解析：798 个会话分布在 13 个不同目录中，却产生约 1,600 次顺序文件调用。
- 工作区注册表在其存储域打开之后才开始列举，而列举并不依赖该存储域。
- `sessionHome`、`placeSession` 和 `fileSession` 通过扫描每个工作区的全部成员来查找会话所属的工作区。
- `session/list` 为每一行返回全部投影提示，回复大小为 2 MB，侧边栏在此之前无法绘制任何标题。

## 决策

- `session-persistence-jsonl` 在并发调用方之间共享一次列举。在列举进行期间到达的调用方等待一次尾随列举，该列举在当前列举结束后才开始，因此调用方绝不会收到早于自身调用的结果。每个调用方得到各自的 header 副本。
- `indexHeaders` 在一次遍历中对每个不同的工作目录只解析一次。
- 工作区注册表在打开存储域之前开始列举，并在原先调用 `list()` 的位置读取结果。
- `WorkspaceEntity.holds(id)` 回答单个会话的成员关系，注册表通过它查找会话所属的工作区。
- `SessionListRequest.projections` 指定调用方需要的投影键；每行随后只携带这些键和 `sessionListMetadata`。Web 客户端先用一次只请求 `title` 与 `schedule` 的请求（465 KB）绘制各行，再用第二次不加过滤的请求读取完整提示。
- `SyncVault.documentId` 按 vault 密钥缓存派生出的 id。

在同一主目录上测得的 Host 就绪时间：2.57 秒 → 2.33 秒（共享列举）→ 2.14 秒（按目录解析）→ 2.04 秒（提前列举）。document id 缓存在启动时没有可测量的变化，因为首次遍历中大多数名称各不相同。打包构建未重新测量。

## 考虑过的替代方案

- **加入正在进行的列举。** 暂不采用：调用方可能收到早于自身写入的结果，要排除这种情况需要在约 20 条写入路径上引入写入纪元。
- **把 Host 打包成更少的文件。** 不采用：测得的收益为 0.3–0.4 秒，却需要改动每个插件解析方式的打包变更。
- **更大的 libuv 线程池或新生代。** 已测量，无效果：启动受主线程限制。

## 影响

已初始化但没有工作区的注册表会开始一次它从不读取的列举。在两次列表请求之间打开的聊天，其模型和权限提示来自它自己的历史快照，而不是来自列表。剩余的启动开销按测量值排序：插件导入（约 0.9 秒）、为每个已存储账户同步挂载同步文档（约 0.3 秒）、客户端模块图重新组合（约 0.19 秒）、投影缓存校验（约 0.15 秒）以及语音模型哈希计算（约 0.1 秒）。
