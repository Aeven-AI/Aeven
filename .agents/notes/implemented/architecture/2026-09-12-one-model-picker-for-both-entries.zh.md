# Agent Note: One model picker for both model entries

Status: implemented

[English](2026-09-12-one-model-picker-for-both-entries.md) | 中文

## Problem

Web composer 在同一份模型目录之上暴露了两个选择器。`/model` 是 `popupSelect` 贡献项，由 `ui-commands` 的共享外壳渲染：该外壳自带搜索输入、在本地过滤已加载行、渲染每行的详情行，并在重试条中呈现加载与选择失败。composer 的模型位（`conversation.input.model`）渲染自己的两级 Model/Effort 菜单（按 Figma 496:26454），自带行渲染、完全没有搜索、没有目录说明行、没有加载重试行，选择失败只给一个瞬态 toast。数据本已统一——每会话一份 `ModelDirectory`、一份目录、一个 `session.selectModel`——但呈现并未统一，且这种分叉肉眼可见：同一份目录在一个入口给出可搜索列表，在另一个入口给出不可搜索列表，而此后每一处行改动都要做两遍。

## Decision

模型位保留两级入口，并停止持有任何列表。其触发器打开 Model/Effort 选择器（每行为标签、当前值与右箭头）；Model 行打开 `/model` 注册的那个 spec，Effort 行在同一个外壳中打开当前模型的推理强度等级。两行都经 `CommandUiContract.openSelect(sessionId, command, spec)`（斜杠路径的无 token 兄弟入口）抵达外壳：Model 行传入的就是那个已注册的 spec 对象（同一性，而非副本），因此没有任何入口会分叉出相似的列表。

因此 `CommandUiContract` 增加了这一个方法，外壳的打开来源联合类型（`TokenSegment`）在 `menu` 与 `enter` 之外增加了 `button` 变体。两条 token 路径保留各自的草稿 CAS 把关，而 `button` 打开不消费任何内容，因为它从未来自草稿；`TokenPathSegment` 命名带 token 的子集，使那些不经过落定即触发的内部执行路径无法抵达 consume-token 派发。

推理强度保持为独立列表，而不是并入模型列表成为额外行：`effortPopupSpec` 提供当前模型由适配器公布的等级、仅在适配器未配置默认值时提供提供方默认行，且每行以这些等级所属的模型作为详情。它有意不注册为命令——一个会话的等级只有紧挨着它所属的模型才有意义，因此该列表只能从模型位抵达——但它仍然是共享外壳，所以搜索与渲染与模型列表一致。`effortLevelsOf` 是行与选择查找共同读取的**唯一**推导来源，因此被选中的行绝不会解析出适配器并不提供的推理强度；推理强度行 id 位于 `effort/` 命名空间，与既有的 `failure/` 行一致。模型行应用该模型的默认推理强度；推理强度行保持路由不变，只替换推理强度。

由于同一套行构造现在服务于动辄数百个模型的目录，外壳打开时也会落在调用方标记的行上：`PopupSelectController.load` 用第一行带 `active: true` 的行作为高亮初值——在过滤后的行内取索引，因此保留了搜索文本的重试不会留下过期索引——视图既有的滚入视野效果跟随该高亮。因此打开模型列表会落在当前模型上：以同样的悬停样式高亮并滚入视野，而不是停在目录首行。

失败文案在每条路径上都属于外壳：被拒绝的选择保持列表打开、搜索文本与高亮不变，并再次选择即重试；加载失败则显示带显式「重新加载」的条。因此模型位的注入面是 `available`、`directory`、`load`（让选择器打开时的取值最新）、`openModel` 与 `openEffort`——没有行、没有过滤、没有失败状态。

## Alternatives considered

**给模型位自带的列表加一个搜索输入，其余保持不变。** 这是最小改动，也能完全保留 Figma 菜单。之所以拒绝：它留下两套行构造、两套过滤与两套失败表面，必须靠手工保持同步——恰恰是这次不一致的根源——并且模型位的列表仍然缺少外壳已有的说明行与重试条。

**把推理强度等级并入模型列表作为额外行。** 一份列表、一份搜索、不需要第二个 spec。之所以拒绝：这会让同一份列表同时回答两个不同的问题，并删除模型位的 Model/Effort 选择器——那是用户已经在使用的既定两级入口；而且等级只有相对于某个模型才有意义，混合列表无法像「每一行都属于该模型」的列表那样清楚地表达这一点。

**删掉选择器，让触发器直接打开模型列表。** 这是通往「composer 按钮直接给出可搜索列表」的最短路径，本次改动的第一版正是如此。评审后拒绝：它移除了用户依赖的一步，并使推理强度等级在 composer 中完全失去入口。

**让按钮通过向 composer 插入 token 来「运行」`/model`。** 这会字面复用斜杠路径，但会写入用户草稿、事后必须清理该 token，并且在草稿非空或已含斜杠命令时都会失效。

**让模型位在共享外壳之上使用第二个 spec，同时把模型列表保留为私有实现。** 两个入口都会用同一个组件，但会有两份 spec，因此行与过滤仍可能分叉——而本次改动要保证的性质是 spec 同一性，而非组件复用。

**保留两个选择器，把差异视为有意为之。** 那种使 TUI 与 Web 略有不同的分歧针对的是**未列出的当前模型**，而不是某个选择器提供哪些能力；两个外观相似却能力不同的列表，不是同一份目录可以接受的呈现。

## Consequences

模型列表现在字面上是同一个组件、同一套行构造：`/model` 与模型位的 Model 行打开同一个对象，因此搜索、过滤、行渲染、空／加载／重试文案与键盘行为都无法分叉。推理强度列表获得了同样的外壳——搜索、方向键与共享失败条——却没有变成第二套实现，而选择器保持其作为两者入口的位置。composer 路径上的模型行也重新带上目录说明，因为共享行构造包含了模型位曾丢弃的详情行——随后两侧都收窄：详情行只显示提供方名称，因为 DeepSeek 为每个模型都公布一段说明而 OpenRouter 没有，而那段说明移入外壳只用于搜索的 `keywords`，于是它仍可被搜到，却不会把提供方名称挤出该行。行的选中标记就是高亮本身所用的悬停底色，而不是图标；图标会与详情行争该行的宽度。

代价是列表由命令覆盖层而非选择器锚定，因此选择器无法得知列表何时打开：它在移交时关闭，触发器只报告自己的 `aria-expanded`。模型位的注入面改变了形状（不再携带选择动作），并且两份列表都在外壳标签 `model` 下打开——因为推理强度列表是同一功能的第二份列表，为它编造一个命令名会把一个并不存在的 `/effort` 放进面向用户的 aria 文本里。客户端命令约定增加了一个方法、联合类型增加了一个变体——这是每个业务包都能看到的约定，因此 `openSelect` 现已成为其他贡献项可用来让按钮与其斜杠命令行共用同一选择器的表面——并且外壳的打开高亮现在对所有贡献项都从被标记的行取初值，因此 `/permission` 也会随之打开在当前预设上。

## Testing

`packages/client/ui-commands` 固定新入口：`openSelect` 用给定 spec 驱动会话自己的控制器、以已绑定的 composer 焦点落定、不派发任何 consume-token，并且对无作用域的会话返回 `false`。它还固定打开时的高亮——有被标记行时落在该行、无标记时落在首行、重试保留搜索文本时索引取自过滤后的行——以及视图在外壳打开时把该行滚入视野。

`packages/client/ui-model-selection` 固定模型位的选择器：触发器的模型与推理强度标签、原始 `provider/model` 回退、加载标签、锁定与不可用状态、Model 与 Effort 两行及其当前取值、Model 行打开 `/model` 贡献项注册的那**同一个 spec 对象**（用 `toBe` 而非深比较）而 Effort 行打开另一个 spec、Escape 关闭选择器且不打开任一列表，以及没有推理元数据的模型不显示 Effort 行。它通过共享 spec 固定两份列表：模型列表标记宿主当前选择并拒绝失败行；推理强度列表恰好携带已公布的等级，并以它们所属的模型为详情（仅在适配器无默认值时出现提供方默认行）；推理强度行保持路由不变，只替换推理强度。

`declared-reasoning` Web e2e 驱动选择器的 Effort 行，并以 golden 固定该列表（Default/Off/High/Max，各自标出所属模型），随后把所选等级记录进 Agent 默认值；`default-model` 经选择器的 Model 行完成切换，并断言列表打开时当前模型被高亮且位于视野内——即便它并非目录首行。
