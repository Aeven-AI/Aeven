# Agent Note：MemOS 核心运行在工作线程上

Status: implemented

[English](2026-11-18-memory-cores-on-worker-threads.md) | 中文

## 问题

MemOS 以同步 SQLite 在 Host 进程内运行每个账户的核心。一个账户的搜索、排序和捕获会占住 Host 唯一的事件循环，因此其他每个账户的轮次都要等待，而一个轮次自身的召回还要与它的捕获竞争。在 2026-11-18 的列表查询修复之后，被分析的一个轮次仍有约 0.9 秒 Host 时间花在搜索和排序上，而且启动后的第一次搜索会在该线程上加载账户的向量索引。

## 决定

`@aeven/memory-memos` 在 `coreWorkers` 个工作线程上运行核心；`0` 让它们留在 Host 进程内。Web 与 Desktop 组合使用一个工作线程，托管组合使用八个。

- **接缝。** Host 为每个账户的 `MemoryCore` 保留一个替身。它的大约二十个方法接收并返回纯数据，因此每次调用都是发给持有该账户核心、数据库连接和向量索引的工作线程的一条消息。其上的运行时不变。
- **放置。** 账户在持有账户最少的工作线程上打开并留在那里。停止的工作线程会让其进行中的调用失败并释放其账户，这些账户在下次使用时重新打开。
- **回调 Host。** LLM 请求回到 Host 的桥。在会话路由内发起的调用会记录 Host 的异步上下文（`AsyncLocalStorage.snapshot()`），工作线程用其 id 标记该调用的后续执行，桥在所记录的上下文中运行，因此路由和轮次判定槽能到达调用返回之后发出的请求。保留最新的 `coreCallContexts` 个。托管嵌入请求进入 Host 的嵌入队列。维护闸门以同步方式询问：工作线程在一个共享单元上最多等待 `coreGateTimeoutMs`，没有答复视为拒绝。
- **证据。** `scripts/load.ts` 让每个账户同时做一次召回。在 40 个账户、每个 2,500 条 trace 的情况下，八个工作线程每秒完成 1,885 次召回，调用线程最多被占用 13 毫秒；进程内核心每秒完成 464 次，占用 68 毫秒。

## 考虑过的替代方案

- **每个账户一个进程，或独立的记忆服务。** 推迟到一台机器不够用时；消息接缝相同。
- **向量索引库。** 在所见规模下不需要：对 45,000 个向量的内存扫描只需数十毫秒。
- **在工作线程中运行整个提供方。** 已否决：召回编排要读取位于 Host 上的会话、工作区和设置。

## 影响

每个工作线程在 MemOS 自己的 512 MB 预算内持有其账户的向量索引，因此内存用量随工作线程数增长。空闲账户不会被关闭。记忆同步仍在 Host 线程上打开每个数据库，会话持久化和 agent 循环也仍在该线程上；`@aeven/hosted-app` 会在该线程被占用时记录日志。
