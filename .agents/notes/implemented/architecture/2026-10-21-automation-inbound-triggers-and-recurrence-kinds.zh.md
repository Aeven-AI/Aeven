# Agent Note: 入站触发与更完整的重复模型

Status: implemented

[English](2026-10-21-automation-inbound-triggers-and-recurrence-kinds.md) | 中文

## 问题

内置自动任务只按时间触发：一次性、间隔、每日、每周。任何应当由外部服务启动它的事情——部署钩子、监控告警、表单提交——都只能被定时器轮询，而定时器当时是产品唯一的触发方式。重复的表达能力也有同样的上限：「每 N 分钟」和「这些工作日」让月末与季末的工作（每月一日对账、第一个周一的报表、续订日）只能近似表达。最接近的已发布同类产品 Grok Bot 的 routine 接受 cron、每月某日、每月第几个某星期几、每年某日以及入站 webhook 触发，所以差距在产品的呈现面上，而不在机制的难度上。

## 决策

`AutomationSchedule` 新增 `hours`、`monthly`、`nth-weekday`、`yearly` 和 `cron`。重复计算被重组为一个归约：某一天是否匹配，以及匹配日的那些钟点；它同时驱动向前的发生扫描和向后的最近到期查找。这同时去掉了一个潜在缺陷：原来的 `latestDueOccurrence` 扫描一个窗口并返回第 16 个匹配，只有对稀疏重复它才是最近的一次。cron 在这里自行解析而不是作为依赖引入：五字段子集，支持 `*`、区间、步长和列表，保留 cron 的规则——当日期与星期都被限制时任一匹配即可，并在计划自身的 IANA 时区中求值。

入站触发是 Host 自身 Web 服务器上的前缀路由 `/automation-webhook`。只接受 `POST`，自动任务的密钥用 `timingSafeEqual` 比较，请求体受 `webhookMaxBodyBytes` 限制（Web profile 中为 8 KiB），超出时不保留内容而直接排空，被接受的请求体作为 `payload` 存到运行记录上。该 payload 在运行通知中以明确的「不可信外部数据」标签出现，因为通知对模型可见，外部发送者的内容绝不能读作指令。准入复用人工运行的路径：密钥本身就是全部权限，暂停的自动任务返回 409，已有工作在执行时该次记为跳过，响应在运行结束之前返回。

密钥存放在独立的 `automation_webhooks` 域，而不是定义上。定义是版本 3，其记录会被复制进每次运行的快照，并由 `automation_list` 交给模型，因此存放在那里的密钥会进入对话记录。页面只在其所有者展开的那张卡片上按需读取密钥，并以掩码显示：复制才是操作，阅读不是。

## 考虑过的替代方案

- **升级定义域并在其中新增一张表。** 否决：该域没有迁移，所有已存储的自动任务都会在打开时被拒绝，这个版本不值得为一份凭据花掉。
- **把密钥存在定义上再用投影过滤。** 否决：漏掉一处投影就会把 bearer 凭据泄漏进模型请求，而运行快照本就整份复制定义。
- **像 `webhook-github` 那样做逐提供方签名适配器。** 暂缓：通用端点才能让任何服务启动 routine，而提供方签名属于能够规范化投递的适配器。
- **引入 cron 包。** 暂缓：五个字段足够阅读和设界，而这个包会给一个清单受仓库校验的包新增依赖。
- **图形化计划编辑器。** 否决：创建与调整按设计是对话式的，所以页面把已存重复渲染成一句话，新增一种重复只需词典条目而不是表单。

## 后果

联合类型有九种，客户端把每种格式化成一句本地语言，因此新增一种就要同时更新三份词典。运行记录带上可选的 `payload`，旧记录没有该字段而 schema 接受缺省。没有任何东西对 webhook 签名，也没有任何东西对投递去重：重复的 `POST` 会启动第二次运行。超过配置上限的请求体在门口就被拒绝，而不是被截断。向后查找按类型设界——按小时与每日两天、每周八天、按月两类六十二天、每年四百天、cron 2929 天——因此关闭时间超过该窗口的 Host 不会补上错过的时间；误期宽限窗口本来也会跳过这些发生。按照所有者的长期指示，本次改动没有编写或运行测试与门禁，只运行了类型检查。
