# Agent Note：agent-preset roster 由插件持有，而非以 context 为键

Status: implemented

[English](2026-09-04-held-agent-preset-roster.md) | 中文

## 问题

三个界面读取同一份面向整个部署的 roster，各自通过自己的快照 store，而每个 store 的 loading 守卫只放行它自己的读取。对运行中的服务实测：一个会话页面在启动时询问了三次 `agentPresets/list`，并在每次会话间跳转时再询问一次，而它所询问的 roster 并不会因所选会话改变而改变。

按跳转计费的那一次才会累积。chip 与标题栏标签在挂载 effect 中发起加载，且位于导航会重建的 conversation scope 内；每次跳转都会重新挂载它们，把同一个问题重新放上线路。

## 决策

**一个 `AgentPresetRosterHolder`，在 `apply` 中构造并传递给每个界面。**

`fresh()` 抵达 Host 并持有其答复。`held()` 返回持有的 roster，其次并入进行中的读取，最后才自行发起。`invalidate()` 将两者一并退役。`beginRosterRead` 以参数接收读取方式，因此每个界面在其调用处声明自己需要哪一种。

管理区块读取新鲜值：它会复制与删除 preset，紧随其后展示的 roster 必须是线路所报告的那一份。chip 与标题栏标签读取持有值：它们只展示 roster，从不改变它。

**holder 是被传递的，而非被查找的，因为经由 Cordis context 取得的任何值都无法作为缓存的键。** `ctx.remote` 在每次属性访问时都返回一个新的代理对象——`ctx.remote === ctx.remote` 为假。以它为键的 `WeakMap` 会在一个对象下写入、在另一个对象下读取，因此每次查找都落空，却又显得正确：底层服务确实是共享的，通过其中任一代理写入的属性对全部代理可见。此前两次尝试都以这种方式作键，都通过了各自的测试，也都没有改变线路上的任何东西。

**不存在任何按时间过期的机制。** 每一条改变 roster 的路径都会自我announce并触发失效：设置写入、复制、删除、编写 preset 文件，以及可能落到 roster 已变更的 Host 上的重连。经由这些路径之外抵达的变更，会一直被以陈旧值作答，直到其中之一发生。计时器只会增加一个无人能够推理的间隔，并且只是缩短而非消除该窗口。

**拒绝结果绝不被持有**，否则一个无人能清除的失败会成为之后每次读取所继承的答案。

## 影响

一次跳转从两次调用降为一次，而留下的那一次——`subagents/list`——确实指名了它所服务的会话。启动时的 roster 读取从三次降为两次，总调用从二十次降为十八次。

新鲜度是调用处的属性。新界面必须做出选择，而选错是无声的：一个管理动作若读取持有值，将展示自身写入之前的 roster。两个方法以其行为命名，好让该选择在做出之处即可读。

`invalidate()` 就是陈旧性的全部契约。未来某条改变 roster 却不调用它的路径将提供陈旧值，且不会有测试失败——类型系统看不见这项义务。

更广的教训超出本包：**Cordis service 不是一个身份。** 任何以其为键的东西——缓存、注册表、按连接的映射——都有同样的缺陷，并会以同样无声的方式失效。

## 验证

该包的语句、分支、函数与行覆盖率均为 100%：持有的答案服务于后来的读者、并入进行中的读取、失效迫使重新抵达 Host、新鲜读取取代持有的答案、因失效在其之下落地而被丢弃的答案，以及不被持有的拒绝结果。

随后对运行中的服务实测了该行为——这正是此前两次尝试所缺少的。之前：每次跳转都携带 `agentPresets/list`。之后：稳态跳转只剩 `subagents/list`，较重的跳转由五次降为四次，启动由二十次降为十八次。

真正钉住新鲜／持有边界的是管理界面的测试：在共享读取内部做缓存，会让复制、删除以及已揭示路径读到变更之前的 roster。

## 备选方案

**以 `ctx.remote` 为键的 `WeakMap`。** 已实现两次，且两次都因上述原因而错误。该失效是无声的，这正是它值得被记录的原因。

**只共享进行中的读取。** 已实现并已回退：它能合并并发读取，而这些读取是跨挂载波次抵达的，而非同时发生。

**存活时间（TTL）。** 否决：这是部署方无从推理的可调参数，而失效路径已经覆盖 roster 改变的每一种方式。

**由插件拥有一个 store，各界面订阅它。** 那是更好的形态，也是更大的改动：今天每个界面都拥有自己的 status 与 error 状态，把它们折叠在一起是对该包的重新设计，而非对它向 Host 提问方式的修复。
