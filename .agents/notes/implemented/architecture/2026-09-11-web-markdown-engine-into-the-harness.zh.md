# Agent Note: 将 Web Markdown 引擎吸纳为客户端包

Status: implemented

[English](2026-09-11-web-markdown-engine-into-the-harness.md) | 中文

## Problem

Web 客户端的 Markdown 渲染器原本位于另一个仓库，仅以 `ui-primitives` 的 npm 依赖形式进入本仓库。这里无法编辑它：`MarkdownText` 只是 `@aeven-ai/hypermarkdown` 之上的适配器，而每一个渲染问题——流式过程中被重新渲染的代码围栏、块关闭时被重建的代码行号栏、某条样式规则——都在另一个仓库里得到答复，再以一次发布的形式抵达这里。

这种分离付出了两项具体代价。引擎与其消费者实际上一同演进，却分别发布，因此 `ui-primitives` 固定在 `0.4.2`，而引擎自己的仓库早已到 `0.4.4`，两者的差异在有人手工比对之前一直是看不见的。而且对引擎源码的修改根本无法在运行中的客户端里看到：检出目录里没有可编辑的源码，于是内环的第一步是发布。

## Decision

引擎落位为 `packages/client/hypermarkdown`，npm 名 `@deepseek-ai/dsh-client-hypermarkdown`，是一个静态链接的客户端库，没有任何 Cordis 接口——与 `ui-primitives`、`client/store`、`client/ui-slots` 同属一种包模式。`ui-primitives` 通过 `workspace:^` devDependency 引用它，`@aeven-ai` 的 npm 依赖已移除。

本次移动是复制而非分叉。源码是 v0.4.4 树的原样拷贝，因此引擎保留自己的写法并可与来源保持可 diff；随源码一并迁移的测试套件（62 个 spec 文件、889 个测试、逐文件 100% 覆盖率）成为其后每一次修改的回归网。

### 本仓库相较独立仓库所要求的部分

有四项，且都是机械性的，而非行为性的。

相对导入带显式 `.ts`/`.tsx` 扩展名，上游的 `lib/` 目录在此为 `src/engine/`——在本仓库中 `lib/` 表示构建产物，且 lint 门禁直接忽略该路径。

上游入口一分为二：`src/HyperMarkdown.tsx` 承载组件，`src/index.ts` 是 barrel。配置目录与库注册表都以 `src/index.ts` 为准，因此仅有 `.tsx` 入口在这里不仅不合惯例，而且对这些门禁完全不可见。

四个插件工厂从包根导出而非 `plugins/*` 子路径，因为静态链接库经由单一根入口到达编译 shell。各模块未改动，因此每个工厂仍是独立文件，导入其中一个仍然不产生额外开销。

样式表是保留嵌套的纯 CSS，而不是上游的 SCSS。引擎的 SCSS 完全未使用任何 Sass 特性——没有变量、mixin 或 `@use`——因此本次移植携带作者手写的文件，并交由 shell 的 lightningcss 流水线处理；代价是该样式表现在需要支持 CSS Nesting 的浏览器，而本 GUI 运行所依赖的引擎全都支持。

有三个上游测试出于非机械性的原因而改动。`tests/example/` 被舍弃：它覆盖的是独立仓库的示例应用，不属于该组件。`"use client"` 断言被替换为关于样式表归属的断言，因为本仓库的客户端产物是由 shell 加载的闭包工厂，而不是框架指令所能指向的 ES 模块。`ui-primitives` 中三个 DOM 一致性 fixture 被重新记录，以反映引擎自身 `0.4.4` 的 settle-render 修复——该修复使已完成的块不再携带动画标记；这是上游有意的行为变更，在记录前以 fixture diff 的形式复核过。

### 本次移植决定不予遵循的部分

引擎及其测试套件保留上游写法，而本仓库的类型感知 lint 规则本会改写它们：`prefer-const`、`no-unsafe-*` 系列、`no-this-alias`、`no-non-null-assertion`、`no-unnecessary-condition`、`unbound-method` 与 `no-deprecated`。这些规则仅对该路径关闭，理由与 `vendor/**` 相同——移植代码应与来源保持可 diff——而风格、正确性、Promise 与未使用代码规则仍然生效。有两个上游构造由该覆盖显式保护，而不是被「修正」：一个两个分支完全相同的 settle 分支，以及一个字面量超出列宽限制、展开后就不再是同一个正则的表达式。重复代码门禁出于同一理由享有同样的豁免：它在本仓库找到的每一处克隆都位于移植后的引擎内部，而合并它们意味着重构本仓库并不拥有的源码。

## Consequences

引擎现在在此编辑，源码改动经由 `pnpm run dev:web` 抵达浏览器：该脚本按构建预设将其识别为静态库包，并同时监视 `tsc`、它自身的 tsdown 产物以及 shell 的 dist 构建。它提供的是「重建后刷新」的循环，而非原地插件替换——静态链接库没有可在运行时替换的 fiber；只有 `dsh.client` 插件才能在不刷新页面的情况下重载。

`ui-primitives` 原本固定在 `0.4.2`，现在消费 `0.4.4`，这是行为变更而不仅是版本号变化：已完成的块以普通形态渲染，因此其行号与标记不再携带动画属性。上述三个一致性 fixture 记录了这一点。

独立仓库的发布流水线不再是本仓库的依赖，它的其他消费者也不再从这里获得引擎改动。让两者同时存活恰恰会重新引入本次改动所消除的漂移，因此独立仓库应当被退役而不是并行维护；在退役之前，它就是一个迟早会分叉的分支。

该包是可发布的 release member，而非私有包：`ui-primitives` 会发布，因此它所链接的引擎也必须发布。

## Alternatives considered

**保留 npm 依赖并以构建形式 vendoring。** 已否决。它保留了漂移——本仓库中的版本落后于另一处的源码——并使引擎在检出目录中不可编辑，而这正是问题的全部。

**把引擎做成 `dsh.client` 插件以便原地热替换。** 已否决。引擎是作为值被 `ui-primitives` 消费的 React 组件库；功能插件不得运行时导入另一个功能插件的值，而本仓库自身的规则把共享运行时代码放在狭窄的静态所有者中，`ui-primitives` 正是这样的所有者。为开发体验而采用一个与其所处分层相矛盾的架构并不值得。

**在构建期把 SCSS 展平为 CSS。** 已否决。这会为一个别无他用的构建流程加入 Sass 步骤，并把生成结果放到维护者编辑的位置——与被当作唯一事实来源的样式表相反。原生嵌套只带来一项浏览器支持约束，而本地客户端已经满足。
