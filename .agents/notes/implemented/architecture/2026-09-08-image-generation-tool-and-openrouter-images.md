# Agent Note: Image generation reaches the model, and OpenRouter serves it

Status: implemented

English | [中文](2026-09-08-image-generation-tool-and-openrouter-images.zh.md)

## Problem

The [media seam](2026-09-03-generated-media-capability-seam.md) and its [providers](2026-09-03-generated-media-providers.md) shipped complete and unreachable: nothing outside `packages/media/` depended on `avn-media`, no profile mounted it, and no tool called it. A person asking for an image in the Web client got image generation only from the subscription-backed vendor tools; the two API providers a BYOK deployment holds — OpenRouter and DeepInfra — had working seam providers that no request could reach.

Selecting an OpenRouter image model as a *chat* model failed with `HTTP 404: No endpoints found that support tool use`, because the live catalog materializes image-output models as chat models. That is a separate defect in `avn-llm-pi-ai`, recorded here because it is what image generation looked like from the outside and is not fixed by this change.

## Decision

**One tool, `generate_image`, in its own package.** `avn-tool-media` is the seam's only model-visible surface. It resolves the request, calls `ctx.media`, and stores each image through `ctx.attachments`. It registers no presentation: a settled result's image blocks already render in the tool card, so the rendering decision stays where [that note](2026-09-02-tool-result-images-render-in-the-card.md) put it.

**Generated bytes become durable attachments, never files or URLs.** This is what makes the image appear in the conversation rather than as a path the model must then describe, and it is the same mechanism the subscription-backed image tools already use.

**OpenRouter images go to the dedicated `/api/v1/images` route, not chat completions.** OpenRouter adds new image models exclusively there, and its chat route refuses them at the tool-compatibility routing step. `avn-media-pi-ai` reaches the same account over the chat-modality transport against a model list frozen into the installed pi-ai, so it is a second path to the same place that stops receiving models.

**The seam's byte labelling moved to `avn-media`.** Both providers must label bytes whose format their route does not reliably state, and `GeneratedMedia.mediaType` is the seam's own field. `imageMediaType` is exported from the seam rather than copied into a second provider.

**Unstorable media types are refused by name in the tool.** The version-one attachment path stores four raster formats. OpenRouter serves SVG on request, and an unrecognized signature stays `application/octet-stream`; naming the type at the tool beats a bare rejection from the storage layer.

## Consequences

`generate_image` joins the subscription-backed image tools rather than replacing them. The names do not collide, the credentials are unrelated, and the agent picks per request, so a deployment holding both a subscription and API keys reaches all of them.

A deployment mounting two image providers must pin one, on the seam or on the tool. The seam reports ambiguous selection rather than guessing, so this fails loudly at the first call rather than silently choosing.

`avn-media-pi-ai` and `avn-media-openrouter` now both register under the default id `openrouter`, and a composition mounting both must rename one. Whether the pi-ai image path keeps a reason to exist is recorded as open in that package's Dev Note.

Reference images and video remain unreachable from the model. The seam carries both; exposing them is a tool-surface decision, not a provider one.

## Verification

Unit coverage is 100% on statements, branches, functions, and lines across the changed packages: the image route's field mapping under its own names, the declared-versus-sniffed media type, skipped and empty response rows, both credential sources, argument defaulting in both directions, every storable and refused media type, and end-to-end execution asserting the stored bytes and the rendered image blocks.

The seam was exercised end to end against the live DeepInfra API with the real plugins mounted: `black-forest-labs/FLUX-1.1-pro` returned a 1024×1024 JPEG, verified with `file`. That run confirms the shared sniffer, because the route answered a PNG-defaulted request with JPEG and the bytes were labelled correctly.

The OpenRouter image path reached the live route and was refused with `HTTP 401: API key expired` — the account's key has expired, not the request. A wrong path would have returned 404, so the endpoint and request are confirmed and the decode path remains covered by unit tests alone until a valid key is available.

## Alternatives considered

**Install a third-party image plugin.** Rejected: it would have added a prompt library, gallery, batch studio and local-workflow surface to obtain one tool whose backends this repository already owns, and its OpenAI-compatible relay posts to `{baseURL}/images/generations`, which is not the path OpenRouter serves.

**Reach OpenRouter images through `avn-media-pi-ai`.** Rejected: zero new code, but the legacy transport and a model list frozen into the installed pi-ai mean new models never appear without a dependency bump.

**Put the tool in the subscription-auth plugin beside the vendor image tools.** Rejected: that package's subject is credentials obtained by OAuth against one vendor's subscription, and each of its tools is bound to one hardcoded vendor transport. A seam-backed BYOK tool shares neither, and lives with the seam it calls.
