# Agent Note：工具结果图片在卡片中渲染

Status: implemented

[English](2026-09-02-tool-result-images-render-in-the-card.md) | 中文

## 问题

产出图片的工具无处展示它。自 Client 开始配对工具结果起，`ContentBlock` 就带有 `image` 分支，`ToolResultNode.content` 原样把这些块送到 Client，产图工具也早已从 `render()` 返回它们。`ui-tool` 中没有任何代码读取它们：`GenericToolCard` 把结果映射为 terminal、diff、read、search 或 web 卡片，其余内容一律压平为文本。这些块被产出、被传输，然后在最后一步被丢弃。

可见后果是：生成的图片确实存在——已存储、持久、可寻址——但记录中只显示一行文本摘要。读者只有在要求模型复述后才能看到图片，此时助手会在自己的消息中写入 markdown 图片，由 `AssistantMarkdown` 渲染。产物只能通过一次不一定发生的额外模型轮次才能触达。

## 决策

**已完成工具结果中的 image 块在该工具的卡片中渲染，无需注册。** `imageCardModel` 按内容顺序从已完成且非错误的结果中派生持久附件，`GenericToolCard` 通过 chat node 已经提供的附件 slot 渲染它们。所有返回 image 块的工具一次性获得该行为，且都无需声明任何内容。

**图库位于行下方、展开区之外。** 生成的图片是结果本身，而非其细节，因此不应等待读者没有理由执行的展开操作。既有卡片区块保持原位——它们描述的是摘要行已经点明的结果。

**没有图片时保持纯文本，绝不显示空白框。** 运行中的调用没有内容，失败结果的部分内容属于诊断而非产物，未挂载附件展示的组合根本无法绘制图片。以上每种情况都让该行与此前完全一致。

**渲染器归 owner 所有，而非卡片所有。** `ToolCallOwnerProps` 新增可选的 `renderImages`，由 chat node 既有的 `renderMessageImages` 贯穿传入。`ui-tool` 不保留附件实现，也不保留图片加载器；它只决定图片*是否*属于卡片，而附件包继续决定图片如何获取与绘制。

生成图片工具使用 [在工具调用位置显示生成图片](../feature/2026-10-02-generated-images-at-tool-calls.zh.md) 中描述的独立调用视图与占位视图。通用图库仍是其他带图片工具的后备展示。

## 影响

任何返回 `image` 内容块的工具现在无需额外工作即可在记录中展示它们，新的产图工具只要返回其 `render()` 本就能返回的块便自动继承该行为。`ToolCallOwnerProps` 只新增了一个可选字段，因此已注册的业务工具视图无需改动即可继续编译，读取该字段才算选择加入。

卡片现在可以在未展开的情况下高于其摘要行，这会改变图片密集轮次的记录密度。若某个结果的 image 块只是附带而非产物，也会被一并渲染；当前没有任何已发布工具返回这类块，需要不同处理的工具可注册自己的 `tool.call.toolview`。

## 验证

`imageCardModel` 的单元覆盖钉住内容顺序、运行中／失败／纯文本三种空结果，以及文本与图片混排的情形。`GenericToolCard` 的组件覆盖断言附件 slot 收到以 `align: 'start'` 派生的分组、未提供 `renderImages` 的组合不渲染图库、不含图片的结果从不调用渲染器。`ui-tool`、`ui-chat` 与 `ui-conversation` 套件覆盖贯穿传参且保持不变。

## 备选方案

**让工具在结果文本中输出 markdown 图片标签。** 官方 Grok CLI 正是这样做的——其 `image_gen` 描述指示模型复述会话相对路径，使其渲染为链接。作为主要机制被否决：它使展示取决于模型是否配合，需要 attachment id 并不具备的可服务 URL，并且必须在每个产图工具中重复。块本身已在结果中；缺失的那一半是渲染器。

**在展开区内、与其他卡片并列渲染。** 否决，因为这保留了真正的抱怨点。读者仍需展开某一行才能发现有图片被产出。

**为每个图片工具注册各自的 `tool.call.toolview`。** 作为错误的抽象层级被否决：image 分支是 `ContentBlock` 的类型，而非某个工具的私有形态，逐工具的视图会为当前和未来的每个产出方重复同一份派生逻辑。
